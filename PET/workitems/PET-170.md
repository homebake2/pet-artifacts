При обрыве соединения после успешного создания питомца на сервере клиент может повторно отправить POST /pet и создать дубликат. Опциональный заголовок Idempotency-Key (клиентский UUID v4). Хранилище — отдельная таблица pet_idempotency_key (profile_id uuid, idempotency_key uuid, pet_id uuid nullable, created_at timestamptz, PRIMARY KEY (profile_id, idempotency_key)). Алгоритм: 1) резервирование — INSERT INTO pet_idempotency_key (profile_id, idempotency_key, pet_id) VALUES ($1,$2,NULL) ON CONFLICT (profile_id, idempotency_key) DO NOTHING; 2) если вставлена новая строка (RowsAffected==1) — создаём питомца как обычно; 3) если конфликт (RowsAffected==0) — SELECT pet_id по ключу: если pet_id IS NOT NULL, возвращаем 201 с уже созданным питомцем без новой вставки; если pet_id IS NULL — редкая гонка параллельных запросов с одним ключом, для MVP принят риск (fail open, без блокировки/повтора); 4) после успешной вставки питомца — UPDATE pet_idempotency_key SET pet_id=$1 WHERE profile_id=$2 AND idempotency_key=$3. Окно дедупликации — 24 часа по created_at; более старые строки допустимо чистить периодической задачей (не блокирует MVP). Полная спецификация — на странице «Добавление питомца — Backend».
