Сейчас питомец недоступен пользователю, пока тот не заполнит профиль (POST /profile), потому что pet.profile_id ссылается на строку profile, а она создаётся только явно — при регистрации профиль не создаётся. Принятое решение: питомцы должны принадлежать пользователю напрямую, без обращения к таблице profile.

Миграция:

1. `ALTER TABLE pet ADD COLUMN user_id uuid REFERENCES users(id);`
2. Бэкфилл: `UPDATE pet SET user_id = profile.user_id FROM profile WHERE profile.id = pet.profile_id;`
3. `ALTER TABLE pet ALTER COLUMN user_id SET NOT NULL;`
4. `ALTER TABLE pet DROP COLUMN profile_id;`
5. Аналогично для `pet_idempotency_key`: добавить `user_id`, бэкфиллить из `profile_id` тем же способом, сделать NOT NULL, обновить составной PRIMARY KEY с `(profile_id, idempotency_key)` на `(user_id, idempotency_key)`, удалить `profile_id`.

Таблица `profile` не удаляется и не меняется — она остаётся самостоятельной сущностью, используемой только эндпоинтами `/profile`.

Блокирует PET-184 (обновление хендлеров должно идти после того, как в БД появится столбец user_id).

**Выполнено:** миграция `database/migrations/000006_pet_user_id.{up,down}.sql` реализует пункты 1-4 для `pet`. Пункт 5 (`pet_idempotency_key`) не выполнялся — на момент выполнения этой задачи таблица `pet_idempotency_key` и сам механизм дедупликации по `Idempotency-Key` в коде ещё не реализованы (см. описание в `dobavlenie-pitomtsa-backend.md`, где эта таблица уже описана сразу с `user_id`). Когда эта таблица будет создаваться, её стоит сразу создавать с `user_id` — без промежуточного `profile_id`.
