Реализация серверной агрегации событий в ряды для графиков динамики. Целевое поведение — страница «Графики динамики — Backend»; форма значений и правила свёртки — «Модель значения события и реестр метрик».

Зависит от PET-2: агрегировать по полям `value` можно только после перевода столбца в `jsonb` и появления реестра метрик.

## Состав работы

* `GET /events/stats` с параметрами `pet_id`, `types`, `from`, `to`, `bucket` (day/week/month); ответ — ряды с интервалами, включая пустые интервалы.
* Свёртка строится по реестру метрик из PET-2, а не отдельным списком правил в обработчике: `measure` — среднее и последнее значение интервала, `quantity` — сумма, `category` — количество событий по каждому значению категории, `label` — не агрегируется.
* Раздельные ряды там, где значения несопоставимы: `feeding` — по каждой единице измерения отдельно; `medication` — количество приёмов, а не сумма доз.
* Границы диапазона и календарные интервалы считаются в UTC по тем же правилам, что `GET /activities` — общий код разбора границ, а не вторая независимая реализация.
* Фильтрация мягко удалённых событий и проверка владения питомцем — по общим правилам (404 на чужого или несуществующего питомца).
* Агрегация выполняется в БД запросом с использованием индекса `event_pet_type_date_idx` из PET-2, а не выборкой всех событий в память сервиса.
* Обновить `open-api/spec.json` и его копию `frontend/openapi/api.json`, перегенерировать типы.

## Готово, когда

* Ряды по каждому `value_kind` считаются корректно на диапазонах день/неделя/месяц, включая интервалы без событий.
* Запрос типа с `value_kind: label` (`other`) даёт 400, а не молча пустой ответ.
* Диапазон свыше 366 дней и `from` позже `to` дают 400.
