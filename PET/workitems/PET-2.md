Перевод события на типизированное значение (`event.value` — объект вместо строки) и расширение множества типов событий до 14 значений. Целевое состояние — страница «Модель значения события и реестр метрик»; здесь — как система к нему приходит.

## Миграция БД

Обратная совместимость не требуется (см. PET-1). Миграция выполняет чистую замену структуры, а не конвертацию: старое значение `event.value` — плоская строка, смысл которой зависел от типа события, и корректного автоматического преобразования её в объект новой формы не существует ни для одного типа, кроме `weight`. Частичная конвертация «только вес, остальное потерять» дала бы БД в состоянии, где часть событий валидна, а часть — молча пуста; это хуже, чем явная очистка.

Порядок шагов миграции `up`:

1. Удалить накопленные события: `DELETE FROM event;`. Шаг обязателен и выполняется ДО изменения структуры — иначе добавление `value jsonb NOT NULL` упадёт на существующих строках, а `USING`-преобразование строки в объект невозможно построить корректно (см. выше). Таблица `pet` и данные пользователей не затрагиваются — удаляются только события.
2. Удалить старый столбец: `ALTER TABLE event DROP COLUMN value;`.
3. Добавить новый столбец: `ALTER TABLE event ADD COLUMN value jsonb NOT NULL;`. `NOT NULL` без `DEFAULT` безопасен только потому, что таблица на шаге 1 очищена — умолчания у типизированного значения нет и быть не должно.
4. Если на `event.type` есть `CHECK`-ограничение со старым списком из 6 значений — удалить его. Множество допустимых типов проверяется приложением по реестру метрик, а не ограничением БД: реестр меняется чаще, чем допустимо гонять миграции, и правило формы `value` всё равно невыразимо через `CHECK`.
5. Создать индекс под агрегацию для графиков (PET-3):

```sql
CREATE INDEX event_pet_type_date_idx
  ON event (pet_id, type, date_time)
  WHERE deleted_at IS NULL;
```

Миграция `down` симметрична и так же разрушительна: удалить события, удалить индекс, удалить `value jsonb`, вернуть `value text NOT NULL`. Это фиксируется явно — `down` не восстанавливает данные и не предназначен для отката на проде.

## Приложение

* `open-api/spec.json` — `value` становится объектом, размеченным по `type` (`oneOf` с дискриминатором), enum типов события расширяется до 14 значений; после правки — `go generate ./...` для `openapi/types.gen.go`. Копию спецификации `frontend/openapi/api.json` обновить в этой же работе (правило репозитория `pet-mono`), без генерации клиента.
* Валидация значения перестаёт быть набором `if` по типу и строится по единому реестру типов: для каждого типа — форма `value`, диапазоны и единица измерения. Реестр — одно место в коде, к которому обращаются и создание, и редактирование, и импорт, и агрегация.
* Поля, не описанные формой `value` для данного типа, приводят к 400 (запрет неизвестных полей), а не отбрасываются молча.
* `POST /events`, `PATCH /events/{id}`, `POST /import/local-data` используют один и тот же валидатор значения — отдельного, ослабленного правила для импорта быть не должно.
* При `PATCH` объект `value` заменяется целиком; слияние вложенных полей не поддерживается.

## Готово, когда

* Миграция применяется на чистой и на заполненной БД без ручных шагов.
* Событие любого из 14 типов создаётся, читается и редактируется с валидацией по реестру.
* Значение неверной формы, лишнее поле и значение вне диапазона дают 400 с понятной ошибкой.
