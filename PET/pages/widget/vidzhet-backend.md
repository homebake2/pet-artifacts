## Назначение

Эндпоинт `GET /widget` возвращает за один запрос всё, что нужно виджету главного экрана в режиме `network`, чтобы показать питомцев, их ближайшие напоминания и кнопки быстрого действия: виджет — отдельный процесс ОС без рантайма приложения, и ему не нужно ни собирать результат из нескольких запросов, ни дублировать правила подбора кнопок у себя.

## Действующие лица и предусловия

* Инициатор — виджет главного экрана от имени авторизованного пользователя.

* Требуется валидный access-токен (заголовок `Authorization: Bearer <access_token>`).

## Основной сценарий

`GET /widget?tz=<часовой пояс IANA>`

1. Система извлекает `userID` из заголовка `Authorization` и проверяет валидность токена.

2. Система разбирает обязательный параметр `tz` (имя часового пояса IANA, в котором клиент видит свои календарные даты; правила — те же, что у `GET /activities`, см. [Просмотр календаря — Backend](../calendar/prosmotr-kalendarya-backend.md)).

3. Система выбирает питомцев пользователя в том же порядке и с теми же правилами скрытия мягко удалённых, что у `GET /pet` (см. [Список питомцев — Backend](../pets/spisok-pitomtsev-backend.md)).

4. Для каждого питомца система формирует:

   * `upcoming_reminders` — до трёх ближайших незавершённых напоминаний питомца с моментом `remind_at` не раньше текущего момента сервера, по возрастанию `remind_at` (при равенстве — по `id`), без ограничения по горизонту — то же правило, что у `GET /pet/{id}/reminders/upcoming` с `limit = 3` (см. [Напоминания — Backend](../calendar/napominaniya-backend.md));

   * `quick_actions` — до шести кнопок быстрого действия: типы-кандидаты (применимые к `species` питомца и имеющие полный набор значений по умолчанию, см. [Быстрое создание события из виджета — Frontend](bystroe-sozdanie-sobytiya-vidzhet-frontend.md), «Кандидаты на кнопку быстрого действия»), отсортированные по убыванию числа не удалённых событий питомца этого типа с даты на 365 дней раньше сегодняшней по сегодняшнюю включительно (даты — локальные в поясе `tz`; событие, общее с другими питомцами, считается для каждого из них), при равенстве — в каноническом порядке типов события. Каждый элемент несёт `type` и `value` — значение по умолчанию этого типа.

5. Система возвращает `200 OK` с телом `{"items": [{"id","name","species","photo_url","upcoming_reminders": [{"type","remind_at"}],"quick_actions": [{"type","value"}]}]}`. Если у пользователя нет питомцев — `{"items": []}` со статусом `200`.

Заголовок `LanguageCode` не используется: сервер не локализует содержимое ответа, подписи типов событий формирует клиент по `type`.

## Бизнес-правила и валидация

* Пользователь видит только своих питомцев; мягко удалённые питомцы исключаются.

* `photo_url` — nullable, presigned GET URL, вычисляется заново на каждый запрос (см. [Фотография питомца — Backend](../pets/fotografiya-pitomtsa-backend.md)).

* Сервер отдаёт максимум шесть кнопок на питомца; клиент сам берёт первые N для своего размера виджета (4 — средний, 6 — большой). Если кандидатов нет, `quick_actions` — пустой массив.

* Правила кандидатов и значения по умолчанию определяются единым реестром типов событий (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)); значения `value` в ответе проходят ту же валидацию, что и `POST /events`.

## Обработка ошибок

| Статус | Условие                                                                                                           |
| ------ | ----------------------------------------------------------------------------------------------------------------- |
| 400    | Параметр `tz` отсутствует или не является именем часового пояса IANA.                                              |
| 401    | Заголовок `Authorization` отсутствует, некорректен или токен истёк.                                                |
| 500    | Ошибка выборки данных (БД и т.п.). Формат тела ошибки — см. «Общие требования: Формат ошибок API».                |
