## Назначение

Страница описывает единую для среднего и большого виджета логику: какие типы события могут стать кнопкой быстрого действия, в каком порядке кнопки показываются, что происходит при нажатии, и как пользователь может отменить только что созданное событие, не открывая приложение.

## Кандидаты на кнопку быстрого действия

Тип события допускается как кандидат на кнопку быстрого действия для конкретного питомца, только если одновременно выполнены оба условия:

1. **Применимость к виду питомца.** Тип входит в множество типов, применимых к `pet.species` этого питомца — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца».

2. **Полный набор значений по умолчанию.** Для *каждого* обязательного поля `value` этого типа в разделе «Значения по умолчанию для полей `value`» той же страницы определено значение по умолчанию — иначе создание события одним тапом невозможно без ввода данных пользователем. На дату этого требования условию удовлетворяют типы `defecation`, `urine`, `vomit`, `diarrhea`, `mood`, `molting`, `heat_cycle` (все — статусные/категориальные типы с «нейтральным» значением по умолчанию, аналогичным уже существующему `defecation: status = normal`; подробности — на самой странице модели, раздел «Значения по умолчанию для полей `value`»). Типы с обязательным числовым измерением (`weight`, `temperature`, `feeding`, `water`, `activity`, `sleep`, `medication`, `egg_laying`) или обязательным свободным текстом (`medication.name`, `other.label`) кандидатами не становятся: универсального «типичного» числа или текста, не зависящего от питомца и ситуации, не существует, а подставлять произвольное число в измерение — вводить пользователя в заблуждение относительно того, что на самом деле произошло.

3. Появление у типа события полного набора умолчаний в будущем (расширение таблицы умолчаний на странице модели) автоматически делает его кандидатом здесь — эта страница не хранит отдельный список типов и не дублирует таблицу умолчаний.

## Сортировка кандидатов

1. Для текущего питомца виджет вычисляет частоту использования каждого типа-кандидата — число его событий за последние 365 дней (`GET /activities?pet_id=<id>&from=<сегодня-365д>&to=<сегодня>` в режиме `network`; см. [Виджет — Frontend (dataSource=local)](vidzhet-frontend-local.md) для режима `local`).

2. Кандидаты сортируются по убыванию этой частоты. При равной частоте (в том числе если частота нулевая у всех — питомец только что создан) кандидаты с одинаковой частотой упорядочиваются между собой по каноническому порядку типов события — тому же, в котором типы перечислены в [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)», отфильтрованному по применимости к виду этого питомца.

3. Из отсортированного списка берутся первые 4 (средний виджет) или первые 6 (большой виджет) кандидатов. Если кандидатов меньше — показываются все имеющиеся, без пустых слотов (см. [Виджеты главного экрана — Frontend](vidzhety-glavnogo-ekrana-frontend.md)). Если кандидатов нет вовсе (виду питомца неприменим ни один из статусных типов из списка выше) — блок кнопок быстрого действия не отображается.

4. Пересчёт сортировки происходит вместе с обновлением снимка данных виджета (см. «Данные виджета» на странице «Виджеты главного экрана»), а не при каждом тапе, — порядок кнопок между двумя обновлениями снимка стабилен, даже если пользователь только что создал событие одной из этих кнопок.

## Создание события

1. Нажатие на кнопку немедленно создаёт для текущего питомца новое событие: `type` — тип этой кнопки, `value` — значения по умолчанию для этого типа (см. «Кандидаты» выше), `date` — текущие дата и время устройства в момент тапа (RFC3339, тем же способом сериализации часового пояса, что и на экране добавления события), `notes` — пусто, `notifications_enabled` — `false` (виджет не предлагает включить напоминание — у быстрого действия нет шага с датой/временем, который пользователь мог бы изменить).

2. В режиме `network` создание выполняется запросом `POST /events` с новым, сгенерированным на этот тап `Idempotency-Key` (тот же протокол защиты от дублирования, что и на экране добавления события, — см. [Добавление события — Frontend](../calendar/dobavlenie-sobytiya-frontend.md), раздел «Idempotency key»); в режиме `local` — так, как описано в [Виджет — Frontend (dataSource=local)](vidzhet-frontend-local.md).

3. На время выполнения запроса кнопка переходит в состояние загрузки; повторный тап по той же или другой кнопке до завершения операции игнорируется.

4. После успешного создания виджет переходит в состояние успеха (см. «Success-стейт» ниже) вместо своего обычного вида.

## Success-стейт

1. Виджет показывает подтверждение: название созданного типа события (локализованное), имя питомца, время события, и кнопку «Отменить».

2. Success-стейт заменяет собой обычное содержимое виджета (кнопки быстрого действия, список питомцев и т.д. временно не видны) и автоматически возвращается к обычному виду при следующем обновлении снимка данных виджета (см. «Данные виджета» на странице «Виджеты главного экрана») либо при следующем открытии приложения — раньше этого момента явного таймера возврата не предусмотрено.

3. Кнопка «Отменить» доступна, пока виджет находится в success-стейте. Нажатие немедленно удаляет только что созданное событие тем же способом, что и обычное удаление события (мягкое удаление — `DELETE /events/{id}` в режиме `network`, см. [Удаление события — Backend](../calendar/udalenie-sobytiya-backend.md); в режиме `local` — см. [Виджет — Frontend (dataSource=local)](vidzhet-frontend-local.md)), после чего виджет возвращается к обычному виду. Если пользователь закрыл success-стейт (см. пункт 2) до нажатия «Отменить», событие остаётся обычным, полноценно созданным событием, дальнейшее его изменение или удаление доступно только из приложения (карточка события, календарь) — отдельного «архива отменяемых событий» виджет не ведёт.

4. Повторное нажатие «Отменить» после того, как оно уже было обработано (либо после того, как событие уже было удалено, например, из приложения), не должно приводить к видимой ошибке — виджет просто возвращается к обычному виду.

## Обработка ошибок

* Если создание события завершилось ошибкой (сеть, сбой сервера, ошибка локальной записи), виджет показывает отдельный error-стейт (не success) с кратким сообщением о том, что создать событие не удалось, и возвращается к обычному виду при следующем обновлении снимка данных или при следующем тапе по любой кнопке. Отдельной автоматической повторной отправки не предусмотрено — повторный тап пользователем инициирует новую попытку с новым `Idempotency-Key`.

* Если запрос `DELETE /events/{id}` (кнопка «Отменить») завершился ошибкой, виджет остаётся в success-стейте и позволяет повторить нажатие «Отменить» — событие в этом случае продолжает существовать до успешного удаления.

* Если у выбранного питомца на момент тапа не осталось ни одного кандидата на кнопки (например, виджет не успел обновить данные после смены питомца или его вида), кнопки скрываются так же, как описано в «Сортировка кандидатов», без отдельного сообщения об ошибке.
