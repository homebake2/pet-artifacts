## 1. Назначение

Два эндпоинта записи данных профиля с разной семантикой: `POST /profile` — создание профиля, `PUT /profile` — частичное обновление уже существующего профиля. Разница между ними должна быть явной и задокументированной, а не выводиться из побочных эффектов реализации.

## 2. Действующие лица и предусловия

* Действительный access-токен, из которого извлекается `user_id`.

* `POST` предназначен для случая, когда профиль пользователя может как существовать, так и не существовать (создание при первом обращении, обновление при повторном).

* `PUT` предназначен только для существующего профиля и должен явно проверять его наличие (см. «Обработка ошибок»), а не предполагать его без проверки.

## 3. Основной сценарий

Тело запроса (`GetProfileRequest`): `first_name`, `middle_name`, `last_name`, `email`, `phone`.

**POST /profile** — создание или полная перезапись:

1. Система атомарно (в рамках одной транзакции или одним upsert-запросом `INSERT ... ON CONFLICT (user_id) DO UPDATE`) выполняет вставку строки, если профиля не было, либо обновление всех пяти полей, если профиль уже существовал.

2. `first_name` обязателен в теле запроса и не может быть пустой строкой.

3. Успешный результат — `204 No Content`.

**PUT /profile** — частичное обновление:

1. Система проверяет, что профиль для данного `user_id` существует.

2. Система обновляет только те поля, которые переданы в запросе (поля — nullable-указатели); непереданные поля не изменяются. См. «Правило семантики обновления полей» ниже.

3. `first_name` не обязателен в каждом запросе — достаточно передать хотя бы одно поле; но если поле `first_name` передано, оно не может быть пустой строкой (см. п. 4).

4. Успешный результат — `200 OK`.

## 4. Бизнес-правила и валидация

* `first_name` обязателен в теле запроса только для `POST`. Для `PUT` обязательное требование присутствия `first_name` в каждом запросе снято — точечное обновление одного поля (например, только телефона) не должно требовать повторной передачи имени.

* **Непустота&#x20;**`first_name`**&#x20;проверяется в обоих методах.** В `POST` — уже реализовано. В `PUT` проверка должна быть добавлена: если поле `first_name` передано в запросе, оно не должно быть пустой строкой; попытка явно очистить имя через `PUT` отклоняется как ошибка валидации (см. «Обработка ошибок», `400 VALIDATION_ERROR`).

* Для `PUT` система должна проверять, что запрос содержит хотя бы одно поле для обновления; запрос без единого поля — ошибка валидации (`400 VALIDATION_ERROR`).

* `POST` при существующем профиле перезаписывает все пять полей целиком: непереданные поля становятся `NULL`. Это ожидаемое поведение полной замены и должно быть явно описано в OpenAPI, чтобы не путать с частичным обновлением.

* Операция вставки/обновления в `POST` должна быть атомарной по отношению к параллельным запросам от одного пользователя (см. «Обработка ошибок», гонка).

* На таблице `profile` действует ограничение `UNIQUE (user_id)`.

* **Серверная валидация формата и длины.** Сервер должен валидировать для обоих методов (`POST` и `PUT`):

  * `email` — если поле передано и непусто, валидируется через `net/mail.ParseAddress(email)` (стандартная библиотека Go): ошибка парсинга — `400 VALIDATION_ERROR`. Это не совпадает побайтово с клиентским `z.email()` (см. «Редактирование профиля — Frontend»), но обе проверки достаточно строгие практически, чтобы разница не встречалась в реальных сценариях; сервер не обязан побайтово копировать клиентский regex — это независимая серверная валидация, а не дублирование клиентской;

  * `phone` — если поле передано и непусто, проверяется тем же регулярным выражением, что и на фронтенде (см. «Редактирование профиля — Frontend»): `^\+?[0-9\s\-().]{1,20}$` (через `regexp.MustCompile`, скомпилированный один раз при старте, а не на каждый запрос); несовпадение — `400 VALIDATION_ERROR`;

  * максимальную длину всех строковых полей: `first_name`, `middle_name`, `last_name` — не более 100 символов; `email` — не более 254 символов; `phone` — не более 20 символов. Конкретные значения лимитов уточняются при реализации, но ограничение должно существовать и быть отражено в OpenAPI.

  Ранее валидация формата/длины на сервере отсутствовала (полагались только на клиентскую валидацию) — это пробел, требующий исправления, см. «Связанные задачи».

### Правило семантики обновления полей (PUT)

Для `PUT /profile` действует единое правило различения «поле не менялось» и «поле явно очищено»:

* `null`**&#x20;в значении поля, либо отсутствие поля в теле запроса** — означает «поле не менялось»; сервер не должен его трогать (сохраняется текущее значение в БД).

* **Пустая строка&#x20;**`""` — означает «поле явно очищено пользователем»; сервер должен записать пустое значение.

Правило действует одинаково для всех nullable строковых полей профиля (`middle_name`, `last_name`, `email`, `phone`) и должно соблюдаться согласованно на бэкенде и фронтенде (см. «Редактирование профиля — Frontend», раздел про partial-update). Правило сформулировано здесь как общее для операций частичного обновления профильных данных; на него можно ссылаться из требований других модулей с аналогичной семантикой частичного обновления (например, «Редактирование питомца» в модуле Pets).

#### Механизм на уровне Go-обработчика

Структура запроса использует поля-указатели `*string`, а не `string`:

```
type UpdateProfileRequest struct {
    FirstName  *string `json:"first_name"`
    MiddleName *string `json:"middle_name"`
    LastName   *string `json:"last_name"`
    Email      *string `json:"email"`
    Phone      *string `json:"phone"`
}
```

Пакет `encoding/json` при декодировании оставляет указатель `nil` и для отсутствующего в JSON ключа, и для явного `"email": null` — для бизнес-правила этого достаточно, так как оба случая трактуются одинаково («поле не менялось»), и различать их между собой не требуется. Значение `"email": ""` даёт ненулевой указатель на пустую строку — этим он отличим от первых двух случаев.

Обработчик собирает `SET`-часть `UPDATE` динамически, добавляя только непереданные-как-nil поля:

```
setClauses := []string{}
args := []any{}
argN := 1

if req.FirstName != nil {
    if *req.FirstName == "" {
        return errValidation("first_name не может быть пустым")
    }
    setClauses = append(setClauses, fmt.Sprintf("first_name = $%d", argN))
    args = append(args, *req.FirstName)
    argN++
}
if req.Email != nil {
    setClauses = append(setClauses, fmt.Sprintf("email = $%d", argN))
    args = append(args, *req.Email) // допускает "" — явная очистка
    argN++
}
// ...аналогично middle_name, last_name, phone

if len(setClauses) == 0 {
    return errValidation("не передано ни одного поля для обновления")
}

query := fmt.Sprintf(
    "UPDATE profile SET %s WHERE user_id = $%d",
    strings.Join(setClauses, ", "), argN,
)
args = append(args, userID)
result, err := db.Exec(query, args...)
// err != nil -> 500 INTERNAL_ERROR; result.RowsAffected() == 0 -> 404 NOT_FOUND
```

Параметризация через `$N`-плейсхолдеры (не конкатенация значений в SQL-строку) обязательна — имена колонок фиксированы и не приходят из пользовательского ввода, поэтому SQL-инъекция через список полей невозможна, но значения полей всё равно ОБЯЗАНЫ идти через параметры `args`.

## 5. Обработка ошибок

| Условие                                                                                               | Метод    | Статус | Код                |
| ----------------------------------------------------------------------------------------------------- | -------- | ------ | ------------------ |
| Токен отсутствует или недействителен                                                                  | оба      | 401    | `UNAUTHORIZED`     |
| Невалидный JSON тела запроса                                                                          | оба      | 400    | `BAD_REQUEST`      |
| `first_name` пуст (в `POST`, либо явно передан пустым в `PUT`), либо ни одно поле не передано в `PUT` | оба      | 400    | `VALIDATION_ERROR` |
| Формат `phone`/`email` невалиден, либо превышена максимальная длина строкового поля                   | оба      | 400    | `VALIDATION_ERROR` |
| `PUT` на несуществующий профиль (обновление не затронуло ни одной строки)                             | PUT      | 404    | `NOT_FOUND`        |
| Ошибка базы данных, включая конфликт уникальности при параллельных запросах                           | POST/PUT | 500    | `INTERNAL_ERROR`   |

* `PUT` на несуществующий профиль обязан возвращать `404 NOT_FOUND` с сообщением, поясняющим, что для создания профиля нужно использовать `POST` — тихий успешный ответ (`200 OK`) при отсутствии реально обновлённой строки недопустим. Это достигается проверкой количества затронутых строк (`RowsAffected`) после `UPDATE`.

* Гонка в `POST` (параллельные запросы от одного пользователя видят «профиля ещё нет» и оба пытаются вставить строку) должна быть устранена на уровне транзакции/upsert, а не проявляться как случайный `500` у одного из параллельных запросов.

* **Race condition при создании профиля с другого устройства между&#x20;**`GET`**&#x20;и сохранением:** для этого запроса — осознанно принимаемый риск; `PUT` полностью перезаписывает переданные поля без ревалидации состояния на момент сохранения, отдельный конфликт-хендлинг не реализуется.

* **Многоустройственное редактирование без optimistic concurrency** (ETag/версионирование) — осознанное решение для MVP: действует стратегия last-write-wins.

Тело всех перечисленных ошибочных ответов соответствует единому формату `errorCode`/`message`/`payload` — см. «Общие требования: Формат ошибок API».

## 6. Хранение состояния и побочные эффекты

`POST`: вставка новой строки либо полная перезапись существующей — атомарно относительно параллельных запросов. `PUT`: частичное обновление только переданных полей существующей строки согласно «Правилу семантики обновления полей» (раздел 4); при отсутствии строки — ошибка, без побочных эффектов. Оба метода не возвращают JSON-тело при успехе.
