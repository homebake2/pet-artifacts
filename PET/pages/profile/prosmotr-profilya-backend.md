## 1. Назначение

Эндпоинт `GET /profile` должен отдавать данные профиля текущего авторизованного пользователя (ФИО, email, телефон, логин) для экрана «Профиль».

## 2. Действующие лица и предусловия

* Инициатор — мобильное приложение, действующее от имени авторизованного пользователя.

* Запрос должен содержать действительный access-токен в заголовке `Authorization: Bearer <access_token>`.

* Наличие строки профиля в таблице `profile` для данного пользователя не гарантируется — это штатный случай, обрабатываемый явным кодом ответа (см. «Обработка ошибок»).

## 3. Основной сценарий

`GET /profile`, заголовок `Authorization: Bearer <access_token>`.

1. Система разбирает Bearer-токен и извлекает `user_id`.

2. Система ищет строку в таблице `profile` по `user_id`.

3. Если строка найдена — система получает `login` пользователя из таблицы `users` по тому же `user_id`.

4. Система формирует и возвращает ответ `200 OK`.

Тело ответа (`200 OK`, `GetMasterProfileResponse`):

| Поле                                         | Обязательность                       | Смысл                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                         | обязательное                         | Идентификатор пользователя (`users.id`), а не первичный ключ строки `profile` — `profile.id` клиенту не передаётся и не должен использоваться для его получения.                                                                                                                                                           |
| `first_name`                                 | обязательное                         | Имя пользователя. Всегда непустая строка — обязательность гарантируется валидацией `POST /profile` (см. «Редактирование профиля — Backend»).                                                                                                                                                                               |
| `middle_name`, `last_name`, `email`, `phone` | опциональные                         | Заполняются, если были сохранены ранее. Если поле не было сохранено — возвращается JSON-значение `null` (а не пустая строка `""` и не отсутствие ключа в объекте ответа). Это единственный поддерживаемый формат «пустого» опционального поля — фронтенд ориентируется именно на него (см. «Просмотр профиля — Frontend»). |
| `login`                                      | обязательное, всегда непустая строка | Логин, которым пользователь входит в систему.                                                                                                                                                                                                                                                                              |

## 4. Бизнес-правила и валидация

* Эндпоинт доступен только методом `GET`.

* На таблице `profile` действует ограничение `UNIQUE (user_id)` — у пользователя не может быть более одной строки профиля.

* Пользователь может получить только собственный профиль (профиль другого пользователя запросить нельзя).

* `login` в ответе должен быть всегда непустой строкой. Поскольку строка `profile` физически не может существовать без соответствующей записи в `users` (внешний ключ `user_id REFERENCES users(id)`), пустой результат подстановки логина означает не «пользователь не найден», а сбой выполнения запроса (например, некорректный JOIN) — такой случай должен обрабатываться как ошибка (см. «Обработка ошибок», 500), а не приводить к успешному ответу с пустым полем.

* Опциональные поля (`middle_name`, `last_name`, `email`, `phone`) сериализуются как JSON `null`, если значение в БД — `NULL`. Сериализация в виде пустой строки или пропуск ключа в ответе не допускается.

## 5. Обработка ошибок

| Статус | Код              | Условие                                                                                                                                                                               |
| ------ | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 401    | `UNAUTHORIZED`   | Токен отсутствует, заголовок некорректен, токен недействителен или истёк.                                                                                                             |
| 404    | `NOT_FOUND`      | Профиль для данного `user_id` не найден (пользователь ещё не заполнял профиль).                                                                                                       |
| 500    | `INTERNAL_ERROR` | Ошибка базы данных, либо не удалось получить непустой `login` для существующего профиля.                                                                                              |
| 405    | `BAD_REQUEST`    | Запрос выполнен методом, отличным от `GET`. Переиспользование кода `BAD_REQUEST` для 405 — осознанное решение (см. связанную задачу), отдельный код `METHOD_NOT_ALLOWED` не вводится. |

Тело всех перечисленных ошибочных ответов соответствует единому формату `errorCode`/`message`/`payload` — см. «Общие требования: Формат ошибок API». Все перечисленные коды ответа, включая `500` и `405`, должны быть отражены в OpenAPI-спецификации эндпоинта.

## 6. Хранение состояния и побочные эффекты

`GET /profile` идемпотентен и не изменяет данные — только читает `profile` и `users`.

## 7. Связанные задачи

* Гарантировать непустой login в ответе GET /profile.

* Задокументировать смысл поля id в ответе GET /profile.

* Дополнить спецификацию ответом 500 для GET /profile.

* Задокументировать в OpenAPI фактическое поведение 405 для GET /profile.
