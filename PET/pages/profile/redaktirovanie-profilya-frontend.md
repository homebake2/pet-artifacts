## 1. Назначение

Экран «Редактирование профиля» должен позволять пользователю заполнить или изменить свои личные данные и сохранить их. Экран открывается с экрана просмотра профиля и после успешного сохранения должен возвращать пользователя туда же.

## 2. Действующие лица и предусловия

* Авторизованный пользователь, перешедший по кнопке «Редактировать» с экрана просмотра профиля.

* Форма должна быть предзаполнена текущими данными пользователя, если они есть.

* Экран должен знать, существует ли у пользователя профиль на сервере (см. п. «Основной сценарий», выбор метода запроса), а не предполагать это.

* **Экран редактирования недоступен, пока предшествующий&#x20;**`GET /profile`**&#x20;не завершился успешно хотя бы один раз.** Если этот запрос завершился сетевой/серверной ошибкой, фронтенд не может достоверно определить, существует ли профиль на сервере, а значит — какой метод (`POST` или `PUT`) использовать при сохранении. В этом случае кнопки перехода к созданию/редактированию профиля на экране просмотра должны быть скрыты или задизейблены до успешной загрузки текущего состояния профиля.

## 3. Основной сценарий

1. Пользователь нажимает «Редактировать» на экране профиля (кнопка доступна только после успешного `GET /profile`, см. п. 2).

2. Система показывает форму с полями: Имя (обязательное), Отчество, Фамилия, Email, Телефон (числовая клавиатура для набора, но само значение в состоянии формы хранится и обрабатывается как строка на всех этапах — ввод, валидация, отправка; см. п. 4).

3. Пользователь изменяет поля.

4. Пользователь нажимает «Сохранить».

5. Система выполняет клиентскую валидацию; если валидация не пройдена — отправка не выполняется, под соответствующим полем показывается сообщение об ошибке.

6. Система определяет, есть ли у пользователя профиль на сервере (по результату ранее выполненного `GET /profile`: профиль отсутствует/404 — значит профиль ещё не создан). Если профиль отсутствует — выполняется `POST /profile` (создание, отправляется вся форма). Если профиль уже существует — выполняется `PUT /profile` (частичное обновление, см. п. 4 про partial-update). В локальном режиме данные сохраняются на устройстве без обращения к серверу.

7. Система показывает индикатор сохранения (загрузки) и блокирует повторную отправку формы до получения ответа.

8. Только после успешного ответа сервера (или успешного сохранения в локальном режиме) система выполняет переход на экран просмотра профиля.

## 4. Бизнес-правила и валидация

| Поле               | Обязательность | Правило                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------ | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Имя                | обязательное   | минимум 1 символ; максимальная длина — см. общий лимит длины строковых полей ниже                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Отчество / Фамилия | необязательные | ограничены только общим лимитом длины строковых полей (см. ниже)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Email              | необязательное | если заполнено — должно проходить валидацию через Zod-валидатор `z.email()` (тот же валидатор, что уже используется для поля email в `src/entities/auth/schemas.ts`, чтобы не вводить второй, чуть иначе ведущий себя формат email в приложении); дополнительных кастомных правил (запрет одноразовых доменов и т.п.) не вводится. Ограничено общим лимитом длины.                                                                                                                                                                                              |
| Телефон            | необязательное | если заполнено — должно соответствовать формату телефонного номера: разрешены цифры, пробелы, дефисы, круглые скобки, точки и один необязательный ведущий «+» (в духе E.164, без строгой привязки к конкретной стране); рекомендуемое регулярное выражение — `^\+?[0-9\s\-().]{1,20}$`. Значение **в состоянии формы React Hook Form всегда остаётся строкой** — приведение к числу (`Number()`, `parseInt` и т.п.) запрещено на любом этапе (ввод, валидация, отправка), чтобы не терять ведущий «+» и не давать ложно-успешную обработку некорректного ввода. |

* **Максимальная длина строковых полей** (first_name, middle_name, last_name, email, phone) ограничивается на бэкенде (см. «Редактирование профиля — Backend», п. 4); клиентская валидация должна использовать те же лимиты, чтобы пользователь узнавал о превышении длины до отправки, а не только по ответу сервера.

* Выбор метода запроса (`POST` при первом заполнении, `PUT` при последующих правках) — обязательная часть сценария сохранения, а не деталь на будущее; экран не должен всегда использовать один и тот же метод независимо от наличия профиля.

* **Partial-update (частичное обновление): алгоритм.** При сохранении через `PUT` форма обязана отправлять только те поля, которые пользователь реально изменил, — а не все поля формы целиком (та же схема, что описана для форм с частичным обновлением в модуле Pets, см. «Редактирование питомца — Frontend»: diff относительно исходных данных, а не полный объект). Отправка полного набора полей при каждом PUT обесценивает частичное обновление на бэкенде и создаёт риск случайной перезаписи параллельно изменённых данных.

  1. **Baseline.** Сразу после успешного `GET /profile` данные, которыми форма предзаполняется, сохраняются как эталон сравнения — передаются в `useForm({ defaultValues })` и одновременно фиксируются отдельной переменной/ref (например, `initialValuesRef`), потому что сам объект `defaultValues` React Hook Form не гарантированно остаётся неизменным (reset формы уже после правок должен это учитывать).

  2. **Определение изменённых полей на submit.** Обработчик `onSubmit(values)` проходит по ключам формы (`firstName`, `middleName`, `lastName`, `email`, `phone`) и для каждого поля сравнивает `values[field]` с `initialValuesRef.current[field]` (строковое сравнение по значению, а не флаг `formState.dirtyFields` — последний остаётся `true`, даже если пользователь изменил поле и затем вручную вернул его к исходному значению, что привело бы к лишней отправке неизменившегося поля).

  3. **Формирование payload.** В объект запроса включаются только поля, для которых сравнение на шаге 2 дало различие: если поле изменилось и стало непустой строкой — отправляется новое значение; если поле изменилось и стало пустой строкой (пользователь стёр значение) — отправляется `""` явно (это осознанный сигнал «очистить поле» — см. «Правило семантики обновления полей» на странице «Редактирование профиля — Backend»); поле, не входящее в diff, не добавляется в объект запроса ключом вовсе (не `null`, не текущее значение — просто отсутствует).

  4. **Ответственность мапперов.** Реализуется в `mapFormProfileToUpdate` (`src/pages/profile-edit/mappers/map-profile.ts`): функция принимает на вход и текущие значения формы, и baseline, и возвращает только diff-объект. `POST` (создание профиля) продолжает использовать отдельный маппер, отправляющий все поля формы — diff-логика применяется только к ветке `PUT`.

## 5. Обработка ошибок

* **Ошибка клиентской валидации:** отправка блокируется, сообщение об ошибке показывается под соответствующим полем; переход на экран просмотра не происходит.

* **Ошибка сохранения на сервере (сетевая ошибка, 4xx, 5xx):** система должна показать сообщение об ошибке и остаться на экране редактирования, сохранив введённые пользователем данные — переход на экран просмотра не должен происходить до получения успешного ответа.

* **Профиль не существовал ранее:** система обязана использовать `POST`, а не `PUT` — использование `PUT` для ещё не созданного профиля недопустимо (такой запрос вернёт ошибку 404, а не тихий успех, см. «Редактирование профиля — Backend»).

* `GET /profile`**&#x20;завершился ошибкой до открытия формы:** экран редактирования не открывается — кнопки «Создать профиль» / «Редактировать» на экране просмотра скрыты или задизейблены, пока предшествующий `GET /profile` не завершится успешно (см. п. 2). Это устраняет неопределённость, какой метод (`POST`/`PUT`) использовать при сохранении.

* **Race condition при создании профиля с другого устройства между&#x20;**`GET`**&#x20;и «Сохранить»:** осознанно принимаемый риск для данного запроса — `POST`/`PUT` перезаписывают присланные поля без ревалидации на момент сохранения; конфликт-хендлинг (повторный `GET` перед сохранением, предупреждение пользователю и т.п.) на этой итерации не реализуется.

* **Многоустройственное редактирование без optimistic concurrency** (ETag/версионирование): осознанное решение для MVP — действует стратегия last-write-wins, отдельная обработка конфликтов одновременного редактирования с разных устройств не реализуется.

* **Смена email не требует повторной верификации:** осознанное решение — email не используется как логин, подтверждение владения почтовым адресом на этом этапе не требуется.

## 6. Хранение состояния и побочные эффекты

* После успешного сохранения (сетевой режим) система обязана инвалидировать кэш `GET /profile` (react-query), чтобы экран просмотра профиля при возврате отображал только что сохранённые данные, а не устаревшие значения из кэша.

* В локальном режиме изменения должны отражаться немедленно после сохранения.
