## 1. Назначение

Единый эндпоинт `POST /import/local-data`, которым пользуются оба клиентских сценария переноса локальных данных в сетевой режим — «Перенос локального аккаунта в сеть» (перенос сразу после создания нового сетевого аккаунта) и «Импорт из локального аккаунта» (перенос в уже существующий сетевой аккаунт). Эндпоинт принимает единовременный (one-shot) снимок данных одного локального аккаунта — профиль, питомцев и их события — и переносит их в аккаунт текущего авторизованного пользователя.

Перенос НЕ является синхронизацией: это однонаправленная (local → network) разовая операция, инициируемая пользователем. Повторный вызов с другим содержимым создаёт дополнительные данные, а не объединяет/разрешает конфликты с ранее перенесёнными — конфликты слияния вне области этого эндпоинта.

## 2. Действующие лица и предусловия

* Инициатор — клиентское приложение с действительным access-токеном сетевого аккаунта, в который выполняется перенос. Токен либо только что выдан регистрацией нового аккаунта (сценарий «Перенос локального аккаунта в сеть»), либо принадлежит уже активной сетевой сессии (сценарий «Импорт из локального аккаунта»). Различия в происхождении токена эндпоинт не видит и не обрабатывает по-разному.

* Целевой аккаунт для переноса — всегда текущий авторизованный пользователь (`userID` из токена). Эндпоинт не принимает идентификатор целевого аккаунта в теле запроса.

* Наличие строки в таблице `profile` не требуется — тот же принцип, что и для питомцев/событий.

## 3. Основной сценарий

Тело запроса (`ImportLocalDataRequest`):

| Поле | Тип | Обязательность | Описание |
| --- | --- | --- | --- |
| profile | object \| null | опционально | Поля профиля (`first_name`, `middle_name`, `last_name`, `email`, `phone`) — тот же набор, что у `POST /profile`. `null`/отсутствие поля — профиль не переносится. |
| pets | array | обязательно (может быть пустым) | Питомцы для переноса. Каждый элемент: `local_id` (string, обязательно — клиентский UUID питомца, используется только как временный ключ ссылки внутри этого запроса, не сохраняется) и все поля питомца, как в `POST /pet` (`name`, `species` обязательны, остальные — как описано на странице «Добавление питомца — Backend»). |
| events | array | обязательно (может быть пустым) | События для переноса. Каждый элемент: `local_id` (string, обязательно — клиентский UUID события, используется только как временный ключ ссылки внутри этого запроса и как ключ соответствия в ответе, не сохраняется), `pet_local_id` (string, обязательно — должен совпадать с одним из `local_id` в `pets` этого же запроса) и все поля события, как в `POST /events` (`date`, `type`, `value` обязательны, `notes` — опционально). `type` — значение из справочника типов события; `value` — типизированный объект той же формы и с той же валидацией, что и в `POST /events` (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)). Собственного, ослабленного формата значения у импорта нет: строка вместо объекта, объект формы, не соответствующей `type`, и лишние поля внутри `value` отклоняются здесь так же, как в `POST /events`. Файлы события (`files` в локальном хранилище) в этот элемент не входят — переносятся отдельно, см. [Файлы события — Frontend (dataSource=local)](../calendar/fayly-sobytiya-frontend-local.md), раздел «Перенос файлов при local → network». |

Заголовок `Idempotency-Key` (UUID v4, генерируется клиентом один раз на попытку переноса) — обязателен для этого эндпоинта (в отличие от `POST /pet`, где он опционален): перенос — массовая операция, которую недопустимо случайно продублировать целиком при повторной отправке после обрыва соединения (см. «Обработка ошибок» и раздел 6).

Сервер при получении запроса ОБЯЗАН выполнить:

1. Проверить `Authorization` и извлечь `userID`.

2. Проверить наличие и формат заголовка `Idempotency-Key`. Если отсутствует — см. «Обработка ошибок» (400).

3. Выполнить резервирование ключа идемпотентности по паре (`user_id`, `idempotency_key`) — тем же механизмом, что описан на странице «Добавление питомца — Backend» («Механизм дедупликации по Idempotency-Key»), с тем отличием, что результатом, возвращаемым при повторном запросе с уже использованным ключом, является ранее сохранённая сводка переноса (см. шаг 8), а не одна сущность. Если ключ уже зарезервирован и завершён — сервер сразу возвращает сохранённый результат, шаги 4–8 не выполняются повторно.

4. Разобрать тело запроса как JSON и провалидировать: `pets`/`events` — массивы (не `null`); каждый питомец — валиден по тем же правилам, что `POST /pet`; каждое событие — валидно по тем же правилам, что `POST /events`, и его `pet_local_id` встречается среди `local_id` присланных питомцев. `local_id` каждого питомца и `local_id` каждого события должны быть уникальны в пределах своего массива (`pets`/`events` соответственно) — оба используются как ключ построения отображения `local_id → id`, возвращаемого в ответе (см. шаг 9), и неуникальный `local_id` сделал бы это отображение неоднозначным. Первая же невалидная запись прерывает обработку всего запроса — см. «Обработка ошибок» (400), результат не сохраняется частично.

5. Открыть транзакцию БД, охватывающую все дальнейшие вставки (шаги 6–8) — либо все записи переноса будут созданы, либо (при любой ошибке) ни одна.

6. Для каждого питомца в `pets` вставить строку в таблицу `pet`, привязанную к `userID`, с новым сгенерированным на сервере `id` (клиентский `local_id` НЕ используется как серверный id и нигде не сохраняется на сервере). Построить временное отображение `local_id → server pet id`, существующее только в рамках обработки этого запроса.

7. Для каждого события в `events` найти соответствующий серверный `pet id` по отображению из шага 6 и вставить строку в таблицу `event`, привязанную к найденному питомцу и `userID`. Построить временное отображение `local_id события → server event id`, существующее только в рамках обработки этого запроса (симметрично отображению питомцев из шага 6).

8. Если в запросе передан `profile` (не `null`) — выполнить те же upsert-действия, что `POST /profile` (вставка либо полная перезапись пяти полей профиля для `userID`), в той же транзакции.

9. Зафиксировать транзакцию, связать `Idempotency-Key` с результатом (см. раздел 6), и вернуть `200 OK` с телом:

| Поле | Тип | Описание |
| --- | --- | --- |
| pets_imported | integer | Количество перенесённых питомцев. |
| events_imported | integer | Количество перенесённых событий. |
| profile_imported | boolean | Был ли перенесён профиль. |
| pets | array | По одному элементу на каждого перенесённого питомца: `local_id` (string, эхо клиентского `local_id` из соответствующего элемента запроса) и `id` (string, новый серверный id этого питомца, построенный на шаге 6). Клиент использует это сопоставление, чтобы после переноса сущностей отдельно, в фоне, перенести бинарное содержимое (фотографию) для питомцев, у которых оно было в локальном хранилище — см. «Локальный режим (dataSource=local)», раздел «Поддержание паритета сущностей при переносе», и «Фотография питомца — Frontend (dataSource=local)», раздел «Перенос фотографии при local → network». Порядок элементов соответствует порядку `pets` в запросе. |
| events | array | По одному элементу на каждое перенесённое событие: `local_id` (string, эхо клиентского `local_id` из соответствующего элемента запроса) и `id` (string, новый серверный id этого события, построенный на шаге 7). Клиент использует это сопоставление симметрично полю `pets` — для последующего фонового переноса файлов событий, см. «Файлы события — Frontend (dataSource=local)», раздел «Перенос файлов при local → network». Порядок элементов соответствует порядку `events` в запросе. |

## 4. Бизнес-правила и валидация

* **Атомарность.** Перенос — единая атомарная операция на уровне БД-транзакции (см. шаг 5). Частичный перенос (например, часть питомцев создана, а событие или профиль — нет из-за ошибки) недопустим ни при каких условиях; при любой ошибке на шагах 6–8 транзакция откатывается целиком, и клиенту возвращается ошибка (см. «Обработка ошибок»), а не частичный успех.

* **Новые идентификаторы.** Сервер ВСЕГДА выдаёт новые `id` для перенесённых питомцев и событий — идентификаторы, под которыми эти сущности существовали в локальном хранилище, не переносятся на сервер ни в каком виде (ни как `id`, ни как дополнительное поле). Ссылочная целостность питомец↔событие внутри запроса восстанавливается сервером через `local_id`/`pet_local_id`, а не через совпадение реальных id.

* **Владелец переносимых данных — только текущий пользователь.** Все перенесённые питомцы и события принадлежат (`user_id`) исключительно вызывающему аккаунту; эндпоинт не принимает и не учитывает никакой чужой `userID`.

* **Мягко удалённые локальные записи не переносятся.** Тело запроса не ДОЛЖНО содержать записи, соответствующие локально мягко удалённым питомцам/событиям (`deletedAt != null` в терминах локального хранилища, см. «Локальный режим (dataSource=local)», раздел «Мягкое удаление») — фильтрация выполняется клиентом до формирования запроса (см. страницы Frontend). Backend не получает и, соответственно, не обязан отдельно распознавать признак `deletedAt` в теле — само их отсутствие в payload и есть контракт. Каждая перенесённая запись создаётся как обычная (не удалённая) запись — с этого момента на неё действуют обычные правила soft-delete сетевого режима.

* **Перенос не удаляет исходные локальные данные.** Эндпоинт — read-only по отношению к локальному хранилищу устройства (он вообще не знает о его существовании, только получает JSON) и не выполняет никаких действий над ним; удаление или сохранение локальных данных после успешного переноса — решение, принимаемое исключительно на клиенте (см. страницы Frontend и «Локальный режим (dataSource=local)», раздел «Переключение источника данных»).

* **Профиль переносится через ту же семантику, что `POST /profile`** (полная перезапись пяти полей, `first_name` обязателен, если объект `profile` передан) — отдельная семантика частичного обновления (как у `PUT /profile`) для переноса не нужна: аккаунт, в который выполняется перенос через «Перенос локального аккаунта в сеть», всегда новый (профиля ещё нет), а перенос через «Импорт из локального аккаунта» в аккаунт с уже заполненным профилем — осознанно принимаемый случай перезаписи (см. страницу «Импорт из локального аккаунта — Frontend», где это явно проговаривается пользователю перед переносом).

* Лимиты длины строковых полей, формат `email`/`phone`, обязательность `name`/`species` у питомца, `date`/`type`/`value` у события — те же, что в `POST /pet`, `POST /events`, `POST /profile` соответственно; повторно не переопределяются на этой странице.

## 5. Обработка ошибок

| Условие | Статус | Код ошибки |
| --- | --- | --- |
| Токен отсутствует или недействителен | 401 | UNAUTHORIZED |
| Заголовок `Idempotency-Key` отсутствует или не является валидным UUID | 400 | VALIDATION_ERROR |
| Невалидный JSON тела запроса | 400 | BAD_REQUEST |
| Питомец в `pets` не проходит валидацию (`POST /pet`) | 400 | VALIDATION_ERROR |
| Событие в `events` не проходит валидацию (`POST /events`), включая несуществующий `pet_local_id` | 400 | VALIDATION_ERROR |
| `profile` передан, но не проходит валидацию (`POST /profile`) | 400 | VALIDATION_ERROR |
| Ошибка БД на любом шаге транзакции (вставка питомца/события/профиля, резервирование идемпотентности) | 500 | INTERNAL_ERROR |

Все ошибки этой таблицы означают, что транзакция не зафиксирована — ни одна из перечисленных в запросе сущностей не создана (см. «Бизнес-правила», атомарность). Тело ошибки — единый формат `errorCode`/`message`/`payload` (см. «Общие требования: Формат ошибок API»).

## 6. Хранение состояния и побочные эффекты

Успешный запрос атомарно создаёт: одну строку `pet` на каждый элемент `pets`, одну строку `event` на каждый элемент `events`, и (если передан `profile`) одну строку/обновление в таблице `profile` — все три вида эффектов относятся к `user_id` вызывающего.

Дедупликация по `Idempotency-Key` использует ту же таблицу-механизм, что и `POST /pet` (пара `user_id + idempotency_key`, окно 24 часа), с сохранением не id одной сущности, а тела ответа переноса (`pets_imported`/`events_imported`/`profile_imported`) — повторный запрос с тем же ключом в пределах окна возвращает этот сохранённый результат и не создаёт новых строк, даже если тело запроса при повторе отличается от первого раза.
