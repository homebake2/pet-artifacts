## 1. Назначение

Экран «Профиль» должен показывать личные данные текущего пользователя (ФИО, логин, email, телефон) и служить точкой входа к редактированию профиля и настройкам. Экран не редактирует данные — только отображает их и предлагает переход к редактированию.

## 2. Действующие лица и предусловия

* Авторизованный пользователь с действительной сессией.

* Приложение может работать в сетевом режиме (данные с сервера) или локальном режиме (данные с устройства); экран должен корректно поддерживать оба режима.

* Профиль на сервере может быть ещё не заполнен — это штатная ситуация, а не ошибка.

## 3. Основной сценарий

1. Пользователь открывает экран «Профиль».

2. Экран переходит в состояние загрузки и запрашивает данные: в сетевом режиме — `GET /profile`, в локальном — из локального хранилища.

3. Система формирует ФИО, соединяя непустые части пробелом, в порядке **Фамилия Имя Отчество**. Имя (first_name) присутствует всегда; отчество и фамилия добавляются, только если заданы.

4. Система отображает: аватар пользователя, ФИО, логин (см. п. «Бизнес-правила»), email, телефон, кнопку «Редактировать».

5. Система предоставляет навигацию на настройки, главный экран и экран редактирования профиля.

## 4. Бизнес-правила и валидация

* Экран только отображает данные, не изменяет их.

* ФИО собирается в порядке **Фамилия Имя Отчество** (типичный для русской локали порядок), непустые части соединяются пробелом. Имя (first_name) присутствует всегда — бэкенд гарантирует его обязательность (см. «Просмотр профиля — Backend»), поэтому оговорка «при наличии» к имени не относится. Отчество и фамилия добавляются, только если заданы.

* Поле **логин**, полученное от `GET /profile`, должно отображаться на экране как неизменяемое поле — пользователь входит в систему именно этим значением, и он должен иметь возможность посмотреть его в профиле. Поле `id` (технический идентификатор пользователя) не предназначено для отображения и не должно попадать в модель экрана.

* Опциональные поля (`middle_name`, `last_name`, `email`, `phone`), если не заполнены, приходят от бэкенда как `null` (см. «Просмотр профиля — Backend»), а не как пустая строка и не как отсутствие ключа в ответе. Фронтенд обязан явно ожидать `null` в качестве признака отсутствия значения и в этом случае показывать плейсхолдер «не заполнено» для соответствующего поля (единое поведение для всех текстовых полей без значения).

* **Телефон приводится к строке перед отображением независимо от источника данных**: в сетевом режиме API возвращает `phone` как строку, а в локальном режиме (Effector-стор) поле исторически хранится как `number` — модель экрана обязана привести значение к строке перед выводом, чтобы отображение не зависело от `dataSource` и не показывало значение нетипизированным.

* Аватар отображается как единый визуальный элемент профиля; на данной итерации системе не требуется поддержка загрузки/смены пользовательского изображения — используется единообразная заглушка для всех пользователей.

## 5. Обработка ошибок

Экран должен явно различать следующие состояния и не смешивать их в одно универсальное «не заполнено»:

| Состояние                                          | Ожидаемое поведение экрана                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Загрузка данных                                    | Показывается индикатор загрузки (спиннер/скелетон) вместо данных или плейсхолдеров.                                                                                                                                                                                                                                                              |
| Профиль существует, но отдельные поля не заполнены | Показывается плейсхолдер «не заполнено» только для незаполненных (`null`) полей; остальные поля показывают реальные значения.                                                                                                                                                                                                                    |
| Профиль не найден (404 от `GET /profile`)          | Показывается состояние «профиль ещё не заполнен» с призывом перейти к редактированию — это не ошибка, а ожидаемое состояние нового пользователя. Для режима `dataSource=local` аналог этого состояния в данном документе не описывается — будет определён отдельно, см. «Локальный режим (dataSource=local) — заглушка».                         |
| Ошибка загрузки (сетевая ошибка, 500 и т.п.)       | Показывается явное сообщение об ошибке загрузки с возможностью повторить запрос; данные не должны выглядеть как «профиль пуст».                                                                                                                                                                                                                  |
| 401 (истёкший/невалидный access-токен)             | Не трактуется экраном как обычная ошибка загрузки с кнопкой «Повторить». Обрабатывается общим механизмом, см. «Общие требования: Сессия, 401 и авто-refresh токена»: экран инициирует авто-refresh токена и, если он не помог, следует общему сценарию (обычно — переход на экран входа), а не показывает локальное сообщение об ошибке с retry. |

## 6. Хранение состояния и побочные эффекты

* `GET /profile` кэшируется через react-query; время свежести и хранения кэша — 30 минут, без автоматических повторных запросов (retry) при ошибке.

* Кэш профиля должен инвалидироваться сразу после успешного сохранения на экране редактирования, чтобы экран просмотра не показывал устаревшие данные после возврата с редактирования.

## 7. Связанные задачи

* Отобразить login на экране просмотра профиля (устраняет неиспользование поля login).

* Добавить состояния загрузки и ошибки на экран просмотра профиля (устраняет смешение состояний «загрузка/ошибка/404/не заполнено»).

* Инвалидировать кэш профиля после сохранения (см. страницу «Редактирование профиля — Frontend»).

* Обработать `null` для опциональных полей профиля на экране просмотра (middle_name/last_name/email/phone), не полагаясь на пустую строку или отсутствие ключа.

* Привести телефон к строке перед отображением независимо от `dataSource` (сетевой/локальный режим).

* Исправить порядок ФИО на экране просмотра на «Фамилия Имя Отчество» (сейчас реализовано как «Имя Отчество Фамилия», см. `src/pages/profile/mappers/map-user-profile.ts`).
