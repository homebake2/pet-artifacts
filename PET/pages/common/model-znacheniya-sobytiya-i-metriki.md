## Назначение

Страница задаёт единую модель поля `value` события здоровья питомца и реестр метрик, по которому строятся графики динамики. Это единственный источник истины для формы `value` по каждому типу события: страницы флоу создания, редактирования, чтения событий, графиков, локального режима и импорта локальных данных ссылаются на эту страницу и не переопределяют форму `value` самостоятельно.

Модель решает две задачи одновременно:

* каждое событие несёт **машиночитаемый факт**, а не строку, которую нужно разбирать эвристиками при отображении и при агрегации;
* любой числовой или категориальный тип события **изначально пригоден для построения графика** без изменения контракта — появление графиков не требует пересмотра модели данных события.

## Структура события

Событие состоит из общей части и типизированного значения:

| Поле | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `id` | uuid | назначается системой | идентификатор события |
| `pet_id` | uuid | обязательно | питомец, которому принадлежит событие |
| `date` | RFC3339 | обязательно | момент события |
| `type` | enum типа события | обязательно | определяет форму `value` (см. таблицу ниже) |
| `value` | объект | обязательно | типизированное значение события; форма объекта определяется `type` |
| `notes` | строка, ≤ 500 символов | опционально | свободный комментарий владельца |

`value` — **объект, а не строка**. Форма объекта определяется значением `type` (размеченное объединение, дискриминатор — `type`). Никакой тип события не хранит несколько разных фактов, склеенных в одну строку, и не требует парсинга строки для получения числа.

Единицы измерения не хранятся в событии, а фиксированы конвенцией на уровне типа (см. столбец «Единица» ниже) — за единственным исключением тех типов, где единица является осмысленным выбором пользователя (`feeding.unit`, `medication.dose_unit`). Это гарантирует, что значения одного типа всегда сравнимы между собой и агрегируемы без конвертации.

`notes` никогда не является носителем структурированного факта: любой факт, который нужен для отображения карточки события, фильтрации или графика, ОБЯЗАН быть полем `value`, а не текстом в `notes`.

## Типы событий и форма `value`

Список значений `type` — см. [Справочник значений (словари enum)](spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)». Конкретные значения вложенных enum (`temperature.kind`, `feeding.unit`, `feeding.food`, `activity.kind`, `medication.dose_unit`, `hygiene.procedure`, `mood.state`, статус выделений) определены там же и не дублируются ни здесь, ни на страницах флоу — эта таблица задаёт только состав полей `value` и их валидацию.

| `type` | Поля `value` | Единица | Валидация | Значение по умолчанию |
| --- | --- | --- | --- | --- |
| `weight` | `amount` (number) | кг | `amount` — 0.001–400 (см. «Диапазоны значений и разнообразие видов») | — |
| `temperature` | `amount` (number), `kind` (enum «Вид замера температуры») | °C | `amount` — 0–50 (см. «Диапазоны значений и разнообразие видов»); `kind` обязателен — замер тела и замер среды несопоставимы и не смешиваются (см. «Разнообразие видов и состав словарей») | — |
| `feeding` | `amount` (number), `unit` (enum «Единица измерения кормления»), `food` (enum «Вид корма») | задаётся полем `unit` | `amount` — 0.01–5000; `unit` и `food` обязательны | — |
| `water` | `amount` (number) | мл | `amount` — 0.1–5000 (см. «Диапазоны значений и разнообразие видов») | — |
| `activity` | `duration_min` (number), `kind` (enum «Вид активности»), `distance_m` (number, опционально) | минуты; `distance_m` — метры | `duration_min` — 1–1440; `kind` обязателен; `distance_m` — 0–100000, если передан | — |
| `sleep` | `duration_min` (number) | минуты | `duration_min` — 1–1440 | — |
| `medication` | `name` (строка), `dose_amount` (number, опционально), `dose_unit` (enum «Единица дозы лекарства», опционально) | задаётся полем `dose_unit` | `name` — 1–100 символов; `dose_amount` — 0.001–10000; `dose_amount` и `dose_unit` передаются только вместе (одно без другого — ошибка валидации) | — |
| `hygiene` | `procedure` (enum «Процедура гигиены») | — | `procedure` обязателен | — |
| `mood` | `state` (enum «Состояние питомца») | — | `state` обязателен | — |
| `urine`, `vomit`, `diarrhea` | `status` (enum «Статус выделений») | — | `status` обязателен; подробности наблюдения (цвет, частота, консистенция) несёт `notes` | — |
| `defecation` | `status` (enum «Статус выделений») | — | `status` обязателен; подробности наблюдения (цвет, частота, консистенция) несёт `notes` | `status`: `normal` («В норме») |
| `other` | `label` (строка) | — | `label` — 1–50 символов; краткое обозначение события, `notes` несёт подробности | — |
| `molting` | `status` (enum «Статус линьки») | — | `status` обязателен | — |
| `egg_laying` | `count` (number), `status` (enum «Статус кладки», опционально) | штуки | `count` — 1–200; `status` опционален, при отсутствии считается `normal` только для отображения (валидация значения по умолчанию не требует) | — |
| `water_quality` | `temperature_c` (number, опц.), `ph` (number, опц.), `ammonia_ppm` (number, опц.), `changed_volume_ml` (number, опц.) | °C; pH; ppm; мл | хотя бы одно из четырёх полей обязано быть передано (пустое `value` без единого показателя не несёт факта); `temperature_c` — 0–40; `ph` — 0–14; `ammonia_ppm` — 0–10; `changed_volume_ml` — 0–200000 | — |
| `heat_cycle` | `phase` (enum «Фаза течки») | — | `phase` обязателен | — |

Поля, не описанные в форме `value` для данного `type`, недопустимы: сервер отклоняет запрос с 400, а не игнорирует лишние поля молча — иначе опечатка в имени поля привела бы к тихой потере введённых пользователем данных.

## Значения по умолчанию для полей `value`

Поле формы `value` может иметь **значение по умолчанию**, определённое для конкретного типа события в столбце «Значение по умолчанию» таблицы выше. Значение по умолчанию — это только начальное состояние поля на экране добавления события, а не часть валидации: пользователь всегда может изменить его на любое другое допустимое значение перед сохранением, и сервер не проверяет, что значение поля равно его умолчанию.

Правила:

* Значение по умолчанию применяется только на экране **добавления** события — при открытии формы для данного типа и при переключении типа события на тип, для которого умолчание определено (см. «Добавление события — Frontend», раздел «Основной сценарий»). Экран **редактирования** события всегда показывает фактически сохранённое значение и умолчания не применяет — см. [Редактирование события — Frontend](../calendar/redaktirovanie-sobytiya-frontend.md).
* У поля без значения по умолчанию (отметка «—» в таблице) начальное состояние формы для этого поля — пустое: пользователь обязан ввести значение сам.
* Умолчание относится к конкретному полю конкретного `type`, а не ко всей форме `value` целиком: остальные поля того же типа, для которых умолчание не определено, остаются пустыми.
* `urine`, `vomit`, `diarrhea` умолчания для `status` не имеют, несмотря на общую форму `value` со `defecation`: типы `value` могут различаться составом умолчаний даже при одинаковом составе полей — умолчание не выводится автоматически по форме `value`, а задаётся отдельно на каждый `type`.
* Добавление нового умолчания или изменение существующего — это правка данной таблицы, не требующая изменения состава полей, единиц или валидации.

## Диапазоны значений и разнообразие видов

Приложение ведёт учёт по всем видам справочника видов питомцев (см. [Справочник значений (словари enum)](spravochnik-znachenii-slovari-enum.md), раздел «Питомцы — Вид (species)») — от улитки и муравьиной фермы до мини-козы. Поэтому числовые диапазоны валидации ОБЯЗАНЫ покрывать всех этих животных, а не только собак и кошек. Диапазон — это защита от заведомо бессмысленного ввода (опечатка, ноль, отрицательное число), а не медицинская норма: приложение не решает за владельца, какое значение «нормально» для его вида.

* **Температура (0–50 °C).** Нижняя граница определяется не теплокровными животными, а холоднокровными: у рыб, амфибий и рептилий температура тела следует за средой, и для холодноводной рыбы или зимующей (брумация) рептилии значения в единицы градусов — норма, а не ошибка ввода. Верхняя граница определяется птицами, у которых нормальная температура тела достигает 44 °C, плюс запас на лихорадку и на замер в точке прогрева у рептилий. Диапазон, суженный до 36–42 °C «как у собак и кошек», сделал бы событие непригодным для большей части видов справочника.

* **Вес (0.001–400 кг).** Нижняя граница — 1 грамм: улитка, паук, новорождённый грызун и птенец канарейки весят единицы граммов, и округление их веса до 10 граммов (`0.01` кг) уничтожило бы сам смысл отслеживания их динамики. Верхняя граница взята с запасом относительно самых крупных видов справочника (мини-пиг, мини-коза).

* **Вода (0.1–5000 мл).** Разовое потребление воды у крупной собаки измеряется литрами, а у мелкой птицы или грызуна — долями миллилитра; нижняя граница выбрана так, чтобы владелец мелкого питомца мог зафиксировать реальный объём, а не вынужденно округлять его до целого миллилитра.

Это же правило действует при добавлении нового числового типа события: границы выбираются по самому мелкому и самому крупному виду справочника, а не по «типичному» питомцу.

Отображение значения адаптируется к масштабу: вес меньше 1 кг клиент показывает в граммах, а не как `0.012 кг`. Хранение при этом остаётся в единой единице типа (кг) — переключается только форматирование, иначе значения перестали бы быть сравнимыми между собой.

## Разнообразие видов и состав словарей

Требование покрывать все виды справочника относится не только к числовым диапазонам, но и к составу вложенных словарей `value`. Словарь, собранный «под собаку и кошку», делает событие бесполезным для владельца змеи, попугая, черепахи или аквариумной рыбы: он вынужден выбрать заведомо неверное значение либо вовсе не заводить событие.

Правило наполнения любого словаря `value`:

* **Распространённые для нескольких видов случаи — отдельные значения словаря.** Кормление живыми и размороженными кормовыми грызунами, насекомыми, сеном, зерном и зеленью — это не экзотика, а основной рацион целых групп видов справочника (рептилии, птицы, грызуны, кролики, мини-коза), поэтому они существуют как самостоятельные значения, а не сваливаются в «прочее».

* **Узкоспецифичные случаи — значение `other` плюс `notes`.** Словарь не пытается перечислить всё: `other` — обязательный элемент любого словаря с открытым «хвостом» (вид корма, вид активности, процедура гигиены), а подробности владелец пишет в `notes`. Отсутствие `other` в таком словаре — ошибка проектирования, а не строгость.

* **Регулярно встречающееся значение `other` — сигнал к расширению словаря, а не к его размыванию.** Если владельцы массово выбирают «прочее» с одинаковым пояснением в `notes`, это основание добавить значение в словарь (по правилу расширения ниже), а не оставлять факт неструктурированным навсегда.

Отдельный случай — температура. У теплокровных владелец фиксирует температуру тела, у рептилий, амфибий и рыб предметом наблюдения обычно является температура среды (террариум, точка прогрева, вода аквариума). Это два разных наблюдения в одной шкале, поэтому `temperature.kind` обязателен, а ряды графика по замерам тела и среды строятся раздельно: усреднение температуры тела птицы с температурой воды аквариума дало бы число, не означающее ничего.

## Применимость типа события к виду питомца

Не каждый тип события физиологически осмыслен для каждого вида справочника видов питомцев ([Справочник значений (словари enum)](spravochnik-znachenii-slovari-enum.md), раздел «Питомцы — Вид (species)»): например, `heat_cycle` (течка) неприменим к рыбе, а `urine` — к птице, у которой моча и кал выводятся вместе через клоаку одним актом дефекации. Каждый тип события ОБЯЗАН иметь запись применимости — множество значений `pet.species`, для которых этот тип доступен.

Применимость определяется полем `pet.species` конкретного питомца. `species` — свободный текст без enum-ограничения на уровне БД: пригодность для закрытого правила применимости обеспечивается не ограничением схемы, а тем, что собственный «Вид» picker приложения — единственный штатный способ заполнить это поле — всегда записывает в него один из 31 токена справочника видов (см. справочник выше). Значение `species`, не входящее в справочник (повреждённые данные, устаревшее или сторонним способом записанное значение), трактуется этим правилом разрешительно — как значение `OTHER` (применимо ко всем типам событий), а не как ошибка.

| `sleep` | все, кроме `FISH`, `TURTLE`, `IGUANA`, `GECKO`, `BEARDED_AGAMA`, `SNAKE`, `PYTHON`, `FROG`, `AXOLOTL`, `TARANTULA`, `HERMIT_CRAB`, `ANT_FARM`, `SNAIL` |
| `medication` | все |

Правила, вытекающие из применимости:

* **`OTHER` (неопределённый вид), как и любое значение `species` вне справочника, допускает все типы события.** Значение `OTHER` используется, когда конкретный вид не входит в справочник; сужать для него набор типов означало бы гадать о физиологии неизвестного животного, поэтому оно — как и любое нераспознанное значение `species` — единственный случай, применимый ко всем без исключения типам.

* **Frontend фильтрует список типов события в форме добавления/редактирования по применимости к виду выбранного питомца** (см. [Добавление события — Frontend](../calendar/dobavlenie-sobytiya-frontend.md), [Редактирование события — Frontend](../calendar/redaktirovanie-sobytiya-frontend.md)): селектор типа события показывает только типы, применимые к `pet.species` этого питомца, а не полный список из справочника.

* **Backend независимо проверяет применимость при создании и редактировании события** (см. «Добавление события — Backend», «Редактирование события — Backend»): если переданный `type` не входит в множество применимых для `pet.species` этого питомца — сервер отклоняет запрос с 400, а не полагается на то, что клиент не предложил недопустимый вариант в форме. Фильтрация на клиенте — это UX, а не единственный источник этой проверки.

* **Таблица применимости — часть той же единицы работы, что и сама модель `value` реестра метрик** (см. «Расширение множества типов событий» ниже): у типа события не может быть формы `value` и записи в реестре метрик без записи применимости — она обязательна для каждого типа, включая универсальные («все»).

## Реестр метрик

Каждый тип события ОБЯЗАН иметь запись в едином реестре метрик. Реестр — общий для backend и frontend источник истины (тот же принцип, что и для enum-словарей, см. [Общие требования: Единый источник enum-словарей](obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md)): backend строит по нему агрегацию для графиков, frontend — форму ввода, отображение карточки события и оси графика. Двух независимых описаний одного типа события в системе быть не должно.

Запись реестра описывает:

* `value_kind` — характер значения: `measure` (мгновенное измерение), `quantity` (количество, накапливаемое за период), `category` (категориальное наблюдение), `label` (свободная метка);
* `metrics` — список метрик типа: ключ, поле внутри `value`, единица;
* `aggregation` — способ свёртки значений метрики внутри интервала графика.

| `type` | `value_kind` | Метрики (поле `value`) | Агрегация в интервале | Форма графика |
| --- | --- | --- | --- | --- |
| `weight` | `measure` | `amount` (кг) | среднее и последнее значение интервала | линия |
| `temperature` | `measure` | `amount` (°C) | среднее и последнее значение интервала — **раздельно по каждому `kind`** | линия, отдельная серия на каждый `kind` |
| `feeding` | `quantity` | `amount` (единица из `unit`) | сумма — **раздельно по каждой `unit`** | столбцы, отдельная серия на каждую `unit` |
| `water` | `quantity` | `amount` (мл) | сумма | столбцы |
| `activity` | `quantity` | `duration_min` (мин), `distance_m` (м) | сумма по каждой метрике независимо | столбцы |
| `sleep` | `quantity` | `duration_min` (мин) | сумма | столбцы |
| `medication` | `quantity` | количество приёмов (число событий) | количество событий | столбцы |
| `hygiene` | `category` | `procedure` | количество событий по каждому значению категории | столбцы по категориям |
| `mood` | `category` | `state` | количество событий по каждому значению категории | столбцы по категориям |
| `urine`, `defecation`, `vomit`, `diarrhea` | `category` | `status` | количество событий по каждому значению категории | столбцы по категориям |
| `other` | `label` | — | не агрегируется | график не строится |
| `molting` | `category` | `status` | количество событий по каждому значению категории | столбцы по категориям |
| `egg_laying` | `quantity` | `count` (шт.) | сумма | столбцы |
| `water_quality` | смешанный (см. ниже) | `temperature_c` (°C), `ph`, `ammonia_ppm` (ppm) — каждая `measure`; `changed_volume_ml` (мл) — `quantity` | `temperature_c`/`ph`/`ammonia_ppm` — среднее и последнее значение интервала, каждая метрика отдельно; `changed_volume_ml` — сумма | линия на каждую `measure`-метрику, столбцы на `changed_volume_ml` |
| `heat_cycle` | `category` | `phase` | количество событий по каждому значению категории | столбцы по категориям |

Правила агрегации, вытекающие из реестра и обязательные к соблюдению:

* **Разные единицы не суммируются.** Метрика `feeding.amount` агрегируется только в пределах одной `unit`: граммы, миллилитры, порции и штуки — независимые серии, а не одно число. Сложение значений с разными единицами запрещено, так как даёт бессмысленный результат: «10 сверчков + 200 г сена» не является величиной.

* **Несопоставимые наблюдения в одной шкале не смешиваются.** Метрика `temperature.amount` агрегируется раздельно по `kind`: температура тела и температура среды измеряются в одних градусах, но описывают разные объекты наблюдения, и их общее среднее не имеет смысла.

* **`medication` агрегируется по количеству приёмов, а не по дозе.** `dose_amount` относится к конкретному препарату и его единице, поэтому суммирование дозы между разными препаратами запрещено. График по дозе одного конкретного препарата не входит в область этой модели и потребует отдельного требования.

* **`measure` не суммируется.** Для мгновенных измерений (вес, температура) сумма лишена смысла: допустимы только среднее и последнее значение интервала.

* **`label` не агрегируется.** Тип `other` намеренно не пригоден для графика: это escape hatch для событий, у которых нет структурированной модели. Если для какого-то события из `other` регулярно нужен график — это признак того, что для него нужен собственный `type` с записью в реестре, а не изменение правил агрегации `other`.

* **`value_kind` может быть задан на уровне отдельной метрики, а не только типа целиком.** Обычно все метрики одного типа имеют одну природу (`measure`, `quantity` или `category`), но когда метрики одного типа описывают факты разной природы — как в `water_quality`, где мгновенные показатели воды (`temperature_c`, `ph`, `ammonia_ppm`) соседствуют с накопленным за период объёмом подмены (`changed_volume_ml`) — `value_kind` и правило свёртки указываются отдельно для каждой такой метрики, а не одним значением на весь тип.

* **Необязательное поле формы `value`, не входящее в реестр метрик, не агрегируется, даже если несёт факт.** `egg_laying.status` — пример: это категориальный факт о конкретной кладке (нормальная/осложнённая), но графика по нему не строится — только `count` зарегистрирован как метрика. Это то же правило, что уже действует для `medication.dose_unit`/`dose_amount` (см. выше «`medication` агрегируется по количеству приёмов, а не по дозе»): не каждое поле формы `value` обязано иметь свою метрику.

* **Пустые интервалы не пропускаются.** Интервал без событий — это явное «нет данных», а не отсутствующая точка: он ОБЯЗАН присутствовать в результате агрегации с нулевым количеством событий, чтобы клиент строил ось времени по полному набору интервалов периода. Без пустых интервалов ось сжалась бы, поставив рядом наблюдения, между которыми лежат недели без измерений, и динамика читалась бы по искажённому масштабу времени.

## Расширение множества типов событий

Тип события существует в системе только целиком. Добавление нового `type` ОБЯЗАНО в рамках той же работы включать:

1. значение в enum типов события ([Справочник значений (словари enum)](spravochnik-znachenii-slovari-enum.md)) и все вложенные enum его `value`;
2. форму `value` и её валидацию в таблице «Типы событий и форма `value`» этой страницы — единую для валидации на backend и схемы формы на frontend;
3. запись применимости к виду питомца в таблице раздела «Применимость типа события к виду питомца» этой страницы — множество значений `pet.species`, для которых тип доступен (не менее одного значения; универсальный тип получает отметку «все»);
4. запись в реестре метрик этой страницы, включая `value_kind`, метрики и агрегацию (для типа с `value_kind: label` — явное указание, что график не строится);
5. поддержку в локальном хранилище режима `dataSource=local` и в контракте `POST /import/local-data` — по правилу паритета сущностей (см. [Локальный режим (dataSource=local) — общая архитектура хранения](lokalnyi-rezhim-datasource-local-zaglushka.md), раздел «Поддержание паритета сущностей при переносе»);
6. иконку и локализованную подпись типа, общие для календаря, формы события и графиков.

Тип события без записи в реестре метрик существовать не может: такой тип нельзя ни отобразить в списке доступных для графика метрик, ни осмысленно свернуть в интервал, и он превратился бы в данные, которые пользователь ввёл, но не может увидеть в динамике. Тип события без записи применимости так же не может существовать: без неё невозможно ни отфильтровать список типов в форме под вид выбранного питомца, ни провалидировать запрос на сервере.

## Хранение

`value` хранится в столбце `event.value` типа `jsonb` (PostgreSQL) с ограничением `NOT NULL`. Тип столбца — `jsonb`, а не `text`: значение является структурированным объектом, и хранение его в виде строки лишило бы БД возможности индексировать и агрегировать поля `value` на стороне сервера, что требуется для графиков.

Соответствие формы объекта значению `type` проверяется приложением при создании и редактировании события (см. «Добавление события — Backend», «Редактирование события — Backend»), а не выражается ограничением уровня БД: правило зависит от `type` и меняется вместе с реестром метрик, поэтому его единственное место — общая для backend и frontend схема, а не `CHECK`-ограничение, которое пришлось бы поддерживать миграцией на каждое изменение реестра.

Для агрегации событий по типу и периоду (см. [Графики динамики — Backend](../calendar/grafiki-dinamiki-backend.md)) таблица `event` ОБЯЗАНА иметь индекс, покрывающий выборку неудалённых событий одного питомца по типу и дате:

```
CREATE INDEX event_pet_type_date_idx
  ON event (pet_id, type, date_time)
  WHERE deleted_at IS NULL;
```

В режиме `dataSource=local` `value` хранится тем же объектом с той же формой и той же валидацией — локальное хранилище не имеет собственного, упрощённого представления значения события (см. [Локальный режим (dataSource=local) — общая архитектура хранения](lokalnyi-rezhim-datasource-local-zaglushka.md)).
