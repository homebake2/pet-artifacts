## Назначение

Согласие на обработку персональных данных оформляется отдельно от остальных документов (152-ФЗ) и фиксируется так, чтобы оператор мог его подтвердить. Принятие условий использования запрашивается вместе с ним, но как отдельное решение. Версии документов меняются без выпуска новой версии приложения; после смены версии согласие запрашивается у всех пользователей заново.

Для пользователей из ЕС основанием обработки является исполнение договора (GDPR, ст. 6(1)(b)); согласие как основание обработки для них не требуется, поэтому запрос не зависит от региона и не меняет основание обработки.

## Документы и версии

* Документов два: `terms` (условия использования) и `personal_data` (согласие на обработку персональных данных на основании политики конфиденциальности). Принимаются раздельно, оба обязательны.

* У каждого документа есть текущая версия — целое число, растущее на единицу. Версии хранятся на сервере, а не в приложении.

* Версия меняется записью в базе данных (вручную или миграцией); отдельный метод API для смены версии не предусмотрен. Меняется версия при любом изменении смысла документа; правка опечаток версию не меняет.

* Актуальные тексты документов на русском и английском языках хранятся на сервере вместе с версией и отдаются приложению запросом (см. «Тексты документов» ниже). Текст и версия меняются вместе, в одной операции.

* В приложении вшиты запасные тексты документов (и их версии), соответствующие версии на момент выпуска приложения. Они показываются, пока актуальные тексты не получены с сервера: запрос не удался или приложение работает без сети. Запасные тексты не нужно обновлять при каждом изменении документов: источник истины — сервер, а принять можно только актуальный текст, полученный с сервера. Чтобы вшитые тексты были как можно свежее, перед запуском и сборкой приложения и перед сборкой сайта выполняется шаг синхронизации: он запрашивает актуальные тексты и версии с сервера и обновляет вшитые тексты (в приложении — запасные тексты и их версии, на сайте — сохранённый снимок текстов). Если сервер недоступен или ответ некорректен, шаг пропускается без ошибки, а сборка продолжается со вшитыми текстами как есть. Шаг не меняет файлы, если тексты уже актуальны.

## Тексты документов

* Приложение запрашивает актуальные тексты и версии документов на языке приложения при открытии экрана документа, при показе запроса принятия и при открытии экрана входа (в последнем случае чтобы документы были доступны до входа без ожидания). Запрос не требует авторизации.

* Последний успешно полученный ответ сохраняется на устройстве отдельно для каждого языка и используется, пока не получен новый; если на устройстве ничего не сохранено, показывается запасной текст. Экран документа не ждёт ответа дольше, чем нужно для показа: пользователь сразу видит сохранённый или запасной текст, а при получении новой версии текст обновляется.

* Принятие отправляется с версией того текста, который показан пользователю. Если показан запасной или устаревший текст, а на сервере уже новая версия, принятие отклоняется (`409 CONSENT_VERSION_MISMATCH`); приложение повторно запрашивает актуальные тексты и просит пользователя ознакомиться с ними и принять снова. Если актуальные тексты получить не удаётся, принятие недоступно и пользователь видит причину с возможностью повторить запрос.

* Оффлайн-режим и принятие: в режиме local запрос принятия не показывается; документы открываются из сохранённых или запасных текстов.

## Что видит пользователь

Запрос показывается в режиме network после входа (по логину и гостевого), если по любому из документов принятая версия ниже текущей или документ ещё не принят. В режиме local запрос не показывается: данные не передаются на сервер.

* Запрос открывается поверх приложения и не закрывается жестом возврата: пользователь либо принимает документы, либо отказывается. До принятия данные аккаунта недоступны.

* В описании запроса коротко и дружелюбно сказано, что по закону РФ оператор обязан спросить согласие на обработку персональных данных.

* Для каждого из двух документов имеется отдельная отметка согласия без предустановленного значения, рядом с ней текст и возможность открыть полный документ (на языке приложения) без выхода из запроса.

* Имеются два действия: отказ (расположено слева) и принятие (справа). Принятие недоступно, пока не отмечены оба документа. Отметки не запоминаются между показами запроса: после смены версии пользователь отмечает их заново.

* Пока выполняется запрос на принятие, повторная отправка недоступна, а состояние отправки видно пользователю (см. [Общие требования: UI-паттерны запросов](obschie-trebovaniya-ui-patterny-zaprosov.md)).

* При отказе пользователю предлагается выбрать одно из двух: выйти из аккаунта или удалить аккаунт. Имеется возможность закрыть предложение, не выбирая, — запрос согласия остаётся на экране.

  * Выход: обычный выход из аккаунта (см. [Выход — Frontend](../auth/logout-frontend.md)); аккаунт и его данные не затрагиваются, при следующем входе запрос показывается снова.

  * Удаление аккаунта: требует дополнительного подтверждения отдельным шагом с предупреждением, что данные удаляются безвозвратно. После подтверждения выполняется удаление аккаунта (`DELETE /profile`) и клиент возвращается на экран входа.

* После принятия клиент продолжает обычный сценарий: при входе — переход по `pets_count`, при повторном запросе посреди сессии — возврат на экран, на котором пользователь находился, с повтором запроса, который был отклонён.

## Контракт

* `GET /consent-documents?language=ru|en` — актуальные тексты документов. Без авторизации. Параметр `language` необязателен (по умолчанию `ru`), другое значение — `400 VALIDATION_ERROR`. Ответ `200`: массив `documents` из элементов `{doc_type, version, language, text}`, по одному на документ; `text` — Markdown без собственного заголовка (заголовок показывает экран).

* `GET /consents` — статус документов для текущего пользователя. Ответ `200`: `consent_required` (boolean) и массив `documents` из элементов `{doc_type, version, accepted}`, где `version` — текущая версия, `accepted` — принята ли именно она этим пользователем.

* `POST /consents` — принять документы. Тело: массив `{doc_type, version}`, где `version` — версия текста, показанного пользователю. Должны быть переданы оба документа; версии должны совпадать с текущими. Ответы: `204` — принято (повтор того же запроса также `204`); `400 VALIDATION_ERROR` — передан не весь набор документов либо неизвестный `doc_type`; `409 CONSENT_VERSION_MISMATCH` — версия не совпадает с текущей (на сервере уже новая версия; клиенту показывается предложение обновить приложение).

* Ошибка `403 CONSENT_REQUIRED` возвращается любым защищённым методом, кроме перечисленных ниже, если у пользователя нет принятых текущих версий обоих документов. Клиент по этой ошибке показывает запрос согласия (как по 401 запускается обновление токена), а не показывает ошибку в экране, где она возникла.

* Не требуют принятых документов и доступны всегда: `GET /consent-documents`, `GET /consents`, `POST /consents`, `POST /auth/logout`, обновление токена, `DELETE /profile`, `GET /config`, проверка состояния сервиса. Остальные защищённые методы, включая методы с токеном в режиме гостя, требуют принятия.

* Ответы входа по логину и гостевого входа содержат поле `consent_required` (boolean), чтобы клиент не делал отдельный запрос. При холодном старте с уже восстановленной сессией запрос показывается по `403 CONSENT_REQUIRED` первого же защищённого запроса.

## Хранение

* Таблица `consent_document(doc_type, version)` — текущие версии, по одной строке на документ.

* Таблица `consent_document_text(doc_type, language, text)` — текущие тексты документов по языкам (`ru`, `en`); для каждого документа есть оба языка. Текст и версия обновляются вместе, в одной транзакции.

* Таблица `user_consent(user_id, doc_type, version, accepted_at)` — журнал принятий. Записи только добавляются, не изменяются; первичный ключ `(user_id, doc_type, version)`. Пользователь считается принявшим документ, если есть запись с текущей версией.

* IP-адрес и данные устройства не сохраняются.

* Записи `user_consent` удаляются вместе с аккаунтом.

* Текущие версии могут кэшироваться в памяти сервера, но не дольше короткого времени, достаточного, чтобы смена версии в базе вступала в силу без перезапуска.

## Сайт: форма предложений

* В форме предложений имеется отдельная отметка согласия на обработку персональных данных без предустановленного значения, с возможностью открыть политику конфиденциальности. Пока она не отмечена, отправка недоступна. Это согласие на обработку данных формы, а не принятие условий использования.

* Контракт и хранение — см. [Предложения на сайте — Backend](../web/predlozheniya-saita-backend.md).

## Не входит

* Отзыв согласия отдельным действием: отзыв равен удалению аккаунта (см. [Общие требования: Сроки хранения данных](obschie-trebovaniya-sroki-hraneniya-dannyh.md)).

* Согласие на персонализацию рекламы остаётся отдельным решением и не заменяется этим запросом (см. [Реклама — Frontend](../ads/reklama-frontend.md)).
