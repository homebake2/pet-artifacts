## Назначение

Страница задаёт сквозные правила записи календаря, привязанной к нескольким питомцам: обычного события («Уже произошло», факт) и напоминания. Одна запись принадлежит одному или нескольким питомцам одного пользователя; данные, расписание, заметка и файлы у неё общие и хранятся один раз. Список доступных типов события ограничивается тем, что применимо ко всем привязанным питомцам; при изменении записи питомцев можно привязывать и отвязывать.

Страница — единственный источник правил этой возможности. Страницы флоу (добавление, редактирование, удаление события, напоминания, календарь, импорт) ссылаются на неё и уточняют только свои контракты.

## Модель

* Запись (факт `event`, настройки напоминания `reminder_plan`) существует в одном экземпляре и связана с питомцами через таблицу связи: `event_pet (event_id, pet_id)` и `reminder_plan_pet (plan_id, pet_id)`, первичный ключ — пара. Столбцов `event.pet_id` и `reminder_plan.pet_id` нет.

* Автор записи — пользователь: у `event` и `reminder_plan` есть `user_id`. Доступ к записи определяется не `user_id`, а питомцами записи и ролями пользователя у них: привязать можно питомцев, у которых роль пользователя `owner` или `full`; все питомцы одной записи принадлежат одному владельцу (иначе `400`). Запись видна пользователю, только если ему доступны все её видимые питомцы, и изменяема, только если у всех них роль `owner` или `full` (см. [Общие требования: Доступ к питомцу](obschie-trebovaniya-dostup-k-pitomtsu.md), раздел «Записи с несколькими питомцами»).

* У записи от 1 до 10 привязанных питомцев. Запись без привязанных питомцев существовать не может.

* **Видимые питомцы записи** — привязанные питомцы, не мягко удалённые. Запись показывается и доступна, пока у неё есть хотя бы один видимый питомец; в её списке питомцев отдаются только видимые. Связь события с мягко удалённым питомцем сохраняется, но скрыта; в составе привязки при изменении она не участвует и не затрагивается.

* Общие для всех питомцев записи поля: у факта — `date`, `type`, `value`, `notes`, файлы; у настроек напоминания — `type`, `value`, `notes`, расписание, `tz`, файлы настроек, а также их напоминания (моменты). Отдельных значений по питомцам нет: одно напоминание — один момент, одно закрытие, один факт при отметке «Выполнено».

* Настройки с источником `medication`, `vaccination` и `vaccination_extra` (см. [Напоминания — Backend](../calendar/napominaniya-backend.md), «Источник настроек») принадлежат записи Ветпаспорта конкретного питомца: у них всегда ровно один питомец, выбор нескольких питомцев для них не предлагается. Факты, создаваемые Ветпаспортом (например, вакцинацией), привязаны к одному питомцу.

## Допустимые типы события и значения

1. Множество типов события, доступных в записи для нескольких питомцев, — **пересечение** множеств типов, применимых к видам привязанных питомцев (см. [Модель значения события и реестр метрик](model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца»). Тип доступен, только если он применим к каждому питомцу.

2. Так же определяются значения вложенных словарей `value` (`hygiene.procedure`, `feeding.food`, `activity.kind`): допустимы только значения, применимые к виду каждого питомца записи.

3. **Измерительные типы** — `weight`, `temperature`, `water_quality` — привязываются ровно к одному питомцу: значение измерения принадлежит конкретному организму (или среде) и не может быть общим. Если у записи более одного питомца, эти типы недоступны; запись с таким типом и несколькими питомцами отклоняется (400). Новый тип события обязан в рамках той же работы получить признак «допускает несколько питомцев» (см. [Модель значения события и реестр метрик](model-znacheniya-sobytiya-i-metriki.md), «Расширение множества типов событий»).

4. Пересечение никогда не пусто: `feeding`, `medication`, `hygiene`, `other` применимы ко всем видам и допускают нескольких питомцев; значение `other` присутствует в каждом вложенном словаре. Вид `OTHER` и значение `species` вне справочника допускают все типы и пересечение не сужают.

5. Изменение набора питомцев пересчитывает доступные типы и значения. Если выбранный тип стал недоступен (неприменим хотя бы к одному питомцу либо измерительный при нескольких питомцах), поля «Тип события» и «Значение» сбрасываются; если недоступным стало только значение вложенного словаря — сбрасывается оно. Пользователю показывается, что список ограничен выбранными питомцами.

6. **Проверка на сервере независима от клиента:** тип, значения вложенных словарей и число питомцев проверяются по итоговому набору видимых питомцев записи; при нарушении — 400, и запись не создаётся и не изменяется.

7. При редактировании сохранённый `type` остаётся в списке вариантов, пока набор питомцев не менялся. Если набор менялся и сохранённый тип стал недоступен, действует правило 5 — тип нужно выбрать заново.

## Создание

1. Имеется возможность выбрать одного или нескольких питомцев (минимум одного, не более 10) из питомцев, на которые у пользователя роль `owner` или `full`. Если экран открыт с предвыбранным питомцем, он отмечен, и можно добавить других. Если у пользователя один питомец, выбор не показывается.

2. Создаётся одна запись, привязанная ко всем выбранным питомцам. Для измерительного типа — ровно один питомец.

3. Факт: дата не позже текущего момента (допуск прежний). Напоминание: расписание даёт хотя бы один будущий момент, потолок 60 напоминаний действует на настройки (на запись, а не на питомца).

4. Дедупликация повторной отправки сохраняет существующие механизмы: для факта — `Idempotency-Key`, уникальный в пределах пользователя (`user_id`, `idempotency_key`); для напоминаний — клиентский `id` настроек.

## Изменение

Форма изменения открывается для записи целиком; пользователь меняет общие поля и набор питомцев. Выбора «для какого питомца» нет — запись одна.

### Факт

* Изменяются `date`, `type`, `value`, `notes` и набор питомцев. Изменение применяется к записи и сразу видно у всех её питомцев.

### Напоминание

Выбор «Что изменить?» строится по данным элемента календаря (`plan_unclosed_count`, `plan_source`) без дополнительного запроса:

| Область | Что меняется | Питомцы | Когда доступна |
| --- | --- | --- | --- |
| «Только это напоминание» | Один момент: заменяется новой независимой записью (существующий механизм «Изменить это») | Набор питомцев новой записи можно изменить (любые питомцы пользователя, не более 10); для настроек `medication` — только питомец лекарства | У настроек больше одного незавершённого напоминания; для `vaccination` недоступна |
| «Все напоминания» | Общие поля настроек и все их напоминания | Можно привязать и отвязать | Всегда (для настроек с источником питомцы не меняются) |

* Если доступна единственная область, выбор не показывается и открывается соответствующая форма.

* «Только это напоминание» создаёт новую запись с собственным набором питомцев; исходные настройки и их питомцы не меняются, закрытый момент пропускается пересозданием расписания, как и раньше. Правила доступных типов и измерительных типов действуют по набору питомцев новой записи.

* Изменение расписания в «Все напоминания» пересоздаёт напоминания настроек по существующим правилам.

## Привязка и отвязка питомцев

Действует при изменении факта и в области «Все напоминания». Клиент отправляет **желаемый полный набор видимых питомцев** записи (`pet_ids`); сервер сравнивает его с текущим набором видимых питомцев.

1. **Привязка** — питомец добавляется в набор. Пользователь должен быть владельцем питомца или иметь на него полный доступ (`full`), питомец не должен быть мягко удалён. Отвязка и привязка применяются только к записи, изменяемой пользователем по правилам доступа (у всех видимых питомцев записи роль `owner` или `full`). Запись, её данные и файлы не копируются: добавляется только связь. Запись сразу появляется у питомца в календаре, в «События питомца», в превью и в графиках (если значение входит в метрики типа).

2. **Отвязка** — питомец убирается из набора: удаляется только связь. Запись, её данные и файлы остаются у остальных питомцев и не удаляются; у отвязанного питомца запись исчезает из календаря, «События питомца», превью и графиков. Отвязка обратима повторной привязкой.

3. Набор не может быть пустым: у записи всегда остаётся хотя бы один питомец (400). Чтобы убрать запись целиком, используется удаление (см. «Удаление»).

4. Привязка и изменение общих полей в одном запросе применяются одновременно: проверки типа, значения и числа питомцев выполняются по итоговому набору и итоговым значениям (в том числе для сохранённых `type`/`value`, если форма их не меняла).

5. Для напоминания привязка питомца не создаёт и не пересоздаёт напоминания: моменты принадлежат настройкам и общие для всех питомцев. Для факта дата записи не проверяется заново, если не передана.

6. Применение атомарно: либо изменены данные и связи, либо ничего. Повторная отправка того же желаемого набора идемпотентна.

## Удаление

* **Удалить у всех.** Запись удаляется целиком (факт — мягко, настройки напоминания — жёстко), у всех питомцев. Для записи с несколькими видимыми питомцами подтверждение содержит перечень питомцев, у которых запись будет удалена.

* **Убрать только у питомца.** Доступно в контексте конкретного питомца («События питомца», превью на карточке питомца, экран напоминаний питомца), если у записи больше одного видимого питомца: удаляется только связь этого питомца (то же, что отвязка). Если питомец единственный, этого варианта нет — только удаление записи.

* Из календаря (вне контекста питомца) доступно удаление «у всех»; отвязать питомца можно в форме изменения.

* Окно отмены (Undo) действует для обоих вариантов: отмена возвращает запись или связь.

* Для напоминаний сохраняется выбор «Только это напоминание» / «Все напоминания» (удаление момента или всех настроек); поверх него в контексте питомца доступен вариант «Убрать только у питомца».

## Отметка прошедшего напоминания

Закрытие напоминания («Выполнено» / «Не выполнено») относится к моменту, общему для всех питомцев настроек. При «Выполнено» создаётся один факт, привязанный к видимым питомцам настроек на момент отметки (с теми же правилами числа питомцев и типа). Отметки отдельно по питомцам нет.

## Файлы

Файлы факта и файлы настроек напоминания принадлежат записи и общие для всех её питомцев; привязка и отвязка питомца файлов не затрагивает. Механизм ссылочных строк сохраняется для создания факта при отметке «Выполнено» и для замены одного напоминания.

## Отображение и чтение по питомцу

* В календаре и в «События питомца» запись — одна карточка. Карточка показывает всех видимых питомцев записи: изображение вида питомца (из справочника видов) и имя каждого; конкретное оформление определяет дизайн-система. Запись подсчитывается на сетке месяца один раз независимо от числа питомцев.

* Чтение «по питомцу» (`GET /activities?pet_id=`, `GET /pet/{id}/events`, превью, графики динамики, виджет, текущий вес) отбирает записи, привязанные к этому питомцу, через таблицу связи; запись с несколькими питомцами попадает в выборку каждого из них. Измерительные типы привязаны к одному питомцу, поэтому графики измерений не смешивают значения разных питомцев.

* Каждый элемент записи в ответах (`GET /activities`, `GET /activities/day`, `GET /pet/{id}/events`, `GET /events/{id}`, ответы напоминаний) содержит массив `pets: [{pet_id, pet_name}]` видимых питомцев вместо отдельных `pet_id`/`pet_name`, а также поле `author` (имя автора и признак «это я»; заполняется, только если питомцем пользуются минимум два человека — см. [Общие требования: Доступ к питомцу](obschie-trebovaniya-dostup-k-pitomtsu.md), раздел «Автор записи»).

## Мягкое удаление питомца

* Событие: связь с мягко удалённым питомцем сохраняется; запись остаётся видимой, пока у неё есть хотя бы один видимый питомец. Если видимых питомцев не осталось, запись нигде не показывается (как события мягко удалённого питомца сегодня).

* Настройки напоминания: при мягком удалении питомца в той же транзакции жёстко удаляются его связи с настройками; настройки, у которых питомцев не осталось, удаляются жёстко вместе с напоминаниями и файлами. Остальные настройки остаются у прочих питомцев (см. [Удаление питомца — Backend](../pets/udalenie-pitomtsa-backend.md)).

## Доступ, выданный владельцем питомца

Права на запись с несколькими питомцами при наличии выданных доступов (видимость — по доступности всех питомцев, изменение — только при `owner`/`full` у всех, разделение записей при завершении доступа) описаны в [Общие требования: Доступ к питомцу](obschie-trebovaniya-dostup-k-pitomtsu.md), разделы «Записи с несколькими питомцами» и «Завершение доступа».

## Передача питомца другому пользователю

При принятии передачи питомца (см. [Передача питомца — Backend](../pets/peredacha-pitomtsa-backend.md)) запись, у которой передаваемый питомец — единственный видимый, переходит получателю целиком (`user_id` записи меняется); запись с другими видимыми питомцами остаётся у отправителя без передаваемого питомца, а получатель получает её копию с одним питомцем. Тем самым инвариант «все питомцы записи принадлежат владельцу записи» сохраняется. Настройки напоминаний не переносятся: их связи с питомцем удаляются по правилам «Мягкое удаление питомца» выше.

## Режим local и перенос на сервер

* Локальные коллекции событий и настроек напоминания содержат `petIds` (массив, 1–10) вместо `petId`; операции (создание, изменение, привязка/отвязка, удаление) выполняются клиентом за одну запись в хранилище с теми же правилами и проверками (пересечение типов, измерительные типы, потолок, файлы). Клиент — единственный барьер проверок.

* `POST /import/local-data`: у элементов `events` и `reminder_plans` вместо `pet_local_id` — `pet_local_ids` (массив, 1–10 различных значений, каждое должно встречаться среди `local_id` питомцев запроса). Правила паритета — [Локальный режим](lokalnyi-rezhim-datasource-local-zaglushka.md), раздел «Поддержание паритета сущностей при переносе».

## Контракт API (сводка)

| Эндпоинт | Изменение |
| --- | --- |
| `POST /events` | Вместо `pet_id` — `pet_ids` (массив uuid, 1–10, различные). Ответ 201 — один `EventResponse` с `pets` |
| `GET /events/{id}`, элементы `GET /activities`, `GET /activities/day`, `GET /pet/{id}/events` | Вместо `pet_id`/`pet_name` — `pets: [{pet_id, pet_name}]` |
| `PATCH /events/{id}` | `pet_id` в теле отсутствует (владение — по `user_id` записи); дополнительно `pet_ids` — желаемый полный набор. Хотя бы одно из `date`/`type`/`notes`/`value`/`pet_ids`. Ответ 204 |
| `DELETE /events/{id}` | Без изменений: удаляет запись целиком. Отвязка питомца — `PATCH` с `pet_ids` |
| `POST /reminder-plans` | Вместо `pet_id` — `pet_ids` (1–10); клиентский `id` настроек один. Ответ 201 — один `ReminderPlanResponse` с `pets` |
| `GET /reminder-plans/{id}`, `GET /reminders/{id}` | Вместо `pet_id`/`pet_name` — `pets` |
| `PATCH /reminder-plans/{id}` | Дополнительно `pet_ids` (только `source = manual`) |
| `POST /reminders/{id}/detach` | В теле `event`/`plan` — `pet_ids` новой записи (любые питомцы пользователя; для `medication` — питомец лекарства) |
| `GET /reminders/upcoming` | Элементы: `pets` вместо `pet_id`/`pet_name` |
| `GET /pet/{id}/reminders/upcoming` | Выбор по связи питомца с настройками |
| `POST /import/local-data` | `pet_local_ids` у `events` и `reminder_plans` |

## Обработка ошибок

| Условие | Статус |
| --- | --- |
| `pet_ids` пуст, повторы или более 10 питомцев | 400 |
| Итоговый набор пуст | 400 |
| Тип или значение вложенного словаря неприменимы хотя бы к одному питомцу итогового набора | 400 |
| Измерительный тип при более чем одном питомце | 400 |
| Хотя бы один питомец мягко удалён | 400 |
| Хотя бы один питомец не найден или принадлежит другому пользователю | 404 (без раскрытия, какой именно) |

## Вне объёма

* Различающиеся значения `value` по питомцам внутри одной записи (для таких случаев — отдельные записи).

* Частичная отметка «Выполнено» напоминания по питомцам.

* Настройки напоминаний, связанные с лекарством или вакцинацией, с несколькими питомцами.
