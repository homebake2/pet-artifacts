## Назначение

Единый переиспользуемый механизм, по которому backend хранит в БД пользовательский контент сразу на нескольких языках и отдаёт клиенту уже готовое значение на языке запроса. Первый потребитель — [Баннеры — Backend](../banners/bannery-backend.md); любая следующая функция, которой нужен переводимый контент из БД (тексты, ссылки на картинки), использует тот же механизм, а не заводит собственный.

Механизм не касается:

* сообщений об ошибках API — они по-прежнему формируются клиентом по `errorCode` (см. «Общие требования: Формат ошибок API»);

* статических строк интерфейса — они остаются в локализации самого клиента (i18next).

## Поддерживаемые языки

Набор поддерживаемых языков — значения параметра `LanguageCode` в API (сейчас `ru`, `en`). Язык по умолчанию (язык-запасной) — `ru`. Добавление нового языка — это расширение enum `LanguageCode` и добавление строк перевода; миграция структуры таблиц для этого не требуется.

## Таблица переводов

Для каждой сущности, у которой есть переводимые поля, заводится отдельная таблица переводов `<entity>_translation`:

* `<entity>_id` — внешний ключ на основную таблицу, `ON DELETE CASCADE`;

* `locale` — код языка (значение из списка поддерживаемых языков), CHECK на допустимые значения;

* первичный ключ `(<entity>_id, locale)` — одна строка на сущность и язык;

* остальные колонки — переводимые поля сущности (тексты и ссылки на картинки, зависящие от языка). Все они nullable на уровне БД; обязательность поля определяется правилами конкретной сущности, а не схемой.

Поля, не зависящие от языка (идентификаторы, флаги, даты, тип действия и т.п.), остаются в основной таблице. Если у сущности есть вложенные коллекции с переводимыми полями (например, слайды), у вложенной таблицы заводится собственная `<child>_translation` по тому же шаблону.

Пустая строка и `NULL` в переводимой колонке приравниваются к отсутствию перевода. Строки перевода для языков вне списка поддерживаемых игнорируются при чтении и не считаются ошибкой. Допустимо, чтобы у сущности была строка перевода только для одного языка.

## Выбор языка при чтении

Язык запроса определяется заголовком `LanguageCode`. Для эндпоинтов, использующих этот механизм, заголовок обязателен (как и объявлено в `components.parameters.LanguageCode`); отсутствие или значение вне enum — `400` в формате «Общие требования: Формат ошибок API». На эндпоинтах, которые механизм не используют (например, эндпоинты питомцев), заголовок по-прежнему не используется для локализации и игнорируется, как описано на их страницах.

Для каждого переводимого поля независимо backend выбирает значение по цепочке:

1. значение из строки перевода для языка запроса;

2. значение из строки перевода для языка по умолчанию (`ru`);

3. значения нет — поле считается отсутствующим (`null`). Если поле обязательно для сущности, сущность считается невалидной (правила обработки невалидных сущностей — на странице конкретной сущности).

Поля выбираются независимо: если у языка запроса переведён заголовок, а текст нет, заголовок берётся на языке запроса, а текст — на языке по умолчанию. Составные значения, которые имеют смысл только вместе (например, URL картинки и её `blurhash`), берутся из одной и той же строки перевода: если `image_url` взят из строки языка по умолчанию, то и `blurhash` берётся оттуда же.

Читать обе строки (язык запроса и язык по умолчанию) следует одним запросом (JOIN/выборка по `locale IN (...)`), без запроса на каждую сущность.

Клиент получает в ответе уже выбранные значения, а не набор переводов: контракт ответа не содержит карт «язык → значение», клиент не реализует собственной цепочки выбора.

## Ограничение сущностей по языку

Если сущности нужно показываться только пользователям определённых языков, это отдельный явный атрибут сущности (например, правило таргетинга по языку), а не побочный эффект наличия или отсутствия перевода. Правило применяется до выбора значений по цепочке выше и описывается на странице сущности.

## Кеширование

Ответ, зависящий от языка, обязан учитывать язык запроса в ключе любого кеша на стороне backend и в вычислении `ETag` (если эндпоинт его поддерживает): один и тот же запрос с разным `LanguageCode` не должен получать одинаковый `ETag`.
