Архитектурное правило для всех эндпоинтов, работающих с ресурсами, принадлежащими конкретному пользователю (питомцы, события, профиль): backend обязан проверять фактическое владение ресурсом на каждом read/update/delete-запросе по id.

* Если ресурс не существует, либо мягко удалён (soft-deleted), либо принадлежит другому пользователю — во всех трёх случаях backend возвращает **единый 404**, а не 403 и не различающиеся по смыслу ответы. Это не позволяет постороннему клиенту по коду ответа определить, существует ли вообще ресурс с данным id у другого пользователя (защита от enumeration).

* Frontend не должен пытаться различать эти случаи — он единообразно обрабатывает такой 404 как «не найдено» (конкретная реакция UI — уход назад/удаление из списка/сообщение — уточняется на странице конкретного сценария).

Это правило уже последовательно применялось в реализованных сценариях Pets и Calendar — данная страница фиксирует его как обязательное общее требование, чтобы не потерять при будущих доработках и не пропустить в новых эндпоинтах.

**Доступ, выданный владельцем.** Питомец и его записи принадлежат владельцу, но владелец может дать другому пользователю доступ (`view` или `full`). Для проверки «ресурс принадлежит пользователю» это означает: ресурс считается доступным, если пользователь — владелец или участник питомца (для записей с несколькими питомцами — по правилам видимости из [Общие требования: Доступ к питомцу](obschie-trebovaniya-dostup-k-pitomtsu.md)). Единый `404` сохраняется для всех, у кого доступа нет вообще. Если доступ есть, но роли недостаточно для операции (запись у роли `view`, операция владельца у участника), возвращается `403 FORBIDDEN`: существование питомца такому пользователю уже известно, и раскрывать нечего.

**Исключение — приглашение к доступу по коду.** Предпросмотр приглашения (`POST /pet-codes/preview`, тип `access`) возвращает тому, кто знает действующий одноразовый код, тот же ограниченный набор данных чужих питомцев набора приглашения и роль, а также имя владельца. Защита та же, что у передачи: недействительные коды неразличимы (единый `404`), подбор ограничен общим rate limit (см. [Доступ к питомцу — Backend](../pets/dostup-k-pitomtsu-backend.md)).

**Исключение — передача питомца по коду.** Предпросмотр питомца получателем по коду передачи (`POST /pet-codes/preview`, тип `transfer`) возвращает ограниченный набор данных чужого питомца (имя, вид, порода, пол, дата рождения, фотография, имя отправителя) тому, кто знает действующий одноразовый код. Это осознанное исключение: доступ даёт код, а не идентификатор питомца, недействительные коды неразличимы (единый 404), подбор кода ограничен rate limit (см. [Передача питомца — Backend](../pets/peredacha-pitomtsa-backend.md)). Остальные эндпоинты питомца по-прежнему отвечают 404 для чужого питомца.
