## Правило

Все пользовательские сущности, доступные для удаления (питомцы, события; в будущем — прочие подобные сущности), удаляются мягко — через поле `deleted_at`, без физического удаления строки. Исключение на MVP — удаление аккаунта пользователя целиком, которое пока не реализуется ни на backend, ни на frontend (см. известные ограничения проекта) и не входит в область этого правила.

## Модель данных

Поле `deleted_at` есть у `pet` (уже зафиксировано) и добавляется у `event` (ранее в модели данных проекта event удалялся физически через `ON DELETE CASCADE` от pet — это уточнение меняет event на мягкое удаление, аналогично pet; модель данных/OpenAPI-схему нужно обновить).

## Фильтрация

Каждый read-эндпоинт (списки и просмотр по id), затрагивающий сущность с `deleted_at`, обязан фильтровать мягко удалённые записи (`WHERE deleted_at IS NULL`), включая вложенные/связанные выборки (например, список событий питомца, календарь). В частности: события мягко удалённого питомца недоступны и через отдельный эндпоинт списка его событий (тот же 404/пустой ответ, что и для карточки самого питомца) — иначе получится противоречие «питомец недоступен, а его события доступны».

## Хранение и восстановление

Мягко удалённые записи хранятся бессрочно (без физической очистки/retention-политики) — это осознанно достаточно для MVP. Функциональность восстановления (undo/recovery) не реализуется в текущей итерации ни для питомцев, ни для событий — это тоже осознанное ограничение MVP, а не пробел.

## UX при гонках удаления

Если запрос на удаление возвращает 404 (ресурс уже удалён — например, с другого устройства), frontend трактует это не как ошибку, а как «уже удалён»: тихо убирает сущность из UI (список/карточку) без сообщения об ошибке, вместо показа общего error-тоста.
