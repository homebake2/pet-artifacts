## Назначение

Владелец питомца может передать его другому пользователю. Передача двухшаговая: владелец создаёт передачу и получает одноразовый код; получатель вводит или считывает код, просматривает питомца и принимает или отклоняет передачу. Пока получатель не принял, питомец остаётся у отправителя без ограничений. После принятия питомец со всеми данными принадлежит получателю, у отправителя доступа к нему нет.

Каждая передача хранится в БД как запись истории. Просмотра истории через API нет (см. «История передач»).

## Модель данных

Таблица `pet_transfer`:

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid | Идентификатор передачи |
| `pet_id` | uuid | Питомец. Без внешнего ключа: запись истории переживает физическое удаление питомца при удалении аккаунта |
| `pet_name`, `pet_species` | text | Снимок имени и вида питомца на момент создания передачи |
| `from_user_id` | uuid NULL | Отправитель (владелец на момент создания). `ON DELETE SET NULL` при удалении аккаунта |
| `to_user_id` | uuid NULL | Получатель: заполняется при принятии или отклонении. `ON DELETE SET NULL` |
| `code` | text | Код передачи (см. «Код передачи») |
| `status` | text | `pending`, `accepted`, `declined`, `cancelled`, `expired` (см. «Справочник значений (словари enum)») |
| `created_at` | timestamptz | Создание передачи |
| `expires_at` | timestamptz | Срок действия кода: `created_at` + 7 суток (константа сервера) |
| `resolved_at` | timestamptz NULL | Момент перехода из `pending` в любой другой статус |

Ограничения:

* Частичный уникальный индекс `UNIQUE (pet_id) WHERE status = 'pending'` — у питомца не более одной активной передачи.

* Частичный уникальный индекс `UNIQUE (code) WHERE status = 'pending'` — коды активных передач не повторяются.

Переходы статусов: `pending → accepted | declined | cancelled | expired`; остальные статусы конечные. `pending` с `expires_at <= now` везде трактуется как `expired`; строка переводится в `expired` при первом обращении к ней и фоновой задачей очистки, выполняемой раз в час.

## Код передачи

* 10 символов из алфавита без визуально неоднозначных знаков (без `0/O`, `1/I/L`), генерируется криптостойким генератором; в интерфейсе отображается как `XXXXX-XXXXX`.

* Первый символ — тип кода: `T` — код передачи, `A` — код приглашения к доступу (см. «Доступ к питомцу — Backend»); остальные 9 символов случайные. Тип определяется по самому коду, поэтому коды передачи и доступа не пересекаются, а клиент принимает любой код одним методом предпросмотра (`POST /pet-codes/preview`). Код с неизвестным первым символом не соответствует формату (`400`).

* Код одноразовый: после любого выхода из `pending` он перестаёт действовать.

* Сравнение регистронезависимое; пробелы и дефисы во входном значении игнорируются (нормализует сервер).

* Код — единственное, что связывает получателя с передачей. QR-код формируется и считывается на клиенте и содержит тот же код; сервер о QR ничего не знает.

* Подбор кода ограничивается: не более 10 неудачных обращений к эндпоинтам с кодом в час на пользователя (`429 RATE_LIMITED`); учёт — по `userID` из токена, в таблице `pet_transfer_code_failure (user_id, created_at)` (`ON DELETE CASCADE` к пользователю). Неудачной считается только попытка с корректным по формату кодом, на которую вернулся `404`; `400` (неверный формат) и `409 TRANSFER_OWN_PET` не учитываются. Лимит проверяется до поиска кода, поэтому после его исчерпания `429` получает и верный код.

## Эндпоинты

Все эндпоинты требуют валидный access-токен.

### `POST /pet/{id}/transfer` — создать передачу

Тела запроса нет.

1. Система разбирает `id` как UUID, извлекает `userID`.

2. Система проверяет питомца по `id = ... AND user_id = ... AND deleted_at IS NULL` — иначе `404` (если питомец чужой, но у пользователя есть к нему доступ — `403`, см. «Бизнес-правила и валидация»).

3. Если у питомца уже есть активная передача (`pending`, не истёкшая) — `409 TRANSFER_ALREADY_PENDING`. Истёкшая передача переводится в `expired`, и создание продолжается.

4. Система создаёт запись `pet_transfer` со статусом `pending` и снимком имени и вида.

5. `201 Created`: `{ "id", "code", "expires_at" }`.

### `GET /pet/{id}/transfer` — активная передача питомца

Проверка питомца — как в `POST`. Если активной передачи нет — `404`. Иначе `200`: `{ "id", "code", "expires_at" }`. Эндпоинт позволяет отправителю повторно показать код и QR.

### `DELETE /pet/{id}/transfer` — отменить передачу

Проверка питомца — как в `POST`. Активную передачу переводит в `cancelled`, `204`. Если активной передачи нет — `404`.

### `POST /pet-codes/preview` — предпросмотр по коду (передача или доступ)

Общий метод предпросмотра для кодов передачи и приглашений к доступу. Тело: `{ "code": string }`.

1. Система нормализует код, определяет тип по первому символу (см. «Код передачи») и далее работает по правилам соответствующего типа.

2. Тип `transfer`: ищет передачу по коду со статусом `pending` и `expires_at > now`; затем проверяет, что питомец существует, не удалён и принадлежит `from_user_id`. Если передача не найдена, не активна, истекла или питомец недоступен — единый `404` (без различения причин). Если `from_user_id = userID` (отправитель ввёл собственный код) — `409 TRANSFER_OWN_PET`.

3. Тип `access`: правила и ошибки — как в «Доступ к питомцу — Backend», раздел `POST /pet-codes/preview`.

4. `200`: `{ "type": "transfer" | "access", "transfer": {...}, "access": {...} }`; заполнено ровно одно из полей `transfer` / `access` — по `type`. Для `transfer`: `{ "pet": { "name", "species", "breed", "gender", "birth_date", "photo_url" }, "sender_name", "expires_at" }`, где `sender_name` — имя отправителя: фамилия и имя из профиля (`last_name` и `first_name`, непустые, через пробел — как `owner.name` в `GET /pet`), а при отсутствии профиля или пустых именах — его логин. `photo_url` — presigned GET URL (см. «Фотография питомца — Backend»), выдаваемый получателю только по действующему коду. Остальные данные питомца и его события в предпросмотре не отдаются.

Предпросмотр ничего не изменяет. Неудачные обращения считаются в общем лимите (см. «Код передачи»).

### `POST /pet-transfers/decline` — отклонить

Тело: `{ "code": string }`. Поиск и проверки — как в предпросмотре. Передача переводится в `declined`, `to_user_id = userID`, `resolved_at = now`. `204`.

### `POST /pet-transfers/accept` — принять

Тело: `{ "code": string }`. Поиск и проверки — как в предпросмотре. Принятие выполняется в одной транзакции (см. «Что переходит к получателю»); при любой ошибке не меняется ничего. `200`: `{ "pet_id": uuid }`.

Повторный вызов с тем же кодом после принятия — `404` (код уже не действует).

## Что переходит к получателю

В одной транзакции система блокирует строки передачи и питомца (`FOR UPDATE`), повторно проверяет `status = 'pending'`, срок и принадлежность питомца отправителю, затем:

1. **Питомец.** `pet.user_id` становится получателем. Идентификатор питомца и его данные не меняются.

2. **Ветпаспорт.** Вакцинации, заболевания, посещения ветеринара, аллергии и лекарства принадлежат питомцу (`pet_id`) и переходят вместе с ним. Факты, созданные Ветпаспортом (в том числе `administered_event_id` вакцинации), привязаны к одному питомцу и переносятся по правилам событий ниже.

3. **События.** Для каждого события, привязанного к питомцу:

   * если после отвязки этого питомца у события не остаётся видимых питомцев — событие переносится целиком: `event.user_id` становится получателем, `idempotency_key` обнуляется (ключ уникален в пределах пользователя и мог бы совпасть с ключами получателя); скрытые связи события с мягко удалёнными питомцами отправителя удаляются;

   * иначе (у события есть другие видимые питомцы) — получатель получает **копию** события с одной связью — с передаваемым питомцем; копия содержит `date`, `type`, `value`, `notes` исходного, но новый `id`, `user_id` получателя, пустой `idempotency_key` и значение `notifications_enabled` по умолчанию (`false`); файлы копии создаются как ссылочные строки на те же объекты S3 (см. «Общие требования: Файлы сущностей»). У исходного события удаляется связь с передаваемым питомцем; оно остаётся у отправителя и остальных его питомцев. Если исходное событие — факт вакцинации передаваемого питомца (`administered_event_id`), ссылка вакцинации переключается на копию. Мягко удалённое событие, общее с другими питомцами отправителя, не копируется: у него только удаляется связь с передаваемым питомцем.

4. **Напоминания не переносятся.** Связи питомца с настройками напоминаний (`reminder_plan_pet`) удаляются жёстко; настройки, у которых питомцев не осталось, удаляются вместе с напоминаниями и файлами; общие с другими питомцами отправителя остаются у них — как при удалении питомца (см. «Удаление питомца — Backend», п. 4). Объекты S3 удаляются после фиксации транзакции, когда на них не осталось ссылок. Ссылки лекарств (`reminder_plan_id`) и вакцинаций (`next_plan_id`, `extra_reminders`) на удалённые настройки читаются как `null` / пустой массив. Получатель при необходимости создаёт напоминания заново.

5. **Файлы.** У файлов переносимых сущностей (фотография питомца, файлы переносимых событий, файлы записей Ветпаспорта) `file.user_id` становится получателем. Объекты S3 и их ключи не меняются.

6. **Доступы.** Все выданные доступы к питомцу прекращаются: строки `pet_access` питомца удаляются, бывшие участники получают уведомление о потере доступа с причиной `pet_transferred`, питомец перестаёт быть действующим в активных приглашениях к доступу (приглашение без действующих питомцев становится `cancelled`). Новый владелец получает питомца без участников; доступ ему при необходимости выдаётся заново (см. [Доступ к питомцу — Backend](dostup-k-pitomtsu-backend.md)). Если получатель сам был участником этого питомца, его доступ также удаляется — он становится владельцем.
7. **Передача.** `status = 'accepted'`, `to_user_id = userID`, `resolved_at = now`.

После фиксации у отправителя питомец недоступен на всех эндпоинтах (`404` по единой политике), у получателя — доступен как собственный; в `GET /pet` получателя он попадает по `created_at` питомца.

## Бизнес-правила и валидация

* Создавать, просматривать и отменять передачу может только владелец питомца; чужой без выданного доступа, несуществующий или мягко удалённый питомец — `404`. Пользователь, которому владелец дал доступ (`full` или `view`), владельцем не считается: передача питомца ему недоступна — `403 FORBIDDEN` (см. [Общие требования: Доступ к питомцу](../common/obschie-trebovaniya-dostup-k-pitomtsu.md)).

* Принять или отклонить передачу не может её отправитель (`409 TRANSFER_OWN_PET`). Других ограничений на получателя нет, в том числе по числу питомцев (лимит не установлен, см. «Список питомцев — Backend»).

* Пока передача `pending`, питомец и его данные полностью доступны владельцу, в том числе для редактирования и добавления событий; принимается состояние на момент принятия.

* Мягкое удаление питомца и удаление аккаунта отправителя переводят активную передачу в `cancelled` в той же транзакции (см. «Удаление питомца — Backend»).

* Принятие, отклонение и отмена конкурируют за блокировку строки передачи: побеждает первая зафиксированная операция, остальные получают `404` (передача уже не `pending`).

* Обратной передачи «одним действием» нет: новый владелец передаёт питомца обычным порядком.

* Недействительные коды не различаются по причине (не существует, истёк, отклонён, отменён, принят, питомец удалён) — единый `404`, чтобы по ответу нельзя было определить, существовал ли код.

## История передач

* Таблица `pet_transfer` — постоянная история: записи не удаляются при мягком удалении питомца и при удалении аккаунта участника (ссылки на пользователей обнуляются, снимок питомца остаётся).

* API для просмотра истории не предусмотрено — ни для владельца, ни для получателя; история доступна только на уровне БД. Появление такой возможности потребует отдельных требований.

* Предыдущие владельцы получателю не раскрываются.

## Обработка ошибок

| Статус | Код | Условие |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | `id` не UUID; `code` пуст или не соответствует формату кода после нормализации |
| 401 | `UNAUTHORIZED` | Токен невалиден — по общим правилам (см. [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md)) |
| 403 | `FORBIDDEN` | Питомец чужой, но у пользователя есть к нему доступ (`full` или `view`): создавать, просматривать и отменять передачу может только владелец |
| 404 | `NOT_FOUND` | Питомец не найден, чужой без доступа или удалён; активной передачи нет (`GET`/`DELETE`); код недействителен (`preview`/`accept`/`decline`) |
| 409 | `TRANSFER_ALREADY_PENDING` | У питомца уже есть активная передача |
| 409 | `TRANSFER_OWN_PET` | Отправитель использует собственный код |
| 429 | `RATE_LIMITED` | Превышен лимит неудачных обращений с кодом |
| 500 | `INTERNAL_ERROR` | Ошибка БД; транзакция принятия откатывается целиком |

## Хранение состояния и побочные эффекты

Принятие меняет владельца питомца, событий, файлов и связи напоминаний в одной транзакции; объекты S3 удаляются только после её фиксации. Режим `dataSource=local` передачу не поддерживает, `POST /import/local-data` не меняется (см. [Локальный режим](../common/lokalnyi-rezhim-datasource-local-zaglushka.md), раздел «Поддержание паритета сущностей при переносе»).
