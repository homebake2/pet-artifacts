## Назначение

Эндпоинт `GET /pet` должен возвращать краткую информацию обо всех питомцах, принадлежащих текущему авторизованному пользователю или доступных ему по выданному доступу, для главного экрана «Питомцы». Пагинация, фильтрация и сортировка (кроме фиксированного порядка, см. ниже) не входят в объём текущей итерации.

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь.

* Требуется валидный access-токен (заголовок `Authorization: Bearer <access_token>`).

* Наличие строки в таблице `profile` не требуется — доступ к питомцам не зависит от заполненности профиля.

## Основной сценарий

`GET /pet`

1. Система извлекает `userID` из заголовка `Authorization` и проверяет валидность токена.

2. Система выбирает все строки таблицы `pet`, где `deleted_at IS NULL` (мягко удалённые питомцы исключаются) и пользователь — владелец (`user_id = userID`) либо участник (есть строка `pet_access` с `user_id = userID`, см. [Доступ к питомцу — Backend](dostup-k-pitomtsu-backend.md)), отсортированные по `created_at` (`ORDER BY created_at`), чтобы порядок был стабильным между запросами.

3. Система возвращает `200 OK` с телом `{"items": [{"id","name","breed","species","photo_url","access","owner"}]}`, где `access` — роль пользователя: `owner`, `full` или `view` (см. «Справочник значений»), а `owner` — владелец питомца `{"id","name"}` (`pet.user_id`; для собственных питомцев — сам пользователь). `owner.name` — имя из профиля владельца (`first_name` и `last_name`, если они заполнены, через пробел), а при отсутствии профиля — логин. Кроме `items`, ответ содержит массив `access_lost` — уведомления о потере доступа текущего пользователя: `[{"pet_id","name","species","reason","occurred_at"}]` (`reason`: `revoked`, `pet_deleted`, `pet_transferred`; без данных питомца, только снимок имени и вида; пустой массив, если уведомлений нет). Элементы `access_lost` отсортированы по `occurred_at` по убыванию; см. [Доступ к питомцу — Backend](dostup-k-pitomtsu-backend.md), «Уведомления о потере доступа». Если у пользователя нет питомцев — `{"items": []}` со статусом `200`.

Заголовок `LanguageCode` не требуется этим эндпоинтом (см. правило ниже).

## Бизнес-правила и валидация

* Пользователь видит своих питомцев и питомцев, к которым владельцы дали ему доступ (любой роли); остальных — нет. Питомцы с доступом идут в общем порядке по `created_at` питомца вместе с собственными.

* Мягко удалённые питомцы (`deleted_at IS NOT NULL`) всегда исключаются из списка — это часть единой политики скрытия мягко удалённых питомцев, действующей на всех эндпоинтах модуля (см. «Общие требования: Soft-delete»).

* Результат сортируется по `created_at` (`ORDER BY created_at`) — без явного порядка выборка была бы нестабильной между запросами.

* Заголовок `LanguageCode` не является обязательным параметром запроса: он не используется сервером для локализации содержимого ответа (сервер не хранит переводов), поэтому требование его обязательности снято на всех эндпоинтах питомцев для единообразия. Если это значение передано клиентом — оно игнорируется.

* Query-параметры фильтрации, поиска и сортировки не поддерживаются в текущей итерации.

* `species` — единственное поле категоризации питомца, возвращаемое backend'ом; хранится как свободный текст, а не как перечисление на уровне БД, поэтому в принципе допускает повреждённое, устаревшее или иным образом заведённое значение вне справочника. При этом клиент — единственный штатный способ заполнить это поле — всегда пишет в него одно из закрытых значений справочника видов (см. «Справочник значений (словари enum)»). Сопоставление species → иконка вида и дефолтная (fallback) иконка для значений вне справочника, а также применимость типов событий к виду (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца») — обе полностью на стороне фронтенда/соответствующих требований, ключом служит то же поле `species` (см. «Список питомцев — Frontend»).

* `photo_url` — nullable, presigned GET URL на фотографию питомца (или `null`, если фотографии нет), вычисляется для каждого питомца в выборке заново на каждый запрос; подробности — см. «Фотография питомца — Backend».

* Лимит на количество питомцев у одного пользователя не устанавливается в текущей итерации.

* Пагинация по питомцам отсутствует в текущей итерации — зафиксировано как осознанный технический долг MVP, отдельная задача на реализацию сейчас не заводится.

## Обработка ошибок

| Статус | Условие                                                                                                                      |
| ------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 401    | Заголовок `Authorization` отсутствует, некорректен или токен истёк.                                                          |
| 500    | Произошла ошибка при выборке питомцев (БД и т.п.). Формат тела ошибки — см. «Общие требования: Формат ошибок API».           |

## Хранение состояния и побочные эффекты

Операция только читает данные (`GET`) и не изменяет состояние БД.
