## Назначение

Управление одной (главной) фотографией питомца: выбор/замена, удаление и отображение. Загрузка выполняется напрямую в S3 по presigned URL, полученному от backend — фронтенд никогда не хранит и не использует S3-ключи (см. «Общие требования: S3-хранилище файлов»).

## Действующие лица и предусловия

* Инициатор — владелец питомца.

* Управление фотографией доступно там, где уже известен id питомца: на карточке питомца и на форме редактирования. На форме добавления фотография не загружается сразу — см. раздел «Фотография при добавлении питомца» ниже, так как загрузка требует существующего id питомца.

## Загрузка/замена фотографии (питомец уже существует)

1. Пользователь выбирает изображение (камера или галерея устройства) через элемент управления фотографией на карточке питомца или на форме редактирования.

2. Система приводит выбранное изображение к одному из допустимых MIME-типов (`image/jpeg`, `image/png`, `image/webp` — см. «Фотография питомца — Backend»); если исходный формат не входит в этот список, конвертация в допустимый формат — ответственность клиента (например, HEIC с камеры iOS конвертируется в JPEG перед загрузкой), отдельная ошибка «неверный формат» пользователю не показывается.

3. Элемент управления фотографией переходит в состояние загрузки (блокирует повторный выбор до завершения) — по общему правилу [Общие требования: UI-паттерны запросов](../common/obschie-trebovaniya-ui-patterny-zaprosov.md).

4. Клиент запрашивает `POST /files/upload-url` с телом `{owner_type: "pet_photo", owner_id: <id питомца>, content_type}` (см. «Общие требования: Файлы сущностей»), получает `file_id` и `upload_url`.

5. Клиент выполняет `PUT upload_url` напрямую в S3 с байтами файла и тем же `Content-Type`.

6. При успешной загрузке в S3 клиент вызывает `POST /files/{file_id}/complete`, используя `file_id` из шага 4.

7. Только после успешного ответа шага 6 система показывает новую фотографию (используя локально выбранное изображение как немедленное превью — до следующего запроса `photo_url` с сервера, см. «Хранение состояния и побочные эффекты») и снимает индикатор загрузки.

## Удаление фотографии

1. Пользователь выбирает «Удалить фотографию» (доступно только если у питомца уже есть фотография).

2. Система показывает диалог подтверждения.

3. После подтверждения элемент управления переходит в состояние загрузки, клиент вызывает `DELETE /files/{file_id}`, где `file_id` — значение поля `photo_file_id` из последнего ответа `GET /pet/{id}` (см. «Фотография питомца — Backend»).

4. После успешного ответа система показывает состояние «фотографии нет» (плейсхолдер/иконка вида, см. «Отображение фотографии» ниже).

## Отображение фотографии

* Карточка питомца и карточки в списке питомцев показывают фотографию по полю `photo_url` из соответствующего ответа (`GET /pet/{id}` и `GET /pet` соответственно, см. «Фотография питомца — Backend»).

* Если `photo_url` — `null`, показывается тот же fallback, что и сегодня без фотографии — иконка вида питомца (species/icon → иконка, см. «Список питомцев — Frontend»). Появление фотографии не отменяет и не заменяет логику fallback-иконки — она остаётся для питомцев без фотографии.

* Если `photo_url` присутствует, но загрузка изображения по этой ссылке завершилась ошибкой (истёкший TTL, сетевая ошибка, отсутствующий в S3 объект) — система показывает ту же fallback-иконку вида, что и при отсутствии фотографии, без отдельного сообщения об ошибке: фотография — необязательный визуальный элемент, её временная недоступность не должна блокировать или загромождать экран.

* `photo_url` — временная ссылка с TTL (см. «Общие требования: S3-хранилище файлов»); клиент не кэширует и не переиспользует её между отдельными загрузками данных питомца — при каждом новом `GET /pet/{id}`/`GET /pet` используется ссылка из этого ответа.

## Фотография при добавлении питомца

Форма добавления питомца (см. «Добавление питомца — Frontend») позволяет выбрать изображение локально (тем же элементом управления, что и на карточке/форме редактирования), но фактическая загрузка невозможна до того, как питомец создан и получен его `id` (см. «Фотография питомца — Backend» — `owner_id` в `POST /files/upload-url` это id питомца). Поэтому:

1. Пользователь выбирает фотографию на форме добавления — она хранится только в памяти экрана (локальный URI выбранного файла), не загружается никуда до сохранения формы.

2. При нажатии «Сохранить» система сначала выполняет обычный сценарий создания питомца (`POST /pet`, см. «Добавление питомца — Frontend»).

3. Если создание питомца успешно и на форме была выбрана фотография — система сразу выполняет сценарий «Загрузка/замена фотографии» (шаги 4–6 выше) для только что полученного id, не показывая пользователю это как отдельный шаг (единый индикатор загрузки на форме до завершения обоих действий).

4. Если создание питомца завершилось ошибкой — загрузка фотографии не выполняется, форма ведёт себя как описано в «Добавление питомца — Frontend» (пользователь остаётся на форме, данные не теряются, включая выбранную локально фотографию).

5. Если создание питомца успешно, но загрузка/привязка фотографии завершилась ошибкой — питомец уже создан и не откатывается: система переходит на карточку созданного питомца (как при обычном успешном создании) и показывает питомца без фотографии; пользователь может добавить фотографию повторно с карточки (см. «Загрузка/замена фотографии» выше). Откат создания питомца из-за сбоя загрузки фотографии не выполняется.

## Бизнес-правила и валидация

* Фотография питомца не входит в diff-механизм формы редактирования (см. «Редактирование питомца — Frontend») — это отдельное действие с собственным немедленным запросом, а не поле, отправляемое вместе с остальными изменениями по кнопке «Сохранить» формы.

* Ограничение размера выбираемого файла на стороне клиента в этой итерации не вводится (см. «Фотография питомца — Backend» — лимит размера не установлен и на бэкенде).

* Владение питомцем проверяется backend на каждом из трёх generic-эндпоинтов (`upload-url`/`complete`/`delete`, см. «Общие требования: Файлы сущностей») — фронтенд не выполняет собственной проверки.

## Обработка ошибок

| Ситуация                                                                 | Что должна сделать система                                                                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Ошибка на любом из шагов загрузки (`upload-url`, `PUT` в S3, `complete`)   | Индикатор загрузки снимается, показывается сообщение об ошибке загрузки фотографии, ранее отображавшаяся фотография (если была) не изменяется. |
| Ошибка `DELETE /files/{file_id}`                                          | Индикатор загрузки снимается, показывается сообщение об ошибке, фотография остаётся отображаться как есть.                    |
| `409` от `POST /files/{file_id}/complete` (лимит кардинальности превышен) | Не возникает для питомца в этой итерации — кардинальность `pet_photo` равна 1, а не «до N» (см. «Общие требования: Файлы сущностей»); строка приведена для полноты таблицы кодов и не требует отдельной обработки на этом экране. |
| 404 (питомец не найден/удалён) на любом из эндпоинтов фотографии          | Обрабатывается так же, как 404 на остальных эндпоинтах питомца (см. «Просмотр карточки питомца — Frontend»).                  |
| Ошибка загрузки самого изображения по `photo_url` (истёкший TTL и т. п.) | См. «Отображение фотографии» — тихий откат на fallback-иконку, без отдельного сообщения об ошибке.                            |
| Сбой загрузки фотографии сразу после успешного создания питомца           | См. «Фотография при добавлении питомца», шаг 5 — переход на карточку без фотографии, без отката создания питомца.             |

## Хранение состояния и побочные эффекты

* После успешной загрузки/замены или удаления фотографии система инвалидирует кэш карточки питомца и кэш списка питомцев (те же кэши, что инвалидируются при обычном редактировании питомца, см. «Редактирование питомца — Frontend»), чтобы оба экрана отразили актуальный `photo_url` при следующем открытии.

* Немедленное превью после успешной загрузки (шаг 7 сценария «Загрузка/замена фотографии») — временное клиентское состояние экрана, не заменяющее последующий `photo_url` с сервера.
