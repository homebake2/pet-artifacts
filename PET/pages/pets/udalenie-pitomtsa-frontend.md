## Назначение

Позволяет пользователю удалить питомца из своего профиля через интерфейс приложения. Удаление на backend всегда мягкое (см. страницу «Удаление питомца — Backend» и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)); интерфейс должен предоставлять точку входа для этого действия и подтверждение перед выполнением.

## Действующие лица и предусловия

* Инициатор — владелец питомца.

* Действие доступно со списка питомцев и/или с экрана карточки питомца.

## Основной сценарий

1. Имеется возможность удалить питомца из списка питомцев и с экрана карточки питомца — аналогично удалению события в календаре.

2. Система показывает диалог подтверждения с указанием имени питомца и предупреждением о необратимости действия — за вычетом короткого окна отмены сразу после удаления (см. шаг 4 ниже), после истечения которого восстановление через UI не предусмотрено.

3. Пользователь подтверждает удаление.

4. Система немедленно убирает питомца из отображаемого списка/закрывает карточку (оптимистичное удаление) и сообщает, что запись удалена, с возможностью отменить удаление в течение 5 секунд; реальный запрос `DELETE /pet/{id}` не отправляется сразу, а откладывается до истечения окна отмены — см. «Общие требования: Оптимистичные обновления (dataSource=network)», раздел «Оптимистичное удаление с окном отмены (Undo)», за полным алгоритмом (включая отмену, уход приложения в фон и обработку ошибки отложенного запроса).

5. Если пользователь не отменил удаление до истечения таймера, система отправляет отложенный `DELETE /pet/{id}`; при успехе (включая `404` «уже удалён») кэши остаются в уже применённом оптимистичном состоянии. При транзиентной ошибке (сеть, таймаут, 5xx) запрос уходит в фоновые повторы, питомец в кэшах не восстанавливается; только когда ошибка постоянная либо автоматические повторы исчерпаны без успеха, питомец восстанавливается в кэшах и пользователю показывается сообщение об ошибке удаления с возможностью повторить удаление (см. там же, раздел «Оптимистичное удаление с окном отмены (Undo)», п. 5).

## Бизнес-правила и валидация

* Удалить можно только питомца, принадлежащего текущему пользователю; проверка владения выполняется сервером.

* Действие удаления обязательно сопровождается диалогом подтверждения — не выполняется без подтверждения.

* После удаления список питомцев должен быть обновлён без необходимости ручного обновления экрана пользователем.

* Поведение при `dataSource=local` (удаление без обращения к сети) будет описано в отдельных требованиях по локальному источнику данных; в текущей итерации не детализируется.

## Обработка ошибок

Ответ `401` на `DELETE /pet/{id}` обрабатывается общими требованиями по сессии и не описывается здесь отдельно (см. [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md)). Ниже — реакции, специфичные для этого экрана.

| Ситуация                                                                        | Что должна сделать система                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 404 при отложенном удалении (питомец уже удалён, в т.ч. из-за гонки параллельных запросов) | Система трактует `404` как «уже удалён», а не как ошибку: оптимистичный результат просто подтверждается, откат не выполняется, сообщение об ошибке не показывается (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md) и общую страницу «Оптимистичные обновления», раздел «Обработка ошибок и откат», п. 4). |
| 500 или сетевая ошибка при отложенном удалении (транзиентная)                    | Питомец НЕ восстанавливается в кэшах и сообщение об ошибке не показывается сразу — запрос ставится в фоновую очередь повторов по экспоненциальному бэкоффу; питомец продолжает быть скрыт из UI (см. «Основной сценарий», шаг 5). Только после исчерпания автоматических попыток без успеха система откатывает удаление (питомец восстанавливается в кэшах) и показывает сообщение «не удалось удалить» с возможностью повторить удаление — см. «Общие требования: Оптимистичные обновления (dataSource=network)», раздел «Оптимистичное удаление с окном отмены (Undo)», п. 5, и «Очередь фоновых мутаций и повторные попытки».                                                                                               |
| Пользователь отменяет диалог подтверждения                                      | Удаление не выполняется, состояние экрана не меняется.                                                                                                                                                                                         |
| Пользователь отменяет удаление до истечения таймера                             | Питомец возвращается в кэш списка на прежнюю позицию, сообщение об удалении скрывается, `DELETE`-запрос не отправляется вовсе (см. общую страницу «Оптимистичные обновления», раздел «Оптимистичное удаление с окном отмены (Undo)»).                                                                                                                          |

## Хранение состояния и побочные эффекты

* В сетевом режиме кэш списка питомцев получает синхронный оптимистичный патч (удаление записи) в момент подтверждения удаления, до отправки запроса; кэш карточки удалённого питомца оптимистично не патчится (карточка достигается только через список; после подтверждения удаления сервером кэш карточки инвалидируется) — см. «Общие требования: Оптимистичные обновления (dataSource=network)», раздел «Какие кэши обновляются оптимистично». Кэш событий этого питомца (например, ключи запросов событий по `petId`) — производный относительно этого экрана и обновляется фоновой инвалидацией вслед за оптимистичным применением, а не синхронным патчем (см. там же, раздел «Фоновое обновление»); после подтверждения отложенного `DELETE` сервером эти события фактически недоступны на backend (см. страницу «Удаление питомца — Backend»).

* Восстановление удалённого питомца через интерфейс за пределами окна отмены (см. «Основной сценарий», шаг 4) не предусмотрено в текущей итерации — соответствующего эндпоинта восстановления нет (см. страницу «Удаление питомца — Backend»).
