## Назначение

У питомца может быть одна фотография (главная/основная). Загрузка, замена и удаление фотографии выполняются через общий generic-механизм («Общие требования: Файлы сущностей») — отдельных endpoint'ов вида `/pet/{id}/photo/...` у питомца нет. Эта страница фиксирует то, что специфично для питомца: значение `owner_type`, правило проверки владения и добавление поля `photo_url` в существующие ответы питомца.

## Подключение к реестру типов владельцев

Питомец зарегистрирован в реестре («Общие требования: Файлы сущностей», раздел «Реестр типов владельцев») так:

| `owner_type` | `owner_id` | Кардинальность | Проверка владения | Допустимые `content_type` |
| --- | --- | --- | --- | --- |
| `pet_photo` | `pet.id` | ровно 1 | `pet.id = owner_id AND pet.user_id = userID AND pet.deleted_at IS NULL` | `image/jpeg`, `image/png`, `image/webp` |

Проверка владения здесь дословно совпадает с проверкой, используемой на остальных эндпоинтах питомца (`GET /pet/{id}`, `PUT /pet/{id}`, `DELETE /pet/{id}`) — отдельного, специфичного только для фотографий, правила владения не вводится.

Загрузка/замена и удаление фотографии питомца выполняются вызовом generic-эндпоинтов с `owner_type = "pet_photo"` и `owner_id = <id питомца>` — полный протокол (presigned PUT URL, подтверждение, замена при повторной загрузке, удаление) описан на странице «Общие требования: Файлы сущностей» и не дублируется здесь.

## Чтение: поле `photo_url` в ответах питомца

Отдельного эндпоинта чтения фотографии нет (см. «Общие требования: Файлы сущностей», раздел «Область действия» — чтение всегда специфично для сущности). Вместо этого:

* `GetPetProfileResponse` (`GET /pet/{id}`) получает два новых nullable-поля: `photo_url` и `photo_file_id`. Сервер ищет в таблице `file` строку с `owner_type = 'pet_photo' AND owner_id = <id питомца> AND confirmed_at IS NOT NULL` (по кардинальности «ровно 1» такая строка не более одной); если найдена — возвращает её `id` как `photo_file_id` и подписывает presigned GET URL на неё (TTL — см. «Общие требования: S3-хранилище файлов») как `photo_url`; если не найдена — оба поля `null`. `photo_file_id` нужен клиенту для `DELETE /files/{file_id}` (см. «Фотография питомца — Frontend», раздел «Удаление фотографии») — без него у клиента не было бы способа адресовать текущую фотографию для удаления, зная только presigned-ссылку на её содержимое.

* `GetShortInfoPetResponse` (элемент `items` в `GET /pet`) получает то же nullable-поле `photo_url`, вычисляемое так же — для каждого питомца в списке, у которого есть подтверждённая строка `file`.

Проверка владения для чтения уже выполняется этими эндпоинтами при выборке питомца/списка питомцов (см. «Просмотр карточки питомца — Backend», «Список питомцев — Backend») — отдельной повторной проверки владения специально для генерации `photo_url` не требуется.

`photo_url` — это временная ссылка, а не постоянный адрес: клиент не должен сохранять её дольше времени жизни экрана и обязан быть готов к тому, что при следующей загрузке данных питомца (даже если фотография не менялась) `photo_url` будет другой строкой с новым сроком действия.

## Бизнес-правила и валидация

* `file_id` фотографии не входит в тело `POST /pet`, `PUT /pet/{id}` и в `GetPetProfileRequest`/`UpdatePetProfileRequest` — фотография управляется исключительно generic-эндпоинтами `/files/...` с `owner_type = "pet_photo"`, а не общим частичным обновлением питомца.

* Мягко удалённого питомца нельзя ни загрузить/заменить, ни удалить фотографию — проверка владения из реестра (см. выше) для такого питомца не проходит, эквивалентный результат `404` на любом из generic-эндпоинтов `/files/...` (см. «Общие требования: Файлы сущностей», раздел «Обработка ошибок»).

* Ограничение размера файла в этой итерации не устанавливается ни на уровне питомца, ни на уровне generic-механизма (см. «Общие требования: Файлы сущностей»).

## Хранение состояния и побочные эффекты

Загрузка, замена и удаление фотографии изменяют только таблицу `file` (см. «Общие требования: Файлы сущностей») — таблица `pet` полем для фотографии не дополняется, `photo_url` вычисляется на чтении присоединением к `file`. Других побочных эффектов, специфичных для питомца, нет.
