## Назначение

Эндпоинт `POST /pet` должен создавать новую запись питомца, привязанную к профилю авторизованного пользователя.

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь.

* Требуется валидный access-токен; у пользователя есть профиль.

## Основной сценарий

`POST /pet`. Заголовок `LanguageCode` не требуется (см. правило ниже).

Тело запроса: `name`, `species` — обязательны, непусты после удаления пробельных символов; `gender`, `birth_date`, `color`, `sterilized`, `habilitation`, `notes`, `breed`, `icon` — опциональны. Опциональный заголовок `Idempotency-Key` (UUID, генерируется клиентом на форме) используется для дедупликации повторных запросов создания (см. правило ниже). Поле `habilitation` — известная опечатка в контракте API, правильное имя — `habitation`. Миграционный путь (см. «Связанные задачи», PET-173): 1) миграция БД `ALTER TABLE pet RENAME COLUMN habilitation TO habitation;`; 2) обновление OpenAPI-спеки — поле `habilitation` заменяется на `habitation` во всех схемах, где оно встречается (создание, обновление, карточка питомца); 3) это breaking change контракта API — FE и BE ОБЯЗАНЫ деплоиться синхронно в одном релизном окне; если синхронный деплой невозможен, BE на переходный период ОБЯЗАН при разборе тела запроса принимать оба имени поля (сначала пробовать `habitation`, при его отсутствии — принимать `habilitation` как fallback), но в ответе ОБЯЗАН всегда отдавать только новое имя `habitation`.

1. Система проверяет заголовок `Authorization` и извлекает `userID`.

2. Система декодирует тело запроса как JSON.

3. Система проверяет, что `name` и `species` непусты после trim.

4. Если передан `icon` — система проверяет его по перечислению допустимых значений (см. «Справочник значений (словари enum)»).

5. Если передан `gender` — система проверяет его по перечислению допустимых значений (см. «Справочник значений (словари enum)»).

6. Если передан `habilitation` — система проверяет его по перечислению допустимых значений (см. «Справочник значений (словари enum)»).

7. Если передан `birth_date` — система парсит его в формате `YYYY-MM-DD` и проверяет, что дата не позднее текущей.

8. Система находит `profileID` по `userID`.

9. Если в запросе передан заголовок `Idempotency-Key` — система выполняет резервирование ключа по алгоритму из блока «Механизм дедупликации по Idempotency-Key» ниже, до вставки строки питомца. Если резервирование обнаруживает, что питомец с этим ключом уже создан — сервер сразу читает его по сохранённому id и возвращает `201 Created` с его данными; дальнейшие шаги (вставка новой строки) не выполняются.

10. Система вставляет новую строку в таблицу `pet` с `deleted_at = NULL`.

11. Система читает созданную запись обратно.

12. Если был передан `Idempotency-Key` — система завершает резервирование, связывая ключ с id только что созданного питомца (см. блок ниже).

13. Система возвращает `201 Created` с данными питомца.

**Механизм дедупликации по Idempotency-Key.** Формат значения — UUID v4, генерируется клиентом (см. страницу «Добавление питомца — Frontend», BE: PET-170). Заголовок опционален: если он не передан, шаги дедупликации ниже полностью пропускаются, и каждый запрос без него создаёт нового питомца. Отдельная таблица в той же PostgreSQL-БД:

```
CREATE TABLE pet_idempotency_key (
  profile_id       uuid NOT NULL,
  idempotency_key  uuid NOT NULL,
  pet_id           uuid,
  created_at       timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (profile_id, idempotency_key)
);
```

1. Резервирование (до вставки питомца): `INSERT INTO pet_idempotency_key (profile_id, idempotency_key, pet_id) VALUES ($1, $2, NULL) ON CONFLICT (profile_id, idempotency_key) DO NOTHING;`

2. Если INSERT реально вставил строку (`RowsAffected() == 1`) — ключ этим профилем ранее не использовался, запрос продолжает выполнение обычным образом (переход к вставке питомца).

3. Если INSERT не вставил строку (`RowsAffected() == 0`, конфликт по PRIMARY KEY) — ключ уже зарегистрирован. Система выполняет `SELECT pet_id FROM pet_idempotency_key WHERE profile_id = $1 AND idempotency_key = $2;`

4. Если найденный `pet_id IS NOT NULL` — питомец с этим ключом уже создан: система читает его по id и возвращает `201 Created` с его данными; новая запись не создаётся — это защищает от дублирования при обрыве соединения после успешного создания на сервере.

5. Если `pet_id IS NULL` — редкий гоночный случай: два запроса с одинаковым ключом пришли почти одновременно, и первый ещё не успел завершить создание питомца. Для MVP это принятый риск (по аналогии с fail-open для крайне узкого гоночного окна): второй запрос не блокируется и не повторяет попытку, а продолжает выполнение как обычный запрос создания, что в этом конкретном редком случае может привести к появлению двух питомцев. Блокировка строки (`SELECT ... FOR UPDATE` с ожиданием) не реализуется в этой итерации.

6. Завершение резервирования (после успешной вставки питомца): `UPDATE pet_idempotency_key SET pet_id = $1 WHERE profile_id = $2 AND idempotency_key = $3;`

7. Окно дедупликации — 24 часа с момента создания строки (`created_at`); клиент, повторяющий запрос позже этого окна, создаст нового питомца. Строки старше 24 часов допустимо удалять периодической очисткой (например, раз в сутки); при ожидаемых объёмах регистраций питомцев рост таблицы незначителен, отдельная задача на cron-очистку не заводится в этой итерации.

## Бизнес-правила и валидация

* Обязательные поля при создании: `name`, `species`.

* `icon`, если передан, должен входить в перечень допустимых значений (см. «Справочник значений (словари enum)»).

* `gender` и `habilitation`, если переданы, должны входить в соответствующие перечисления допустимых значений (см. «Справочник значений (словари enum)») — валидируются так же строго, как `icon`.

* `birth_date`, если передан, должен быть валидной датой в формате `YYYY-MM-DD` и не позднее текущей даты.

* Питомец всегда привязывается к профилю вызывающего пользователя.

* Ограничения длины полей: `name` — не более 100 символов, `notes` — не более 1000 символов, `breed` и `color` — не более 100 символов каждое; превышение — `400`.

* `birth_date`, если передан, дополнительно ограничен снизу: не может быть раньше, чем 500 лет назад от текущей даты сервера; иначе `400`.

* Дублирующиеся имена питомцев в рамках одного профиля разрешены — уникальность `name` не проверяется.

* Идемпотентность: при повторном `POST /pet` с тем же `Idempotency-Key` и тем же профилем (пара `profile_id + idempotency_key`) в пределах 24-часового окна дедупликации новая запись не создаётся (см. основной сценарий и блок «Механизм дедупликации по Idempotency-Key»).

* Поле `is_deleted` не входит в модель запроса создания и не принимается сервером — состояние удаления управляется исключительно через `DELETE /pet/{id}`.

* Заголовок `LanguageCode` не требуется на этом эндпоинте (согласовано со всеми остальными эндпоинтами питомцев — см. PET-44).

## Обработка ошибок

| Статус | Условие                                                                                                                                                                                                                                                                                         |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | Некорректный JSON; `name` или `species` пусты; `icon`, `gender` или `habilitation` недопустимы; `birth_date` в неверном формате, в будущем или раньше 500 лет назад; `name`/`notes`/`breed`/`color` превышают допустимую длину. Формат тела ошибки — см. «Общие требования: Формат ошибок API». |
| 401    | Заголовок `Authorization` отсутствует или некорректен.                                                                                                                                                                                                                                          |
| 500    | Профиль не найден; ошибка вставки строки; не удалось прочитать созданную запись.                                                                                                                                                                                                                |

## Хранение состояния и побочные эффекты

Добавляет одну строку в таблицу `pet`. При наличии `Idempotency-Key` дополнительно вставляет, а затем обновляет одну строку в таблице `pet_idempotency_key` (см. «Механизм дедупликации по Idempotency-Key» в основном сценарии). Других побочных эффектов нет.
