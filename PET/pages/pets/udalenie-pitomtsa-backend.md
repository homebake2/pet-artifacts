## Назначение

Эндпоинт `DELETE /pet/{id}` должен помечать питомца как удалённого (мягкое удаление), после чего он исключается из выдачи всех эндпоинтов питомцев.

## Действующие лица и предусловия

* Инициатор — владелец питомца.

* Требуется валидный access-токен; питомец существует в профиле и не был удалён ранее.

## Основной сценарий

`DELETE /pet/{id}`, тело запроса отсутствует.

1. Система разбирает `id` из пути как UUID.

2. Система проверяет `Authorization` и находит `profileID` (см. [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md)).

3. Система проверяет существование питомца по `id = ... AND profile_id = ... AND deleted_at IS NULL` — иначе `404`.

4. Система выполняет `UPDATE pet SET deleted_at = текущее время WHERE id = ... AND profile_id = ...`.

5. Система возвращает `204 No Content`.

Мягкое удаление не затрагивает связанные события (таблица `event`) и не удаляет строку `pet` физически. События мягко удалённого питомца остаются в БД, но нигде не выводятся — это уже покрыто общим правилом (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)), отдельной политики хранения для событий не требуется.

## Бизнес-правила и валидация

* Удалить можно только питомца, принадлежащего профилю вызывающего пользователя.

* Удаление всегда мягкое: данные питомца физически сохраняются в БД, помечаются `deleted_at`.

* После удаления питомец должен быть скрыт на всех эндпоинтах питомцев: не отображается в `GET /pet`, недоступен через `GET /pet/{id}` (`404`) и недоступен для `PUT /pet/{id}` (`404`) — единая политика скрытия мягко удалённых питомцев (см. PET-40 и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)).

* Это правило распространяется и на вложенные выборки: `GET /pet/{id}/events` для мягко удалённого питомца должен возвращать `404` — так же, как и карточка самого питомца, а не отдавать список его событий. Конкретный механизм (см. страницу «Просмотр карточки питомца — Backend»): перед выборкой событий обработчик проверяет существование питомца тем же условием, что и `GET /pet/{id}` — `SELECT ... FROM pet WHERE id = $1 AND profile_id = $2 AND deleted_at IS NULL`; если строка не найдена (питомец не существует, принадлежит другому профилю или `deleted_at IS NOT NULL`) — сервер возвращает `404` и запрос к таблице событий не выполняется вовсе (а не выполняется с последующей фильтрацией пустого списка). Это уже общее правило (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)); для этого эндпоинта проверка реализована и зафиксирована в требованиях (см. «Связанные задачи», PET-139).

* Повторный вызов `DELETE /pet/{id}` на уже удалённом питомце должен возвращать `404` (питомец скрыт политикой из PET-40) и не должен повторно изменять `deleted_at` — таким образом операция идемпотентна: результат повторного вызова предсказуем и безопасен, ошибка не считается сбоем клиента. Такой `404` при гонке удаления трактуется клиентом (FE) как «уже удалён», а не как ошибка (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md) и страницу «Удаление питомца — Frontend»).

* Эндпоинт восстановления удалённого питомца не предусмотрен в текущей итерации — это осознанное решение, а не незакрытый вопрос. Undo/restore рассматривается как возможность в одной из будущих итераций и потребует отдельных требований; при возникновении такой потребности заводится отдельная задача.

## Обработка ошибок

| Статус | Условие                                                                                                           |
| ------ | ----------------------------------------------------------------------------------------------------------------- |
| 400    | `id` не является валидным UUID.                                                                                   |
| 401    | Токен невалиден — обрабатывается по общим правилам (см. [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md)). |
| 404    | Питомец не найден, принадлежит другому профилю или уже мягко удалён.                                              |
| 500    | Ошибка получения профиля, поиска питомца или выполнения `UPDATE`.                                                 |

## Хранение состояния и побочные эффекты

Изменяется только поле `deleted_at` строки питомца. Прочие поля питомца и связанные события не затрагиваются: события остаются в БД в неизменном виде, но перестают быть доступны через любой эндпоинт, включая `GET /pet/{id}/events` (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)).
