## Назначение

Отдельный экран полного списка событий одного питомца — с бесконечной пагинацией и поиском по событиям. Открывается только по кнопке «Показать все» с карточки питомца, где блок событий показывает не более 5 последних записей (см. «Просмотр карточки питомца — Frontend»).

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь.

* Переход выполняется с карточки питомца, с передачей `pet_id` и текущего отображаемого имени питомца.

## Основной сценарий

1. Пользователь нажимает «Показать все» в блоке событий на карточке питомца.

2. Система открывает экран «События {Имя питомца}»: в хедере — кнопка «Назад» (стрелка) слева и заголовок «События {Имя питомца}», где {Имя питомца} — имя, переданное с карточки питомца в момент открытия (повторный запрос данных питомца на этом экране не выполняется).

3. Под хедером — поле поиска (плейсхолдер поясняет, что поиск идёт по названию и заметке события).

4. Система запрашивает первую страницу событий: `GET /pet/{id}/events?limit=<page_size>&offset=0`, без `search` (в локальном режиме — эквивалентный локальный запрос, см. «События питомца — Frontend (dataSource=local)»). Размер страницы (`page_size`) фиксирован для экрана и не связан с ограничением в 5 событий на карточке питомца.

5. На время загрузки первой страницы система показывает skeleton, повторяющий структуру списка событий (см. «Общие требования: UI-паттерны запросов»).

6. После успешной загрузки система показывает список событий в том же виде, что и на карточке питомца (те же карточки событий), отсортированный по дате по убыванию (порядок, возвращаемый backend).

7. При прокрутке списка до конца уже загруженных элементов система запрашивает следующую страницу с тем же `search` (если задан) и `offset`, увеличенным на `page_size`, и добавляет полученные события в конец уже отображённого списка, не сбрасывая и не перерисовывая уже показанные элементы. См. раздел «Бесконечная пагинация» ниже.

8. Пользователь вводит текст в поле поиска. После debounce (см. «Бизнес-правила и валидация») система отбрасывает уже загруженные страницы, показывает skeleton списка заново и повторяет шаг 4 с `offset=0` и параметром `search`, равным введённому тексту.

9. Нажатие на событие в списке открывает редактирование события (см. «Редактирование события — Frontend»); свайп/действие удаления доступно так же, как и в блоке событий карточки питомца (см. «Удаление события — Frontend»).

10. Нажатие «Назад» возвращает на карточку питомца.

## Бесконечная пагинация

* Пагинация — по номеру страницы (offset-based), как реализовано в `GET /pet/{id}/events` (см. «Просмотр карточки питомца — Backend»); курсорная пагинация не используется.

* Экран хранит накопленный список уже загруженных страниц и текущий `offset` следующей страницы для актуального значения `search`.

* Подгрузка следующей страницы инициируется приближением к концу видимого списка (например, когда отрисован последний или предпоследний элемент), а не только по достижению самого конца — чтобы пользователь не видел паузу перед подгрузкой при быстрой прокрутке.

* Индикатор подгрузки следующей страницы — небольшой спиннер в подвале списка; он не заменяет и не скрывает уже отображённые события.

* Признак «страниц больше нет»: каждый ответ `GET /pet/{id}/events` содержит поле `total` — общее число событий, подходящих под текущий `search` (см. «Просмотр карточки питомца — Backend»). Клиент считает, что достигнут конец списка, когда накопленное число загруженных событий (`offset` последней запрошенной страницы + число элементов в её `items`) становится больше или равно `total`. Ответ с пустым `items` (или `items` короче `limit`) при этом условии не является отдельным сигналом — он лишь следствие того, что `total` уже достигнут. После этого повторные подгрузки для текущего значения `search` не выполняются, пока не изменится `search` (после чего запрашивается новый `total` для нового фильтра).

* Повторная подгрузка следующей страницы, пока предыдущая ещё не завершилась, не выполняется (защита от дублирующих запросов при быстрой прокрутке).

* Ошибка загрузки очередной (не первой) страницы не сбрасывает уже показанный список — см. таблицу «Обработка ошибок» ниже.

## Бизнес-правила и валидация

* Поиск ищет по `notes` (заметка события) и по свободнотекстовому подполю значения события, если оно есть у типа события (`other.label`, `medication.name` — см. «Модель значения события и реестр метрик»); совпадение по любому из полей достаточно. Поиск не учитывает регистр и ищет по подстроке (частичное совпадение), в соответствии с backend-контрактом параметра `search`.

* Поиск не ищет по локализованному названию типа события (например, «Кормление», «Вес»): локализация типов выполняется только на клиенте (см. «Просмотр карточки питомца — Backend», описание параметра `search`) — это осознанное ограничение текущей итерации.

* Ввод в поле поиска обрабатывается с debounce (рекомендуемое значение — 300 мс), чтобы не отправлять запрос на каждое нажатие клавиши.

* Очистка поля поиска (пустая строка) равносильна отсутствию `search` — возвращается полный список событий питомца с первой страницы.

* Экран не содержит собственных форм добавления событий; кнопки «Добавить событие» на этом экране нет — добавление событий остаётся точкой входа только с карточки питомца.

* Экран только читает данные и переходит в существующие флоу редактирования/удаления события; сам не выполняет мутирующих запросов.

## Обработка ошибок

| Ситуация                                                              | Что должна показать система                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ошибка загрузки первой страницы (сеть, 5xx, таймаут)                  | Блок ошибки на весь список с сообщением и кнопкой «Повторить», отличимый от пустого результата поиска (см. «Общие требования: UI-паттерны запросов»). Кнопка «Повторить» повторяет тот же запрос (тот же `search`, `offset=0`).                                |
| Ошибка загрузки очередной (не первой) страницы                        | Уже показанный список не скрывается и не сбрасывается; в подвале списка показывается компактное сообщение об ошибке с кнопкой «Повторить», которая повторяет запрос той же страницы (тот же `offset`).                                                        |
| Питомец не найден (404, в том числе мягко удалённый или чужой)         | Отдельный экран/блок «Питомец не найден» с возможностью вернуться к списку питомцев — та же семантика, что и на карточке питомца (см. «Просмотр карточки питомца — Frontend»).                                                                                |
| 401 (истёкшая/некорректная авторизация)                                | Не обрабатывается как обычная ошибка экрана — срабатывает единый механизм авто-refresh токена (см. «Общие требования: Сессия, 401 и авто-refresh токена»).                                                                                                    |
| Первая страница успешно загрузилась, но список пуст                   | Пустое состояние: «Нет событий», если `search` не задан; «Ничего не найдено по запросу «…»» (или аналогичная формулировка), если `search` задан.                                                                                                              |
| dataSource=local: ошибка чтения локального хранилища                  | Та же семантика, что и ошибка загрузки в сетевом режиме — см. [События питомца — Frontend (dataSource=local)](sobytiya-pitomtsa-frontend-local.md).                                                                                                            |

## Хранение состояния и побочные эффекты

* Экран сам не изменяет данные — все мутации (редактирование, удаление события) выполняются существующими флоу, на которые этот экран только переходит.

* После успешного редактирования или удаления события, выполненного из этого экрана, необходимо инвалидировать те же кэши, что и при редактировании/удалении события с карточки питомца или из календаря (кэш событий питомца, сетка календаря, список дня — см. «Редактирование события — Frontend», раздел «Хранение состояния и побочные эффекты»), включая усечённый превью-список на карточке питомца (`limit=5`), чтобы оба места отражали изменения без ручного обновления.

* Накопленный список загруженных страниц и текущий `offset`/`search` существуют только в состоянии этого экрана и не переживают его закрытие: при повторном открытии экран всегда начинает с первой страницы без `search`.
