## Назначение

Владелец питомца даёт другому пользователю доступ к питомцу и ко всем его связанным записям с одной из двух ролей: `view` («только просмотр») или `full` («полный доступ»). Одним приглашением владелец может выдать доступ к одному питомцу или сразу к выбранному набору своих питомцев (в том числе ко всем), с одной ролью на весь набор. Доступ к «всем питомцам» не выдаётся автоматически: набор всегда выбирает владелец.

Выдача двухшаговая, как передача: владелец создаёт приглашение и получает одноразовый код; получатель вводит или считывает код, просматривает питомцев и принимает или отклоняет приглашение. После принятия питомцы появляются у получателя рядом с его собственными; владельцем они не становятся. Что именно разрешено ролям — см. матрицу прав на странице общих требований.

Владелец в любой момент меняет роль участника или отзывает доступ (по каждому питомцу отдельно); участник в любой момент может отказаться от доступа сам. Если доступ прекращён не по инициативе участника, он получает уведомление (см. «Уведомления о потере доступа»).

## Модель данных

Таблица `pet_access` — действующие доступы:

| Поле | Тип | Описание |
| --- | --- | --- |
| `pet_id` | uuid | Питомец. `ON DELETE CASCADE` (физическое удаление питомца при удалении аккаунта владельца) |
| `user_id` | uuid | Участник. `ON DELETE CASCADE` при удалении аккаунта участника (переназначение автора записей — см. «Завершение доступа» на странице общих требований) |
| `role` | text | `full` или `view` |
| `granted_by` | uuid NULL | Владелец, выдавший доступ. `ON DELETE SET NULL` |
| `created_at`, `updated_at` | timestamptz | Выдача и последнее изменение роли |

Первичный ключ — `(pet_id, user_id)`: у участника не более одной роли у питомца. Владелец питомца в таблице не хранится и не может быть участником собственного питомца.

Таблица `pet_access_invite` — приглашения и их история:

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | uuid | Идентификатор приглашения |
| `from_user_id` | uuid NULL | Владелец, создавший приглашение. `ON DELETE SET NULL` |
| `to_user_id` | uuid NULL | Получатель: заполняется при принятии или отклонении. `ON DELETE SET NULL` |
| `role` | text | Выдаваемая роль: `full` или `view` |
| `code` | text | Код приглашения (формат и свойства — как у кода передачи, см. «Передача питомца — Backend», раздел «Код передачи») |
| `status` | text | `pending`, `accepted`, `declined`, `cancelled`, `expired` |
| `created_at` | timestamptz | Создание |
| `expires_at` | timestamptz | `created_at` + 7 суток (константа сервера) |
| `resolved_at` | timestamptz NULL | Момент выхода из `pending` |

Таблица `pet_access_invite_pet` — питомцы приглашения:

| Поле | Тип | Описание |
| --- | --- | --- |
| `invite_id` | uuid | Приглашение. `ON DELETE CASCADE` |
| `pet_id` | uuid | Питомец. Без внешнего ключа: история переживает физическое удаление питомца |
| `pet_name`, `pet_species` | text | Снимок имени и вида питомца на момент создания |

Первичный ключ — `(invite_id, pet_id)`; в приглашении от 1 до 20 питомцев (константа сервера).

Таблица `pet_access_notice` — уведомления о потере доступа (см. «Уведомления о потере доступа»):

| Поле | Тип | Описание |
| --- | --- | --- |
| `user_id` | uuid | Бывший участник. `ON DELETE CASCADE` |
| `pet_id` | uuid | Питомец. Без внешнего ключа |
| `pet_name`, `pet_species` | text | Снимок имени и вида на момент потери доступа |
| `reason` | text | `revoked`, `pet_deleted`, `pet_transferred` |
| `created_at` | timestamptz | Момент потери доступа |

Первичный ключ — `(user_id, pet_id)`: не более одного уведомления на питомца (новое заменяет прежнее).

Ограничения и правила:

* Частичный уникальный индекс `UNIQUE (code) WHERE status = 'pending'`; код не совпадает с кодами активных передач (генерация проверяет обе таблицы).

* Переходы статусов — как у передачи: `pending → accepted | declined | cancelled | expired`; остальные конечные. `pending` с `expires_at <= now` везде трактуется как `expired` (перевод при первом обращении и фоновой задачей очистки раз в час).

* **Действующие питомцы приглашения** — те из `pet_access_invite_pet`, которые не мягко удалены и всё ещё принадлежат `from_user_id`. Приглашение, у которого не осталось действующих питомцев, неактивно: везде трактуется как `cancelled` (перевод при первом обращении и фоновой задачей очистки).

* **Лимит участников — 10 на питомца**, суммарно с активными приглашениями (`pet_access` питомца + `pending` не истёкшие приглашения, в которых он действующий). Приглашение занимает место у каждого своего питомца. Константа сервера.

* Подбор кода ограничивается тем же лимитом, что и для кодов передачи: не более 10 неудачных обращений к эндпоинтам с кодом (передачи и доступа вместе) в час на пользователя, учёт в `pet_transfer_code_failure`; `429 RATE_LIMITED`. Неудачной считается попытка с корректным по формату кодом, на которую вернулся `404`.

## Эндпоинты владельца

Все эндпоинты требуют валидный access-токен. Для каждого `id` питомца, не принадлежащего пользователю: если у пользователя есть доступ к питомцу — `403 FORBIDDEN`, если нет — `404`; мягко удалённый питомец — `404` всем.

### `POST /pet/{id}/access-invites` — создать приглашение

Тело: `{ "role": "full" | "view", "pet_ids"?: uuid[] }`.

1. Система разбирает `id` как UUID, проверяет питомца и что пользователь — его владелец.

2. `pet_ids` — набор питомцев приглашения. Если не передан, набор состоит только из `{id}`. Если передан, он обязан содержать `{id}`; все элементы — различные питомцы пользователя, не мягко удалённые (иначе `404`, если питомец не принадлежит пользователю или удалён; `400` — дубликаты или превышение размера набора).

3. Для каждого питомца набора проверяется лимит участников — иначе `409 ACCESS_LIMIT_REACHED` (приглашение не создаётся).

4. Создаёт запись `pet_access_invite` со статусом `pending` и строки `pet_access_invite_pet` со снимками имени и вида.

5. `201 Created`: `{ "id", "code", "role", "pet_ids", "expires_at" }`.

Несколько активных приглашений допустимы (разным людям, с разными ролями и наборами).

### `GET /pet/{id}/access` — участники и активные приглашения питомца

Только владелец. `200`:

```json
{
  "members": [{ "user_id", "name", "role", "granted_at" }],
  "invites": [{ "id", "code", "role", "pet_ids", "expires_at" }]
}
```

`name` — имя из профиля участника (`first_name`), а при его отсутствии — логин. `members` и `invites` отсортированы по `created_at`; в `invites` только активные приглашения, в состав которых входит этот питомец (`pet_ids` — их полный набор действующих питомцев). Участникам список недоступен (`403`).

### `PUT /pet/{id}/access/{user_id}` — изменить роль

Только владелец. Тело: `{ "role": "full" | "view" }`. Меняет роль участника у этого питомца; у остальных питомцев участника роль не меняется. Если участника нет — `404`. Роль меняется сразу, `updated_at = now`; `204`. Повторная отправка той же роли идемпотентна.

### `DELETE /pet/{id}/access/{user_id}` — отозвать доступ

Только владелец. Удаляет строку `pet_access` этого питомца; создаёт уведомление о потере доступа с причиной `revoked`; `204`. Записи, созданные участником, остаются у питомца (см. «Завершение доступа» в общих требованиях). Если участника нет — `404`.

### `DELETE /pet/{id}/access-invites/{invite_id}` — отменить приглашение

Только владелец. Активное приглашение (целиком, со всем набором питомцев) переводится в `cancelled`, `204`. Если приглашения нет, оно не `pending` или не включает питомца `id` — `404`.

## Эндпоинт участника

### `DELETE /pet/{id}/access/me` — отказаться от доступа

Любой участник (`full` или `view`) удаляет собственную строку `pet_access` этого питомца; записи остаются у питомца, как при отзыве; уведомление о потере доступа не создаётся; `204`. Для владельца — `403 FORBIDDEN` (владелец отказывается от питомца только удалением или передачей). Если доступа у пользователя нет — `404`.

## Эндпоинты получателя

### `POST /pet-access-invites/preview` — предпросмотр по коду

Тело: `{ "code": string }`.

1. Система нормализует код (как у передачи) и ищет приглашение `pending` с `expires_at > now`; затем определяет его действующих питомцев.

2. Приглашение не найдено, не активно, истекло или действующих питомцев нет — единый `404` (без различения причин).

3. `from_user_id = userID` — `409 ACCESS_OWN_PET`.

4. У пользователя уже есть доступ ко всем действующим питомцам приглашения — `409 ACCESS_ALREADY_GRANTED`. Если доступ есть к части питомцев, предпросмотр возвращает только остальные (те, что будут выданы).

5. `200`: `{ "pets": [{ "name", "species", "breed", "gender", "birth_date", "photo_url" }], "role", "owner_name", "expires_at" }`. `owner_name` — `first_name` из профиля владельца, а при отсутствии профиля — логин. Остальные данные питомцев и записи не отдаются.

Предпросмотр ничего не изменяет.

### `POST /pet-access-invites/decline` — отклонить

Тело: `{ "code" }`. Поиск и проверки — как в предпросмотре. Приглашение переходит в `declined`, `to_user_id = userID`, `resolved_at = now`; `204`.

### `POST /pet-access-invites/accept` — принять

Тело: `{ "code" }`. Поиск и проверки — как в предпросмотре. В одной транзакции система блокирует строку приглашения и строки питомцев (`FOR UPDATE`), повторно проверяет `status = 'pending'`, срок и набор действующих питомцев (питомцы, ставшие недействующими за время ожидания, не выдаются), затем для каждого действующего питомца, к которому у получателя ещё нет доступа, вставляет `pet_access (pet_id, user_id = получатель, role = role приглашения, granted_by = from_user_id)`, удаляет уведомление о потере доступа к этому питомцу (если было) и переводит приглашение в `accepted` (`to_user_id`, `resolved_at`). Лимит участников повторно проверяется в транзакции для каждого питомца: питомец, у которого место закончилось, не выдаётся; если не выдан ни один — `409 ACCESS_LIMIT_REACHED`. Питомцы, к которым доступ уже был, остаются с прежней ролью. `200`: `{ "pet_ids": uuid[] }` — питомцы, доступ к которым у получателя появился.

Повторный вызов с тем же кодом — `404`.

## Уведомления о потере доступа

Если доступ участника к питомцу прекращён не его собственным решением, система в той же транзакции записывает в `pet_access_notice` (со снимком имени и вида) причину:

| `reason` | Когда |
| --- | --- |
| `revoked` | Владелец отозвал доступ |
| `pet_deleted` | Владелец мягко удалил питомца либо удалил свой аккаунт |
| `pet_transferred` | Питомец передан другому владельцу (принятие передачи) |

Отказ участника от доступа уведомления не создаёт. Для каждого пользователя не более одного уведомления на питомца; повторная потеря заменяет прежнее уведомление.

* `GET /pet` возвращает уведомления текущего пользователя отдельным массивом `access_lost` (контракт — см. [Список питомцев — Backend](spisok-pitomtsev-backend.md)).

* `DELETE /pet-access-notices/{pet_id}` — отметить уведомление просмотренным: удаляет его; `204`. Если уведомления нет — `204` (идемпотентно). Только собственные уведомления: чужие недоступны ни по какому `pet_id`.

* Уведомление хранится, пока пользователь его не отметил; срока давности нет. Новая выдача доступа к тому же питомцу удаляет уведомление. Уведомление не даёт доступа к данным питомца: в нём только снимок имени и вида.

## Что видит и может участник

* Питомец появляется у участника в `GET /pet` (поле `access`), доступен на всех эндпоинтах питомца по правилам матрицы прав; роль возвращается в `GET /pet` и `GET /pet/{id}` полем `access` (`owner` / `full` / `view`).

* Остальные эндпоинты (профиль, события, календарь, Ветпаспорт, напоминания, файлы, виджет, графики) проверяют доступ по `pet_access` и роли вместо проверки `pet.user_id`; правила записей с несколькими питомцами — на странице общих требований.

* Участник видит владельца питомца (`id` и имя) в поле `owner` ответов `GET /pet` и `GET /pet/{id}`, а также имя владельца в предпросмотре приглашения; имена других пользователей — только как авторов записей (см. «Автор записи» в общих требованиях); списка участников у него нет. Прежние владельцы участникам не раскрываются.

## Бизнес-правила и валидация

* Создавать приглашения, видеть участников, менять роль, отзывать доступ и отменять приглашения может только владелец питомца.

* Участник не может передавать, удалять питомца или выдавать доступ дальше — независимо от роли.

* Пока приглашение `pending`, питомцы и их данные для владельца доступны без ограничений; принимается состояние на момент принятия.

* Принятие, отклонение и отмена конкурируют за блокировку строки приглашения: побеждает первая зафиксированная операция, остальные — `404`.

* Недействительные коды не различаются по причине — единый `404`.

* Принятие приглашения владельцем: `409 ACCESS_OWN_PET`. Смена роли выполняется только владельцем через `PUT`.

* Мягкое удаление питомца и удаление аккаунта владельца: питомец перестаёт быть действующим в активных приглашениях (приглашение без действующих питомцев становится `cancelled`); бывшие участники получают уведомление `pet_deleted`; `pet_access` при мягком удалении не удаляется (доступ скрыт вместе с питомцем), а при физическом удалении питомца удаляется каскадом.

* Принятие передачи питомца: в той же транзакции удаляются все `pet_access` питомца, бывшие участники получают уведомление `pet_transferred`, питомец перестаёт быть действующим в приглашениях владельца (см. «Передача питомца — Backend»).

## История

Таблицы `pet_access_invite` и `pet_access_invite_pet` — постоянная история приглашений (как `pet_transfer`): записи не удаляются при удалении питомца и аккаунтов (ссылки на пользователей обнуляются). API просмотра истории не предусмотрено.

## Обработка ошибок

| Статус | Код | Условие |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | `id`, `user_id` или `pet_id` не UUID; `role` отсутствует или не `full`/`view`; `pet_ids` содержит дубликаты, не содержит `id` или слишком велик; `code` пуст или не соответствует формату |
| 401 | `UNAUTHORIZED` | Токен невалиден — по общим правилам (см. [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md)) |
| 403 | `FORBIDDEN` | У пользователя есть доступ к питомцу, но операция только для владельца; владелец вызывает `DELETE .../access/me` |
| 404 | `NOT_FOUND` | Питомец не найден, чужой без доступа или удалён; участника или приглашения нет; код недействителен |
| 409 | `ACCESS_OWN_PET` | Владелец использует собственный код |
| 409 | `ACCESS_ALREADY_GRANTED` | У получателя уже есть доступ ко всем питомцам приглашения |
| 409 | `ACCESS_LIMIT_REACHED` | У какого-либо питомца участники и активные приглашения достигли лимита (при создании приглашения) либо ни одному питомцу не удалось выдать доступ (при принятии) |
| 429 | `RATE_LIMITED` | Превышен лимит неудачных обращений с кодом |
| 500 | `INTERNAL_ERROR` | Ошибка БД; транзакция откатывается целиком |

## Хранение состояния и побочные эффекты

Выдача, смена роли и отзыв меняют `pet_access`, `pet_access_invite`, `pet_access_invite_pet` и `pet_access_notice`; записи, созданные участником, при отзыве и отказе остаются у питомца (см. «Завершение доступа» в общих требованиях). Объекты S3 при этом не удаляются. Режим `dataSource=local` доступ не поддерживает, `POST /import/local-data` не меняется (см. [Общие требования: Доступ к питомцу](../common/obschie-trebovaniya-dostup-k-pitomtsu.md), раздел «Режим local»).
