## Назначение

Определяет, как хранятся и отображаются файлы события (фотографии и документы, до 10 суммарно), когда активен режим `dataSource=local`. В этом режиме нет сервера и нет S3 — файлы хранятся непосредственно на устройстве, без загрузки куда-либо, той же общей моделью хранения файлов, что и фотография питомца (см. «Локальный режим (dataSource=local)», раздел «Хранение файлов»). Как и в сетевом режиме (см. «Файлы события — Frontend»), отдельного экрана просмотра файлов события нет — управление ведётся из раздела «Файлы» форм добавления/редактирования события.

## Хранение

Локальная запись события (см. «Локальный режим (dataSource=local)», раздел «Модель хранения») получает дополнительное поле `files` (массив объектов, по умолчанию пустой, не более 10 элементов). Каждый элемент — `{ localFileId (UUID, генерируется на клиенте при добавлении), uri (путь к файлу в постоянном хранилище приложения), contentType, filename (nullable — заполняется для документов, `null` для фотографий, симметрично сетевому режиму, см. «Файлы события — Backend») }`. `uri` — путь в постоянном хранилище приложения (не временный кэш-путь пикера — выбранный файл копируется в постоянную директорию, чтобы остаться доступным после перезапуска приложения), той же природы, что и `photoUri` питомца (см. «Фотография питомца — Frontend (dataSource=local)»). `localFileId` существует только в локальном хранилище — при переносе на сервер он не сохраняется (см. «Перенос файлов при local → network» ниже), новый `file_id` присваивается сервером так же, как и в сетевом режиме.

Добавление файла для локального события — синхронная с точки зрения пользователя операция: клиент копирует выбранный файл в постоянное хранилище приложения и добавляет получившийся элемент в конец массива `files` локальной записи события по её `id`; отдельного шага «upload-url/complete», описанного для сетевого режима, здесь нет — он существовал в сетевом режиме только из-за необходимости передать файл на сервер. Если пользователь выбрал несколько файлов сразу, они добавляются в массив последовательно, в порядке выбора, — порядок в `files` определяет порядок отображения списка (симметрично тому, как порядок сетевого `files` определяется порядком `position`, см. «Файлы события — Backend»).

Лимит 10 файлов на событие (фото и документы суммарно) действует и в режиме `local`: клиент не позволяет добавить в `files` больше 10 элементов, тем же способом ограничения выбора, что описан в «Файлы события — Frontend», раздел «Добавление файлов» — не только на сервере (которого в этом режиме нет), но и здесь, локально.

Удаление отдельного файла — удаление соответствующего элемента (по `localFileId`) из массива `files` локальной записи события и удаление самого файла из постоянного хранилища приложения; повторное удаление уже отсутствующего элемента (например, по устаревшему `localFileId`) идемпотентно, как и в сетевом режиме.

## Отображение

Раздел «Файлы» форм добавления/редактирования события в режиме `local` отображает список элементов напрямую по `files` локальной записи (без сетевого запроса и без TTL — в отличие от `files`/`url` в сетевом режиме), в порядке элементов массива: фотография (`contentType`, начинающийся с `image/`) — миниатюрой, документ — иконкой и `filename`. Список событий календаря показывает количество файлов как `files.length` вместо `files_count` сетевого режима — тот же визуальный значок «скрепка + число», см. «Файлы события — Frontend», раздел «Отображение количества файлов в списке событий». Если файл по одному из путей отсутствует/повреждён, элемент показывается с тем же плейсхолдером «не удалось загрузить», что и в сетевом режиме, без отдельного сообщения об ошибке.

## Обработка ошибок

Ошибка копирования файла в постоянное хранилище или записи массива `files` показывается пользователю тем же способом, что и сбой сохранения в сетевом режиме (см. [Общий раздел «Обработка ошибок хранилища»](../common/lokalnyi-rezhim-datasource-local-zaglushka.md)); уже добавленные ранее файлы не изменяются. Попытка добавить файл сверх лимита 10 обрабатывается тем же способом, что описан в «Файлы события — Frontend», раздел «Добавление файлов» — клиент не позволяет выбрать больше оставшихся слотов, отдельного серверного `409` в этом режиме не возникает, так как ограничение проверяется исключительно локально.

## Перенос файлов при local → network

Перенос данных `POST /import/local-data` (см. «Импорт локальных данных — Backend») не принимает бинарное содержимое `files` в своём JSON-теле — контракт этого эндпоинта рассчитан только на текстовые поля события. Вместо этого файлы переносятся отдельным шагом, который клиент выполняет сразу после успешного основного переноса, используя поле `events` ответа `POST /import/local-data` (см. «Импорт локальных данных — Backend», раздел 3) для сопоставления перенесённого локального события с его новым серверным `id` — тем же принципом, что и перенос фотографии питомца по полю `pets` того же ответа (см. «Фотография питомца — Frontend (dataSource=local)», раздел «Перенос фотографии при local → network»).

### Формирование очереди

После успешного `POST /import/local-data` клиент формирует единую очередь переноса файлов на основе двух источников:

* по одному элементу для каждого непустого `photoUri` каждого перенесённого питомца (уже описано в «Фотография питомца — Frontend (dataSource=local)»);
* по одному элементу для каждого элемента массива `files` каждого перенесённого события — событие с 3 файлами добавляет в очередь 3 отдельных элемента, каждый со своим `owner_id` (серверный id этого события), локальным путём к файлу, `contentType` и `filename` (для документов); порядок элементов одного события в очереди сохраняет порядок, в котором файлы были в локальном массиве `files`, — так серверный `position`, назначаемый при `complete` (см. «Файлы события — Backend»), в итоге воспроизводит тот же порядок списка, что был в локальном режиме.

Если ни у одного перенесённого питомца, ни у одного перенесённого события не было файлов — очередь пуста, и никаких дополнительных действий/индикаторов не требуется.

### Фоновый перенос

Поведение фонового переноса для непустой очереди полностью повторяет «Фотография питомца — Frontend (dataSource=local)», раздел «Фоновый перенос» — единый неблокирующий индикатор, последовательный (не параллельный) перенос элементов очереди по одному, инвалидация соответствующих кэшей после каждого успешного переноса, независимая обработка ошибок отдельного элемента (пропуск и переход к следующему без автоматического повтора), итоговое ненавязчивое уведомление с числом неперенесённых файлов по завершении очереди — с той разницей, что очередь теперь смешанная (фотографии питомцев и файлы событий, а среди файлов событий — и фотографии, и документы) и единый счётчик прогресса/итоговое уведомление относится ко всем элементам очереди вместе.

Для элемента очереди, относящегося к событию, перенос конкретного файла использует тот же протокол, что и обычное добавление файла события в сетевом режиме (см. «Файлы события — Frontend», раздел «Добавление файлов»: чтение байт файла по локальному пути → `POST /files/upload-url` с `owner_type: "event_file"`, `owner_id` = серверный id события, `content_type` и (для документов) `filename` из элемента очереди → `PUT` в S3 → `POST /files/{file_id}/complete`), где серверный id события берётся из сопоставления `local_id → id` в поле `events` ответа `POST /import/local-data`.

### Ограничение: перенос не переживает закрытие приложения

Действует то же явно зафиксированное ограничение, что и для переноса фотографии питомца (см. «Фотография питомца — Frontend (dataSource=local)», раздел «Ограничение: перенос не переживает закрытие приложения»): если приложение закрывается до того, как очередь исчерпана, оставшиеся в очереди файлы (питомцев и/или событий) не переносятся автоматически, но данные не теряются — исходные локальные файлы остаются на устройстве без изменений, а соответствующие питомцы/события в сетевом режиме уже существуют; недостающие файлы можно добавить вручную (для события — через раздел «Файлы» формы редактирования, см. «Файлы события — Frontend», раздел «Добавление файлов»).
