## Назначение

Экран "Календарь" — основной способ для владельца просматривать историю событий здоровья своих питомцев: сеточный календарь месяца с индикатором количества событий на день и список карточек событий выбранного дня.

## Действующие лица и предусловия

* Пользователь авторизован и находится на вкладке "Календарь".

* Приложение поддерживает два режима работы: онлайн (данные с сервера) и офлайн (локальный кэш). Поведение офлайн-ветки (dataSource=local) описано на отдельной странице — см. [Просмотр календаря — Frontend (dataSource=local)](prosmotr-kalendarya-frontend-local.md).

## Основной сценарий

1. При открытии вкладки "Календарь" система выбирает текущую дату по умолчанию.

2. Онлайн: для каждого питомца пользователя система параллельно запрашивает `GET /activities` с параметрами `pet_id`, `from`/`to` = границы месяца выбранной даты, вычисленные в UTC (см. "Бизнес-правила и валидация"). Офлайн: система использует локально сохранённые данные питомцев.

3. Система объединяет события всех питомцев в единый список; принадлежность события конкретному питомцу определяется исключительно по `pet_id` исходного запроса `GET /activities`, а не по какому-либо полю внутри самого события — событие само по себе не содержит идентификатора питомца в ответе API.

4. Календарная сетка отображает индикатор количества событий на каждый день месяца (группировка по календарному дню в UTC); список карточек ниже показывает события только выбранного дня (строгое совпадение дня, также в UTC).

5. При выборе другого дня система обновляет список карточек; при переходе на другой месяц система выполняет новый запрос данных за этот месяц.

6. Если на выбранный день событий нет, система показывает пустое состояние с понятным текстом.

7. Кнопка "+" открывает экран добавления события.

8. Иконка и название питомца в карточке события система берёт из справочника видов питомцев. Иконка и подпись типа события берутся из единого справочника типов событий — см. следующий раздел.

9. Экран должен поддерживать pull-to-refresh: жест обязан гарантированно инициировать повторный запрос событий за все уже подгруженные месяцы и показывать индикатор обновления до завершения всех запросов.

## Бизнес-правила и валидация

**Часовой пояс группировки и диапазона дат — UTC, а не часовой пояс устройства.** Единая конвенция для FE и BE (см. соответствующее требование на странице "Просмотр календаря — Backend"). Конкретный алгоритм конвертации:

**1. Границы месяца для запроса.** Выбранная пользователем дата (в локальном времени устройства) сначала конвертируется в её UTC-эквивалент, и уже от этой UTC-даты берётся календарный месяц. Затем вычисляются:

```
from = первый день UTC-месяца, формат YYYY-MM-DD (например, "2026-08-01")
to   = последний день UTC-месяца, формат YYYY-MM-DD (например, "2026-08-31")
```

Технически: `new Date(selectedDate.getUTCFullYear(), selectedDate.getUTCMonth(), 1)` и последний день — через `getUTCFullYear`/`getUTCMonth() + 1, 0`; локальные геттеры (`getFullYear`, `getMonth`) для этого расчёта не используются, иначе возле полуночи по местному времени граница месяца разъедется с тем, что backend отдаёт по UTC.

**2. Группировка индикаторов на сетке.** Каждое событие приходит с сервера с полем date (RFC3339, UTC). День, в который событие попадает на сетке календаря, вычисляется по UTC-компонентам этой даты (`date.getUTCFullYear()`, `date.getUTCMonth()`, `date.getUTCDate()`), а не по локальным геттерам — это гарантирует, что день на сетке FE совпадает с днём, под которым это же событие сгруппировано в ответе `GET /activities` на backend.

**3. Фильтрация карточек выбранного дня и отображение времени.** Сравнение "событие относится к выбранному дню" выполняется по тем же UTC-компонентам (п. 2), а не по локальному дню устройства. Время события в карточке выводится также через UTC-геттеры (`date.getUTCHours()`/`getUTCMinutes()`), а не через локале-зависимые методы вроде `toLocaleTimeString()`, которые интерпретируют момент времени в часовом поясе устройства и увели бы отображаемый день/час от UTC-группировки на сетке.

* Карточки списка фильтруются по точному совпадению даты события с выбранным днём (в UTC).

* Питомец без событий в выбранном месяце не создаёт индикаторов, но не исключается из списка питомцев пользователя.

* Каждый тип события имеет иконку и локализованную подпись, единые для календаря, формы добавления/редактирования события и графиков динамики — одно и то же событие нигде не выглядит по-разному. Список типов здесь не дублируется — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»; подписи берутся из общего справочника типов, см. [Общие требования: Единый источник enum-словарей](../common/obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md). Для типа `other` используется нейтральная иконка «прочее».

* Карточка события отображает значение по форме `value`, соответствующей типу события (например, число с единицей измерения, выбранная категория, название лекарства с дозой), а не сырую строку и не JSON: `value` — типизированный объект, и его поля выводятся осмысленно, с единицей измерения и локализованной подписью категории. Конкретные формы `value` по каждому типу — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md); на этой странице они не дублируются.

## Обработка ошибок

* Пока запрос данных питомца выполняется, система должна показывать индикатор загрузки на экране календаря (skeleton/spinner), а не пустой календарь.

* Частичная ошибка (упал запрос одного из N питомцев): система показывает успешно загруженные данные остальных питомцев и не блокирует ими весь экран; для питомца(ев), чей запрос завершился ошибкой, система показывает точечный индикатор ошибки с возможностью повторить запрос только за этого питомца — молчаливое исключение питомца из списка недопустимо, но и полный отказ в показе успешных данных из-за одной ошибки недопустим.

* Если у пользователя нет питомцев, система показывает пустой календарь без ошибок.

* При переходе из офлайн в онлайн (и обратно) система должна использовать актуальный для текущего режима источник данных при следующем обращении к серверу/локальному хранилищу; явного специального экрана перехода не требуется.

## Хранение состояния и побочные эффекты

* Данные о событиях кэшируются в React Query по единому ключу вида `['activities', petId, 'YYYY-MM']`. Других независимых способов получения тех же данных (с иным ключом кэша) в системе быть не должно — экран календаря и карточка питомца обязаны использовать одну и ту же фабрику ключей запросов, чтобы инвалидация кэша в одном месте всегда отражалась в другом.

* После успешного добавления, редактирования или удаления события система должна инвалидировать (или рефетчить) кэш активностей затронутого питомца за соответствующий месяц, чтобы календарь отражал актуальные данные без ручного обновления экрана пользователем.

* Кэш активностей также должен инвалидироваться при удалении и восстановлении питомца — сейчас это не триггерится.

* Точечный «Повторить» у отдельного питомца (см. «Обработка ошибок») и жест pull-to-refresh — разные механизмы: точечное «Повторить» перезапускает запрос только за этого питомца, pull-to-refresh перезапрашивает данные всех питомцев за все подгруженные месяцы.

## Известные ограничения MVP

* Число параллельных запросов `GET /activities` растёт линейно с количеством питомцев пользователя. Это сознательно принятое ограничение MVP. Возможное решение на будущее — batch-эндпоинт на бэкенде, принимающий несколько `pet_id` за один запрос (см. страницу "Просмотр календаря — Backend").
