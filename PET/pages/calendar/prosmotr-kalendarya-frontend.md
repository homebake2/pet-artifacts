## Назначение

Экран "Календарь" — основной способ для владельца просматривать историю событий здоровья своих питомцев: сеточный календарь месяца с индикатором количества событий на день и список карточек событий выбранного дня.

## Действующие лица и предусловия

* Пользователь авторизован и находится на вкладке "Календарь".

* Приложение поддерживает два режима работы: онлайн (данные с сервера) и офлайн (локальный кэш). Поведение офлайн-ветки (dataSource=local) описано на отдельной странице — см. [Просмотр календаря — Frontend (dataSource=local)](prosmotr-kalendarya-frontend-local.md).

## Основной сценарий

1. При открытии вкладки "Календарь" система выбирает текущую дату по умолчанию.

2. **Сетка месяца.** Онлайн: система запрашивает `GET /activities/calendar` одним запросом с параметрами `from`/`to` = границы месяца выбранной даты, вычисленные в UTC (см. "Бизнес-правила и валидация"); ответ содержит количество событий на каждый день месяца по всем питомцам пользователя сразу, без содержимого событий. Офлайн: система использует локально сохранённые данные питомцев.

3. Календарная сетка отображает индикатор количества событий на каждый день месяца по полученным из `GET /activities/calendar` значениям `count`.

4. **Список дня.** При выборе дня система отдельно запрашивает `GET /activities/day` с параметром `date` = выбранный день (вычисленный в UTC); ответ содержит полные события всех питомцев пользователя за этот день одним списком, каждое — с полями `pet_id`/`pet_name` для определения принадлежности питомцу (принадлежность больше не определяется параметром отдельного запроса на питомца — см. "Просмотр календаря — Backend").

5. При переходе на другой месяц система выполняет новый запрос `GET /activities/calendar` за этот месяц; при выборе другого дня в уже открытом месяце система выполняет новый запрос `GET /activities/day` для этого дня, не перезапрашивая сетку месяца.

6. Если на выбранный день событий нет, система показывает пустое состояние с понятным текстом.

7. Кнопка "+" открывает экран добавления события.

8. Иконка и название питомца в карточке события система берёт из справочника видов питомцев (по `pet_id`/`pet_name` из ответа `GET /activities/day`). Иконка и подпись типа события берутся из единого справочника типов событий — см. следующий раздел.

9. Экран должен поддерживать pull-to-refresh: жест обязан гарантированно инициировать повторный запрос `GET /activities/calendar` за все уже подгруженные месяцы и `GET /activities/day` за выбранный день, и показывать индикатор обновления до завершения всех запросов.

## Бизнес-правила и валидация

**Часовой пояс группировки и диапазона дат — UTC, а не часовой пояс устройства.** Единая конвенция для FE и BE (см. соответствующее требование на странице "Просмотр календаря — Backend"). Конкретный алгоритм конвертации:

**1. Границы месяца для запроса `GET /activities/calendar`.** Выбранная пользователем дата (в локальном времени устройства) сначала конвертируется в её UTC-эквивалент, и уже от этой UTC-даты берётся календарный месяц. Затем вычисляются:

```
from = первый день UTC-месяца, формат YYYY-MM-DD (например, "2026-08-01")
to   = последний день UTC-месяца, формат YYYY-MM-DD (например, "2026-08-31")
```

Технически: `new Date(selectedDate.getUTCFullYear(), selectedDate.getUTCMonth(), 1)` и последний день — через `getUTCFullYear`/`getUTCMonth() + 1, 0`; локальные геттеры (`getFullYear`, `getMonth`) для этого расчёта не используются, иначе возле полуночи по местному времени граница месяца разъедется с тем, что backend отдаёт по UTC.

**2. Выбранный день для запроса `GET /activities/day`.** Дата `date` вычисляется по тем же UTC-компонентам выбранной пользователем даты (`getUTCFullYear()`, `getUTCMonth()`, `getUTCDate()`), а не по локальным геттерам — это гарантирует, что день, для которого запрошен список, совпадает с днём, под которым backend сгруппировал количество событий в ответе `GET /activities/calendar` на сетке.

**3. Отображение времени в карточке.** Время события в карточке выводится через UTC-геттеры (`date.getUTCHours()`/`getUTCMinutes()`), а не через локале-зависимые методы вроде `toLocaleTimeString()`, которые интерпретируют момент времени в часовом поясе устройства и увели бы отображаемый час от UTC-группировки на сетке.

* Питомец без событий в выбранном месяце не создаёт индикаторов на сетке, но не исключается из списка питомцев пользователя.

* Каждый тип события имеет иконку и локализованную подпись, единые для календаря, формы добавления/редактирования события и графиков динамики — одно и то же событие нигде не выглядит по-разному. Список типов здесь не дублируется — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»; подписи берутся из общего справочника типов, см. [Общие требования: Единый источник enum-словарей](../common/obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md). Для типа `other` используется нейтральная иконка «прочее».

* Карточка события отображает значение по форме `value`, соответствующей типу события (например, число с единицей измерения, выбранная категория, название лекарства с дозой), а не сырую строку и не JSON: `value` — типизированный объект, и его поля выводятся осмысленно, с единицей измерения и локализованной подписью категории. Конкретные формы `value` по каждому типу — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md); на этой странице они не дублируются.

## Обработка ошибок

* Пока запрос `GET /activities/calendar` выполняется, система должна показывать индикатор загрузки на сетке календаря (skeleton/spinner), а не пустую сетку. Пока запрос `GET /activities/day` выполняется, система должна показывать отдельный индикатор загрузки в блоке списка дня, не блокируя этим уже отрисованную сетку.

* Ошибка `GET /activities/calendar` показывает точечный индикатор ошибки на сетке с возможностью повторить запрос, не блокируя остальной экран. Ошибка `GET /activities/day` показывает точечный индикатор ошибки в блоке списка дня с возможностью повторить запрос только за этот день, не влияя на уже отрисованную сетку месяца.

* Если у пользователя нет питомцев, система показывает пустой календарь без ошибок.

* При переходе из офлайн в онлайн (и обратно) система должна использовать актуальный для текущего режима источник данных при следующем обращении к серверу/локальному хранилищу; явного специального экрана перехода не требуется.

## Хранение состояния и побочные эффекты

* Данные сетки месяца кэшируются в React Query по единому ключу вида `['activities-calendar', 'YYYY-MM']`. Данные списка дня кэшируются по ключу вида `['activities-day', 'YYYY-MM-DD']`. Блок событий на карточке питомца использует отдельный ключ вида `['activities', petId, 'YYYY-MM']` (см. "Просмотр карточки питомца — Frontend") — это независимый от календаря кэш, так как использует другой эндпоинт (`GET /activities`).

* После успешного добавления, редактирования или удаления события система должна инвалидировать (или рефетчить) кэш сетки месяца (`['activities-calendar', ...]`) и кэш списка дня (`['activities-day', ...]`) для затронутого месяца/дня, а также кэш активностей затронутого питомца на карточке питомца (`['activities', petId, ...]`) — событие, добавленное или изменённое на любом из экранов, должно немедленно и одинаково отражаться на сетке календаря, в списке дня и на карточке питомца.

* Кэш сетки и списка дня также должен инвалидироваться при удалении и восстановлении питомца.

* pull-to-refresh перезапрашивает кэш сетки месяца за все подгруженные месяцы и кэш списка дня за выбранный день.
