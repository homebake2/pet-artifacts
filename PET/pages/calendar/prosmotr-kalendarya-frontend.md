## Назначение

Экран "Календарь" — основной способ для владельца просматривать историю событий здоровья своих питомцев: сеточный календарь месяца с индикатором количества событий на день и список карточек событий выбранного дня.

## Действующие лица и предусловия

* Пользователь авторизован и находится на вкладке "Календарь".

* Приложение поддерживает два режима работы: онлайн (данные с сервера) и офлайн (локальный кэш). Поведение офлайн-ветки (dataSource=local) описано на отдельной странице — см. [Просмотр календаря — Frontend (dataSource=local)](prosmotr-kalendarya-frontend-local.md).

## Основной сценарий

1. При открытии вкладки "Календарь" система выбирает текущую дату по умолчанию.

2. **Сетка месяца.** Онлайн: система запрашивает `GET /activities/calendar` одним запросом с параметрами `from`/`to` = границы месяца выбранной даты в часовом поясе устройства и `tz` = часовой пояс устройства (см. "Бизнес-правила и валидация"); ответ содержит количество элементов (фактов и незавершённых напоминаний) на каждый день месяца по всем питомцам пользователя сразу и признак `has_reminders`, без содержимого элементов. Офлайн: система использует локально сохранённые данные питомцев.

3. Календарная сетка отображает индикатор количества событий на каждый день месяца по полученным из `GET /activities/calendar` значениям `count`. День, для которого `has_reminders = true`, дополнительно отображает индикатор наличия напоминаний, визуально отличимый от индикатора количества событий (оформление определяется дизайн-системой приложения, здесь фиксируется только сам факт различимости и условие показа). День без незавершённых напоминаний (`has_reminders = false`) этот индикатор не показывает, даже если на день есть другие события.

4. **Список дня.** При выборе дня система отдельно запрашивает `GET /activities/day` с параметрами `date` = выбранный день в часовом поясе устройства и `tz` = часовой пояс устройства; ответ содержит полные факты и незавершённые напоминания всех питомцев пользователя за этот день одним списком (вид элемента — поле `item_type`: `event` или `reminder`), каждый — с массивом `pets` (`{pet_id, pet_name}`) для определения принадлежности питомцам: запись, привязанная к нескольким питомцам, приходит одним элементом (принадлежность не определяется параметром отдельного запроса на питомца — см. "Просмотр календаря — Backend").

5. При переходе на другой месяц система выполняет новый запрос `GET /activities/calendar` за этот месяц; при выборе другого дня в уже открытом месяце система выполняет новый запрос `GET /activities/day` для этого дня, не перезапрашивая сетку месяца.

6. Если на выбранный день событий нет, система показывает пустое состояние с понятным текстом.

6а. Если в списке выбранного дня достаточно записей и они различаются по типу, питомцу или виду животного, над списком имеется возможность отфильтровать его по типу события, питомцу и виду животного (см. «Фильтры списка дня»).

7. Имеется возможность перейти к добавлению события.

8. Изображение вида и название каждого питомца в карточке события система берёт из справочника видов питомцев (по элементам `pets` из ответа `GET /activities/day`). Карточка события для нескольких питомцев — одна: она показывает изображение вида и имя каждого привязанного питомца (см. [Общие требования: Несколько питомцев в событии и напоминании](../common/obschie-trebovaniya-neskolko-pitomtsev-v-zapisi.md)); запись учитывается на сетке месяца один раз. Обозначение и подпись типа события берутся из единого справочника типов событий — см. следующий раздел.

9. Имеется возможность вручную обновить данные экрана: действие обязано гарантированно инициировать повторный запрос `GET /activities/calendar` за все уже подгруженные месяцы и `GET /activities/day` за выбранный день, и показывать индикатор обновления до завершения всех запросов.

## Бизнес-правила и валидация

**Часовой пояс группировки и диапазона дат — часовой пояс устройства, а не UTC.** Календарный день события — это день его момента времени (`date_time`) в часовом поясе устройства: событие, записанное пользователем в UTC+3 на 00:30 27 сентября, отображается под 27-м числом, а не под 26-м. Единая конвенция для FE и BE: клиент передаёт имя часового пояса устройства (IANA, например `Europe/Moscow`) query-параметром `tz` в `GET /activities/calendar` и `GET /activities/day`, и backend группирует события по дням в этом же поясе (см. соответствующее требование на странице "Просмотр календаря — Backend"). Если среда не сообщает имя часового пояса устройства, в `tz` передаётся `UTC`. Конкретный алгоритм:

**1. Границы месяца для запроса `GET /activities/calendar`.** От выбранной пользователем даты берётся календарный месяц в локальном времени устройства. Затем вычисляются:

```
from = первый день локального месяца, формат YYYY-MM-DD (например, "2026-08-01")
to   = последний день локального месяца, формат YYYY-MM-DD (например, "2026-08-31")
tz   = часовой пояс устройства (например, "Europe/Moscow")
```

UTC-компоненты даты (`getUTCFullYear`, `getUTCMonth`) для этого расчёта не используются, иначе возле полуночи по местному времени граница месяца разъедется с ячейками сетки, которые строятся в локальном времени устройства.

**2. Выбранный день для запроса `GET /activities/day`.** Дата `date` вычисляется по локальным компонентам выбранной пользователем даты (год, месяц, день в часовом поясе устройства), а не по UTC-компонентам — это гарантирует, что день, для которого запрошен список, совпадает с ячейкой сетки и с днём, под которым backend сгруппировал количество событий в ответе `GET /activities/calendar`.

**3. Отображение времени в карточке.** Дата и время события в карточке выводятся в часовом поясе устройства — том же, в котором событие отнесено к дню на сетке; формат даты и времени следует локали текущего языка интерфейса приложения, а не локали устройства.

* Питомец без событий в выбранном месяце не создаёт индикаторов на сетке, но не исключается из списка питомцев пользователя.

* Каждый тип события имеет обозначение и локализованную подпись, единые для календаря, формы добавления/редактирования события и графиков динамики — одно и то же событие нигде не выглядит по-разному. Список типов здесь не дублируется — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»; подписи берутся из общего справочника типов, см. [Общие требования: Единый источник enum-словарей](../common/obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md). Для типа `other` используется нейтральное обозначение «прочее».

* Для типа `vaccination` карточка показывает локализованное название типа («Вакцинация»), `value.name` и, если задан `value.vaccination_at` (дополнительное напоминание вакцинации), момент вакцинации в формате локали интерфейса; подписей текстом сервер не присылает.

* Карточка события отображает значение по форме `value`, соответствующей типу события (например, число с единицей измерения, выбранная категория, название лекарства с дозой), а не сырую строку и не JSON: `value` — типизированный объект, и его поля выводятся осмысленно, с единицей измерения и локализованной подписью категории. Конкретные формы `value` по каждому типу — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md); на этой странице они не дублируются.

* Карточка в списке дня (см. "Основной сценарий", шаг 4) по полю `item_type` отличает факт от напоминания: карточка напоминания показывает индикатор напоминания, карточка факта — нет — тот же принцип условного индикатора, что уже применяется к количеству файлов события (см. [Файлы события — Frontend](fayly-sobytiya-frontend.md), раздел «Отображение количества файлов в списке событий»). Напоминание, момент которого уже наступил, дополнительно отображается как требующее отметки (см. [Напоминания — Frontend](napominaniya-frontend.md), раздел «Отметка прошедшего напоминания»). Открытие карточки факта ведёт на редактирование события (см. [Редактирование события — Frontend](redaktirovanie-sobytiya-frontend.md)), открытие карточки напоминания — к изменению, отметке или удалению напоминания (см. [Напоминания — Frontend](napominaniya-frontend.md)). Количество файлов на карточке — `files_count` элемента.

* Индикатор дня с напоминаниями на сетке месяца (см. "Основной сценарий", шаг 3) и индикатор напоминания на карточке в списке дня — два независимых, но согласованных отображения одного и того же факта (`has_reminders` на уровне дня — агрегат: в дне есть хотя бы одно незавершённое напоминание): пользователь видит на сетке, что в дне есть напоминание, а открыв список дня — на какой именно карточке. Индикатор на сетке должен визуально отличаться от обычного индикатора количества событий настолько, чтобы оба состояния (просто «есть события» и «есть напоминания») были различимы одновременно на одном дне.

## Фильтры списка дня

Общие правила (комбинирование, порог доступности, выбор значений, отображение активных фильтров, сброс) — см. [Общие требования: Фильтры списков событий](../common/obschie-trebovaniya-filtry-spiskov-sobytii.md). В списке дня применяются фильтры «тип события», «питомец» и «вид животного» (все — многовыбор).

* Список дня (`GET /activities/day`) не пагинируется: ответ содержит все элементы дня, поэтому фильтры применяются на клиенте к уже полученному списку без дополнительных запросов. Если список дня в будущем станет постраничным, фильтры переносятся на сервер по тому же принципу, что на экране «События питомца» (серверные параметры и блок доступных значений вне зависимости от выбора) — до тех пор клиентская фильтрация допустима только потому, что в списке уже есть все элементы дня.

* Фильтры действуют на оба вида элементов — факты и напоминания: тип напоминания берётся из его настроек (поле `type`), питомцы — из `pets`.

* Доступность каждого фильтра определяется по всему списку выбранного дня (без учёта выбранных фильтров): элементов строго больше 5, и в списке не менее двух различных значений (типов, питомцев, видов животного — вид берётся из `pets[].species`). Пример: 10 записей одного питомца — фильтр по питомцу и по виду не показывается; фильтр по типу показывается, если типов не меньше двух. Если не доступен ни один фильтр, область фильтров не отображается.

* Значения «питомец» и «вид животного» отображаются так же, как на карточке события: название питомца и локализованное название вида из справочника видов (см. «Справочник значений (словари enum)»).

* Выбор фильтров относится к конкретному дню: при выборе другого дня, переходе на другой месяц и повторном открытии вкладки выбор сбрасывается (набор значений и их число зависят от дня). Ручное обновление данных выбор не сбрасывает; значения, которых больше нет в списке дня, убираются из выбора.

* Фильтры не влияют на сетку месяца: индикаторы количества событий и напоминаний на днях показывают все элементы дня независимо от выбранных фильтров.

* Пустой результат фильтрации отличается от пустого дня: показывается «Ничего не найдено» с возможностью сбросить фильтры (на день без событий фильтры не показываются). Отметка и редактирование, добавление и удаление элементов работают так же, как без фильтров; после добавления элемента, не подходящего под выбранные фильтры, он в отфильтрованном списке не показывается, пока фильтры не сброшены.

## Обработка ошибок

* Пока запрос `GET /activities/calendar` выполняется, система не показывает отдельного индикатора загрузки сетки: сетка отображается сразу, без смещения вёрстки, а точки дней появляются по приходу данных. Пока запрос `GET /activities/day` выполняется, система должна показывать отдельный индикатор загрузки в блоке списка дня, не блокируя этим уже отрисованную сетку.

* Ошибка `GET /activities/calendar` показывает точечный индикатор ошибки на сетке с возможностью повторить запрос, не блокируя остальной экран. Ошибка `GET /activities/day` показывает точечный индикатор ошибки в блоке списка дня с возможностью повторить запрос только за этот день, не влияя на уже отрисованную сетку месяца.

* Если у пользователя нет питомцев, система показывает пустой календарь без ошибок.

* При переходе из офлайн в онлайн (и обратно) система должна использовать актуальный для текущего режима источник данных при следующем обращении к серверу/локальному хранилищу; явного специального экрана перехода не требуется.

## Хранение состояния и побочные эффекты

* Данные сетки месяца кэшируются в React Query по единому ключу вида `['activities-calendar', 'month', 'YYYY-MM', tz]`. Данные списка дня кэшируются по ключу вида `['activities-day', 'date', 'YYYY-MM-DD', tz]`. `YYYY-MM` и `YYYY-MM-DD` — локальные месяц и день устройства, `tz` — часовой пояс устройства: один и тот же месяц/день в разных поясах — разные данные, поэтому после смены часового пояса устройства сетка и список дня запрашиваются заново, а не берутся из кэша, сгруппированного в прежнем поясе. Инвалидация по префиксу (`['activities-calendar', ...]`, `['activities-day', ...]`) сбрасывает кэш всех поясов разом. Превью событий на карточке питомца и экран «События питомца» (`GET /pet/{id}/events`) используют отдельные кэши, независимые от календаря (см. "Просмотр карточки питомца — Frontend" и "События питомца — Frontend").

* После успешного добавления, редактирования или удаления события система должна инвалидировать (или рефетчить) кэш сетки месяца (`['activities-calendar', ...]`) и кэш списка дня (`['activities-day', ...]`) для затронутого месяца/дня, а также кэши превью событий и списка «События питомца» затронутого питомца — событие, добавленное или изменённое на любом из экранов, должно немедленно и одинаково отражаться на сетке календаря, в списке дня и на экране питомца. Оптимистично патчатся только кэши списков (см. [Общие требования: Оптимистичные обновления (dataSource=network)](../common/obschie-trebovaniya-optimistichnye-obnovleniya.md)); кэш детали события обновляется инвалидацией/refetch после подтверждения.

* Кэш сетки и списка дня также должен инвалидироваться при удалении и восстановлении питомца.

* Ручное обновление перезапрашивает кэш сетки месяца за все подгруженные месяцы и кэш списка дня за выбранный день.
