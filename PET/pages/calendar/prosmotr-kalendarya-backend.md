## Назначение

Флоу отдаёт события здоровья питомца для построения экрана календаря: точки-индикаторы на сетке месяца и список событий выбранного дня, сгруппированные по календарным дням за запрошенный диапазон дат.

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь с профилем (валидный access-токен).

* Запрашиваемый питомец должен принадлежать профилю инициатора; иначе система должна отвечать так же, как и на запрос несуществующего питомца (см. "Обработка ошибок"), в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

## Основной сценарий

1. `GET /activities`, query: `pet_id` (uuid, обязателен), `from`, `to` (YYYY-MM-DD, обязательны), заголовок Authorization обязателен.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат pet_id, from, to.

4. Система проверяет, что диапазон from..to не превышает 366 дней.

5. Система проверяет авторизацию и определяет profile_id.

6. Система проверяет, что питомец с указанным pet_id существует и принадлежит профилю инициатора.

7. Система получает имя питомца и все его события, дата которых попадает в диапазон [from, to] включительно. Границы диапазона и дата события (`date_time`) трактуются и сравниваются в UTC — см. "Бизнес-правила и валидация".

8. Система группирует события по календарному дню (в UTC) и строит по одному элементу items на каждый день диапазона (включая дни без событий, с пустым списком событий на такой день).

9. Система возвращает 200 OK с телом {"pet_name": string, "items": [...]}.

Связанные эндпоинты чтения событий с иной областью применения:

* `GET /events/{id}` — карточка одного события по его идентификатору; возвращает 404, если событие не найдено, принадлежит чужому питомцу или мягко удалено (`deleted_at IS NOT NULL`).

* `GET /pet/{id}/events` — плоский список всех событий питомца без фильтра по датам и без группировки по дням. Эндпоинт сохраняется как задел на будущий сценарий ("вся история питомца" без разбивки по месяцам) и на момент актуализации данных требований не используется ни одним экраном фронтенда; ведёт себя так же, как GET /activities, в части проверки принадлежности питомца и фильтрации мягко удалённых записей (см. ниже).

## Бизнес-правила и валидация

**Часовой пояс — UTC.** Столбец `event.date_time` имеет тип `timestamptz` (PostgreSQL): значение хранится с учётом часового пояса и при любом чтении/сравнении автоматически приводится к UTC движком БД — конвертация вручную на уровне запроса не требуется, но сравнение диапазона всё равно строится по явным UTC-границам (см. ниже), а не по подразумеваемому часовому поясу сессии.

**Граница диапазона from/to.** Параметры `from`/`to` приходят в формате `YYYY-MM-DD` без времени и часового пояса. Сервер трактует их как календарные даты в UTC и строит полуоткрытый интервал:

```
date_time >= (from || 'T00:00:00Z')::timestamptz
  AND date_time < ((to::date + 1) || 'T00:00:00Z')::timestamptz
```

То есть нижняя граница — начало суток `from` в UTC (00:00:00Z включительно), верхняя граница — начало суток, следующих за `to` в UTC (00:00:00Z исключительно). Такая форма (`>=` ... `<`) корректно включает весь день `to` целиком, в отличие от `<=` to 23:59:59, которое ломается на событии, произошедшем ровно в полночь следующего дня по UTC.

**Группировка по дню.** Календарный день события для группировки в ответе `GET /activities` вычисляется как `date_time AT TIME ZONE 'UTC'`, приведённое к дате (`::date`) — то есть день определяется исключительно по UTC-представлению момента времени, независимо от того, в каком смещении событие было изначально записано клиентом.

* Диапазон from..to в /activities не должен превышать 366 дней; более длинный диапазон — ошибка валидации, а не молчаливое обрезание.

* from позже to — ошибка валидации (400), а не пустой успешный ответ.

* Поле type каждого события — одно из 6 фиксированных значений (weight, urine, defecation, vomit, diarrhea, other, см. [Общие требования: Единый источник enum-словарей](../common/obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md)); на чтении дополнительная валидация не требуется, так как значение уже провалидировано при создании/редактировании события.

* Мягко удалённые питомцы не должны попадать в результаты ни одного из перечисленных эндпоинтов чтения событий — обращение к мягко удалённому питомцу обрабатывается так же, как обращение к несуществующему питомцу.

* Мягко удалённые события (`deleted_at IS NOT NULL`) должны исключаться из всех трёх эндпоинтов чтения (`/activities`, `/events/{id}`, `/pet/{id}/events`) — фильтр `deleted_at IS NULL` обязателен во всех выборках событий, см. задачу PET-137 на странице "Удаление события — Backend" и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md).

## Обработка ошибок

| Статус | Условие                                                                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 405    | Метод запроса не GET                                                                                                           |
| 400    | Отсутствует обязательный параметр / некорректный формат даты или pet_id / from позже to / диапазон from..to превышает 366 дней |
| 401    | Токен авторизации отсутствует или недействителен                                                                               |
| 404    | Питомец с указанным pet_id не найден, принадлежит другому профилю или мягко удалён                                             |
| 500    | Внутренняя ошибка при определении профиля, проверке принадлежности питомца или получении событий                               |

Во всех трёх эндпоинтах чтения событий (/activities, /events/{id}, /pet/{id}/events) обращение к чужому или несуществующему питомцу/событию должно давать одинаковый результат — 404 Not Found. Единообразие исключает ситуацию, когда клиент не может отличить "у питомца действительно нет событий" от "питомца не существует или он не мой".

## Хранение состояния и побочные эффекты

Эндпоинт идемпотентен и только читает данные; побочных эффектов на состояние системы нет.

## Известные ограничения MVP

* Экран календаря делает один запрос `GET /activities` на каждого питомца пользователя параллельно — число запросов растёт линейно с количеством питомцев. Для MVP это сознательно принятое ограничение, см. задачу PET-121 ниже. На будущее возможное решение — batch-эндпоинт, принимающий несколько pet_id за один запрос и возвращающий сгруппированные по питомцам активности одним ответом.
