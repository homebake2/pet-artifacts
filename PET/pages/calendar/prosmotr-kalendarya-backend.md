## Назначение

Флоу отдаёт данные о событиях здоровья питомцев для двух разных представлений экрана календаря и для блока событий карточки питомца — каждое своим эндпоинтом с минимальной по объёму формой ответа под конкретное представление:

* **Сетка месяца календаря** (`GET /activities/calendar`) — только количество событий на каждый день диапазона по всем питомцам пользователя, без содержимого самих событий.

* **Список событий выбранного дня в календаре** (`GET /activities/day`) — полные события всех питомцев пользователя за один день, одним запросом.

* **Блок событий на карточке питомца** (`GET /activities`) — полные события одного питомца за диапазон дат.

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь (валидный access-токен). Наличие строки в таблице `profile` не требуется.

* `GET /activities/calendar` и `GET /activities/day` отдают данные по всем питомцам инициатора сразу: параметр `pet_id` они не принимают, принадлежность питомцев инициатору проверяется неявно через `user_id`, а не через явную проверку конкретного ресурса по id.

* `GET /activities` требует конкретного `pet_id`; запрашиваемый питомец должен принадлежать инициатору, иначе система должна отвечать так же, как и на запрос несуществующего питомца (см. "Обработка ошибок"), в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

## Основной сценарий

### A. `GET /activities/calendar` — количество событий по дням (сетка календаря)

1. `GET /activities/calendar`, query: `from`, `to` (YYYY-MM-DD, обязательны), заголовок Authorization обязателен. Параметр `pet_id` не принимается.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат from, to.

4. Система проверяет, что диапазон from..to не превышает 366 дней.

5. Система проверяет авторизацию и извлекает userID.

6. Система вычисляет для каждого календарного дня диапазона [from, to] количество событий (`COUNT(*)`), принадлежащих всем не мягко удалённым питомцам userID, без выборки самих событий. Границы диапазона и календарный день трактуются так же, как в "Бизнес-правила и валидация" ниже (те же правила, что и у `GET /activities`).

7. Ответ содержит по одному элементу на каждый день диапазона, включая дни без событий (`count: 0`) — диапазон не должен иметь "дыр".

8. Система возвращает 200 OK с телом `{"items": [{"date": "YYYY-MM-DD", "count": number}, ...]}`.

### B. `GET /activities/day` — все события всех питомцев за один день

1. `GET /activities/day`, query: `date` (YYYY-MM-DD, обязателен), заголовок Authorization обязателен. Параметр `pet_id` не принимается.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат date.

4. Система проверяет авторизацию и извлекает userID.

5. Система выбирает все события всех не мягко удалённых питомцев userID, чей календарный день (в UTC) равен date. Мягко удалённые события исключаются.

6. Каждый элемент `items` содержит те же поля события, что и элемент `events` внутри дня в ответе `GET /activities` — `id`, `date`, `type`, `notes`, `value`, `files_count` (см. [Файлы события — Backend](fayly-sobytiya-backend.md)) — и дополнительно `pet_id` и `pet_name`: в отличие от `GET /activities`, где принадлежность единственному запрошенному питомцу определяется параметром запроса, а не полем в самом событии, здесь в одном списке смешаны события разных питомцев, и клиенту нужно поле в объекте события, чтобы определить, какому питомцу оно принадлежит и подставить его иконку/название вида (см. «Просмотр календаря — Frontend»).

7. Элементы `items` сортируются по `date_time` по возрастанию.

8. Система возвращает 200 OK с телом `{"date": "YYYY-MM-DD", "items": [...]}`.

### C. `GET /activities` — события одного питомца (карточка питомца)

1. `GET /activities`, query: `pet_id` (uuid, обязателен), `from`, `to` (YYYY-MM-DD, обязательны), заголовок Authorization обязателен.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат pet_id, from, to.

4. Система проверяет, что диапазон from..to не превышает 366 дней.

5. Система проверяет авторизацию и извлекает userID.

6. Система проверяет, что питомец с указанным pet_id существует и принадлежит инициатору (`pet.user_id`).

7. Система получает имя питомца и все его события, дата которых попадает в диапазон [from, to] включительно. Границы диапазона и дата события (`date_time`) трактуются и сравниваются в UTC — см. "Бизнес-правила и валидация".

8. Система группирует события по календарному дню (в UTC) и строит по одному элементу items на каждый день диапазона (включая дни без событий, с пустым списком событий на такой день).

9. Система возвращает 200 OK с телом {"pet_name": string, "items": [...]}.

Область применения этого эндпоинта — блок событий карточки питомца; экран календаря использует `GET /activities/calendar` и `GET /activities/day` (см. выше), а не этот эндпоинт.

Связанные эндпоинты чтения событий с иной областью применения:

* `GET /events/{id}` — карточка одного события по его идентификатору; возвращает 404, если событие не найдено, принадлежит питомцу другого пользователя или мягко удалено (`deleted_at IS NOT NULL`).

* `GET /pet/{id}/events` — плоский список всех событий питомца без фильтра по датам и без группировки по дням. Эндпоинт сохраняется как задел на будущий сценарий ("вся история питомца" без разбивки по месяцам) и на момент актуализации данных требований не используется ни одним экраном фронтенда; ведёт себя так же, как GET /activities, в части проверки принадлежности питомца и фильтрации мягко удалённых записей (см. ниже).

## Бизнес-правила и валидация

**Часовой пояс — UTC.** Столбец `event.date_time` имеет тип `timestamptz` (PostgreSQL): значение хранится с учётом часового пояса и при любом чтении/сравнении автоматически приводится к UTC движком БД — конвертация вручную на уровне запроса не требуется, но сравнение диапазона всё равно строится по явным UTC-границам (см. ниже), а не по подразумеваемому часовому поясу сессии. Это правило единое для `GET /activities`, `GET /activities/calendar` и `GET /activities/day`.

**Граница диапазона from/to** (`GET /activities`, `GET /activities/calendar`). Параметры `from`/`to` приходят в формате `YYYY-MM-DD` без времени и часового пояса. Сервер трактует их как календарные даты в UTC и строит полуоткрытый интервал:

```
date_time >= (from || 'T00:00:00Z')::timestamptz
  AND date_time < ((to::date + 1) || 'T00:00:00Z')::timestamptz
```

То есть нижняя граница — начало суток `from` в UTC (00:00:00Z включительно), верхняя граница — начало суток, следующих за `to` в UTC (00:00:00Z исключительно). Такая форма (`>=` ... `<`) корректно включает весь день `to` целиком, в отличие от `<=` to 23:59:59, которое ломается на событии, произошедшем ровно в полночь следующего дня по UTC.

**Граница дня** (`GET /activities/day`). Параметр `date` трактуется так же, как один день диапазона `GET /activities`/`GET /activities/calendar`: полуоткрытый интервал `date_time >= (date || 'T00:00:00Z')::timestamptz AND date_time < ((date::date + 1) || 'T00:00:00Z')::timestamptz`.

**Группировка/фильтрация по дню.** Календарный день события для группировки в ответе `GET /activities`, для подсчёта в `GET /activities/calendar` и для фильтрации в `GET /activities/day` вычисляется одинаково — как `date_time AT TIME ZONE 'UTC'`, приведённое к дате (`::date`) — то есть день определяется исключительно по UTC-представлению момента времени, независимо от того, в каком смещении событие было изначально записано клиентом.

* Диапазон from..to в `GET /activities` и `GET /activities/calendar` не должен превышать 366 дней; более длинный диапазон — ошибка валидации, а не молчаливое обрезание. `GET /activities/day` принимает одну дату и этому ограничению не подчиняется.

* from позже to (`GET /activities`, `GET /activities/calendar`) — ошибка валидации (400), а не пустой успешный ответ.

* Поле type каждого события (`GET /activities`, `GET /activities/day`) — одно из значений справочника типов события (см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»); список значений здесь не дублируется. На чтении дополнительная валидация не требуется, так как значение уже провалидировано при создании/редактировании события.

* Поле `value` каждого события (`GET /activities`, `GET /activities/day`) — типизированный объект, форма которого определяется `type` (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)). Эндпоинты чтения отдают `value` как есть: они не преобразуют его, не «уплощают» в строку и не достраивают отсутствующие поля — клиент получает ровно ту структуру, которая была сохранена при создании/редактировании события.

* Мягко удалённые питомцы не должны попадать в результаты ни одного из перечисленных эндпоинтов чтения событий (`GET /activities`, `GET /activities/calendar`, `GET /activities/day`, `GET /events/{id}`, `GET /pet/{id}/events`) — обращение к мягко удалённому питомцу по `pet_id` (там, где он есть) обрабатывается так же, как обращение к несуществующему питомцу; в `GET /activities/calendar`/`GET /activities/day`, где `pet_id` не запрашивается, события мягко удалённых питомцев исключаются фильтром без отдельной ошибки.

* Мягко удалённые события (`deleted_at IS NOT NULL`) должны исключаться из всех пяти эндпоинтов чтения (`/activities`, `/activities/calendar`, `/activities/day`, `/events/{id}`, `/pet/{id}/events`) — фильтр `deleted_at IS NULL` обязателен во всех выборках событий, см. страницу "Удаление события — Backend" и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md).

## Обработка ошибок

`GET /activities/calendar`:

| Статус | Условие                                                                             |
| ------ | ------------------------------------------------------------------------------------ |
| 405    | Метод запроса не GET                                                                  |
| 400    | Отсутствует обязательный параметр / некорректный формат даты / from позже to / диапазон from..to превышает 366 дней |
| 401    | Токен авторизации отсутствует или недействителен                                     |
| 500    | Внутренняя ошибка при подсчёте событий                                               |

`GET /activities/day`:

| Статус | Условие                                                             |
| ------ | -------------------------------------------------------------------- |
| 405    | Метод запроса не GET                                                 |
| 400    | Отсутствует обязательный параметр date / некорректный формат даты    |
| 401    | Токен авторизации отсутствует или недействителен                     |
| 500    | Внутренняя ошибка при получении событий                              |

Ни `GET /activities/calendar`, ни `GET /activities/day` не возвращают 404: они не адресуют конкретный ресурс по id, а агрегируют/выбирают данные по всем питомцам инициатора — пользователь без питомцев или без событий получает 200 с пустым результатом (`count: 0` по всем дням / пустой `items`), а не ошибку.

`GET /activities`:

| Статус | Условие                                                                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 405    | Метод запроса не GET                                                                                                           |
| 400    | Отсутствует обязательный параметр / некорректный формат даты или pet_id / from позже to / диапазон from..to превышает 366 дней |
| 401    | Токен авторизации отсутствует или недействителен                                                                               |
| 404    | Питомец с указанным pet_id не найден, принадлежит другому пользователю или мягко удалён                                        |
| 500    | Внутренняя ошибка при проверке принадлежности питомца или получении событий                                                    |

Во всех эндпоинтах чтения событий, адресующих конкретный ресурс по id (`/activities` — по `pet_id`, `/events/{id}`, `/pet/{id}/events`), обращение к чужому или несуществующему питомцу/событию должно давать одинаковый результат — 404 Not Found. Единообразие исключает ситуацию, когда клиент не может отличить "у питомца действительно нет событий" от "питомца не существует или он не мой".

## Хранение состояния и побочные эффекты

Все три эндпоинта (`GET /activities`, `GET /activities/calendar`, `GET /activities/day`) идемпотентны и только читают данные; побочных эффектов на состояние системы нет.
