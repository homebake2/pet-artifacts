## Назначение

Флоу отдаёт данные о событиях здоровья питомцев для двух разных представлений экрана календаря и для блока событий карточки питомца — каждое своим эндпоинтом с минимальной по объёму формой ответа под конкретное представление.

Календарь показывает элементы двух видов: **факты** (`event`, уже произошедшие события) и **напоминания** (`reminder`, незавершённые — см. [Напоминания — Backend](napominaniya-backend.md); настройки напоминания в календаре не показываются). Остальные эндпоинты отдают только факты.

* **Сетка месяца календаря** (`GET /activities/calendar`) — количество элементов (фактов и незавершённых напоминаний) на каждый день диапазона по всем питомцам пользователя и признак того, что в этот день есть хотя бы одно незавершённое напоминание, без содержимого самих элементов.

* **Список выбранного дня в календаре** (`GET /activities/day`) — полные факты и незавершённые напоминания всех питомцев пользователя за один день, одним запросом.

* **Блок событий на карточке питомца** (`GET /activities`) — полные факты одного питомца за диапазон дат.

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь (валидный access-токен). Наличие строки в таблице `profile` не требуется.

* `GET /activities/calendar` и `GET /activities/day` отдают данные по всем питомцам инициатора сразу: параметр `pet_id` они не принимают, принадлежность питомцев инициатору проверяется неявно через `user_id`, а не через явную проверку конкретного ресурса по id.

* `GET /activities` требует конкретного `pet_id`; запрашиваемый питомец должен принадлежать инициатору, иначе система должна отвечать так же, как и на запрос несуществующего питомца (см. "Обработка ошибок"), в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

## Основной сценарий

### A. `GET /activities/calendar` — количество событий по дням (сетка календаря)

1. `GET /activities/calendar`, query: `from`, `to` (YYYY-MM-DD, обязательны), `tz` (имя часового пояса IANA, обязателен), заголовок Authorization обязателен. Параметр `pet_id` не принимается.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат from, to, а также наличие и корректность tz.

4. Система проверяет, что диапазон from..to не превышает 366 дней.

5. Система проверяет авторизацию и извлекает userID.

6. Система вычисляет для каждого календарного дня диапазона [from, to] количество элементов (фактов `event` плюс незавершённых напоминаний `reminder`) и признак `has_reminders` (существует ли в этот день хотя бы одно незавершённое напоминание), принадлежащих всем не мягко удалённым питомцам userID, без выборки самих элементов. День напоминания определяется по его `remind_at` так же, как день факта — по `date_time`. Границы диапазона и календарный день трактуются так же, как в "Бизнес-правила и валидация" ниже (те же правила, что и у `GET /activities`).

7. Ответ содержит по одному элементу на каждый день диапазона, включая дни без событий (`count: 0`, `has_reminders: false`) — диапазон не должен иметь "дыр".

8. Система возвращает 200 OK с телом `{"items": [{"date": "YYYY-MM-DD", "count": number, "has_reminders": boolean}, ...]}`.

### B. `GET /activities/day` — все события всех питомцев за один день

1. `GET /activities/day`, query: `date` (YYYY-MM-DD, обязателен), `tz` (имя часового пояса IANA, обязателен), заголовок Authorization обязателен. Параметр `pet_id` не принимается.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат date, а также наличие и корректность tz.

4. Система проверяет авторизацию и извлекает userID.

5. Система выбирает все факты и все незавершённые напоминания всех не мягко удалённых питомцев userID, чей календарный день (в часовом поясе `tz`) равен date. Мягко удалённые факты исключаются; закрытые напоминания (`closed_at IS NOT NULL`) не выбираются. Незавершённое напоминание, момент которого уже наступил, выбирается и отдаётся наравне с будущими — оно остаётся в календаре, пока пользователь его не закроет.

6. Каждый элемент `items` содержит поле `item_type` — `event` (факт) или `reminder` (напоминание) — и те же поля, что и элемент `events` внутри дня в ответе `GET /activities` — `id`, `date`, `type`, `notes`, `value`, `files_count` (см. [Файлы события — Backend](fayly-sobytiya-backend.md)) — и дополнительно `pet_id` и `pet_name`. Для `reminder`: `id` — идентификатор напоминания, `date` — его `remind_at`, `type`/`value`/`pet_id`/`pet_name` — из его настроек, `notes` — собственная заметка напоминания, а при её отсутствии — заметка настроек (см. «Напоминания — Backend», раздел «Заметка напоминания»), `files_count` — число файлов настроек плюс собственных файлов напоминания, и дополнительно поля `plan_id`, `plan_source`, `plan_source_title` (источник настроек и его название, см. «Напоминания — Backend», раздел «Источник настроек»; название — `null` при `manual`) и `plan_unclosed_count` (сколько незавершённых напоминаний у настроек, включая это — то же значение, что в `GET /reminders/{id}`). Поля настроек отдаются в списке, чтобы клиент выбирал «это / все» при открытии и удалении напоминания без отдельного запроса. Зачем `pet_id` и `pet_name`: в отличие от `GET /activities`, где принадлежность единственному запрошенному питомцу определяется параметром запроса, а не полем в самом событии, здесь в одном списке смешаны события разных питомцев, и клиенту нужно поле в объекте события, чтобы определить, какому питомцу оно принадлежит и подставить его иконку/название вида (см. «Просмотр календаря — Frontend»).

7. Элементы `items` (факты и напоминания вместе) сортируются по `date_time` (для напоминания — `remind_at`) по возрастанию, при равном значении — по `id` по возрастанию.

8. Система возвращает 200 OK с телом `{"date": "YYYY-MM-DD", "items": [...]}`.

### C. `GET /activities` — события одного питомца (карточка питомца)

1. `GET /activities`, query: `pet_id` (uuid, обязателен), `from`, `to` (YYYY-MM-DD, обязательны), `tz` (имя часового пояса IANA, обязателен), заголовок Authorization обязателен.

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат pet_id, from, to, а также наличие и корректность tz.

4. Система проверяет, что диапазон from..to не превышает 366 дней.

5. Система проверяет авторизацию и извлекает userID.

6. Система проверяет, что питомец с указанным pet_id существует и принадлежит инициатору (`pet.user_id`).

7. Система получает имя питомца и все его события, дата которых попадает в диапазон [from, to] включительно. Границы диапазона трактуются как календарные даты в часовом поясе `tz` — см. "Бизнес-правила и валидация".

8. Система группирует события по календарному дню (в часовом поясе `tz`) и строит по одному элементу items на каждый день диапазона (включая дни без событий, с пустым списком событий на такой день).

9. Система возвращает 200 OK с телом {"pet_name": string, "items": [...]}.

Область применения этого эндпоинта — блок событий карточки питомца; экран календаря использует `GET /activities/calendar` и `GET /activities/day` (см. выше), а не этот эндпоинт.

Связанные эндпоинты чтения событий с иной областью применения:

* `GET /events/{id}` — карточка одного события по его идентификатору; возвращает 404, если событие не найдено, принадлежит питомцу другого пользователя или мягко удалено (`deleted_at IS NOT NULL`).

* `GET /pet/{id}/events` — все события питомца без фильтра по датам и без группировки по дням, с постраничной выдачей (`limit`/`offset`) и опциональным текстовым фильтром `search`; используется превью-блоком событий на карточке питомца и отдельным экраном полного списка событий питомца с бесконечной пагинацией — см. «Просмотр карточки питомца — Backend» (там же — актуальный контракт запроса/ответа этого эндпоинта, включая поле `total`). Ведёт себя так же, как GET /activities, в части проверки принадлежности питомца и фильтрации мягко удалённых записей (см. ниже).

## Бизнес-правила и валидация

**Часовой пояс — пояс клиента из параметра `tz`.** `GET /activities`, `GET /activities/calendar` и `GET /activities/day` принимают обязательный query-параметр `tz` — имя часового пояса IANA (например, `Europe/Moscow`), в котором клиент видит календарь. Календарные даты `from`/`to`/`date` трактуются как локальные даты этого пояса, а календарный день события определяется по его `date_time`, переведённому в этот пояс. Значения по умолчанию нет: отсутствующий `tz`, неизвестное имя пояса, а также значение `Local` (пояс процесса сервера, не имеющий смысла для клиента) — ошибка валидации (400 `VALIDATION_ERROR`), а не молчаливая подстановка UTC. Распознавание имени пояса не должно зависеть от наличия системной базы часовых поясов в окружении деплоя — база IANA поставляется вместе с сервисом. Столбец `event.date_time` имеет тип `timestamptz` (PostgreSQL) и хранит момент времени; сами моменты времени событий в ответах отдаются в UTC — `tz` влияет только на границы выборки и на то, к какому дню отнесено событие. Это правило единое для `GET /activities`, `GET /activities/calendar` и `GET /activities/day`.

**Граница диапазона from/to** (`GET /activities`, `GET /activities/calendar`). Параметры `from`/`to` приходят в формате `YYYY-MM-DD` без времени и часового пояса. Сервер трактует их как календарные даты в поясе `tz` и строит полуоткрытый интервал моментов времени:

```
date_time >= начало суток from по местному времени tz
  AND date_time < начало суток, следующих за to, по местному времени tz
```

То есть нижняя граница — полночь `from` в поясе `tz` (включительно), верхняя граница — полночь суток, следующих за `to`, в поясе `tz` (исключительно). Такая форма (`>=` ... `<`) корректно включает весь день `to` целиком, в отличие от `<=` to 23:59:59, которое ломается на событии, произошедшем ровно в полночь следующего дня. Сутки берутся по местному времени пояса, поэтому в день перехода на летнее/зимнее время они длятся 23 или 25 часов.

**Граница дня** (`GET /activities/day`). Параметр `date` трактуется так же, как один день диапазона `GET /activities`/`GET /activities/calendar`: полуоткрытый интервал от полуночи `date` в поясе `tz` (включительно) до полуночи следующих суток в поясе `tz` (исключительно).

**Группировка/фильтрация по дню.** Календарный день события для группировки в ответе `GET /activities`, для подсчёта в `GET /activities/calendar` и для фильтрации в `GET /activities/day` вычисляется одинаково — как календарная дата момента `date_time`, переведённого в пояс `tz`, — то есть день определяется местным временем пояса клиента, независимо от того, в каком смещении событие было изначально записано клиентом. Пояс для границ диапазона и для группировки по дням интерпретируется сервисом по одной и той же базе часовых поясов, по которой проверяется корректность `tz`.

* Диапазон from..to в `GET /activities` и `GET /activities/calendar` не должен превышать 366 дней; более длинный диапазон — ошибка валидации, а не молчаливое обрезание. `GET /activities/day` принимает одну дату и этому ограничению не подчиняется.

* from позже to (`GET /activities`, `GET /activities/calendar`) — ошибка валидации (400), а не пустой успешный ответ.

* Поле type каждого события (`GET /activities`, `GET /activities/day`) — одно из значений справочника типов события (см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»); список значений здесь не дублируется. На чтении дополнительная валидация не требуется, так как значение уже провалидировано при создании/редактировании события.

* Поле `value` каждого события (`GET /activities`, `GET /activities/day`) — типизированный объект, форма которого определяется `type` (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)). Эндпоинты чтения отдают `value` как есть: они не преобразуют его, не «уплощают» в строку и не достраивают отсутствующие поля — клиент получает ровно ту структуру, которая была сохранена при создании/редактировании события.

* У фактов (`event`) нет полей уведомлений. Агрегат `has_reminders` в ответе `GET /activities/calendar` — производное значение (существование хотя бы одного незавершённого напоминания в этот день), а не поле конкретного элемента; `GET /activities/calendar` не возвращает содержимое самих элементов.

* Эндпоинты `GET /activities`, `GET /events/{id}`, `GET /pet/{id}/events` и `GET /events/stats` (графики) возвращают только факты: напоминания и их настройки в них не участвуют. Напоминание читается отдельно — `GET /reminders/{id}` и `GET /reminder-plans/{id}` (см. [Напоминания — Backend](napominaniya-backend.md)).

* Закрытые напоминания и настройки напоминаний ни в одном из эндпоинтов чтения календаря не отдаются. Для напоминаний также действует фильтр по не мягко удалённым питомцам; фильтр `deleted_at IS NULL` к ним не применяется — у напоминаний нет мягкого удаления (они удаляются жёстко).

* Мягко удалённые питомцы не должны попадать в результаты ни одного из перечисленных эндпоинтов чтения событий (`GET /activities`, `GET /activities/calendar`, `GET /activities/day`, `GET /events/{id}`, `GET /pet/{id}/events`) — обращение к мягко удалённому питомцу по `pet_id` (там, где он есть) обрабатывается так же, как обращение к несуществующему питомцу; в `GET /activities/calendar`/`GET /activities/day`, где `pet_id` не запрашивается, события мягко удалённых питомцев исключаются фильтром без отдельной ошибки.

* Мягко удалённые события (`deleted_at IS NOT NULL`) должны исключаться из всех пяти эндпоинтов чтения (`/activities`, `/activities/calendar`, `/activities/day`, `/events/{id}`, `/pet/{id}/events`) — фильтр `deleted_at IS NULL` обязателен во всех выборках событий, см. страницу "Удаление события — Backend" и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md).

## Обработка ошибок

`GET /activities/calendar`:

| Статус | Условие                                                                             |
| ------ | ------------------------------------------------------------------------------------ |
| 405    | Метод запроса не GET                                                                  |
| 400    | Отсутствует обязательный параметр / некорректный формат даты / отсутствует или некорректный часовой пояс tz / from позже to / диапазон from..to превышает 366 дней |
| 401    | Токен авторизации отсутствует или недействителен                                     |
| 500    | Внутренняя ошибка при подсчёте событий                                               |

`GET /activities/day`:

| Статус | Условие                                                             |
| ------ | -------------------------------------------------------------------- |
| 405    | Метод запроса не GET                                                 |
| 400    | Отсутствует обязательный параметр date / некорректный формат даты / отсутствует или некорректный часовой пояс tz |
| 401    | Токен авторизации отсутствует или недействителен                     |
| 500    | Внутренняя ошибка при получении событий                              |

Ни `GET /activities/calendar`, ни `GET /activities/day` не возвращают 404: они не адресуют конкретный ресурс по id, а агрегируют/выбирают данные по всем питомцам инициатора — пользователь без питомцев или без событий получает 200 с пустым результатом (`count: 0` по всем дням / пустой `items`), а не ошибку.

`GET /activities`:

| Статус | Условие                                                                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 405    | Метод запроса не GET                                                                                                           |
| 400    | Отсутствует обязательный параметр / некорректный формат даты или pet_id / отсутствует или некорректный часовой пояс tz / from позже to / диапазон from..to превышает 366 дней |
| 401    | Токен авторизации отсутствует или недействителен                                                                               |
| 404    | Питомец с указанным pet_id не найден, принадлежит другому пользователю или мягко удалён                                        |
| 500    | Внутренняя ошибка при проверке принадлежности питомца или получении событий                                                    |

Во всех эндпоинтах чтения событий, адресующих конкретный ресурс по id (`/activities` — по `pet_id`, `/events/{id}`, `/pet/{id}/events`), обращение к чужому или несуществующему питомцу/событию должно давать одинаковый результат — 404 Not Found. Единообразие исключает ситуацию, когда клиент не может отличить "у питомца действительно нет событий" от "питомца не существует или он не мой".

## Хранение состояния и побочные эффекты

Все три эндпоинта (`GET /activities`, `GET /activities/calendar`, `GET /activities/day`) идемпотентны и только читают данные; побочных эффектов на состояние системы нет.
