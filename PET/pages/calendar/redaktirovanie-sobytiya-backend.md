## Назначение

Флоу изменяет одно или несколько полей уже существующего события без создания новой записи и без изменения владельца-питомца.

## Действующие лица и предусловия

* Авторизованный владелец питомца, связанного с событием. Наличие строки в таблице `profile` не требуется.

* Событие существует, не мягко удалено (`deleted_at IS NULL`); питомец, которому оно принадлежит, принадлежит инициатору и не мягко удалён.

## Основной сценарий

1. `PATCH /events/{id}`. Тело: pet_id (обязательное, используется для сверки прав доступа), date/type/notes/value (каждое опционально по отдельности, но хотя бы одно должно быть передано).

2. Система разбирает id из пути — при ошибке возвращает 400.

3. Система проверяет авторизацию и извлекает userID.

4. Система находит неудалённое событие (`deleted_at IS NULL`) по id — если не найдено (в т.ч. если событие мягко удалено), возвращает 404, см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md).

5. Система разбирает тело запроса как JSON.

6. Система проверяет, что pet_id передан и является валидным UUID.

7. Система проверяет, что хотя бы одно из полей date/type/notes/value передано.

8. Система сверяет переданный pet_id с фактическим pet_id события — при несовпадении возвращает 404 (перенос события другому питомцу через этот эндпоинт не поддерживается), в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

9. Система проверяет, что питомец принадлежит инициатору (`pet.user_id`) — иначе возвращает 404.

10. Система проверяет, что питомец не мягко удалён — иначе возвращает 400.

11. Система валидирует переданные type (одно из значений справочника типов события — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md)) и date (RFC3339), а также value по форме, соответствующей type (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)), и длину notes (не более 500 символов), если эти поля переданы. Если передан type, value обязателен в этом же запросе и валидируется по форме нового type (см. "Бизнес-правила и валидация").

12. Проверка "type меняется" выполняется по факту присутствия поля `type` в JSON-теле запроса, а не сравнением с текущим значением type события в БД: если клиент прислал `type` — value обязателен в этом же запросе независимо от того, совпадает ли присланный type с уже сохранённым. Если `type` присутствует в теле, а `value` отсутствует — сервер возвращает 400 (см. "Обработка ошибок"), не выполняя UPDATE.

13. Система обновляет только те столбцы, которые были явно переданы в запросе (частичное обновление).

14. Система возвращает 204 No Content.

## Бизнес-правила и валидация

* pet_id обязателен всегда и используется исключительно как сверка прав доступа, не как способ перепривязки события к другому питомцу.

* Перенос события между питомцами через этот эндпоинт не поддерживается — несовпадение pet_id с фактическим питомцем события даёт 404.

* Метод — PATCH (частичное обновление): клиент передаёт только изменяемые поля, остальные поля события сохраняют текущее значение. Использование PUT для этого эндпоинта не предусмотрено.

* Обновляемые поля: date, type, notes, value — хотя бы одно обязательно.

* type валидируется по тому же справочнику типов события, что и при создании (см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md)); date — строго RFC3339; value — по той же форме, определяемой type, что и при создании события (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md) и **Добавление события — Backend**): при смене type в этом же запросе всегда обязательно передавать соответствующий новому типу value; notes — не более 500 символов, симметрично созданию события.

* При частичном обновлении `value` передаётся целиком: объект значения заменяется целиком, а не сливается по полям. Частичное слияние вложенных полей `value` не поддерживается — иначе результат зависел бы от прежней формы значения, и при смене типа в объекте могли бы остаться поля, не описанные формой нового типа.

* Конкурентное редактирование: сервер не выполняет никакой конфликт-детекции между одновременными PATCH-запросами к одному событию — действует стратегия last-write-wins, последний по времени обработки запрос определяет итоговое состояние события. Это осознанное решение для MVP.

* Проверка владения событием (сверка pet_id, пользователя и статуса soft-delete) выполняется по общей политике, см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md) и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md); сама реализация soft-delete у event (столбец deleted_at и его миграция) — см. страницу "Удаление события — Backend".

* Ответ 204 No Content не содержит обновлённых данных события; клиенту, которому нужны актуальные данные сразу после сохранения, следует выполнить отдельный GET /events/{id}.

## Обработка ошибок

| Статус | Условие                                                                                                                                                                                                                                                                                 |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | id некорректен / JSON некорректен / pet_id не заполнен или не UUID / ни одно поле обновления не передано / type недопустим / value не соответствует форме для type либо содержит поля вне этой формы / date не RFC3339 / notes превышает 500 символов / питомец мягко удалён / в теле передан type, но не передан value |
| 404    | Событие не найдено, мягко удалено / переданный pet_id не совпадает с фактическим питомцем события / питомец не принадлежит инициатору                                                                                                                                                   |
| 500    | Внутренняя ошибка при получении данных или обновлении записи                                                                                                                                                                                                                              |

## Хранение состояния и побочные эффекты

Выполняет UPDATE только явно переданных столбцов таблицы event. Не затрагивает данные питомца. Владелец-питомец события в рамках этого эндпоинта не изменяется — это осознанное ограничение, а не недосмотр.
