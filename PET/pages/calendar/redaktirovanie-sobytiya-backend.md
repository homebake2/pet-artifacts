## Назначение

Флоу изменяет одно или несколько полей уже существующего события без создания новой записи, а также набор питомцев, к которым привязано событие: питомцев можно привязывать и отвязывать (см. [Общие требования: Несколько питомцев в событии и напоминании](../common/obschie-trebovaniya-neskolko-pitomtsev-v-zapisi.md)). Событие одно на всех своих питомцев, поэтому изменение применяется сразу ко всем.

## Действующие лица и предусловия

* Авторизованный пользователь, у которого роль `owner` или `full` у каждого видимого питомца события. Автор события (`event.user_id`) доступ не определяет. Наличие строки в таблице `profile` не требуется.

* Событие существует, не мягко удалено (`deleted_at IS NULL`) и имеет хотя бы одного видимого (не мягко удалённого) питомца. Если у инициатора нет доступа хотя бы к одному видимому питомцу события, событие для него не существует — `404`; если доступ ко всем есть, но хотя бы у одного роль `view` — `403 FORBIDDEN`. Добавляемые питомцы (`pet_ids`) должны иметь роль `owner` или `full` (иначе `403` / `404` по тем же правилам). См. [Общие требования: Доступ к питомцу](../common/obschie-trebovaniya-dostup-k-pitomtsu.md).

## Основной сценарий

1. `PATCH /events/{id}`. Тело: date/type/notes/value/pet_ids (каждое опционально по отдельности, но хотя бы одно должно быть передано; pet_ids — желаемый полный набор видимых питомцев события, от 1 до 10 различных значений, см. «Бизнес-правила и валидация»).

2. Система разбирает id из пути — при ошибке возвращает 400.

3. Система проверяет авторизацию и извлекает userID.

4. Система находит неудалённое событие (`deleted_at IS NULL`) по id — если не найдено (в т.ч. если событие мягко удалено), возвращает 404, см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md).

5. Система разбирает тело запроса как JSON.

6. Если передан pet_ids, система проверяет, что это массив из 1–10 различных валидных UUID.

7. Система проверяет, что хотя бы одно из полей date/type/notes/value/pet_ids передано.

8. Система проверяет, что событие принадлежит инициатору (`event.user_id`) и имеет хотя бы одного видимого питомца — иначе возвращает 404, в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

9. Если передан pet_ids, система проверяет, что каждый питомец принадлежит инициатору (`pet.user_id`) — иначе возвращает 404.

10. Если передан pet_ids, система проверяет, что ни один питомец из него не мягко удалён — иначе возвращает 400.

11. Система валидирует переданные type (одно из значений справочника типов события — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md) — применимое к виду каждого питомца итогового набора, заданному полем `species`, а при нескольких питомцах не измерительное; итоговый набор — pet_ids либо текущие видимые питомцы события, если pet_ids не передан; проверка выполняется и для сохранённых type/value, если запрос меняет набор питомцев, но не меняет их; см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца») и date (RFC3339), а также value по форме, соответствующей type (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)), длину notes (не более 500 символов), если эти поля переданы. Если передан type, value обязателен в этом же запросе и валидируется по форме нового type (см. "Бизнес-правила и валидация").

12. Проверка "type меняется" выполняется по факту присутствия поля `type` в JSON-теле запроса, а не сравнением с текущим значением type события в БД: если клиент прислал `type` — value обязателен в этом же запросе независимо от того, совпадает ли присланный type с уже сохранённым. Если `type` присутствует в теле, а `value` отсутствует — сервер возвращает 400 (см. "Обработка ошибок"), не выполняя UPDATE.

13. Если в теле запроса присутствует date, система проверяет, что она не позднее текущего момента (`now()`, UTC) с тем же допуском, что при создании (см. «Добавление события — Backend») — иначе 400 и UPDATE не выполняется. Если date в теле запроса нет, проверка не выполняется — уже сохранённая дата не пересматривается только из-за изменения других полей (type, value, notes).

14. Система обновляет только те столбцы, которые были явно переданы в запросе (частичное обновление).

15. Если передан pet_ids, в той же транзакции система приводит связи `event_pet` к желаемому набору видимых питомцев: добавляет связи отсутствующих питомцев, удаляет связи видимых питомцев, которых нет в наборе. Связи с мягко удалёнными питомцами не затрагиваются.

16. Система возвращает 204 No Content.

## Бизнес-правила и валидация

* Права доступа проверяются по владельцу события (`event.user_id`), отдельный pet_id в запросе не передаётся.

* **Привязка и отвязка питомцев.** pet_ids — желаемый полный набор видимых питомцев события (непустой, без повторов, не более 10). Питомцы набора, которых у события не было, привязываются (добавляется связь, событие не копируется); видимые питомцы, не вошедшие в набор, отвязываются (удаляется только связь, само событие и его файлы остаются у прочих питомцев). Событие не может остаться без видимых питомцев — пустой набор даёт 400; чтобы убрать событие целиком, используется удаление. Привязываемый питомец проверяется так же, как при создании: принадлежность инициатору (404), отсутствие мягкого удаления (400), применимость type и значений вложенных словарей к его виду (400), измерительный type допускает ровно одного питомца (400). Повторная отправка того же набора идемпотентна.

* Метод — PATCH (частичное обновление): клиент передаёт только изменяемые поля, остальные поля события сохраняют текущее значение. Использование PUT для этого эндпоинта не предусмотрено.

* Обновляемые поля: date, type, notes, value, pet_ids — хотя бы одно обязательно.

* date, если передана, не может быть позднее текущего момента — то же условие, что и при создании (см. «Добавление события — Backend»). Событие — это факт; запланированные события с уведомлениями редактируются через [Напоминания — Backend](napominaniya-backend.md). Если date в запросе нет, дата не перепроверяется.

* type валидируется по тому же справочнику типов события и той же применимости к виду питомца, что и при создании (см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md) и [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца»); date — строго RFC3339; value — по той же форме, определяемой type, что и при создании события (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md) и **Добавление события — Backend**): при смене type в этом же запросе всегда обязательно передавать соответствующий новому типу value; notes — не более 500 символов, симметрично созданию события.

* При частичном обновлении `value` передаётся целиком: объект значения заменяется целиком, а не сливается по полям. Частичное слияние вложенных полей `value` не поддерживается — иначе результат зависел бы от прежней формы значения, и при смене типа в объекте могли бы остаться поля, не описанные формой нового типа.

* Конкурентное редактирование: сервер не выполняет никакой конфликт-детекции между одновременными PATCH-запросами к одному событию — действует стратегия last-write-wins, последний по времени обработки запрос определяет итоговое состояние события. Это осознанное решение для MVP.

* Проверка владения событием (сверка pet_id, пользователя и статуса soft-delete) выполняется по общей политике, см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md) и [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md); сама реализация soft-delete у event (столбец deleted_at и его миграция) — см. страницу "Удаление события — Backend".

* Ответ 204 No Content не содержит обновлённых данных события; клиенту, которому нужны актуальные данные сразу после сохранения, следует выполнить отдельный GET /events/{id}.

## Обработка ошибок

| Статус | Условие                                                                                                                                                                                                                                                                                 |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | id некорректен / JSON некорректен / pet_ids пуст, содержит повторы, более 10 элементов или не UUID / ни одно поле обновления не передано / измерительный type при более чем одном питомце итогового набора / type недопустим / type не применим к виду питомца, заданному полем `species` (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца») / value не соответствует форме для type либо содержит поля вне этой формы, либо значение вложенного словаря `value` не применимо к виду питомца (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость значений вложенных словарей `value` к виду питомца») / date не RFC3339 / date в будущем / notes превышает 500 символов / привязываемый питомец мягко удалён / в теле передан type, но не передан value |
| 404    | Событие не найдено, мягко удалено, не принадлежит инициатору или не имеет видимых питомцев / привязываемый питомец не найден или принадлежит другому пользователю                                                                                                                                                   |
| 500    | Внутренняя ошибка при получении данных или обновлении записи                                                                                                                                                                                                                              |

## Хранение состояния и побочные эффекты

Выполняет UPDATE только явно переданных столбцов таблицы event и, если передан pet_ids, вставляет и удаляет строки связи `event_pet`. Не затрагивает данные питомцев и файлы события.
