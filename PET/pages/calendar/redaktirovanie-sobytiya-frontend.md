## Назначение

Флоу позволяет пользователю изменить одно или несколько полей уже созданного события здоровья питомца без создания новой записи.

## Действующие лица и предусловия

* Авторизованный пользователь, просматривающий список событий выбранного дня на экране календаря.

* Событие, которое требуется отредактировать, принадлежит одному из питомцев пользователя. Проверка владения событием — на сервере, по общей политике IDOR, см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

## Основной сценарий

1. Пользователь нажимает на карточку события в списке событий выбранного дня.

2. Система открывает экран редактирования события, переиспользуя форму добавления события (тот же компонент формы, работающий в режиме "редактирование") с явной визуальной индикацией режима (заголовок экрана, текст кнопки "Сохранить изменения" вместо "Добавить"), чтобы пользователь не путал добавление нового события с изменением существующего.

3. Система предзагружает данные события через `GET /events/{id}` и заполняет форму текущими значениями полей. Маппинг ответа на поля формы должен быть явным и корректно приводить типы для каждого поля: **date** — строка RFC3339 из ответа преобразуется в объект Date/раздельные поля "Дата"/"Время" формы; **type** — значение enum из ответа устанавливается как выбранный вариант селектора типа события (это поле ранее не предзаполнялось из-за бага маппера); **value** — строка приводится к представлению, ожидаемому per-type схемой поля значения; **notes** — строка подставляется как есть, пустая строка/отсутствие поля трактуется как пустое значение. Корректность этого маппинга по каждому полю покрывается юнит-тестом, см. задачу PET-133 ниже.

4. Пользователь изменяет одно или несколько полей и нажимает "Сохранить".

5. Система выполняет клиентскую валидацию (та же схема, что и при добавлении, включая per-type валидацию value — см. **Добавление события — Frontend**, — за исключением того, что все поля, кроме petId, редактируются независимо — при редактировании достаточно, чтобы после применения изменений хотя бы одно из полей date/type/notes/value отличалось от текущего). При смене type в форме система ревалидирует value по новой per-type схеме и подсказывает пользователю привести значение в соответствие новому типу, если оно перестало ему соответствовать, см. задачу PET-134 ниже.

6. Система отправляет `PATCH /events/{id}` с изменёнными полями и pet_id события; если среди изменённых полей передаётся type, вместе с ним всегда передаётся value, провалидированный по схеме нового типа.

7. Система дожидается ответа сервера и только после успешного завершения запроса закрывает экран редактирования и возвращает пользователя на календарь.

## Бизнес-правила и валидация

* pet_id передаётся всегда и должен совпадать с фактическим питомцем события — перенос события другому питомцу через этот флоу не поддерживается.

* Хотя бы одно из полей date/type/notes/value должно быть передано на сервер.

* Для всех полей, которые передаются в запросе, действуют те же ограничения формата и длины, что и при добавлении события, включая per-type формат value.

* Дата события (date), передаваемая формой на сервер, всегда сериализуется строго в формате RFC3339 — раздельные поля "Дата"/"Время" формы объединяются маппером в единое RFC3339-значение перед отправкой, симметрично флоу добавления события.

* Конкурентное редактирование одного и того же события с разных устройств/вкладок не синхронизируется — действует стратегия last-write-wins: последний успешно сохранённый PATCH побеждает, более ранние изменения молча перезаписываются без конфликт-детекции и без предупреждения пользователя. Это осознанное решение для MVP, а не пропуск в требованиях.

## Обработка ошибок

* Если `GET /events/{id}` возвращает 404 (событие удалено — в т.ч. мягко удалено, см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md) — или недоступно), система показывает пользователю сообщение об ошибке и возвращает его на календарь.

* Если `PATCH /events/{id}` завершается ошибкой (400/404/500 либо сетевой сбой), система показывает понятное сообщение об ошибке и оставляет пользователя на экране редактирования с введёнными изменениями.

* На время загрузки данных события и на время сохранения система показывает индикаторы загрузки/сохранения и блокирует повторную отправку формы.

* Редактирование события доступно в обоих режимах, как и при добавлении события: онлайн — PATCH /events/{id}; офлайн — изменение события в локальных данных питомца.

## Хранение состояния и побочные эффекты

После успешного сохранения (сервер отвечает 204 No Content, без обновлённого тела события) система должна инвалидировать кэш активностей затронутого питомца, чтобы список событий и карточка питомца отразили изменения без ручного обновления экрана; при необходимости отобразить актуальные данные события сразу после сохранения система выполняет отдельный GET /events/{id} или использует локально применённые изменения формы.
