## Назначение

Флоу удаляет запись о событии здоровья питомца из системы (мягкое удаление — без физического стирания строки).

## Действующие лица и предусловия

* Авторизованный владелец питомца, связанного с событием. Наличие строки в таблице `profile` не требуется.

* Событие существует и принадлежит питомцу инициатора.

## Основной сценарий

1. `DELETE /events/{id}`, тело запроса отсутствует.

2. Система разбирает id из пути — при ошибке возвращает 400.

3. Система проверяет авторизацию и извлекает userID.

4. Система находит неудалённое событие (deleted_at IS NULL) по id и определяет его pet_id — если не найдено (в т.ч. если событие уже мягко удалено), возвращает 404.

5. Система проверяет, что питомец события принадлежит инициатору (`pet.user_id`) — если нет, возвращает 404.

6. Система выполняет мягкое удаление — устанавливает event.deleted_at = now(), не удаляя строку из таблицы event физически.

7. Система возвращает 204 No Content.

## Бизнес-правила и валидация

* Удаление возможно только для события, принадлежащего питомцу инициатора.

* Мягкое удаление питомца не блокирует удаление его событий — в отличие от создания и редактирования событий (где мягко удалённый питомец запрещает операцию), удаление событий у мягко удалённого питомца разрешено осознанно: это позволяет владельцу очистить историю событий даже после того, как питомец был мягко удалён.

* Удаление события мягкое (по аналогии с мягким удалением питомца): у строки события устанавливается deleted_at, строка физически не удаляется. UI восстановления удалённого события пока не предусмотрен, поэтому для пользователя удаление выглядит окончательным, хотя на уровне БД оно обратимо в принципе.

* Повторный вызов удаления для уже удалённого события возвращает 404 — операция не идемпотентна по коду ответа (второй вызов не считается успешным), что является осознанным поведением: клиент по коду 404 отличает "уже удалено/не существует" от повторного успешного удаления. На клиенте этот 404 сознательно трактуется как успех и не показывается пользователю как ошибка — см. страницу "Удаление события — Frontend".

* 404 используется как для случая "событие не существует", так и для случая "событие принадлежит другому пользователю" — это осознанное решение по безопасности, не позволяющее внешнему наблюдателю различить эти два случая и тем самым подтвердить существование чужого события, в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

* Все эндпоинты, читающие события (в т.ч. GET /activities, GET /activities/calendar, GET /activities/day, GET /events/{id} и GET /pet/{id}/events), должны исключать мягко удалённые события (фильтр deleted_at IS NULL) — аналогично политике мягкого удаления питомцев, см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md).

* Политика хранения мягко удалённых событий: строки хранятся бесконечно, физическая очистка/архивация не предусмотрена — этого достаточно для MVP.

## Известный пробел в реализации

Требования выше описывают мягкое удаление через поле `event.deleted_at`, однако на момент актуализации требований в модели данных таблицы event такого столбца ещё нет — миграция не выполнена. Это ключевая задача, от которой также зависит корректная фильтрация мягко удалённых событий в GET /events/{id} и GET /activities (см. страницы "Редактирование события — Backend" и "Просмотр календаря — Backend").

**Требуемая миграция**:

```
ALTER TABLE event ADD COLUMN deleted_at timestamptz NULL;
```

Столбец nullable, без значения по умолчанию: `NULL` означает "не удалено", конкретный timestamp — момент мягкого удаления (в UTC, как и `date_time`, см. страницу "Просмотр календаря — Backend"). После миграции фильтр `deleted_at IS NULL` обязателен во всех эндпоинтах, читающих события — без явного исключения:

* `GET /activities` — события одного питомца по диапазону дат (см. страницу "Просмотр календаря — Backend");

* `GET /activities/calendar` — количество событий по дням по всем питомцам пользователя (см. страницу "Просмотр календаря — Backend");

* `GET /activities/day` — все события всех питомцев пользователя за один день (см. страницу "Просмотр календаря — Backend");

* `GET /events/{id}` — карточка одного события (см. страницу "Редактирование события — Backend", шаг поиска события по id);

* `GET /pet/{id}/events` — плоский список событий питомца (см. страницу "Просмотр календаря — Backend").

До выполнения этой миграции ни один из перечисленных эндпоинтов физически не может отфильтровать мягко удалённые события — колонка отсутствует, поэтому все три эндпоинта временно продолжают отдавать записи, помеченные как удалённые. Именно это и есть текущий пробел.

## Обработка ошибок

| Статус | Условие                                                                                                   |
| ------ | --------------------------------------------------------------------------------------------------------- |
| 400    | id не является валидным UUID                                                                              |
| 401    | Токен авторизации отсутствует или недействителен                                                          |
| 404    | Событие не найдено, уже удалено или принадлежит другому пользователю                                      |
| 500    | Внутренняя ошибка при получении события, проверке принадлежности или удалении записи                       |

## Хранение состояния и побочные эффекты

Мягко удаляет строку в таблице event, устанавливая deleted_at; строка физически не удаляется и остаётся в таблице бессрочно. Не затрагивает данные питомца. Все эндпоинты, читающие события, должны фильтровать по deleted_at IS NULL, чтобы мягко удалённые события не отображались.
