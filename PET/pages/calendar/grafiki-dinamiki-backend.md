## Назначение

Флоу отдаёт готовые агрегированные ряды (серии точек по интервалам времени) для построения графиков динамики питомца: вес, температура, объём кормления и питья, длительность активности и сна, количество приёмов лекарств, количество категориальных наблюдений.

Агрегация выполняется на сервере, а не на клиенте. Это и есть причина существования эндпоинта: клиент не выкачивает все события за период и не сворачивает их сам. Собственная свёртка на клиенте означала бы, что сетевой и локальный режимы считают графики двумя независимыми реализациями и способны разойтись в цифрах на одних и тех же данных; при серверной агрегации сетевой режим имеет ровно один алгоритм — этот, а локальный режим обязан воспроизводить его результат один-в-один (см. [Графики динамики — Frontend (dataSource=local)](grafiki-dinamiki-frontend-local.md)).

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь (валидный access-токен). Наличие строки в таблице `profile` не требуется.

* Запрашиваемый питомец должен принадлежать инициатору; иначе система должна отвечать так же, как и на запрос несуществующего питомца (см. "Обработка ошибок"), в соответствии с [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md).

## Основной сценарий

1. `GET /events/stats`, query-параметры, заголовок Authorization обязателен:

| Параметр | Тип | Обязательность | Назначение |
| --- | --- | --- | --- |
| `pet_id` | uuid | обязателен | питомец, по событиям которого строятся ряды |
| `types` | список значений `type` через запятую | опционально | по умолчанию — все типы события, у которых `value_kind` ≠ `label` |
| `from`, `to` | YYYY-MM-DD | обязательны | границы периода |
| `bucket` | enum: `day`, `week`, `month` | обязателен | шаг интервала агрегации |

Значения `type` и `bucket` — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md).

2. Система проверяет метод запроса (должен быть GET).

3. Система проверяет наличие и формат `pet_id`, `from`, `to`, `bucket`, а также допустимость каждого значения в `types`.

4. Система проверяет, что диапазон `from..to` не превышает 366 дней.

5. Система проверяет авторизацию и извлекает userID.

6. Система проверяет, что питомец с указанным `pet_id` существует, не удалён мягко и принадлежит инициатору (`pet.user_id`).

7. Система получает имя питомца и его неудалённые события запрошенных типов, дата которых попадает в период (границы — см. "Бизнес-правила и валидация").

8. Система разворачивает каждый запрошенный тип в набор метрик по [реестру метрик](../common/model-znacheniya-sobytiya-i-metriki.md) и сворачивает события в интервалы по правилам агрегации из того же реестра.

9. Система возвращает 200 OK с телом `{"pet_name": string, "series": [...]}`.

## Форма ответа

Элемент `series` описывает одну линию/набор столбцов графика:

| Поле | Тип | Присутствие | Назначение |
| --- | --- | --- | --- |
| `type` | enum типа события | всегда | тип события, из которого построена серия |
| `metric` | строка | всегда | ключ метрики из реестра метрик |
| `category` | строка | только при `value_kind` = `category` | конкретное значение категории, к которому относится серия |
| `unit` | строка | если у метрики есть единица | единица измерения значений серии |
| `value_kind` | enum: `measure`, `quantity`, `category` | всегда | характер значения; определяет форму графика на клиенте |
| `aggregation` | строка | всегда | способ свёртки, применённый к интервалам этой серии |
| `buckets` | массив | всегда | точки серии по интервалам, по возрастанию `bucket_start` |

Элемент `buckets`:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `bucket_start` | YYYY-MM-DD | дата начала интервала (UTC) |
| `value` | number \| null | агрегированное значение интервала; `null` — событий в интервале не было |
| `count` | number | количество событий, попавших в интервал |

Правила разворачивания типов в серии (следуют из реестра метрик и не переопределяются здесь):

* Для `value_kind` = `category` возвращается **по одной серии на каждое значение категории**, встречающееся в реестре для этого типа; `value` каждого интервала — количество событий с этим значением категории.

* Для `feeding` возвращается **по одной серии на каждую `unit`**: граммы, миллилитры и порции — независимые серии, значения разных единиц не складываются.

* Для `weight` и `temperature` возвращаются **две серии-метрики** — среднее значение интервала и последнее значение интервала; они различаются полем `metric` и полем `aggregation` при одинаковых `type` и `unit`.

* Для `temperature` ряды дополнительно разделяются по виду замера (`temperature.kind`): замеры температуры тела и температуры среды обитания попадают в разные серии и никогда не сводятся в одно значение — при одной и той же единице (°C) это разные объекты наблюдения (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Разнообразие видов и состав словарей»).

* Тип `activity` даёт по одной серии на каждую свою метрику (длительность и дистанция), так как единицы у них разные.

## Бизнес-правила и валидация

**Границы периода и UTC.** Правила трактовки `from`/`to` и определения календарного дня — **те же, что у `GET /activities`**: полуоткрытый интервал от `from` 00:00:00Z включительно до начала суток, следующих за `to`, исключительно; календарный день события определяется по его UTC-представлению. Эти правила определены на странице [Просмотр календаря — Backend](prosmotr-kalendarya-backend.md), раздел "Бизнес-правила и валидация", и здесь не переопределяются — двух разных трактовок одного и того же диапазона дат в системе быть не должно.

**Границы интервалов агрегации.**

* `bucket=day` — календарные сутки по UTC.

* `bucket=week` — календарная неделя по UTC, **начинается с понедельника**; `bucket_start` — дата понедельника.

* `bucket=month` — календарный месяц по UTC; `bucket_start` — первое число месяца.

Интервал, частично выходящий за пределы `from..to` (первая и последняя неделя/месяц периода), включается в ответ целиком как интервал, но агрегирует только события, попавшие в запрошенный период — расширять выборку событий за границы `from..to` запрещено.

**Пустые интервалы обязательны.** Каждый интервал, покрывающий период `from..to`, ОБЯЗАН присутствовать в `buckets` — в том числе интервал без событий, с `value: null` и `count: 0`. Пропуск такого интервала недопустим: интервалы задают ось времени графика, и неполный их набор исказил бы масштаб периода на клиенте (правило «Пустые интервалы не пропускаются» из [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)).

Серия, у которой все интервалы пусты, всё равно возвращается — «нет данных за период» отличимо от «такой метрики нет».

* Диапазон `from..to` не должен превышать 366 дней — то же ограничение, что у `GET /activities`; более длинный диапазон — ошибка валидации (400), а не молчаливое обрезание.

* `from` позже `to` — ошибка валидации (400), а не пустой успешный ответ.

* **Тип с `value_kind` = `label` (`other`) не может быть запрошен.** Если такой тип передан в `types` явно, система отвечает 400 — молчаливое исключение неагрегируемого типа из ответа недопустимо: пользователь получил бы пустой график вместо объяснения, почему график по этому типу не строится. При отсутствии `types` такие типы просто не входят в множество по умолчанию.

* Мягко удалённые события (`deleted_at IS NOT NULL`) исключаются из агрегации; события мягко удалённого питомца недоступны, обращение к такому питомцу обрабатывается как обращение к несуществующему (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)).

* Значения `value` уже провалидированы при создании и редактировании события, поэтому на чтении повторная валидация формы `value` не выполняется.

**Индекс выборки.** Выборка неудалённых событий одного питомца по типу и дате опирается на индекс `event_pet_type_date_idx`, определённый на странице [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Хранение»; здесь DDL не дублируется.

## Обработка ошибок

| Статус | Условие |
| ------ | ------- |
| 405    | Метод запроса не GET |
| 400    | Отсутствует обязательный параметр / некорректный формат даты, `pet_id` или `bucket` / неизвестное значение в `types` / запрошен неагрегируемый тип (`value_kind` = `label`) / `from` позже `to` / диапазон `from..to` превышает 366 дней |
| 401    | Токен авторизации отсутствует или недействителен |
| 404    | Питомец с указанным `pet_id` не найден, принадлежит другому пользователю или мягко удалён |
| 500    | Внутренняя ошибка при проверке принадлежности питомца или при агрегации событий |

Обращение к чужому или несуществующему питомцу даёт тот же результат, что и обращение к несуществующему — 404 Not Found, единообразно с остальными эндпоинтами чтения событий.

## Хранение состояния и побочные эффекты

Эндпоинт идемпотентен и только читает данные; побочных эффектов на состояние системы нет. Агрегированные ряды не материализуются и не кэшируются на сервере — они вычисляются на каждый запрос из таблицы `event`, поэтому результат всегда согласован с последним изменением событий.

## Известные ограничения MVP

* Эндпоинт отдаёт ряды по одному питомцу за запрос; сравнение динамики нескольких питомцев на одном графике не поддерживается.

* График по дозе конкретного препарата не поддерживается: `medication` агрегируется по количеству приёмов (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md)).
