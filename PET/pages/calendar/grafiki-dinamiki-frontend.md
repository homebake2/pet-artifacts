## Назначение

Экран «Динамика» показывает владельцу изменение показателей питомца во времени: график выбранной метрики за выбранный период. Экран отвечает за выбор питомца, метрики и периода и за отрисовку рядов; он не вычисляет агрегаты сам — их отдаёт `GET /events/stats`.

## Действующие лица и предусловия

* Пользователь авторизован и имеет хотя бы одного питомца.

* Приложение поддерживает два режима работы: сетевой (данные с сервера) и локальный. Поведение ветки `dataSource=local` описано на отдельной странице — см. [Графики динамики — Frontend (dataSource=local)](grafiki-dinamiki-frontend-local.md).

## Основной сценарий

1. Точка входа — карточка питомца, раздел (вкладка) «Динамика». Питомец, на карточке которого открыт раздел, выбран по умолчанию; переключение питомца доступно на самом экране.

2. Пользователь выбирает метрику (тип события). Список доступных для графика метрик строится **из реестра метрик** — экран не содержит собственного захардкоженного перечня: тип с `value_kind` = `label` в список не попадает, а новый тип события появляется в списке автоматически вместе с записью в реестре.

3. Пользователь выбирает период. Период однозначно определяет `bucket` запроса:

| Период | `bucket` |
| --- | --- |
| Неделя | `day` |
| Месяц | `week` |
| Год | `month` |

4. Система запрашивает `GET /events/stats` с `pet_id`, `types` (выбранный тип), `from`/`to` (границы периода) и `bucket`.

5. Система отрисовывает полученные ряды: каждая серия ответа — отдельная линия или отдельный набор столбцов.

6. По умолчанию при первом открытии выбираются метрика с наибольшим числом наблюдений у питомца и период «Месяц».

## Бизнес-правила и валидация

**Форма графика определяется `value_kind` из реестра метрик**, а не типом события напрямую:

| `value_kind` | Форма графика |
| --- | --- |
| `measure` | линия |
| `quantity` | столбцы |
| `category` | столбцы по категориям (по серии на значение категории) |

Экран не содержит собственной логики «какой тип чем рисовать» помимо реестра: добавление нового типа события не должно требовать правки условий отрисовки на этом экране.

* **Подпись оси Y берётся из единицы метрики** (поле `unit` серии / единица из реестра). Ось без единицы допустима только для метрик, у которых единицы нет (`category`, количество приёмов).

* **Серии с разными единицами НИКОГДА не рисуются на одной оси и не объединяются в одну серию.** Для `feeding` граммы, миллилитры и порции отображаются как отдельные серии с раздельными осями (или раздельными графиками); их сложение или размещение на общей числовой оси запрещено — результат был бы бессмысленным.

* Две серии-метрики одного типа (среднее и последнее значение интервала для `weight` и `temperature`) имеют одну единицу и потому допустимы на одной оси; какая из них показана по умолчанию и как переключается — выбор экрана, но подпись серии обязана явно называть способ свёртки.

* Серии температуры по разным видам замера (тело и среда обитания) не смешиваются в одну линию, даже несмотря на общую единицу: подпись серии обязана называть вид замера, чтобы владелец рептилии или рыбы не принял температуру воды за температуру питомца.

* **Пустой интервал (`value: null`) не интерполируется.** Для линии пропуск отображается как разрыв линии (точки по краям пропуска не соединяются), для столбцов — как отсутствующий/нулевой столбец. Соединение соседних непустых точек линией через пропуск запрещено: это нарисовало бы наблюдение, которого не было.

* Ряды отрисовываются в том порядке интервалов, в котором пришли; клиент не досчитывает и не добавляет собственные интервалы — полный набор интервалов гарантирован ответом.

* **Пустое состояние.** Если у питомца нет ни одного события выбранного типа за период (все интервалы всех серий пусты), экран показывает понятное пустое состояние с предложением добавить событие этого типа, а не пустой холст графика с осями и без данных.

## Обработка ошибок

* Пока запрос выполняется, экран показывает индикатор загрузки (skeleton) на месте графика — по [Общие требования: UI-паттерны запросов](../common/obschie-trebovaniya-ui-patterny-zaprosov.md).

* Ошибка запроса отображается сообщением с кнопкой повтора; текст сообщения формируется по [Общие требования: Формат ошибок API](../common/obschie-trebovaniya-format-oshibok-api.md).

* 404 (питомец не найден или не принадлежит пользователю) показывается как явное сообщение о недоступности питомца, а не как пустой график.

* Смена метрики или периода при уже отображённом графике не должна очищать экран в пустое состояние до получения ответа — применяется обычный паттерн загрузки поверх предыдущих данных.

## Хранение состояния и побочные эффекты

* Ответ кэшируется в React Query по ключу вида `['event-stats', petId, type, from, to, bucket]`. Ключ строится единой фабрикой ключей запросов; других независимых способов получить те же ряды (с иным ключом кэша) в системе быть не должно.

* Кэш рядов ОБЯЗАН инвалидироваться после успешного добавления, редактирования или удаления события того же питомца — симметрично правилу инвалидации кэша активностей на странице [Просмотр календаря — Frontend](prosmotr-kalendarya-frontend.md). Иначе график и календарь показывали бы разные данные по одному и тому же питомцу.

* Кэш рядов также инвалидируется при удалении и восстановлении питомца.

* Экран только читает данные; побочных эффектов на данные питомца и события нет.

## Известные ограничения MVP

* На одном графике отображается один тип события одного питомца; сравнение метрик разных типов или разных питомцев не поддерживается.
