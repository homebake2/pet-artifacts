## Назначение

Флоу хранит запланированные события здоровья питомца и ведёт по ним напоминания. Запись о событии, которое уже произошло, — факт (`event`, см. [Добавление события — Backend](dobavlenie-sobytiya-backend.md)); запись о запланированном — набор из двух сущностей:

* **Настройки напоминания** (`reminder_plan`) — то, что пользователь ввёл при создании: питомец, тип события, значение, заметка и расписание (частота, даты начала и окончания, от одного до четырёх времён суток) — такое же гибкое, как расписание приёма лекарства; кроме того, расписание бывает разовым. Настройки сами в календаре не показываются.

* **Напоминание** (`reminder`) — одна строка на каждый момент расписания (дата + время). Именно напоминания показываются в календаре (см. [Просмотр календаря — Backend](prosmotr-kalendarya-backend.md)) и по ним на устройстве срабатывают локальные уведомления — в указанный момент, без заблаговременных предупреждений. Данные напоминания (тип, значение, заметка, питомец) берутся из его настроек, собственных копий у напоминания нет; единственное исключение — необязательная собственная заметка (см. «Заметка напоминания»).

У настроек есть **источник** (`source`): они созданы пользователем (`manual`) либо расписанием лекарства (`medication`) или датой следующей вакцинации (`vaccination`). Настройки со связанным источником остаются согласованными со своей записью в Ветпаспорте (см. «Источник настроек»).

Сервер не участвует в доставке уведомлений и не хранит расписание их срабатывания на устройстве — только настройки и моменты напоминаний.

## Модель данных

```
reminder_plan
  id             uuid PRIMARY KEY      -- назначается клиентом (UUID v4), см. «Идемпотентность создания»; для связанных источников — сервером
  pet_id         uuid NOT NULL
  source         text NOT NULL         -- 'manual' | 'medication' | 'vaccination'; задаётся при создании и не меняется
  source_id      uuid NULL             -- medication.id либо vaccination.id; NULL при 'manual'
  type           text NOT NULL         -- значение справочника типов события
  value          jsonb NOT NULL        -- форма определяется type, как у event.value
  notes          text NULL             -- не более 500 символов
  frequency_type text NOT NULL         -- 'once' | 'daily' | 'specific_days' | 'every_n_days'
  weekdays       jsonb NULL            -- массив int 1..7 (пн=1 .. вс=7), только при 'specific_days'
  interval_days  integer NULL          -- 2..365, только при 'every_n_days'
  times          text[] NOT NULL       -- от 1 до 4 различных значений 'HH:mm'; при 'once' — ровно одно
  start_date     date NOT NULL         -- при 'once' — дата напоминания
  end_date       date NULL             -- NULL = без даты окончания; при 'once' всегда NULL
  tz             text NOT NULL         -- имя часового пояса IANA
  created_at     timestamptz NOT NULL

reminder
  id            uuid PRIMARY KEY       -- назначается сервером
  plan_id       uuid NOT NULL REFERENCES reminder_plan(id) ON DELETE CASCADE
  remind_at     timestamptz NOT NULL   -- момент напоминания
  notes         text NULL              -- заметка этого напоминания; если задана, показывается вместо заметки настроек (см. ниже)
  closed_at     timestamptz NULL       -- когда напоминание закрыто
  close_reason  text NULL              -- 'done' | 'skipped' | 'deleted' | 'replaced'
  fact_event_id uuid NULL              -- факт, созданный при закрытии как «выполнено»
```

**Заметка напоминания.** `reminder.notes` — необязательное поле. Если оно непустое, именно оно отдаётся как заметка напоминания (в календаре, в `GET /reminders/{id}`, в факте при отметке «выполнено»), а заметка настроек (`reminder_plan.notes`) не используется; если пустое или `NULL` — отдаётся заметка настроек. Напоминания настроек `manual` всегда создаются с `notes = NULL`. Собственную заметку получают только напоминания настроек `medication` — доза по времени приёма (`dose_note`, см. [Лекарства — Backend](../vetpassport/lekarstva-backend.md)); она назначается при каждом создании и пересоздании напоминаний таких настроек. Заметка напоминания не редактируется отдельно: её изменение, как и любое изменение данных одного напоминания, выполняется заменой (эндпоинт H).

**Незавершённое напоминание** — строка `reminder` с `closed_at IS NULL`. **Закрытое** (`closed_at IS NOT NULL`) — напоминание, которое пользователь закрыл; причина закрытия хранится в `close_reason`:

| `close_reason` | Как закрыто |
| --- | --- |
| `done` | отмечено «выполнено» (эндпоинт G); `fact_event_id` указывает на созданный факт |
| `skipped` | отмечено «не выполнено» (эндпоинт G) |
| `deleted` | удалено по одному (эндпоинт F) |
| `replaced` | заменено новой записью (эндпоинт H) |

`closed_at` и `close_reason` задаются только вместе; `fact_event_id` — только при `done`. Закрытые напоминания пользователю не показываются и ни в каком ответе не отдаются, но строка остаётся в БД: по ней пересоздание расписания не создаёт заново момент, который пользователь уже закрыл (причина закрытия на это не влияет), а повторная отметка отличает уже выполненное от удалённого (см. эндпоинт G).

Если у настроек не осталось ни одного незавершённого напоминания, настройки удаляются вместе со всеми их напоминаниями (в том числе закрытыми).

## Источник настроек

`source` и `source_id` задаются при создании настроек и не меняются. Запись владельца (`medication.reminder_plan_id`, `vaccination.next_plan_id`) и `source`/`source_id` настроек записываются в одной транзакции и всегда согласованы.

* `manual` — настройки созданы пользователем: `POST /reminder-plans` (всегда `manual`; полей источника в теле нет) либо замена одного напоминания (эндпоинт H).

* `medication` — набор напоминаний лекарства, `source_id` = `medication.id`.

* `vaccination` — напоминание на дату следующей вакцинации, `source_id` = `vaccination.id`.

Напоминание, чьи настройки связаны с записью Ветпаспорта, не должно расходиться с ней или терять смысл, поэтому для `source != manual` действуют правила:

1. **Тип не меняется никогда.** `type` связанных настроек нельзя изменить ни в «Изменить все» (эндпоинт C), ни при замене одного напоминания (эндпоинт H): новая запись обязана иметь тот же `type`. Нарушение — 400.

2. **`value` и `notes` настроек принадлежат владельцу** — название и дозировка лекарства (`value.name`, `notes`), подпись вакцинации (`value.label`). `PATCH /reminder-plans/{id}` не принимает их для связанных настроек (400). Они меняются только через владельца: изменение названия или дозировки лекарства, названия вакцинации применяется к настройкам автоматически в той же транзакции (см. [Лекарства — Backend](../vetpassport/lekarstva-backend.md), [Вакцинации — Backend](../vetpassport/vaktsinatsii-backend.md)).

3. **Расписание правится через настройки и применяется к владельцу** в той же транзакции:
   * `medication` — допустимы виды частоты лекарства (`daily`, `specific_days`, `every_n_days`; `once` — 400). Поля расписания лекарства (`frequency_type`, `weekdays`, `interval_days`, `start_date`, `end_date`) заменяются переданными. `times` лекарства заменяются переданным списком времён: у времени, которое осталось в списке, сохраняется его `dose_note`, у добавленного `dose_note` пуст, исчезнувшие времена удаляются. Напоминания пересоздаются с заметками из `dose_note` обновлённых `times` (см. «Заметка напоминания»).
   * `vaccination` — допустимо только разовое расписание (`once`, иначе 400). Дата напоминания записывается в `vaccination.next_date`. Время суток хранится только в напоминании: оно не меняет время факта на дату введения (у факта своё время, `administered_time`) и самой вакцинации.

4. **Одно напоминание заменяется только у `medication`.** Замена одного напоминания (эндпоинт H) для `vaccination` недоступна (409): напоминание единственное, и его изменение — это «Изменить все». Для `medication` замена допустима; новая запись независима (`manual`), лекарство не меняется, приёмы лекарства за пределами замены остаются на месте.

5. **Удаление и отметка** (эндпоинты D, F, G) работают как у `manual`; запись владельца при этом не меняется — ссылка на настройки на чтении становится `null`, как только настроек нет.

6. Питомец связанных настроек не меняется (как и у `manual`).

Ответы `ReminderPlanResponse` и `ReminderResponse` отдают `source`, `source_id` и `source_title` (название лекарства либо вакцинации; `null` при `manual`) — по ним клиент показывает пользователю, какая запись будет затронута, и блокирует недоступные поля.

## Расчёт расписания

Единый расчёт для настроек любого источника: его же использует лекарство при создании, пересоздании и ручном «Добавить напоминания» (см. [Лекарства — Backend](../vetpassport/lekarstva-backend.md)).

**Поля расписания.**

* `frequency_type` — `once` (один раз), `daily` (каждый день), `specific_days` (определённые дни недели), `every_n_days` (через каждые N дней). Вида «по необходимости» нет.

* `weekdays` — обязателен, если и только если `frequency_type = specific_days`: 1–7 уникальных значений 1..7.

* `interval_days` — обязателен, если и только если `frequency_type = every_n_days`: целое 2..365.

* `times` — от 1 до 4 различных значений `HH:mm` (допускается `HH:MM:SS`), местное время пояса `tz`; при `once` — ровно одно.

* `start_date` — `YYYY-MM-DD`, обязательна; при `once` это дата напоминания.

* `end_date` — `YYYY-MM-DD`, опциональна, не раньше `start_date`; при `once` не передаётся.

Поля, не относящиеся к выбранному `frequency_type`, не передаются (передача — 400).

**Алгоритм.** Перебор календарных дат начиная со `start_date` по возрастанию. Дата `d` входит в расписание, если:

* `once` — только `d = start_date`;
* `daily` — любая дата;
* `specific_days` — ISO-номер дня недели `d` присутствует в `weekdays`;
* `every_n_days` — `(d - start_date)` в днях кратно `interval_days` (отсчёт идёт от `start_date`, в том числе когда она в прошлом).

Перебор останавливается на `end_date` (дата позже неё не включается), при достижении потолка (см. ниже) либо, если `end_date` нет и совпадающих дат нет в пределах 730 дней от `start_date` (защита от бесконечного перебора при некорректных входных данных). Для каждой входящей даты создаётся по одному моменту на каждое время из `times`, времена внутри даты — в порядке возрастания времени суток независимо от порядка в массиве (потолок отсекает моменты с конца этого упорядоченного перебора): `remind_at` — эта дата и время как местное время пояса `tz`. Если местного времени не существует (переход на летнее время вперёд), момент сдвигается на длину пропуска; если оно встречается дважды (переход назад), берётся первое вхождение.

Отличия при создании напоминаний:

* Создаются только моменты строго позже `now()`; прошедшие моменты расписания не материализуются (даже если `start_date` в прошлом).

* Моменты, для которых у тех же настроек уже есть закрытая строка `reminder` с тем же `remind_at`, пропускаются.

* **Потолок — 60** создаваемых напоминаний за одну операцию (создание, пересоздание), считая по всем временам сразу. Остаток курса не материализуется (см. «Бизнес-правила и валидация»).

Если расчёт даёт ноль моментов — запрос отклоняется (400).

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь. Наличие строки в таблице `profile` не требуется.

* Питомец должен существовать, принадлежать инициатору и не быть мягко удалённым — иначе все эндпоинты ниже возвращают 404. Настройки и напоминания мягко удалённого питомца не существуют: они удаляются вместе с ним (см. «Бизнес-правила и валидация»).

## Основной сценарий

Часовой пояс передаётся query-параметром `tz` — имя пояса IANA; он **обязателен** у эндпоинтов A, C, H, отсутствие, неизвестное имя или `Local` — 400. Значения по умолчанию нет.

### A. `POST /reminder-plans` — создать настройки и напоминания

1. Тело: `id` (uuid, обязательно — назначается клиентом), `pet_id` (uuid, обязательно), `type`, `value` (обязательно), `notes` (опционально), расписание по правилам раздела «Расчёт расписания»: `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date`.

2. Система проверяет авторизацию, формат полей, согласованность полей расписания с `frequency_type`, питомца (принадлежность и мягкое удаление — 404), `type` и применимость `type` к виду питомца, форму `value` и применимость значений вложенных словарей `value` — теми же правилами, что `POST /events` (см. «Добавление события — Backend», шаги 7–12 и «Бизнес-правила и валидация»).

3. Система рассчитывает моменты (см. «Расчёт расписания»). Если моментов нет — 400.

4. В одной транзакции система вставляет строку `reminder_plan` (`source = manual`) и по одной строке `reminder` на каждый рассчитанный момент.

5. Ответ — 201 Created с `ReminderPlanResponse`: `id`, `pet_id`, `pet_name`, поля данных и расписания (`type`, `value`, `notes`, `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date`), `source`, `source_id`, `source_title`, `reminders` (массив `{id, remind_at}` незавершённых напоминаний), `files` (файлы настроек, см. «Файлы»), `future_reminders_with_files_count` (число незавершённых напоминаний с `remind_at > now()`, у которых есть собственные файлы).

**Идемпотентность создания.** Клиентский `id` заменяет `Idempotency-Key`: если настройки с таким `id` уже существуют и принадлежат инициатору — система возвращает их (201, то же тело) без повторной вставки; если `id` занят чужими настройками — 409.

### B. `GET /reminder-plans/{id}` — настройки целиком (форма «Изменить все»)

Возвращает `ReminderPlanResponse` (см. выше) для настроек инициатора. Настройки не найдены, чужие или питомец мягко удалён — 404.

### C. `PATCH /reminder-plans/{id}` — изменить все напоминания

1. Тело: любые из `type`, `value`, `notes` (каждое опционально), а также поля расписания — только целиком: `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date` (`end_date: null` — без даты окончания). Хотя бы одно поле обязательно. Если передан `type`, `value` обязателен в этом же запросе (как в «Редактирование события — Backend»); `value` заменяется целиком. `notes` — пустая строка очищает значение.

2. Система проверяет принадлежность, а переданные поля — теми же правилами, что при создании. Для настроек с `source != manual` дополнительно действуют правила раздела «Источник настроек»: `type`, `value`, `notes` не принимаются (400), расписание ограничено видом источника.

3. Если переданное расписание отличается от сохранённого, система в одной транзакции:

   * рассчитывает моменты по новому расписанию (см. «Расчёт расписания») и требует, чтобы был хотя бы один — иначе 400;
   * жёстко удаляет незавершённые напоминания настроек с `remind_at > now()` вместе с их собственными файлами (`reminder_file`);
   * вставляет рассчитанные напоминания (моменты с закрытыми строками пропускаются; у настроек `medication` — с заметками из `dose_note`);
   * записывает новое расписание и `tz` в настройки;
   * для настроек с `source != manual` применяет расписание к владельцу (см. «Источник настроек», правило 3).

   Прошедшие незавершённые напоминания (`remind_at <= now()`) и закрытые не затрагиваются. Если переданное расписание совпадает с сохранённым, напоминания не пересоздаются и владелец не меняется. Потеря собственных файлов при пересоздании происходит без дополнительного подтверждения на сервере: предупреждение показывает клиент по `future_reminders_with_files_count` (см. «Напоминания — Frontend»).

4. Поля `type`, `value`, `notes` (у `manual`) обновляются только в строке настроек: все напоминания сразу отдают новые данные.

5. Ответ — 204 No Content.

### D. `DELETE /reminder-plans/{id}` — удалить все напоминания

Жёстко удаляет настройки, все их напоминания (в том числе закрытые) и файлы (см. «Бизнес-правила и валидация»). Ответ — 204. Настройки не найдены, чужие или питомец мягко удалён — 404.

### E. `GET /reminders/{id}` — одно напоминание (форма «Изменить это»)

Возвращает `ReminderResponse`: `id`, `plan_id`, `remind_at`, `type`, `value`, `notes` (заметка напоминания, а при её отсутствии — настроек), `pet_id`, `pet_name`, `plan_source`, `plan_source_title` (источник и его название, см. «Источник настроек»), `plan_files` (файлы настроек), `files` (собственные файлы напоминания), `plan_unclosed_count` (сколько незавершённых напоминаний у настроек, включая это; по нему клиент решает, предлагать ли выбор «это / все»). Закрытое, чужое, несуществующее напоминание или напоминание мягко удалённого питомца — 404.

### F. `DELETE /reminders/{id}` — удалить одно напоминание

В одной транзакции система закрывает напоминание без факта (`closed_at = now()`, `close_reason = 'deleted'`, `fact_event_id` не задаётся) и удаляет его собственные файлы; строка остаётся как отметка закрытого момента. Если у настроек не осталось незавершённых напоминаний, удаляются и сами настройки. Ответ — 204. Напоминание не найдено или уже закрыто — 404.

### G. `POST /reminders/{id}/complete` — закрыть прошедшее напоминание

1. Тело: `done` (boolean, обязательно) — «выполнено» (`true`) или «не выполнено» (`false`).

2. Напоминание должно быть незавершённым и прошедшим (`remind_at <= now()`); будущее напоминание закрыть этим способом нельзя — 409.

3. В одной транзакции система:

   * если `done = true` — создаёт факт `event` с `pet_id`, `type`, `value` из настроек, `notes` — заметка напоминания (а при её отсутствии — настроек) и `date = remind_at` и создаёт для него ссылочные строки файлов (см. «Файлы»);
   * записывает `closed_at = now()`, `close_reason` (`done` либо `skipped`) и, если создан факт, его `fact_event_id`; собственные файлы напоминания удаляются (на их объекты остаются ссылки факта);
   * если незавершённых напоминаний у настроек не осталось — удаляет настройки (вместе со строкой закрытого напоминания);
   * для настроек с `source = vaccination` при `done = true` очищает `next_date` вакцинации (см. [Вакцинации — Backend](../vetpassport/vaktsinatsii-backend.md)).

4. Ответ — 200 OK с телом `{"fact_event_id": uuid | null}`.

**Повторный вызов.** Для напоминания, закрытого с `close_reason` `done` или `skipped`, пока его настройки существуют, возвращается 200 с тем же `fact_event_id`, повторно ничего не создаётся (значение `done` во втором вызове игнорируется). Для напоминания, закрытого как `deleted` или `replaced`, — 404. Если настройки уже удалены, повторный вызов получает 404 — клиент трактует его как «уже закрыто».

### H. `POST /reminders/{id}/detach` — заменить одно напоминание новой записью

Операция «Изменить это» с изменением данных или времени (см. «Напоминания — Frontend»): напоминание закрывается без факта, а вместо него создаётся новая независимая запись — факт либо новые настройки со своим расписанием.

1. Заголовок `Idempotency-Key` (UUID v4) обязателен. Тело содержит ровно одно из: `event` — тело `POST /events`; `plan` — тело `POST /reminder-plans` (с клиентским `id`); для `plan` обязателен query-параметр `tz`. Оба — ни одного или оба сразу — 400.

2. Напоминание должно быть незавершённым. `pet_id` новой записи должен совпадать с питомцем напоминания — перенос между питомцами не поддерживается (иначе 400). Для настроек `vaccination` замена недоступна — 409; для `medication` `type` новой записи обязан совпадать с типом напоминания (иначе 400). Новые настройки — всегда `manual`.

3. В одной транзакции система создаёт новую запись по правилам соответствующего эндпоинта (`POST /events` либо `POST /reminder-plans`), создаёт для неё ссылочные строки файлов настроек и собственных файлов напоминания (см. «Файлы»), закрывает исходное напоминание по правилам эндпоинта F, но с `close_reason = 'replaced'` (включая удаление опустевших настроек).

4. Ответ — 201 Created: `{"event": EventResponse}` либо `{"plan": ReminderPlanResponse}`.

Повтор после успешного выполнения (напоминания уже нет): если найден факт с таким `Idempotency-Key` для этого питомца либо настройки с таким `id`, система возвращает его вместо 404.

### I. `GET /reminders/upcoming` — ближайшие напоминания (для уведомлений на устройстве)

Query: `limit` (целое 1–64, по умолчанию 64). Возвращает ближайшие по времени незавершённые напоминания с `remind_at >= now()` по всем не мягко удалённым питомцам инициатора: массив `items` из `{id, plan_id, remind_at, pet_id, pet_name, type}`, отсортированный по `remind_at`, при равенстве — по `id`. Эндпоинт только читает; клиент использует его, чтобы привести запланированные локальные уведомления в соответствие с сервером (см. «Напоминания — Frontend», раздел «Локальные уведомления»).

### J. `GET /pet/{id}/reminders/upcoming` — ближайшие напоминания питомца (для виджета)

Query: `limit` (целое 1–10, по умолчанию 3). Возвращает ближайшие по времени незавершённые напоминания одного питомца с `remind_at >= now()`: массив `items` из `{id, plan_id, remind_at, type}`, отсортированный по `remind_at`, при равенстве — по `id`. Горизонта по времени нет — берутся `limit` ближайших. Питомец не найден, чужой или мягко удалён — 404. Эндпоинт только читает; используется виджетом главного экрана (см. [Виджеты главного экрана — Frontend](../widget/vidzhety-glavnogo-ekrana-frontend.md)).

## Файлы

Файлы управляются generic-механизмом «Общие требования: Файлы сущностей»; в реестре владельцев регистрируются два типа:

| `owner_type` | `owner_id` | Кардинальность | Проверка владения | Допустимые `content_type` |
| --- | --- | --- | --- | --- |
| `reminder_plan_file` | `reminder_plan.id` | до 10 | настройки существуют и принадлежат питомцу инициатора, питомец не мягко удалён | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` |
| `reminder_file` | `reminder.id` | до 10 | напоминание незавершённое, его настройки принадлежат питомцу инициатора, питомец не мягко удалён | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` |

* Пользователь видит у напоминания файлы настроек и собственные файлы напоминания вместе. Чтобы они всегда помещались в один факт или одну запись (до 10 файлов, см. «Файлы события — Backend»), при подтверждении загрузки сервер дополнительно проверяет сумму: число файлов настроек плюс наибольшее число собственных файлов среди их напоминаний (для `reminder_file` — плюс число собственных файлов этого напоминания) не должно превышать 10 — иначе 409.

* Файлы настроек относятся ко всем напоминаниям; собственные файлы — только к одному.

* **Ссылки вместо копий.** При создании факта (эндпоинт G) и при замене напоминания (эндпоинт H) файлы не копируются: для каждого файла создаётся новая строка `file` нового владельца (`event_file` либо `reminder_plan_file`) с тем же `object_key`, `content_type` и `filename` (ссылочная строка, см. «Общие требования: Файлы сущностей»), объект в S3 не создаётся и не читается. Порядок: сначала файлы настроек, затем собственные, `position` назначается заново. Объект в S3 удаляется только тогда, когда на него не осталось ни одной строки `file`, поэтому удаление настроек, напоминания или факта не ломает файлы остальных. Операций с S3 внутри транзакции нет.

* Чтение: `files` (и `plan_files`) в ответах — как у события: `{file_id, url, content_type, filename}` с временными presigned-ссылками; в списках календаря — только `files_count` (файлы настроек + собственные).

## Бизнес-правила и валидация

* Настройки и напоминания создаются только для питомцев инициатора; все проверки владения возвращают 404, а не 403 (см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md)).

* Правила `type`, `value`, применимости к виду питомца, длины `notes` — те же, что у `POST /events`; правила расписания — раздел «Расчёт расписания».

* Расписание обязано давать хотя бы один будущий момент при создании и при любом изменении расписания; иначе 400. Расписание, чьи моменты уже прошли, можно сохранить без изменения расписания (например, изменив только заметку).

* **Потолок = 60.** Одна операция расчёта создаёт не больше 60 напоминаний — ограничение защищает от чрезмерного числа строк при нескольких временах в день. Расписание длиннее потолка (в том числе без `end_date`) материализует только ближайшие 60 моментов; остаток не создаётся автоматически. Когда все созданные напоминания закрыты, настройки удаляются, и продолжение — это создание нового напоминания (тот же подход, что у лекарств).

* Дата и время трактуются как местное время часового пояса `tz`; в ответах моменты `remind_at` — в UTC.

* **Исключение из правила soft-delete.** Общее правило проекта — мягкое удаление (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)). Настройки и напоминания удаляются жёстко: у них нет истории, которую нужно сохранять, а факты, созданные при отметке «выполнено», живут независимо. Вместе с владельцем жёстко удаляются его строки `file`; объекты S3 — по правилу ссылок (см. «Файлы»).

* **Удаление питомца удаляет его напоминания.** При мягком удалении питомца в той же транзакции жёстко удаляются все его настройки напоминаний, напоминания и их файлы (см. [Удаление питомца — Backend](../pets/udalenie-pitomtsa-backend.md)). События (факты) питомца при этом удаляются мягко по общему правилу. Ссылки лекарств и вакцинаций питомца на настройки на чтении возвращаются как `null`.

* Правка отдельного напоминания меняет только его собственные файлы; любое изменение его времени или данных (тип, значение, заметка) выполняется заменой через эндпоинт H.

* Конкурентные изменения не синхронизируются: действует last-write-wins, как в «Редактирование события — Backend».

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Некорректный JSON / не заполнено обязательное поле / формат `id`, `pet_id`, дат, `times`, `tz` / отсутствует `tz` там, где он обязателен / нарушена согласованность полей расписания с `frequency_type` / менее 1 или более 4 времён (при `once` — не одно), повторы / `end_date` раньше `start_date` или передана при `once` / расписание не даёт ни одного будущего момента / `type` недопустим или не применим к виду питомца / `value` не соответствует форме типа / `notes` длиннее 500 символов / поля расписания переданы не целиком / у настроек с источником `type` меняется либо передаются `value`/`notes`, расписание недопустимо для источника / в `detach` не ровно одно из `event` и `plan`, неверный `Idempotency-Key`, другой `pet_id`, другой `type` у настроек `medication` / неверный `limit` |
| 401 | Токен авторизации отсутствует или недействителен |
| 404 | Питомец, настройки или напоминание не найдены, чужие, закрыты либо питомец мягко удалён |
| 409 | `id` настроек занят чужими настройками / напоминание ещё не наступило (`complete`) / замена напоминания вакцинации (`detach`) / превышена сумма файлов (см. «Файлы») |
| 500 | Внутренняя ошибка |

## Хранение состояния и побочные эффекты

Эндпоинты изменяют таблицы `reminder_plan`, `reminder`, при отметке «выполнено» и при замене в виде факта — `event`, а также `file` (создание ссылочных строк и удаление); объект S3 удаляется после фиксации транзакции, когда на него не осталось ссылок. Для настроек с источником `medication` / `vaccination` эндпоинт C дополнительно изменяет поля расписания соответствующей строки `medication` / `vaccination` в той же транзакции. Каждая операция выполняется в одной транзакции БД. Данные питомца не изменяются. Эндпоинты `GET /reminders/upcoming` и `GET /pet/{id}/reminders/upcoming` побочных эффектов не имеют.
