## Назначение

Напоминание — запланированное событие здоровья питомца, о котором приложение напоминает локальными уведомлениями устройства в указанный момент. Пользователь один раз вводит данные события и расписание — разовое либо повторяющееся так же гибко, как расписание приёма в разделе «Лекарства»: частота, даты начала и окончания, от одного до четырёх времён суток; на каждый момент расписания создаётся отдельное напоминание, показываемое в календаре. Страница описывает создание напоминаний, их изменение (одного или всех сразу), отметку прошедшего напоминания и удаление.

Термины: **настройки напоминания** — введённые пользователем данные и расписание (в календаре не показываются); **напоминание** — один момент расписания, элемент календаря (см. [Напоминания — Backend](napominaniya-backend.md)); **связанные настройки** — настройки, созданные расписанием лекарства либо датой следующей вакцинации (у них есть источник — запись Ветпаспорта; см. «Связанные напоминания»).

## Основной сценарий

### A. Создание

1. Пользователь открывает экран добавления события и на шаге «Вид записи» выбирает «Напоминание» (см. [Добавление события — Frontend](dobavlenie-sobytiya-frontend.md)).

2. Шаг «Данные события»: Питомец, Тип события, Значение, Заметка (опционально), блок файлов (до 10) — состав и правила полей `type`/`value`/`notes` те же, что у факта. Полей «Дата» и «Время» на этом шаге нет — они задаются расписанием.

3. Шаг «Расписание». Заголовок — «Когда напоминать?». Поля:

   * **Частота** (обязательный выбор одного из четырёх вариантов): «Один раз» (по умолчанию), «Каждый день», «Определённые дни недели», «Через каждые N дней». Варианта «По необходимости» нет.
     * «Один раз» — поле «Дата» (обязательна, не раньше сегодняшней) и одна строка времени; даты окончания и добавления времён нет.
     * «Определённые дни недели» — выбор дней недели (Пн–Вс, множественный, минимум один отмечен).
     * «Через каждые N дней» — поле «Интервал (дней)» (целое, 2–365).
   * **Дата начала** (для повторяющихся вариантов; обязательна; при создании не раньше сегодняшней).
   * **Дата окончания** (для повторяющихся вариантов) — вариант «Без даты окончания» (по умолчанию) либо заданная дата, не раньше даты начала.
   * **Времена** (для повторяющихся вариантов) — список из 1–4 строк, в каждой время суток. Имеется возможность добавить время (до 4 строк) и удалить любую строку (нельзя оставить меньше одной); одинаковые времена недопустимы. Действие добавления — «Добавить время». По умолчанию — одна пустая строка.

   Уведомление приходит ровно в выбранное время; заблаговременных предупреждений нет.

   Расписание должно давать хотя бы один момент строго позже текущего момента устройства; иначе показывается сообщение «В выбранном расписании нет будущих напоминаний». Если моментов больше 60, показывается подсказка «Будут созданы ближайшие 60 напоминаний» (см. «Напоминания — Backend», потолок).

4. Сохранение выполняется на шаге «Расписание». Клиент генерирует `id` настроек (UUID v4) один раз при открытии формы — он же защищает от дублирования при повторной отправке — и вызывает `POST /reminder-plans` с обязательным `tz` — часовым поясом устройства. Действие сохранения блокируется и индицирует загрузку на время запроса (см. [Общие требования: UI-паттерны запросов](../common/obschie-trebovaniya-ui-patterny-zaprosov.md)). Выбранные файлы загружаются generic-механизмом на владельца `reminder_plan_file` с этим `id`.

5. После успешного ответа клиент синхронизирует локальные уведомления (см. «Локальные уведомления»), показывает сообщение об успешном сохранении, закрывает экран и возвращает пользователя на календарь.

### B. Открытие напоминания

Имеется возможность открыть напоминание из списка дня календаря. Если напоминание ещё не наступило, а у его настроек несколько незавершённых напоминаний (`plan_unclosed_count > 1` элемента списка дня), система сразу, без дополнительного запроса, предлагает выбор «Что изменить?» с вариантами «Только это напоминание» и «Все напоминания». Если незавершённое напоминание у настроек одно, выбор не показывается — открывается форма «Все напоминания». Для настроек с источником «вакцинация» вариант «Только это напоминание» не предлагается. Данные для решения берутся из элемента списка дня (`plan_unclosed_count`, `plan_source`, `plan_id`, `pet_id`); запрос `GET /reminders/{id}` нужен только форме «Изменить это».

Если напоминание уже наступило (см. раздел E), вместо выбора открывается отметка о выполнении.

### C. Изменить все напоминания

1. Клиент загружает `GET /reminder-plans/{id}` и открывает форму с полными данными настроек: Тип, Значение, Заметка, расписание (частота, дни недели или интервал, дата начала либо дата, дата окончания, времена), файлы настроек. Питомец отображается и не меняется. Форма одноэкранная, без шагов.

2. Пользователь меняет поля и сохраняет. Достаточно, чтобы изменилось хотя бы одно поле. Для связанных настроек часть полей недоступна для изменения (см. «Связанные напоминания»).

3. Если изменились только Тип, Значение, Заметка или файлы, клиент отправляет `PATCH /reminder-plans/{id}` с изменёнными полями, а расписание не трогает — существующие напоминания остаются на месте и сразу показывают новые данные.

4. Если изменилось что-либо в расписании, клиент перед отправкой показывает диалог подтверждения («Отмена» / «Продолжить»), если применимо хотя бы одно из условий:
   * у настроек есть источник — для вакцинации «Запись о вакцинации «{название}» тоже будет изменена», для лекарства «Запись о лекарстве «{название}» тоже будет изменена»;
   * `future_reminders_with_files_count > 0` — «У {N} напоминаний есть собственные файлы — при изменении расписания они будут удалены».

   После подтверждения клиент отправляет `PATCH` с расписанием целиком (и остальными изменёнными полями) и обязательным `tz`. Сервер удаляет будущие незавершённые напоминания и создаёт новые по новому расписанию; прошедшие незавершённые остаются как есть, а моменты, которые пользователь уже закрыл (отметил, удалил по одному или заменил), заново не создаются (см. «Напоминания — Backend», эндпоинт C). Новое расписание должно давать хотя бы один будущий момент. Ограничение проверяется только если расписание менялось: настройки, чьи моменты уже прошли, можно сохранить, изменив только заметку; дата начала в прошлом допустима, если не менялась.

5. Прошедшие незавершённые напоминания в форме расписания не показываются и отмечаются отдельно (раздел E).

6. После успеха клиент синхронизирует локальные уведомления, показывает сообщение и возвращает пользователя на календарь.

### D. Изменить только это напоминание

1. Клиент загружает `GET /reminders/{id}` и открывает те же шаги, что при добавлении события, предзаполненные: «Вид записи» (предвыбрано «Напоминание»), «Данные события» (Питомец не меняется), «Расписание» — для вида «Напоминание» расписание предзаполняется как разовое: «Один раз», дата и время этого напоминания. Если выбран вид «Уже произошло», вместо расписания задаются «Дата» и «Время» факта (не позже текущего момента). Файлы настроек показываются только для чтения, собственные файлы напоминания можно добавлять и удалять. Если у напоминания связанные настройки лекарства, Тип события недоступен для изменения (см. «Связанные напоминания»).

2. Если по итогам редактирования изменились только собственные файлы напоминания (вид записи, данные, расписание не менялись), клиент загружает/удаляет файлы на владельце `reminder_file` — напоминание остаётся на месте, остальные напоминания не затрагиваются.

3. Если изменилось что-либо ещё, клиент вызывает `POST /reminders/{id}/detach` с `Idempotency-Key` (и `tz`, если создаётся новое напоминание): исходное напоминание закрывается без факта (больше не показывается), а вместо него создаётся новая независимая запись — факт либо новые настройки со своим расписанием. Файлы настроек и собственные файлы остаются доступными новой записи (сервер создаёт ссылки на них), добавленные при редактировании — присоединяются к ней. Остальные напоминания прежних настроек не затрагиваются.

4. После успеха клиент синхронизирует локальные уведомления, показывает сообщение и возвращает пользователя на календарь.

### E. Отметка прошедшего напоминания

1. Напоминание, момент которого наступил, остаётся в календаре и отображается как требующее отметки, пока пользователь его не закроет; автоматически оно не закрывается.

2. Имеется возможность отметить прошедшее напоминание как «Выполнено» или «Не выполнено» (вопрос — «Вы выполнили это?»). Оба варианта вызывают `POST /reminders/{id}/complete` с `done = true` / `false`: напоминание закрывается и больше пользователю не показывается. При «Выполнено» дополнительно создаётся факт с данными напоминания, датой и временем напоминания и файлами — он появляется в календаре как обычная запись «Уже произошло».

3. Будущее напоминание отметить нельзя.

### F. Удаление

1. Имеется возможность удалить напоминание. Сначала система показывает подтверждение «Удаление необратимо — продолжить?» («Отмена» / «Удалить»). Окна отмены нет: удаление жёсткое (см. «Напоминания — Backend», исключение из soft-delete).

2. После подтверждения, если у настроек несколько незавершённых напоминаний, система предлагает выбор «Что удалить?»: «Только это напоминание» (`DELETE /reminders/{id}`) либо «Все напоминания» (`DELETE /reminder-plans/{id}`). Если напоминание единственное, выбора нет — удаляется оно (вместе с настройками). «Только это напоминание» пользователю видно как удаление; прочие напоминания расписания остаются. Для связанных настроек выбор дополнительно сообщает, что сама запись Ветпаспорта («{название}») останется. Выбор строится по данным элемента списка дня (`plan_unclosed_count`, `plan_source`, `plan_source_title`) без дополнительного запроса.

3. После успеха клиент синхронизирует локальные уведомления и убирает запись из календаря.

## Связанные напоминания

Связанные настройки созданы расписанием лекарства либо датой следующей вакцинации. Форма и действия для них ограничены так, чтобы напоминание нельзя было развести с записью Ветпаспорта или лишить смысла:

* **Тип события недоступен для изменения** — ни в «Изменить все», ни в «Изменить это».

* **Значение и Заметка в «Изменить все» показываются только для чтения** с пояснением, что они меняются в записи Ветпаспорта («Лекарство» либо «Вакцинация»); название и дозировка лекарства, подпись вакцинации применяются к напоминаниям автоматически.

* **Форма «Изменить все» для связанных настроек — один общий шаг только из полей.** Питомец, Тип события, Значение и Заметка в ней не показываются и не редактируются (меняются в записи Ветпаспорта), поэтому в форме остаются только файлы настроек и расписание, без индикатора шагов и поясняющих текстов. Вид формы (без шагов) определяется с первого кадра, до загрузки настроек, по источнику напоминания, известному из списка календаря.

* **Расписание изменяемо, и изменение применяется к связанной записи.** Перед сохранением показывается диалог из раздела C (шаг 4): связанная запись тоже будет изменена.
  * Лекарство: частота, дни, интервал, даты и времена обновляют расписание лекарства; дозы по времени приёма сохраняются у оставшихся времён, у добавленного времени дозы нет.
  * Вакцинация: расписание только разовое — «Один раз»; изменение даты меняет «Дату следующей вакцинации» вакцинации. Время суток меняет только напоминание.
  * Вид частоты «Один раз» у лекарства и повторяющиеся варианты у вакцинации не предлагаются.

* **«Изменить это»:** для напоминания лекарства доступно — новая запись независима от лекарства, Тип события в ней сохраняется; шаг «Питомец и тип» в этой форме не показывается, так как питомец и тип не меняются и выбирать в нём нечего. Для напоминания вакцинации не предлагается: оно единственное, его изменение — «Изменить все».

* **Удаление и отметка** работают как у обычных напоминаний; лекарство или вакцинация при этом не удаляются и не меняются.

Источник и название связанной записи клиент получает из `source` и `source_title` ответов `GET /reminder-plans/{id}` и `GET /reminders/{id}`.

## Локальные уведомления

* Планирование и отмена выполняются исключительно клиентом, средствами ОС устройства; сервер не участвует в доставке и не хранит расписание срабатывания. Конкретный API/библиотека не фиксируется. Уведомление приходит в момент напоминания (`remind_at`).

* Платформы ограничивают число одновременно запланированных локальных уведомлений приложения (например, iOS — 64), а напоминаний может быть до 60 на каждые настройки. Поэтому клиент не планирует уведомление «на каждое напоминание», а **синхронизирует** набор запланированных уведомлений с сервером: запрашивает `GET /reminders/upcoming` (ближайшие незавершённые напоминания, не более 64), планирует отсутствующие и отменяет запланированные, которых в ответе нет. Так отмена, перенос, удаление, закрытие и удаление питомца обрабатываются одним правилом, без отдельного учёта.

* **Пополнение до лимита.** Если приложение не открывали, а запланированные уведомления сработали, новые уведомления за пределами лимита не появляются — это ожидаемое поведение. При следующем открытии (запуск, возврат на передний план, вход в аккаунт) синхронизация планирует недостающие ближайшие напоминания, пока набор не дойдёт до лимита платформы.

* Синхронизация выполняется после каждой успешной операции с напоминаниями, при запуске приложения, при возврате его на передний план и после входа в аккаунт — поэтому напоминания, созданные на другом устройстве, также получают уведомления на этом, а продолжение расписания подхватывается по мере срабатывания ближайших.

* При выходе из аккаунта все запланированные уведомления приложения отменяются, а при следующем входе набор строится заново.

* Уведомление планируется на момент напоминания (`remind_at`) и содержит питомца и тип события. Идентификатор уведомления детерминирован: `{id напоминания}`; в данных уведомления передаётся признак напоминания, чтобы синхронизация управляла только своими уведомлениями. Приложение не затрагивает прочие запланированные уведомления.

* Ошибка планирования (например, нет разрешения на уведомления) не откатывает сохранение: пользователь получает отдельное сообщение о том, что уведомления создать не удалось, а напоминания остаются в календаре.

## Бизнес-правила и валидация

* Правила расписания — те же, что в «Напоминания — Backend», раздел «Расчёт расписания»: согласованность дней недели/интервала с частотой, интервал 2–365, минимум один день недели, времена 1–4 без повторов в формате `HH:mm` (у «Один раз» — одно), дата окончания не раньше даты начала. При создании и изменении расписания в нём должен быть хотя бы один момент строго позже текущего момента устройства; клиент сверяет условие при каждом изменении и повторно перед отправкой (время идёт, пока форма открыта); при нарушении отправка блокируется. Сервер проверяет то же независимо.

* Клиентская валидация `type`, `value`, `notes` и применимости к виду питомца совпадает с валидацией добавления события (см. [Добавление события — Frontend](dobavlenie-sobytiya-frontend.md)).

* Запросы создания, изменения и замены с новым напоминанием передают `tz` — часовой пояс устройства; даты и времена трактуются как местные для этого пояса.

* Сумма файлов: файлы настроек и собственные файлы напоминания вместе не превышают 10; блок файлов не позволяет превысить лимит (см. «Напоминания — Backend», раздел «Файлы»).

* Питомец напоминания не меняется ни при каком редактировании.

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле / нарушены правила расписания | Форма не отправляется, сообщение рядом с полем |
| Расписание не даёт будущих моментов | Форма не отправляется, сообщение «В выбранном расписании нет будущих напоминаний» |
| Любая ошибка сервера при создании, изменении, замене, удалении, отметке | Показывается понятное сообщение, пользователь остаётся на экране с введёнными данными; повторная попытка возможна (для создания и замены повтор использует тот же `id` / `Idempotency-Key`) |
| Транзиентная ошибка (нет сети, таймаут, 5xx) | Тот же результат: операции с напоминаниями не ставятся в очередь фоновых повторов |
| 404 при открытии напоминания или настроек (уже удалено или закрыто на другом устройстве) | Сообщение «напоминание не найдено», возврат на календарь |
| 404 на `DELETE` | Трактуется как «уже удалено», без сообщения об ошибке |
| 404 на `complete` | Трактуется как «уже закрыто», без сообщения об ошибке |
| 409 на `complete` (напоминание ещё не наступило) | Сообщение об ошибке, календарь обновляется |
| 409 на `detach` (напоминание вакцинации) | Сообщение об ошибке, форма закрывается, календарь обновляется |
| 409 из-за лимита файлов | Сообщение о том, что превышен лимит файлов |
| Ошибка планирования локальных уведомлений | Отдельное сообщение, сохранение не отменяется (см. «Локальные уведомления») |

## Хранение состояния и побочные эффекты

* Операции с напоминаниями (создание, изменение всех, замена одного, удаление, отметка) в сетевом режиме выполняются оптимистично по общим правилам (см. [Общие требования: Оптимистичные обновления (dataSource=network)](../common/obschie-trebovaniya-optimistichnye-obnovleniya.md), раздел «Напоминания»): формы закрываются сразу; карточки созданных напоминаний появляются в календаре сразу, но пока сервер их не подтвердил, на них нельзя нажать; отметка и удаление убирают карточку сразу, удаление можно отменить в окне отмены; изменение сразу обновляет карточки в календаре. Постоянная ошибка откатывает изменение и показывает сообщение. В локальном режиме запись происходит синхронно и отдельный оптимистичный слой не нужен.

* После успешной операции инвалидируются кэши календаря: список дня и сетка месяца (['activities-day', ...], ['activities-calendar', ...]), блок ближайшего события, а также карточки настроек и напоминания. Если операция создала факт (отметка «Выполнено», замена на факт), дополнительно инвалидируются кэши событий питомца (превью, список «События питомца»). Если изменены связанные настройки, дополнительно инвалидируется кэш списка лекарств либо вакцинаций питомца.

* Напоминания не входят в список «События питомца» и в графики динамики — они показываются только в календаре и в блоке ближайшего события.
