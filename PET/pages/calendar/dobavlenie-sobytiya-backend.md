## Назначение

Флоу создаёт новую запись о событии здоровья питомца (взвешивание, температура, кормление, вода, активность, сон, лекарство, гигиена, состояние, выделения, прочее).

## Действующие лица и предусловия

* Инициатор — авторизованный пользователь. Наличие строки в таблице `profile` не требуется.

* Питомец должен существовать, принадлежать инициатору и не быть мягко удалённым.

## Основной сценарий

1. `POST /events`. Тело: pet_id (uuid, обязательно), date (RFC3339, обязательно), type (одно из значений справочника типов события — см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»; обязательно), value (типизированный объект, форма которого определяется type, обязательно — см. "Бизнес-правила и валидация"), notes (строка, опционально, не более 500 символов), опционально заголовок idempotency key (см. "Хранение состояния и побочные эффекты").

2. Система проверяет метод запроса (должен быть POST).

3. Система проверяет авторизацию и извлекает userID.

4. Система разбирает тело запроса как JSON.

5. Если передан idempotency key, ранее уже использованный для этого питомца, система возвращает ранее созданное событие вместо создания нового (см. "Хранение состояния и побочные эффекты").

6. Система проверяет, что все обязательные поля присутствуют: pet_id, date, type, value.

7. Система проверяет, что type — одно из значений справочника типов события (см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md)).

8. Система проверяет, что date — валидная дата в формате RFC3339.

9. Система проверяет value по форме, соответствующей type (см. "Бизнес-правила и валидация"), и длину notes (не более 500 символов).

10. Система разбирает pet_id как UUID.

11. Система ищет питомца по pet_id и userID (`pet.user_id`) — если не найден или принадлежит другому пользователю, возвращает 404.

12. Система проверяет, что питомец не мягко удалён — если удалён, возвращает 400.

13. Система вставляет новое событие в таблицу event.

14. Система читает созданное событие обратно из БД.

15. Система возвращает 201 Created с телом EventResponse (id, date, value, notes, pet_id, pet_name).

## Бизнес-правила и валидация

* Обязательные поля: pet_id, date, type, value. notes — опционально.

* type строго ограничен значениями справочника типов события (см. [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md)).

* `value` — типизированный объект, форма которого определяется значением `type` (размеченное объединение, дискриминатор — `type`). Полная таблица форм `value` по каждому типу события, их единиц измерения и правил валидации — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md); эта страница форму `value` не переопределяет.

* Сервер валидирует `value` по форме, соответствующей переданному `type`, — единой для валидации на backend и схемы формы на frontend.

* Поля, не описанные формой `value` для данного `type`, приводят к 400, а не игнорируются молча: иначе опечатка в имени поля привела бы к тихой потере введённых пользователем данных.

* `value` хранится в столбце `event.value` типа `jsonb NOT NULL` — значение является структурированным объектом, а не строкой.

* `notes` — только свободный комментарий владельца; `notes` никогда не является носителем структурированного факта. Любой факт, нужный для отображения карточки события, фильтрации или графика, ОБЯЗАН быть полем `value`.

* date должен строго соответствовать формату RFC3339 и явно проверяется на этапе валидации запроса, а не полагается на реакцию базы данных на некорректный формат.

* notes ограничено 500 символами.

* Питомец должен принадлежать инициатору — при нарушении система возвращает 404, а не 403, чтобы не подтверждать факт существования чужого питомца (см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md)).

* Нельзя создать событие для мягко удалённого питомца.

* Дата события (date) может относиться как к прошлому, так и к будущему без дополнительных ограничений диапазона — владелец может задокументировать событие с любой датой (например, добавить запись задним числом или запланировать будущий приём). Симметричное правило действует и на клиенте — см. страницу "Добавление события — Frontend".

* Дублирующиеся события (тот же pet_id + type + date) в текущей итерации разрешены — сервер не выполняет проверку на похожие/повторяющиеся события.

## Хранение состояния и побочные эффекты

Добавляет одну строку в таблицу event. Не изменяет данные питомца.

Для защиты от дублирования события при обрыве соединения и повторной отправке запроса клиентом `POST /events` поддерживает опциональный заголовок `Idempotency-Key`.

**Формат.** Значение заголовка — UUID v4, сгенерированный клиентом один раз при открытии формы добавления события (см. страницу «Добавление события — Frontend»). Если заголовок передан, но не является валидным UUID — 400 (см. «Обработка ошибок»).

**Хранение и дедупликация.** Ключ хранится не в отдельной таблице, а прямо в строке события: столбец `event.idempotency_key` (nullable text) с уникальным составным индексом:

```
CREATE UNIQUE INDEX event_pet_idempotency_key_idx
  ON event (pet_id, idempotency_key)
  WHERE idempotency_key IS NOT NULL;
```

Индекс частичный (`WHERE idempotency_key IS NOT NULL`), чтобы не конфликтовали события без ключа. Уникальность — на пару (pet_id, idempotency_key), а не глобально на ключ: один и тот же UUID, случайно сгенерированный для разных питомцев, не считается дубликатом.

**Алгоритм (шаг «если передан idempotency key» основного сценария):**

1. Если заголовок `Idempotency-Key` не передан — пропустить этот шаг, событие создаётся как обычно (`idempotency_key` = NULL).

2. Перед вставкой выполнить `SELECT` события по `(pet_id, idempotency_key)`. Если строка найдена — вернуть её как ответ `201 Created` с тем же телом `EventResponse`, что и при первом успешном создании — новая строка НЕ вставляется, обработка на этом завершается.

3. Если строка не найдена — выполнить обычную вставку, включая переданный `idempotency_key` в строку. Гонка параллельных запросов с одним и тем же ключом (двойной тап, повторная отправка при таймауте) закрывается уникальным индексом: вторая параллельная вставка падает с нарушением уникального индекса — сервер трактует это НЕ как 500, а повторяет шаг 2 (SELECT) и возвращает найденную строку, аналогично обработке гонки регистрации по login (см. страницу «Вход и регистрация — Backend», §3b).

**Окно дедупликации.** Не ограничено по времени — пока строка события существует (не мягко удалена), тот же `(pet_id, idempotency_key)` продолжает возвращать это же событие. Мягкое удаление события не освобождает ключ — повторная отправка с тем же ключом после удаления события всё равно вернёт данные удалённой записи (200/201 с тем же телом), а не создаст новую; отдельная очистка/TTL ключей не предусмотрена для MVP, объём одной строки на событие незначителен.
