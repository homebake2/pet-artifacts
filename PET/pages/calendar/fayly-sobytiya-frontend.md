## Назначение

Управление файлами события (до 10 штук суммарно — фотографий и документов вместе): добавление, удаление отдельного файла и отображение уже прикреплённых. В этой итерации отдельного экрана «просмотр события с файлами» нет — управление встроено в уже существующие экраны добавления и редактирования события (те же формы, что для остальных полей события), а список событий календаря показывает только количество прикреплённых файлов, без доступа к ним напрямую. Загрузка выполняется напрямую в S3 по presigned URL, полученному от backend — фронтенд никогда не хранит и не использует S3-ключи (см. «Общие требования: S3-хранилище файлов»).

## Действующие лица и предусловия

* Инициатор — владелец питомца, которому принадлежит событие.

* Управление файлами доступно на форме редактирования события (где уже известен id события), а также на форме добавления события — с оговоркой, описанной в разделе «Файлы при добавлении события» ниже: фактическая загрузка на форме добавления откладывается до создания события.

## Раздел «Файлы» в форме события

Формы добавления и редактирования события (см. «Добавление события — Frontend», «Редактирование события — Frontend») получают дополнительный раздел «Файлы», независимый от остальных полей формы:

* Список уже прикреплённых файлов (для формы редактирования — заполняется из `files` ответа `GET /events/{id}`, см. «Файлы события — Backend»; для формы добавления — изначально пуст). Фотография показывается миниатюрой, документ — иконкой вида файла (например, по расширению/`content_type`) вместе с `filename`; для документа с пустым `filename` (см. «Файлы события — Backend», где это может возникнуть при данных, созданных не через это приложение) показывается нейтральная подпись «Документ» вместо пустой строки.

* Кнопка «Добавить файл», открывающая выбор источника: «Сделать фото», «Выбрать из галереи» (изображение) или «Выбрать документ» (системный выбор файлов, ограниченный форматом PDF — см. «Файлы события — Backend», допустимые `content_type`). Кнопка скрывается/блокируется, если уже прикреплено (для формы редактирования) или локально выбрано (для формы добавления) 10 файлов — суммарно, без разделения на фото и документы.

* Каждый элемент списка — с кнопкой удаления (крестик/иконка корзины).

## Добавление файлов (событие уже существует — форма редактирования)

1. Пользователь выбирает «Добавить файл» и один или несколько файлов через системный пикер (за один раз можно выбрать несколько изображений; выбор документа — по одному, так как системные пикеры документов на мобильных платформах обычно рассчитаны на одиночный выбор).

2. Если число уже прикреплённых файлов события плюс число выбранных в этот раз превышает 10, пикер не позволяет завершить выбор сверх оставшегося количества слотов, и система поясняет ограничение («Осталось мест: N»).

3. Для изображений система приводит каждый выбранный файл к одному из допустимых MIME-типов (`image/jpeg`, `image/png`, `image/webp`); конвертация неподдерживаемого исходного формата (например, HEIC) — ответственность клиента. Для документов допустим только `application/pdf` — выбор пикера уже ограничен этим форматом на уровне шага 1, отдельной клиентской конвертации документов нет.

4. Раздел «Файлы» переходит в состояние загрузки (блокирует повторное добавление до завершения) — по общему правилу [Общие требования: UI-паттерны запросов](../common/obschie-trebovaniya-ui-patterny-zaprosov.md).

5. Клиент загружает выбранные файлы последовательно, один за другим (не параллельно — единый и предсказуемый индикатор прогресса вида «Загружено N из M»): для каждого — `POST /files/upload-url` с телом `{owner_type: "event_file", owner_id: <id события>, content_type, filename}`, где `filename` передаётся только для документов (исходное имя выбранного файла) и не передаётся для фотографий (см. «Файлы события — Backend»); затем `PUT upload_url` напрямую в S3; затем `POST /files/{file_id}/complete`.

6. После успешного `complete` каждого файла система немедленно добавляет его в список раздела «Файлы» (используя локально выбранный файл — превью изображения или имя документа — как немедленное отображение, до следующего запроса данных события с сервера, см. «Хранение состояния и побочные эффекты»).

7. Состояние загрузки снимается после того, как обработаны все выбранные файлы — как успешно, так и с ошибкой (см. «Обработка ошибок»).

## Удаление файла

1. Пользователь нажимает кнопку удаления на конкретном элементе списка раздела «Файлы».

2. Система показывает диалог подтверждения.

3. После подтверждения элемент переходит в состояние загрузки, клиент вызывает `DELETE /files/{file_id}`, где `file_id` — значение поля `file_id` соответствующего элемента `files` (для уже сохранённых на сервере файлов) — либо, если файл был добавлен в рамках текущего открытия формы редактирования, тот же `file_id`, полученный на шаге 5/6 сценария «Добавление файлов».

4. После успешного ответа файл исчезает из списка; освобождается один слот из лимита 10.

## Отображение количества файлов в списке событий

Список карточек событий выбранного дня на экране календаря (см. «Просмотр календаря — Frontend») показывает по полю `files_count` соответствующего элемента (см. «Файлы события — Backend») компактный значок «скрепка + число» на карточке события, если `files_count > 0`; если `files_count = 0`, значок не отображается. Значок не кликабелен и не открывает список файлов — единственный способ увидеть и открыть сами файлы в этой итерации — экран редактирования события (см. «Добавление файлов» и «Удаление файла» выше); нажатие на карточку события по-прежнему открывает редактирование целиком, а не какое-то отдельное действие с файлами.

## Файлы при добавлении события

Форма добавления события (см. «Добавление события — Frontend») позволяет выбрать до 10 файлов локально (тем же разделом «Файлы», что и на форме редактирования), но фактическая загрузка невозможна до того, как событие создано и получен его `id` (см. «Файлы события — Backend» — `owner_id` в `POST /files/upload-url` это id события). Поэтому:

1. Пользователь выбирает от 0 до 10 файлов на форме добавления события — они хранятся только в памяти экрана (локальные URI/пути выбранных файлов, для документов — также их имя), не загружаются никуда до сохранения формы.

2. При нажатии «Сохранить» система сначала выполняет обычный сценарий создания события (`POST /events`, см. «Добавление события — Frontend»).

3. Если создание события успешно и на форме были выбраны файлы — система сразу выполняет сценарий «Добавление файлов» (шаги 3–6 выше) для только что полученного id события, не показывая пользователю это как отдельный шаг (единый индикатор загрузки на форме до завершения обоих действий, с прогрессом «Загружено N из M»).

4. Если создание события завершилось ошибкой — загрузка файлов не выполняется, форма ведёт себя как описано в «Добавление события — Frontend» (пользователь остаётся на форме, данные не теряются, включая выбранные локально файлы).

5. Если создание события успешно, но загрузка одного или нескольких файлов завершилась ошибкой — событие уже создано и не откатывается: система переходит к обычному успешному завершению добавления события (закрытие формы, снек об успехе, возврат на календарь — см. «Добавление события — Frontend»), а файлы, которые не удалось загрузить, дополнительно перечисляются в отдельном ненавязчивом уведомлении («N файлов не удалось добавить»); пользователь может добавить оставшиеся файлы позже, открыв событие на редактирование (см. «Добавление файлов» выше). Откат создания события из-за сбоя загрузки одного или нескольких файлов не выполняется.

## Бизнес-правила и валидация

* Файлы события не входят в diff-механизм формы редактирования (см. «Редактирование события — Frontend») — это отдельные немедленные действия (добавление/удаление), а не поле, отправляемое вместе с остальными изменениями по кнопке «Сохранить изменения» формы.

* Лимит 10 файлов на событие (фото и документы суммарно) проверяется клиентом до начала загрузки и повторно сервером на каждом `complete` (см. «Файлы события — Backend»); клиент обязан корректно обработать `409` (см. «Обработка ошибок»), а не полагаться исключительно на собственный подсчёт.

* Для документов клиент ОБЯЗАН передавать `filename` при `POST /files/upload-url` — исходное имя выбранного файла, без модификаций (см. «Файлы события — Backend»). Для фотографий `filename` не передаётся.

* Ограничение размера выбираемого файла на стороне клиента в этой итерации не вводится (см. «Файлы события — Backend» — лимит размера не установлен и на бэкенде).

* Владение событием проверяется backend на каждом из трёх generic-эндпоинтов (`upload-url`/`complete`/`delete`, см. «Общие требования: Файлы сущностей») — фронтенд не выполняет собственной проверки.

* Изменение порядка файлов (reorder) не поддерживается в этой итерации — порядок в списке полностью определяется порядком, в котором файлы были успешно добавлены (см. «Файлы события — Backend»).

* Отдельный полноэкранный просмотр/скачивание содержимого файла (открытие фотографии на весь экран, открытие PDF во внешнем просмотрщике) в этой итерации не реализуется — раздел «Файлы» показывает миниатюру/иконку и позволяет только добавлять и удалять файлы, не просматривать их содержимое.

## Обработка ошибок

| Ситуация                                                                     | Что должна сделать система                                                                                                                                     |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ошибка на любом из шагов загрузки одного из файлов (`upload-url`, `PUT` в S3, `complete`) | Загрузка этого файла прерывается, клиент переходит к следующему файлу в очереди (если есть); по завершении всей очереди показывается одно итоговое сообщение с числом файлов, которые не удалось добавить, если таких больше нуля; уже успешно добавленные файлы остаются в списке. |
| `409` от `POST /files/{file_id}/complete` (лимит 10 достигнут)                 | Обрабатывается так же, как прочие ошибки загрузки этого конкретного файла (см. строку выше), с уточняющим текстом «Достигнут лимит файлов события» вместо общей формулировки. |
| Ошибка `DELETE /files/{file_id}`                                               | Состояние загрузки на этом элементе снимается, показывается сообщение об ошибке, файл остаётся в списке как есть.                                              |
| 404 (событие не найдено/удалено, либо принадлежит мягко удалённому питомцу) на любом из эндпоинтов файлов | Обрабатывается так же, как 404 на остальных эндпоинтах события (см. «Редактирование события — Frontend»).                                                      |
| Сбой загрузки одного или нескольких файлов сразу после успешного создания события | См. «Файлы при добавлении события», шаг 5 — обычное успешное завершение добавления события плюс отдельное уведомление о непровеченных файлах, без отката создания события. |

## Хранение состояния и побочные эффекты

* После успешного добавления или удаления файла система инвалидирует кэш данных этого события и кэш активностей затронутого питомца (те же кэши, что инвалидируются при обычном редактировании события, см. «Редактирование события — Frontend»), чтобы форма редактирования и список событий календаря отразили актуальные `files`/`files_count` при следующем открытии.

* Немедленное отображение только что добавленного файла (шаг 6 сценария «Добавление файлов») — временное клиентское состояние экрана, не заменяющее последующий `files` с сервера.
