## Назначение

К событию можно прикрепить до 10 файлов суммарно — фотографий и документов вместе (например, фото зафиксированного состояния и скан результата анализа к одному и тому же событию), а не двух отдельных лимитов по 10 каждого вида. Загрузка, чтение и удаление отдельного файла выполняются через общий generic-механизм («Общие требования: Файлы сущностей») с кардинальностью «до N» (N = 10) — отдельных endpoint'ов вида `/events/{id}/files` у события нет. Эта страница фиксирует то, что специфично для события: значение `owner_type`, правило проверки владения, допустимые виды файлов, лимит галереи и два разных представления списка файлов в ответах событий — полное (для одного события) и в виде счётчика (для списков).

В этой итерации отдельного экрана «детали события» с просмотром прикреплённых файлов не строится — прикрепление и удаление файлов происходит через экраны добавления/редактирования события (см. «Файлы события — Frontend»); соответственно и требования этой страницы к чтению ориентированы на то, что уже нужно этим двум экранам и списку событий календаря, а не на гипотетический будущий экран просмотра.

## Подключение к реестру типов владельцев

Событие зарегистрировано в реестре («Общие требования: Файлы сущностей», раздел «Реестр типов владельцев») так:

| `owner_type` | `owner_id` | Кардинальность | Проверка владения | Допустимые `content_type` |
| --- | --- | --- | --- | --- |
| `event_file` | `event.id` | до 10 | `event.id = owner_id AND event.deleted_at IS NULL AND EXISTS (SELECT 1 FROM pet WHERE pet.id = event.pet_id AND pet.user_id = userID AND pet.deleted_at IS NULL)` | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` |

Проверка владения здесь совпадает с проверкой, используемой при создании и редактировании события (см. «Добавление события — Backend», «Редактирование события — Backend») — включая то, что мягко удалённый питомец блокирует операцию. Это отличается от удаления самого события (см. «Удаление события — Backend»), где мягко удалённый питомец операцию не блокирует, — для файлов сознательно выбрано более строгое правило создания/редактирования, а не правило удаления, поскольку прикрепление файла — это добавление новых данных к событию, а не их устранение. Отдельного, специфичного только для файлов, правила владения не вводится.

**Виды файлов.** Ровно два вида, различаемые исключительно по `content_type` — отдельного поля «вид файла» в модели нет:

* **Фотография** — `content_type` начинается с `image/` (в допустимом перечне это `image/jpeg`, `image/png`, `image/webp`).
* **Документ** — любой другой допустимый `content_type` (в этой итерации это только `application/pdf`; другие форматы документов не поддерживаются и дают `400`, как и любой недопустимый `content_type`, см. «Общие требования: Файлы сущностей»).

**Имя файла.** Для документов клиент ОБЯЗАН передавать `filename` в `POST /files/upload-url` (см. «Общие требования: Файлы сущностей» — поле общего механизма) — без него документ невозможно осмысленно подписать в UI (см. «Файлы события — Frontend»). Для фотографий `filename` не требуется и не используется на чтении, даже если передан. Backend НЕ выполняет серверной валидации обязательности `filename` для документов в этой итерации — некорректно сформированный клиентом запрос (документ без `filename`) не отклоняется отдельным `400`, а приводит к тому, что документ читается с пустым именем (см. «Чтение», fallback-подпись); это сознательно принятое упрощение для MVP, а не пробел: единственный клиент, вызывающий этот протокол, — собственное приложение, всегда передающее `filename` для документов (см. «Файлы события — Frontend»).

Загрузка и удаление файлов события выполняются вызовом generic-эндпоинтов с `owner_type = "event_file"` и `owner_id = <id события>` — полный протокол (presigned PUT URL, подтверждение, лимит кардинальности, удаление) описан на странице «Общие требования: Файлы сущностей» и не дублируется здесь.

## Чтение: `files` и `files_count` в ответах события

Отдельного эндпоинта чтения списка файлов события нет (см. «Общие требования: Файлы сущностей», раздел «Область действия» — чтение всегда специфично для сущности). Форма события, в которой возвращаются файлы, различается по тому, читается ли одно событие целиком или список событий:

* **Одно событие** — `EventResponse`, форма, используемая `POST /events` и `GET /events/{id}` (см. «Добавление события — Backend»; `GET /events/{id}` используется для предзагрузки формы редактирования, см. «Редактирование события — Frontend»), получает новое поле `files`: массив (может быть пустым) объектов `{file_id, url, content_type, filename}`, не более 10 элементов. `filename` — `null` для фотографий и для документов, у которых оно не было передано при загрузке (см. выше).

* **Список событий** — элементы `GET /activities` (карточка питомца), элементы `GET /activities/day` (список дня в календаре) и элементы `GET /pet/{id}/events` (см. «Просмотр календаря — Backend») получают новое поле `files_count`: целое число прикреплённых файлов события (0, если файлов нет), БЕЗ полного списка и БЕЗ presigned URL. Агрегат `GET /activities/calendar` (сетка месяца) полей событий не содержит вовсе — там нет ни `files`, ни `files_count`, только количество событий по дням. Список событий используется только для карточек списка/календаря, которым для отображения значка «есть файлы (N)» не нужны ни ссылки на сами файлы, ни их состав — а массовое подписание presigned GET URL для каждого файла каждого события диапазона (до 366 дней) было бы затратной операцией без практической пользы на этом экране (см. «Файлы события — Frontend», раздел «Отображение количества файлов в списке событий»). Открыть и посмотреть содержимое конкретного файла в этой итерации можно только через полную форму `EventResponse` — на экране редактирования события (см. «Файлы события — Frontend»), не из списка/календаря.

Формирование обоих полей: сервер выбирает из таблицы `file` строки с `owner_type = 'event_file' AND owner_id = <id события> AND confirmed_at IS NOT NULL`, упорядоченные по `position` по возрастанию (см. «Общие требования: Файлы сущностей», раздел «Подтверждение загрузки» — назначение `position` при кардинальности «до N»). Для `files` каждая строка превращается в элемент массива с presigned GET URL (TTL — см. «Общие требования: S3-хранилище файлов») как `url` и `id` как `file_id` (нужен клиенту для `DELETE /files/{file_id}`, см. «Файлы события — Frontend», раздел «Удаление файла»). Для `files_count` presigned URL не подписываются вовсе — достаточно `COUNT(*)` по тому же условию, без выборки самих строк.

Проверка владения для чтения уже выполняется этими эндпоинтами при выборке самого события (см. «Просмотр календаря — Backend») — отдельной повторной проверки владения специально для `files`/`files_count` не требуется.

Каждый `url` в `files` — временная ссылка, а не постоянный адрес (тот же принцип, что и `photo_url` питомца, см. «Фотография питомца — Backend»): клиент не должен сохранять её дольше времени жизни экрана и обязан быть готов к тому, что при следующей загрузке того же события `url` будет другой строкой с новым сроком действия.

## Бизнес-правила и валидация

* `file_id` файлов не входит в тело `POST /events` и `PATCH /events/{id}` — файлы управляются исключительно generic-эндпоинтами `/files/...` с `owner_type = "event_file"`, а не вместе с остальными полями события.

* Лимит — не более 10 подтверждённых файлов на одно событие (фото и документы вместе), обеспечивается кардинальностью «до N» реестра (см. «Общие требования: Файлы сущностей»): 11-я попытка `POST /files/{file_id}/complete` для того же события возвращает `409 Conflict` — клиент обязан сначала удалить один из существующих файлов.

* Порядок файлов в `files` — это порядок их подтверждения (`position`, назначаемый при `complete`, см. «Общие требования: Файлы сущностей»); изменение порядка (reorder) уже загруженных файлов не поддерживается в этой итерации.

* Мягкое удаление события не удаляет каскадно его строки в таблице `file` и не удаляет объекты в S3 — таблица `file` не знает о soft-delete владельца. Это осознанное решение, а не пробел: мягко удалённое событие уже исключено из всех эндпоинтов чтения (см. «Удаление события — Backend»), поэтому его файлы перестают быть доступны на чтение вместе с самим событием; отдельная очистка осиротевших строк `file`/объектов S3 не реализуется в этой итерации, по той же логике, что и бессрочное хранение мягко удалённых событий.

* Ограничение размера файла в этой итерации не устанавливается ни на уровне события, ни на уровне generic-механизма (см. «Общие требования: Файлы сущностей»).

## Хранение состояния и побочные эффекты

Загрузка и удаление файлов события изменяют только таблицу `file` (см. «Общие требования: Файлы сущностей») — таблица `event` полем для файлов не дополняется, `files`/`files_count` вычисляются на чтении присоединением к `file`. `position` монотонно растёт в пределах пары (`event_file`, `<id события>`) по мере подтверждения новых файлов и не переиспользуется и не компактируется при удалении одного из файлов — оставшиеся сохраняют свои прежние значения `position`; это не создаёт видимых «дыр» в ответе `files`, так как клиент лишь сортирует элементы по возрастанию `position`, не полагаясь на их непрерывность. Других побочных эффектов, специфичных для события, нет.
