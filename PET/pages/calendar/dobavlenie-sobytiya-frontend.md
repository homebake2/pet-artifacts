## Назначение

Экран "Добавление события" позволяет пользователю зафиксировать новое событие здоровья питомца: питомец, тип события, значение, дата/время, необязательная заметка.

## Действующие лица и предусловия

* Авторизованный пользователь, у которого есть хотя бы один питомец. Если питомцев нет, см. отдельное поведение в разделе "Обработка ошибок".

* Экран открывается с вкладки "Календарь" по кнопке "+", опционально с предзаполненными параметрами petId/date.

## Основной сценарий

1. Система открывает экран добавления события, при наличии параметров petId/date предзаполняет ими форму.

2. Форма содержит поля: Питомец (Select, показывается только если petId не передан), Тип события (6 вариантов: weight, urine, defecation, vomit, diarrhea, other — см. [Общие требования: Единый источник enum-словарей](../common/obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md)), Значение (формат зависит от типа события, обязательно — см. "Бизнес-правила и валидация"), Дата, Время, Заметка (опционально).

3. При нажатии "Сохранить" система выполняет клиентскую валидацию формы; при ошибке валидации отправка блокируется, и система показывает пользователю, какие поля некорректны.

4. Раздельные поля "Дата" и "Время" перед отправкой конвертируются маппером формы в единое значение `date` в формате RFC3339: дата и время интерпретируются в локальном часовом поясе устройства пользователя и сериализуются в RFC3339 со смещением этого часового пояса (или эквивалентным UTC-представлением) — на сервер всегда уходит одно корректное RFC3339-значение, а не два независимых поля.

5. После успешной валидации система выполняет сохранение: онлайн — `POST /events` с клиентским idempotency key (см. "Хранение состояния и побочные эффекты"); офлайн — генерирует локальный UUID и добавляет событие в локальные данные питомца (pet.events).

6. Система дожидается результата операции сохранения (ответа сервера онлайн, либо завершения локальной записи офлайн) и только после этого показывает снек с сообщением об успешном сохранении, закрывает экран и возвращает пользователя на календарь.

## Бизнес-правила и валидация

* Клиентская схема валидации формы обязана требовать те же поля и тот же формат, что и сервер, чтобы форма никогда не отправляла заведомо отклоняемый запрос:

* petId — обязательно.

* type — обязательно, одно из 6 предопределённых значений: weight, urine, defecation, vomit, diarrhea, other (см. [Общие требования: Единый источник enum-словарей](../common/obschie-trebovaniya-edinyi-istochnik-enum-slovarei.md)).

* value — обязательно, формат зависит от type (per-type схема, единая для Zod-валидации на FE и валидации на BE, см. задачи PET-124 (FE) и PET-125 (BE)); точный формат и валидация по каждому type — см. таблицу ниже.

| type                                          | Тип поля формы / Zod-схема                                                                                                                                                                                            | Валидация на клиенте                                                                                                                        | Роль notes                                                                                     |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `weight`                                      | числовой Input (клавиатура decimal-pad), значение сериализуется в строку с точкой как разделителем перед отправкой, например `"4.5"`; единица измерения — кг, фиксирована UI-лейблом, отдельного поля для единицы нет | `z.coerce.number().min(0.01).max(200)` — диапазон совпадает с серверным (0.01–200 кг); ошибка формы, если пусто, не число или вне диапазона | опциональный комментарий                                                                       |
| `urine` / `defecation` / `vomit` / `diarrhea` | Select с двумя вариантами (не свободный текст): «в норме» → `"normal"`, «отклонение» → `"abnormal"`                                                                                                                   | `z.enum(["normal", "abnormal"])` — форма не позволяет ввести значение вне этих двух вариантов, поле обязательно к выбору                    | основной источник подробностей наблюдения (цвет, частота, консистенция и т.п.)                 |
| `other`                                       | текстовый Input — краткое обозначение события                                                                                                                                                                         | `z.string().min(1).max(50)` — не пусто и не длиннее 50 символов                                                                             | подробности и контекст события; value здесь не заменяет notes, а лишь коротко называет событие |

Схема формы использует discriminated union по полю type: при смене типа события поле «Значение» полностью перерисовывается под новый тип (числовой Input, Select или текстовый Input) и предыдущее значение сбрасывается, чтобы не остаться, например, числом «4.5» в текстовом поле для other. См. задачу PET-124 ниже.

* Для type=other: value — краткое обозначение события (например, короткая метка, что произошло), notes — подробности и контекст; это разграничение действует только для other, для остальных типов value несёт основной структурированный факт, а notes остаётся свободным комментарием.

* date — обязательно, всегда передаётся в формате RFC3339 (см. "Основной сценарий").

* notes — опционально (не более 500 символов).

* Дата события может относиться как к прошлому, так и к будущему без каких-либо ограничений диапазона на стороне клиента: в date-picker'е нет верхней границы (максимальной даты) — пользователь может задокументировать событие задним числом или запланировать будущее событие, симметрично правилу на бэкенде (см. страницу "Добавление события — Backend").

* Дублирующиеся события (тот же питомец + тип + дата/время) в текущей итерации разрешены без каких-либо предупреждений — форма не проверяет и не блокирует создание похожего события. Предупреждение об этом на будущее вынесено в отдельную задачу с низким приоритетом, см. PET-129 ниже.

## Обработка ошибок

* Если обязательные поля не заполнены или не соответствуют формату для выбранного type, система блокирует отправку формы и указывает, какие поля требуют внимания, до отправки запроса на сервер.

* Если операция сохранения завершилась ошибкой (сетевой сбой, 400/404/500 от сервера — онлайн, либо ошибка записи в локальное хранилище — офлайн), система должна показать пользователю понятное сообщение об ошибке (snackbar) и оставить пользователя на экране формы с введёнными данными, см. также [Общие требования: Формат ошибок API](../common/obschie-trebovaniya-format-oshibok-api.md).

* 404 по указанному pet_id (питомец не найден или принадлежит другому пользователю) обрабатывается отдельно от прочих ошибок: система показывает конкретное сообщение "питомец не найден" вместо общего snackbar об ошибке сохранения, см. задачу PET-132 ниже.

* Если у пользователя нет ни одного питомца и он пытается выбрать питомца в поле "Питомец", система предлагает создать питомца прямо с этого экрана; после успешного создания питомца пользователь возвращается на экран добавления события с этим питомцем, предзаполненным в поле "Питомец", см. задачу PET-131 ниже.

* На время выполнения запроса сохранения кнопка "Сохранить" должна быть заблокирована и показывать индикатор состояния сохранение, чтобы предотвратить повторную отправку той же формы.

## Хранение состояния и побочные эффекты

* Онлайн: после успешного 201 Created система должна инвалидировать кэш активностей (['activities', petId, ...]) затронутого питомца, чтобы календарь и карточка питомца сразу отразили новое событие без ручного обновления.

* Офлайн: новое событие сразу дописывается в локальные данные питомца (pet.events) и становится видимым в календаре немедленно. Стратегия последующей синхронизации офлайн-созданных событий с сервером будет описана отдельно — см. [Локальный режим (dataSource=local) — заглушка](../common/lokalnyi-rezhim-datasource-local-zaglushka.md).

**Idempotency key.** Для защиты от дублирования события при обрыве соединения и повторной отправке формы клиент генерирует и передаёт заголовок `Idempotency-Key` вместе с запросом `POST /events` (см. серверную часть механизма — страница «Добавление события — Backend», раздел «Хранение состояния и побочные эффекты»). Точный протокол:

1. Ключ — UUID v4, генерируется один раз при открытии формы (например, через `crypto.randomUUID()`) и сохраняется в состоянии формы на весь срок её открытия, а не пересоздаётся на каждую попытку отправки — иначе повтор после сетевого сбоя получит новый ключ и защита не сработает.

2. Ключ передаётся в заголовке `Idempotency-Key` запроса `POST /events`.

3. Если сохранение завершилось ошибкой сети/таймаутом и пользователь повторно нажимает «Сохранить» (или форма делает retry автоматически), тот же самый ключ передаётся повторно — сервер по нему либо создаст событие один раз, либо вернёт уже созданное ранее (см. алгоритм на backend-странице), поэтому дубликат на сервере не возникает независимо от числа повторов.

4. После успешного сохранения и закрытия формы ключ не переиспользуется: следующее открытие формы добавления события генерирует новый UUID.

Офлайн-режим (dataSource=local) этот заголовок не использует — локальная запись события защищена от дублирования иначе (генерацией локального UUID события напрямую), см. выше «Основной сценарий».
