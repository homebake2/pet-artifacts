## Назначение

Экран "Добавление события" позволяет пользователю добавить новую запись о здоровье питомца одного из двух видов: «Уже произошло» (факт — событие, которое уже случилось; описано на этой странице) или «Напоминание» (запланированное событие, о котором приложение напомнит уведомлениями; описано в [Напоминания — Frontend](napominaniya-frontend.md)). Для факта задаются питомец, тип события, значение, дата/время и необязательная заметка.

## Действующие лица и предусловия

* Авторизованный пользователь, у которого есть хотя бы один питомец. Если питомцев нет, см. отдельное поведение в разделе "Обработка ошибок".

* Экран открывается с вкладки "Календарь" по действии "+", опционально с предзаполненными параметрами petId/date.

## Основной сценарий

1. Система открывает экран добавления события, при наличии параметров petId/date предзаполняет ими форму. Добавление выполняется по шагам; первый шаг — «Вид записи». Пользователь выбирает один из двух вариантов (выбор обязателен, предвыбранного варианта нет); переход к следующему шагу доступен после выбора. Тексты шага:

   * заголовок — «Что вы хотите добавить?»;
   * «Уже произошло» — пояснение «Запись о том, что событие уже случилось: например, покормили питомца или сходили к ветеринару»;
   * «Напоминание» — пояснение «Событие ещё впереди: приложение напомнит о нём в указанное время».

   Выбор «Напоминание» ведёт на шаги «Данные события» и «Расписание» (расписание задаётся так же гибко, как в разделе «Лекарства»), описанные в [Напоминания — Frontend](napominaniya-frontend.md), раздел «Создание». Выбор «Уже произошло» ведёт на шаг «Данные события» (факт), описанный ниже и составляющий остальную часть этой страницы. Имеется возможность вернуться на предыдущий шаг; введённые данные при этом не теряются, а питомец, тип, значение и заметка сохраняются и при смене вида записи (дата и время — только если остаются допустимыми для нового вида).

2. Шаг «Данные события» (факт). Форма содержит поля: Питомец (Select, показывается только если petId не передан), Тип события (Select, ограниченный типами, применимыми к виду выбранного питомца, заданному полем `species`, — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца»; полный перечень значений — [Справочник значений (словари enum)](../common/spravochnik-znachenii-slovari-enum.md), раздел «Календарь — Тип события (event type)»), Значение (состав и вид поля зависят от типа события, обязательно — см. "Бизнес-правила и валидация"), Дата, Время (не позже текущего момента — см. «Бизнес-правила и валидация»), Заметка (опционально). У факта нет уведомлений. При начальном отображении поля «Значение» для выбранного типа события, а также при каждой перерисовке этого поля после смены типа (см. «Бизнес-правила и валидация»), поля, для которых в [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md) (раздел «Значения по умолчанию для полей `value`») определено значение по умолчанию, предзаполняются этим значением; пользователь может изменить его как любое другое значение поля перед сохранением. Если дата из параметра date, с которым открыт экран, находится в будущем, она в форму факта не подставляется — пользователь выбирает дату сам.

3. При сохранении формы система выполняет клиентскую валидацию формы; при ошибке валидации отправка блокируется, и система показывает пользователю, какие поля некорректны.

4. Раздельные поля "Дата" и "Время" перед отправкой конвертируются маппером формы в единое значение `date` в формате RFC3339: дата и время интерпретируются в локальном часовом поясе устройства пользователя и сериализуются в RFC3339 со смещением этого часового пояса (или эквивалентным UTC-представлением) — на сервер всегда уходит одно корректное RFC3339-значение, а не два независимых поля.

5. После успешной валидации система выполняет сохранение: онлайн — `POST /events` с клиентским idempotency key (см. "Хранение состояния и побочные эффекты"); офлайн — генерирует локальный UUID и добавляет событие в локальные данные питомца (pet.events).

6. Онлайн: система не дожидается ответа сервера — оптимистичное применение результата (см. [Общие требования: Оптимистичные обновления (dataSource=network)](../common/obschie-trebovaniya-optimistichnye-obnovleniya.md)) происходит синхронно сразу после шага 5, и система немедленно показывает сообщение об успешном сохранении, закрывает экран и возвращает пользователя на календарь, не дожидаясь ответа `POST /events`. Офлайн: поведение не меняется — система дожидается завершения локальной записи и загрузки выбранных на форме файлов (см. [Файлы события — Frontend](fayly-sobytiya-frontend.md), раздел «Файлы при добавлении события») и только после этого показывает сообщение, закрывает экран и возвращает пользователя на календарь; до этого момента экран остаётся открытым под индикатором сохранения.

## Бизнес-правила и валидация

* Клиентская схема валидации формы обязана требовать те же поля и тот же формат, что и сервер, чтобы форма никогда не отправляла заведомо отклоняемый запрос:

* petId — обязательно.

* type — обязательно, одно из значений справочника типов события, применимых к виду выбранного питомца (см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость типа события к виду питомца»).

* Если поле «Питомец» изменяется на другого питомца после того, как тип события уже выбран, а новый тип неприменим к виду нового питомца — поле «Тип события» и связанное с ним поле «Значение» сбрасываются, симметрично сбросу «Значения» при смене типа (см. ниже).

* value — обязательно, типизированный объект, форма которого определяется type. Полная таблица форм `value`, единиц измерения и правил валидации по каждому типу события — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md); эта страница форму `value` не переопределяет и не дублирует.

* Поле «Значение» формы строится по форме `value` для выбранного типа: числовой ввод, выбор из списка, текстовый ввод либо составное значение из нескольких полей — например, кормление: количество + единица + вид корма; активность: длительность + вид + опционально дистанция; лекарство: название + опционально доза и её единица; температура: значение + вид замера (тело или среда обитания).

* Селекторы вложенных словарей `value`, для которых определена применимость по виду питомца (`hygiene.procedure`, `feeding.food`, `activity.kind` — см. [Модель значения события и реестр метрик](../common/model-znacheniya-sobytiya-i-metriki.md), раздел «Применимость значений вложенных словарей `value` к виду питомца»), показывают только значения, применимые к виду выбранного питомца, — тем же способом, что и селектор «Тип события» фильтруется по применимости `type` (см. выше). Остальные селекторы вложенных словарей показывают полный список значений справочника без фильтрации по виду.

* Схема формы (Zod) — discriminated union по полю `type`: одна ветка на каждый тип события, соответствующая форме `value` этого типа.

* При смене типа события поле «Значение» полностью перерисовывается под новый тип, а предыдущее значение сбрасывается — значение прежнего типа не переносится в поля новой формы даже частично. Поля новой формы получают значение по умолчанию, если оно определено для нового типа (см. «Основной сценарий», шаг 2), а не всегда становятся пустыми.

* Единицы измерения, фиксированные конвенцией (кг, мл, минуты, метры, °C), показываются лейблом поля и пользователем не вводятся. Там, где единица является выбором пользователя (единица кормления, единица дозы лекарства), это отдельное обязательное поле формы.

* Клиентская валидация обязана совпадать с серверной: те же обязательные поля, те же диапазоны и те же множества допустимых значений, чтобы форма никогда не отправляла заведомо отклоняемый запрос и не отклоняла запрос, который сервер принял бы.

* Для type=other поле значения — краткое обозначение события (например, короткая метка, что произошло), notes — подробности и контекст; это разграничение действует только для other, для остальных типов value несёт структурированный факт, а notes остаётся свободным комментарием и никогда не носителем факта.

* date — обязательно, всегда передаётся в формате RFC3339 (см. "Основной сценарий").

* notes — опционально (не более 500 символов).

* Факт — запись о событии, которое уже произошло: выбрать «Дату» и «Время» позже текущего момента устройства нельзя (в выборе даты нет дат в будущем, а при выбранной сегодняшней дате время не может быть позже текущего). Клиент сверяет условие при каждом изменении полей и повторно непосредственно перед сохранением; при нарушении отправка блокируется, и пользователю показывается, что дату/время нужно изменить. Сервер проверяет то же независимо (см. «Добавление события — Backend»). Других ограничений диапазона даты в прошлом нет — можно задокументировать событие задним числом.

* У факта нет уведомлений и признака уведомлений. Запланированные события с уведомлениями создаются как напоминания — см. [Напоминания — Frontend](napominaniya-frontend.md).

* Дублирующиеся события (тот же питомец + тип + дата/время) в текущей итерации разрешены без каких-либо предупреждений — форма не проверяет и не блокирует создание похожего события.

## Обработка ошибок

* Если обязательные поля не заполнены или не соответствуют формату для выбранного type, система блокирует отправку формы и указывает, какие поля требуют внимания, до отправки запроса на сервер.

* Если на момент сохранения дата/время перестали удовлетворять условию «не позже текущего момента» (например, форма была открыта долго), система блокирует отправку и показывает, что дату/время нужно изменить.

* Онлайн: реакция на ошибку `POST /events` (кроме 404 по pet_id, см. ниже) зависит от класса ошибки, см. [Общие требования: Оптимистичные обновления (dataSource=network)](../common/obschie-trebovaniya-optimistichnye-obnovleniya.md), раздел «Классификация ошибок мутации»: транзиентная ошибка (сетевой сбой, таймаут, 5xx) не откатывает оптимистичное изменение — событие ставится в очередь фоновых повторов (см. там же, раздел «Очередь фоновых мутаций и повторные попытки») и показывает только индикацию «синхронизируется»/«требует внимания» (см. там же, раздел «Визуальная индикация фоновой синхронизации»), без немедленного сообщения об ошибке; постоянная ошибка (400/403/409) откатывает оптимистичное изменение и показывает пользователю понятное сообщение об ошибке там, где он находится в этот момент — экран формы к этому моменту уже закрыт и не переоткрывается сам по себе, введённые данные для повторной отправки не сохраняются, см. также [Общие требования: Формат ошибок API](../common/obschie-trebovaniya-format-oshibok-api.md).

* Офлайн: если операция сохранения завершилась ошибкой записи в локальное хранилище, система должна показать пользователю понятное сообщение об ошибке и оставить пользователя на экране формы с введёнными данными.

* Онлайн: 404 по указанному pet_id (питомец не найден или принадлежит другому пользователю) обрабатывается отдельно от прочих ошибок: система откатывает оптимистичное изменение и показывает конкретное сообщение "питомец не найден" вместо общего сообщения об ошибке сохранения — там, где пользователь находится в этот момент, так как экран формы к этому моменту уже закрыт.

* Если у пользователя нет ни одного питомца и он пытается выбрать питомца в поле "Питомец", система предлагает создать питомца прямо с этого экрана; после успешного создания питомца пользователь возвращается на экран добавления события с этим питомцем, предзаполненным в поле "Питомец".

* Онлайн: действие сохранения блокируется и индицирует состояние сохранения на интервал между вызовом и немедленным переходом (см. [Общие требования: Оптимистичные обновления (dataSource=network)](../common/obschie-trebovaniya-optimistichnye-obnovleniya.md), раздел «Соотношение с блокировкой повторной отправки»), а не на всё время запроса `POST /events`. Офлайн: действие сохранения блокируется на время выполнения локальной записи, как и раньше.

## Хранение состояния и побочные эффекты

* Онлайн: кэши списков, через которые достигается событие, получают синхронный оптимистичный патч в момент подтверждения сохранения (см. [Общие требования: Оптимистичные обновления (dataSource=network)](../common/obschie-trebovaniya-optimistichnye-obnovleniya.md), раздел «Какие кэши обновляются оптимистично»), а не ждут 201 Created: превью событий затронутого питомца, список дня и сетка месяца экрана «Календарь» (['activities-day', ...], ['activities-calendar', ...], см. [Просмотр календаря — Frontend](prosmotr-kalendarya-frontend.md)); в список «События питомца» созданное событие не вставляется (получает его фоновым refetch). Пока ответ не пришёл, событие показывает индикацию фоновой синхронизации, а не выглядит подтверждённым, и доступно только для просмотра (см. там же, раздел «Визуальная индикация фоновой синхронизации»). В синхронном патче новое событие добавляется в список дня своей даты с сохранением серверного порядка, а в сетке месяца у этого дня увеличивается счётчик событий и при необходимости выставляется признак уведомлений — пользователь, вернувшись на календарь, сразу видит новое событие. После успешного 201 Created эти кэши получают фоновый refetch для подстраховки, без скелетона (см. там же, раздел «Фоновое обновление»).

* Офлайн: новое событие сразу сохраняется в локальное хранилище и становится видимым в календаре немедленно — точный алгоритм см. [Добавление события — Frontend (dataSource=local)](dobavlenie-sobytiya-frontend-local.md). Данные `local` и `network` — независимые пространства данных без автоматической синхронизации между ними (осознанное архитектурное решение, см. [Локальный режим (dataSource=local) — общая архитектура хранения](../common/lokalnyi-rezhim-datasource-local-zaglushka.md), раздел «Переключение источника данных»).

**Idempotency key.** Для защиты от дублирования события при обрыве соединения и повторной отправке формы клиент генерирует и передаёт заголовок `Idempotency-Key` вместе с запросом `POST /events` (см. серверную часть механизма — страница «Добавление события — Backend», раздел «Хранение состояния и побочные эффекты»). Точный протокол:

1. Ключ — UUID v4, генерируется один раз при открытии формы (например, через `crypto.randomUUID()`) и сохраняется в состоянии формы на весь срок её открытия, а не пересоздаётся на каждую попытку отправки — иначе повтор после сетевого сбоя получит новый ключ и защита не сработает.

2. Ключ передаётся в заголовке `Idempotency-Key` запроса `POST /events`.

3. Если сохранение завершилось ошибкой сети/таймаутом и сохранение повторяется (по запросу пользователя или автоматически), тот же самый ключ передаётся повторно — сервер по нему либо создаст событие один раз, либо вернёт уже созданное ранее (см. алгоритм на backend-странице), поэтому дубликат на сервере не возникает независимо от числа повторов.

4. После успешного сохранения и закрытия формы ключ не переиспользуется: следующее открытие формы добавления события генерирует новый UUID.

Офлайн-режим (dataSource=local) этот заголовок не использует — локальная запись события защищена от дублирования иначе (генерацией локального UUID события напрямую), см. выше «Основной сценарий».
