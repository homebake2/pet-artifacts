## 1. Назначение

Флоу выдаёт новую пару access/refresh токенов взамен ещё не истёкшего refresh-токена, без повторного ввода логина и пароля. Позволяет клиенту продлевать сессию после истечения access-токена (14 дней), пока refresh-токен (60 дней) действителен.

## Смотрите также

* [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md) — атомарность ротации токена на BE, single-session, лимит 1 попытки refresh на клиенте.

## 2. Действующие лица и предусловия

* Инициатор — клиентское приложение, владеющее refresh-токеном.

* Предусловие: сохранённое в БД значение `refresh_token` пользователя должно точно совпадать с переданным токеном.

* Эндпоинт не проверяет заголовок `Authorization` — идентификация пользователя идёт через тело запроса с `refresh_token`.

## 3. Основной сценарий

Запрос: `POST /auth/refresh`

| Поле          | Тип    | Обязательность       |
| ------------- | ------ | -------------------- |
| refresh_token | string | обязательно, непусто |

Сервер ОБЯЗАН выполнить:

1. Проверить метод — POST.

2. Декодировать JSON-тело.

3. Проверить непустоту `refresh_token`.

4. Распарсить и проверить подпись/срок JWT.

5. Проверить claim `type == "refresh"`.

6. Извлечь claims `login` и `id`; проверить, что `id` — валидный UUID.

7. Найти пользователя по `login`, прочитать сохранённый `refresh_token`.

8. Сравнить точно с переданным.

9. Сгенерировать новую пару токенов и атомарно выполнить ротацию: единичным `UPDATE users SET refresh_token = $new WHERE refresh_token = $old` (или эквивалентной транзакцией), проверяя число затронутых строк. Если затронуто 0 строк — переданный токен уже не совпадает с текущим значением в БД (устарел, отозван конкурентным вызовом или уже использован) — сервер ОБЯЗАН вернуть 401 вместо генерации новых токенов.

10. Сохранение нового `refresh_token` — часть той же атомарной операции ротации из предыдущего шага, а не отдельный запрос; если она не завершилась успешно, клиенту возвращается ошибка, а не токены.

11. Вернуть `200 OK` с новой парой токенов:

| Поле          | Тип    | Обязательность |
| ------------- | ------ | -------------- |
| access_token  | string | обязательно    |
| refresh_token | string | обязательно    |

## 4. Бизнес-правила и валидация

* Обновление возможно только по действительному refresh-токену.

* Каждый вызов ОБЯЗАН выдавать новую пару токенов и инвалидировать предыдущий refresh-токен (ротация) — повторное использование старого refresh-токена после успешной ротации ОБЯЗАНО отклоняться сервером с 401. Сравнение и запись нового значения ОБЯЗАНЫ быть одной атомарной операцией на уровне БД (см. шаг ротации в разделе 3) — клиент (см. «Обновление токена — Frontend») полагается на эту атомарность как на данность при дедупликации параллельных вызовов, поэтому оба требования являются взаимозависимыми и должны меняться согласованно.

* Сроки жизни новых токенов те же (14/60 дней), отсчёт начинается заново с момента вызова.

* Ошибка сохранения нового `refresh_token` ОБЯЗАНА возвращаться клиенту как 500 — сервер никогда не отдаёт токены, которые не смог сохранить. Это правило одинаково применяется и к флоу логина, устраняя прежнюю асимметрию обработки ошибок между /auth/login и /auth/refresh.

* Ранее выданный access-токен явно не отзывается этим флоу (это не требуется: обновление продлевает сессию, а не завершает её) — отзыв access-токена относится к flow logout/удаления аккаунта.

* Ограничение частоты вызовов `/auth/refresh` (rate limiting) признано неприоритетным для текущего масштаба системы и сознательно не реализуется в этой версии; при появлении признаков злоупотребления (подбор токенов, автоматизированные атаки) требование должно быть пересмотрено отдельной задачей.

* Если ответ сервера с новой парой токенов не доходит до клиента (потеря сети после успешной ротации на сервере), клиент останется с уже недействительным refresh-токеном; восстановление в этом случае требует полного повторного входа через флоу "Вход и регистрация". Это принятый компромисс — синхронизация подтверждения доставки с клиентом до отказа от старого токена усложнила бы протокол без соразмерной выгоды при текущем масштабе системы.

## 5. Обработка ошибок

| Условие                         | Статус | Код              | Сообщение                                |
| ------------------------------- | ------ | ---------------- | ---------------------------------------- |
| Метод не POST                   | 405    | BAD_REQUEST      | «Method not allowed»                     |
| Тело не JSON                    | 400    | BAD_REQUEST      | «Некорректный запрос»                    |
| refresh_token пуст              | 400    | VALIDATION_ERROR | «Отсутствует refresh_token»              |
| Токен невалиден/истёк           | 401    | UNAUTHORIZED     | «Невалидный или истёкший refresh token»  |
| type ≠ "refresh"                | 401    | UNAUTHORIZED     | «Некорректный тип токена»                |
| Нет claim login/id              | 401    | UNAUTHORIZED     | «Невалидный refresh token»               |
| id не UUID                      | 401    | UNAUTHORIZED     | «Невалидный user id в токене»            |
| Пользователь не найден          | 401    | UNAUTHORIZED     | «Пользователь не найден»                 |
| Ошибка БД при поиске            | 500    | INTERNAL_ERROR   | «Внутренняя ошибка сервера»              |
| Токен не совпадает с БД         | 401    | UNAUTHORIZED     | «Токен отозван или устарел»              |
| Ошибка генерации JWT            | 500    | INTERNAL_ERROR   | «Ошибка генерации access/refresh токена» |
| Ошибка сохранения refresh_token | 500    | INTERNAL_ERROR   | «Ошибка обновления токена»               |
| Успех                           | 200    | —                | новая пара токенов                       |

405 ОБЯЗАН быть документирован в OpenAPI для `/auth/refresh`, как и для остальных auth-эндпоинтов.

## 6. Хранение состояния и побочные эффекты

* `refresh_token` пользователя в БД перезаписывается при каждом успешном вызове.

* История предыдущих токенов не хранится — хранится только текущее актуальное значение.
