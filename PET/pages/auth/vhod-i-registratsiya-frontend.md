## 1. Назначение

Экран аутентификации — единственная точка входа в приложение PetHealth. Система должна объединять вход и регистрацию в одну форму: пользователь вводит логин и пароль один раз, а решение "это новый аккаунт или существующий" принимает бэкенд. Экран также должен предоставлять альтернативный путь без сети — гостевой/локальный режим данных, не связанный с серверным auth-флоу.

## 2. Действующие лица и предусловия

* Инициатор — пользователь мобильного приложения, ещё не выполнивший вход в текущей сессии.

* Экран аутентификации — стартовый маршрут приложения.

* На экране должен быть переключатель источника данных (Локальный/Сетевой, по умолчанию local). Сетевой запрос выполняется только в режиме network; режим local — часть UI и не относится к серверному auth-флоу, реализуется как есть.

* Отдельного экрана "Регистрация" не предусмотрено — одна форма с полями "Логин" и "Пароль" и один сабмит.

## 3. Основной сценарий

1. Пользователь видит логотип, заголовок, форму (логин, пароль), подсказку об автоматической регистрации, кнопку "Продолжить без аккаунта" и переключатель источника данных.

2. Пользователь вводит `login` (мин. 2 символа) и `password` (мин. 8 символов на клиенте, синхронизировано с серверной валидацией) и нажимает "Войти".

3. Клиент ОБЯЗАН выполнить валидацию длины полей до отправки запроса (zod-схема или эквивалент); при нарушении запрос не отправляется.

4. Клиент отправляет `POST /auth/login` с телом:

   | Поле     | Тип    | Обязательность |
   | -------- | ------ | -------------- |
   | login    | string | обязательно    |
   | password | string | обязательно    |

5. При успешном ответе `200 OK` с телом:

   | Поле          | Тип    | Обязательность |
   | ------------- | ------ | -------------- |
   | access_token  | string | обязательно    |
   | refresh_token | string | обязательно    |

   клиент ОБЯЗАН сохранить пару токенов и выполнить переход на главный экран.

6. Гостевой вход ОБЯЗАН использовать отдельный клиентский путь (не фиксированные `login`/`password` = "quest", которые перестают проходить серверную валидацию пароля ≥8 символов, см. решение выше). Клиент ОБЯЗАН сгенерировать и персистентно хранить стабильный локальный идентификатор устройства/гостевой сессии и передавать его на гостевой путь входа на бэкенде, который создаёт пользователя с рандомным логином и флагом «гость». Миграция гостя в постоянный аккаунт не входит в эту версию — отдельная будущая фича.

7. Единственная точка вызова серверного auth на клиенте — `postLogin`. Отдельный вызов регистрации (`postRegister`) НЕ ДОЛЖЕН существовать в кодовой базе: поскольку бэкенд обрабатывает `/auth/login` и `/auth/register` идентично, различение на клиенте избыточно и должно быть устранено.

8. Кнопка "Войти" ОБЯЗАНА блокироваться на время выполнения запроса, чтобы исключить повторный тап и дублирующиеся запросы — детальное поведение см. в «Общие требования: UI-паттерны запросов», здесь оно не переописывается.

## 4. Бизнес-правила и валидация

* Клиентская валидация: `login` — минимум 2 символа, `password` — минимум 8 символов (единое значение с серверной валидацией, см. «Вход и регистрация — Backend»). Форма не должна отправлять запрос при нарушении.

* Отдельного выбора "Войти"/"Зарегистрироваться" быть не должно — решение принимает бэкенд по факту существования логина.

* Гостевой вход технически создаёт на бэкенде отдельного пользователя с рандомным логином и флагом «гость» (is_guest), идентифицируемого по клиентскому device/session id — это НЕ обычный логин с фиксированными кредами.

* Режим local/network — независимый переключатель UI; в режиме local сетевой запрос не выполняется, поиск/создание пользователя происходит в локальном списке без токенов. Это ожидаемое поведение, изменений не требует.

* На сервере хранится только один активный refresh_token на пользователя, поэтому вход с другого устройства тихо завершает сессию на первом (см. «Общие требования: Сессия, 401 и авто-refresh токена»). Реальная реализация auto-refresh с обработкой 401 — отдельная большая задача, ведётся в рамках «Обновление токена — Frontend», а не здесь.

## 5. Обработка ошибок

| Условие                                    | Что делает клиент                   | Что видит пользователь                                                                          |
| ------------------------------------------ | ----------------------------------- | ----------------------------------------------------------------------------------------------- |
| Пустой/слишком короткий login или password | Запрос не отправляется              | Текст ошибки под полем                                                                          |
| 400 VALIDATION_ERROR                       | Ошибка валидации полей на форме     | Сообщение об ошибке валидации, отличное от текста «неверный пароль»                             |
| 403 FORBIDDEN (пароль не совпал)           | Ошибка на обоих полях               | «Неверный пароль. Если вы хотели зарегистрироваться, этот логин уже занят другим пользователем» |
| Сетевая ошибка или 500                     | Ошибка на обоих полях               | «Сервис недоступен, попробуйте позже» — отдельно от текста про неверный пароль                  |
| Успех (200 OK)                             | Токены сохраняются, переход на Home | —                                                                                               |

Клиент ОБЯЗАН различать 400 VALIDATION_ERROR, 403 FORBIDDEN и прочие/сетевые ошибки тремя разными сообщениями пользователю — единый текст «Логин или пароль неверные» для всех кодов ошибок, кроме 403, не допускается. Коды 404 и 409 в этом флоу не возникают (бэкенд не различает "вход" и "регистрацию" как отдельные операции).

## 6. Хранение состояния и побочные эффекты

* Токены ОБЯЗАНЫ храниться в защищённом нативном хранилище (Keychain на iOS / Keystore на Android), а не в обычном AsyncStorage, и восстанавливаться из него при холодном старте приложения.

* При установке токенов заголовок `Authorization` ОБЯЗАН быть проставлен в приватном HTTP-клиенте до выполнения любого защищённого запроса.

* `currentUser` сохраняется в локальном хранилище и переживает перезапуск приложения; пароль пользователя в открытом виде НЕ ДОЛЖЕН сохраняться в `currentUser` после успешного логина — он не нужен клиенту повторно.

* Навигация на главный экран инициируется наличием непустого `currentUser` и валидных восстановленных токенов; если токены не удалось восстановить из защищённого хранилища, пользователь ДОЛЖЕН быть направлен на экран аутентификации, а не показан как "вошедший" без действующей авторизации.
