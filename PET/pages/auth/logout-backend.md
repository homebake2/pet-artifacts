## 1. Назначение

Флоу инвалидирует сессию пользователя на сервере при выходе из аккаунта. Успешный вызов ОБЯЗАН лишать переданный refresh-токен возможности быть использованным для обновления пары токенов, а также инвалидировать любой access-токен, выданный до момента logout.

* [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md) — single-session ограничение, атомарность операций с токенами на BE, конкурентность refresh/logout.

* [Общие требования: Формат ошибок API](../common/obschie-trebovaniya-format-oshibok-api.md) — errorCode/message/payload и требование не раскрывать причину отказа в сообщении.

## 2. Действующие лица и предусловия

* Инициатор — клиентское приложение, владеющее ранее выданным `refresh_token`.

* Предусловие: у пользователя в БД сохранено значение `refresh_token`, совпадающее с переданным токеном.

* Эндпоинт не проверяет заголовок `Authorization`/access-токен — идентификация пользователя происходит через тело запроса с refresh-токеном.

## 3. Основной сценарий

Запрос: `POST /auth/logout`

| Поле          | Тип    | Обязательность       |
| ------------- | ------ | -------------------- |
| refresh_token | string | обязательно, непусто |

Сервер ОБЯЗАН выполнить:

1. Проверить метод запроса — POST.

2. Декодировать JSON-тело.

3. Проверить, что `refresh_token` не пустой.

4. Распарсить и проверить подпись/срок действия JWT.

5. Проверить claim `type == "refresh"`.

6. Извлечь claim `login` из токена.

7. Найти пользователя по `login` и прочитать сохранённый `refresh_token`.

8. Сравнить сохранённое значение с переданным токеном байт-в-байт.

9. Сравнение сохранённого значения с переданным токеном и его обнуление ОБЯЗАНЫ выполняться одной атомарной операцией (транзакция или единичный `UPDATE ... WHERE refresh_token = $1`, проверяющий число затронутых строк), а не раздельными select/update — иначе конкурентный вызов logout/refresh тем же токеном создаёт окно гонки. При совпадении сервер устанавливает `refresh_token = NULL` и `tokens_invalidated_at = now()`, чтобы любой access-токен, выданный до этого момента, перестал приниматься защищёнными эндпоинтами. Если атомарная операция не затронула ни одной строки (токен уже не совпадает — устарел, отозван или переиспользован конкурентно) — см. раздел «Обработка ошибок».

10. Вернуть `204 No Content` без тела.

## 4. Бизнес-правила и валидация

* Логаут возможен только по действительному refresh-токену.

* Сравнение переданного и сохранённого токена — точное, строковое.

* После успешного логаута: `refresh_token` пользователя в БД равен NULL, а `tokens_invalidated_at` обновлён текущим временем.

* Любой access-токен с claim `iat` раньше `tokens_invalidated_at` пользователя ОБЯЗАН отклоняться защищёнными эндпоинтами с 401, даже если срок его действия (14 дней) не истёк.

* Все ответы 401 этого эндпоинта (токен истёк/невалиден, тип не refresh, пользователь не найден, токен не совпадает с сохранённым) ОБЯЗАНЫ возвращать одно и то же унифицированное сообщение об ошибке — сервер не обязан и не должен раскрывать клиенту причину отказа детальнее, чем «токен недействителен», чтобы не давать сигналов, полезных для атак на чужие сессии. Реальная причина при этом ОБЯЗАНА логироваться на сервере для отладки.

## 5. Обработка ошибок

| Условие                           | Статус | Код              | Сообщение                               |
| --------------------------------- | ------ | ---------------- | --------------------------------------- |
| Метод не POST                     | 405    | BAD_REQUEST      | «Method not allowed»                    |
| Тело не JSON                      | 400    | BAD_REQUEST      | «Некорректный запрос»                   |
| refresh_token пустой              | 400    | VALIDATION_ERROR | «Отсутствует refresh_token»             |
| Токен не парсится/истёк/невалиден | 401    | UNAUTHORIZED     | «Невалидный или истёкший refresh token» |
| type ≠ "refresh"                  | 401    | UNAUTHORIZED     | «Некорректный тип токена»               |
| Отсутствует claim login           | 401    | UNAUTHORIZED     | «Невалидный refresh token»              |
| Пользователь не найден            | 401    | UNAUTHORIZED     | «Пользователь не найден»                |
| Ошибка БД при поиске              | 500    | INTERNAL_ERROR   | «Внутренняя ошибка сервера»             |
| Токен не совпадает с сохранённым  | 401    | UNAUTHORIZED     | «Токен отозван или устарел»             |
| Ошибка БД при очистке             | 500    | INTERNAL_ERROR   | «Не удалось выполнить выход»            |
| Успех                             | 204    | —                | тело отсутствует                        |

405 ОБЯЗАН быть документирован в OpenAPI для `/auth/logout`, как и для остальных auth-эндпоинтов.

Сообщения в таблице выше исторически различались по причине отказа. Согласно правилу из раздела 4, все они ОБЯЗАНЫ быть сведены к единому тексту (например, «Сессия недействительна»/UNAUTHORIZED) — конкретная причина («не найден», «истёк», «отозван», «неверный тип») логируется на сервере, но не передаётся клиенту.

## 6. Хранение состояния и побочные эффекты

* Изменения при успешном вызове: `refresh_token` пользователя обнуляется, `tokens_invalidated_at` обновляется текущим временем.

* Аудит/история сессий не ведётся — хранится только текущее состояние (активен ли refresh-токен и с какого момента invalid access-токены).

* Access-токены не хранятся на сервере как отдельные записи; их отзыв реализуется сравнением claim `iat` с `tokens_invalidated_at` пользователя, а не через хранение самих токенов.

* Обнуление refresh_token и обновление tokens_invalidated_at выполняются одной атомарной операцией, согласованной с ожиданием клиента о единственной активной сессии (см. «Общие требования: Сессия, 401 и авто-refresh токена»).
