## 1. Назначение

Флоу должен продлевать сессию пользователя без повторного логина через `POST /auth/refresh`. Обновление access-токена ОБЯЗАНО происходить автоматически и прозрачно для пользователя — приложение не должно показывать ошибки авторизации, пока refresh-токен действителен.

## 2. Действующие лица и предусловия

* Инициатор — само приложение: автоматический интерцептор HTTP-клиента, реагирующий на ответ 401 от защищённых эндпоинтов.

* Предусловие: в защищённом хранилище токенов сохранён действующий `refresh_token`.

## 3. Основной сценарий

1. Приватный HTTP-клиент выполняет запрос к защищённому эндпоинту с текущим `access_token` в заголовке `Authorization`.

2. Сервер отвечает `401` (access-токен истёк, отозван или недействителен).

3. Интерцептор ОБЯЗАН перехватить этот ответ и инициировать обновление токена: вызвать `POST /auth/refresh` с текущим `refresh_token`.

4. При успехе (`200 OK`) сервер возвращает новую пару токенов; клиент ОБЯЗАН немедленно сохранить обе новые пары значений (access и refresh) в защищённом хранилище токенов, обновить заголовок `Authorization` и повторить исходный запрос с новым `access_token`.

5. Если во время ожидания ответа `/auth/refresh` возникают другие параллельные запросы, получившие 401, интерцептор ОБЯЗАН дедуплицировать вызовы обновления через единый in-flight promise, а не через отдельный флаг/семафор с ручной постановкой в очередь. Вызов `/auth/refresh` ОБЯЗАН иметь таймаут 5 секунд (см. «Общие требования: UI-паттерны запросов») и ограничен одной попыткой — при любой неудаче (401, 500, сеть, таймаут) повторные автоматические попытки не выполняются, вместо этого интерцептор переходит к форсированному logout.

   **Механизм дедупликации.** Интерцептор хранит ссылку на promise обновления в переменной, общей для всех запросов одного экземпляра приватного HTTP-клиента (например, module-scoped `let refreshPromise: Promise<TokenPair> | null = null`):

   1. Когда 401-обработчик срабатывает и `refreshPromise` ещё не задан (`null`) — он вызывает `/auth/refresh`, немедленно (синхронно, до await) записывает получившийся promise в `refreshPromise` и затем сам его await-ит.

   2. Когда 401-обработчик срабатывает, пока `refreshPromise` уже задан (обновление уже идёт) — он НЕ вызывает `/auth/refresh` повторно, а сразу await-ит уже существующий `refreshPromise` — то есть все параллельно упавшие с 401 запросы физически дожидаются одного и того же промиса, а не независимых копий вызова.

   3. По завершении promise (успех или неудача), в блоке `finally`, `refreshPromise` ОБЯЗАН быть сброшен в `null`, чтобы следующий 401 (уже после завершения текущего цикла обновления) инициировал новый вызов, а не бесконечно ждал устаревший promise.

   4. При успехе каждый await-ящий обработчик получает из результата promise один и тот же новый `access_token` и повторяет свой собственный исходный запрос с ним; при неудаче — каждый получает тот же reject и обрабатывается согласно таблице «Обработка ошибок» ниже (переход к форсированному logout).

6. Если пользователь инициирует logout, пока вызов /auth/refresh ещё выполняется, интерцептор ОБЯЗАН отменить или проигнорировать результат этого refresh — успешный ответ, пришедший после начала logout, не должен переписывать уже сброшенное состояние сессии.

## 4. Бизнес-правила и валидация

* Автообновление токена — обязательная часть клиента, а не опциональная возможность; должно быть подключено к единственному приватному HTTP-клиенту приложения, используемому для всех защищённых запросов.

* `refresh_token` обязателен для вызова `/auth/refresh`; отсутствие сохранённого refresh-токена (например, после logout) ОБЯЗАНО приводить к прямому переходу на экран аутентификации без попытки вызова.

* Backend ротирует refresh-токен при каждом обновлении: клиент ОБЯЗАН сразу заменять старый refresh_token новым из ответа — старое значение становится недействительным на сервере. Если клиент не смог записать новую пару токенов в защищённое хранилище (Keychain/Keystore) — такой refresh считается неуспешным, несмотря на 200 OK от сервера, и приводит к форсированному logout, а не к работе с токенами только в памяти.

## 5. Обработка ошибок

| Условие                                                             | Что делает клиент                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 401 от защищённого запроса, refresh ещё не запущен                  | Запускает единственный вызов /auth/refresh и синхронно сохраняет его promise в refreshPromise; остальные параллельные 401-обработчики видят непустой refreshPromise и await-ят именно его, не запуская собственный вызов                                                                                                                                                                |
| /auth/refresh вернул 200 OK                                         | Сохраняет новую пару токенов, обновляет Authorization, повторяет все отложенные запросы с новым access_token                                                                                                                                                                                                                                                                            |
| /auth/refresh вернул 401 (refresh-токен истёк/отозван/не совпадает) | Сбрасывает $currentUser, $tokens, Authorization и направляет пользователя на экран аутентификации для повторного логина — дальнейшие отложенные запросы завершаются ошибкой                                                                                                                                                                                                             |
| /auth/refresh вернул 500 или сеть недоступна                        | Обновление считается неуспешным с первой попытки (лимит 1 попытка) — интерцептор форсирует logout. Если сервер уже успел выполнить ротацию на своей стороне до сетевого сбоя, повторный вход неизбежен: сообщение об ошибке ОБЯЗАНО отражать это (не «попробуйте ещё раз обновить», а прямая подсказка войти заново). |

## 6. Хранение состояния и побочные эффекты

* После успешного обновления `$tokens` и заголовок `Authorization` ОБЯЗАНЫ быть обновлены новой парой значений.

* `$tokens` ОБЯЗАНЫ персистироваться в защищённом нативном хранилище (см. страницу "Вход и регистрация — Frontend", раздел 6) — обновлённая пара сохраняется туда же, где хранится текущая сессия.

* Обновление токена ограничено одной попыткой и таймаутом 5 секунд; сбой записи новой пары в защищённое хранилище трактуется как неуспешный refresh (форсированный logout).
