## 1. Назначение

Флоу отвечает за выдачу пары токенов (access + refresh) пользователю мобильного приложения PetHealth. Система должна объединять вход и регистрацию в одну операцию: сервер сам решает, зарегистрировать новый аккаунт или проверить пароль существующего, на основании того, найден ли переданный `login` в базе. Отдельного шага "регистрации" как самостоятельного бэкенд-сценария не предусмотрено.

* [Общие требования: Сессия, 401 и авто-refresh токена](../common/obschie-trebovaniya-sessiya-401-i-avto-refresh-tokena.md) — single-session ограничение (1 refresh_token на пользователя), атомарность операций с токенами.

* [Общие требования: Формат ошибок API](../common/obschie-trebovaniya-format-oshibok-api.md) — errorCode/message/payload; локализация сообщений остаётся задачей клиента.

## 2. Действующие лица и предусловия

* Инициатор — клиентское приложение, не авторизованный пользователь (токен не требуется и не проверяется).

* Предусловий для существования пользователя нет: эндпоинт должен работать одинаково независимо от того, существует ли уже аккаунт с указанным `login`.

* Доступен по двум путям — `POST /auth/login` и `POST /auth/register`. Оба маршрута ОБЯЗАНЫ вести себя идентично и обрабатываться одним обработчиком; разделения на "чисто вход" и "чисто регистрацию" не предусмотрено. Отдельно от этого пути существует гостевой доступ (см. ниже) — он не использует общий пароль "quest" и обрабатывается отдельным обработчиком.

## 3. Основной сценарий

Тело запроса (одинаково для `/auth/login` и `/auth/register`):

| Поле     | Тип    | Обязательность                           | Описание                                                           |
| -------- | ------ | ---------------------------------------- | ------------------------------------------------------------------ |
| login    | string | обязательно, непусто                     | логин пользователя                                                 |
| password | string | обязательно, непусто, минимум 8 символов | пароль в открытом виде, передаётся по HTTPS, хешируется на сервере |

Перед сравнением/поиском сервер ОБЯЗАН нормализовать `login`: убрать пробелы по краям (trim) и сравнивать без учёта регистра — иначе "User" и "user" трактуются как разные аккаунты (см. «Связанные задачи», PET-100). Минимальная длина `login` — 2 символа (см. «Связанные задачи», PET-101).

Сервер при получении запроса ОБЯЗАН выполнить:

1. Проверить, что метод запроса — POST. Иначе см. раздел «Обработка ошибок».

2. Декодировать тело запроса как JSON в структуру с полями `login` и `password`.

3. Проверить, что оба поля непустые, `login` не короче 2 символов (после trim), а `password` не короче 8 символов.

4. Нормализовать `login` (trim + приведение к нижнему регистру для сравнения) и выполнить поиск пользователя по нормализованному значению.

5. Если пользователь не найден — сначала выполнить проверку rate limit регистрации по IP (пошаговый алгоритм — см. §3b «Rate limiting на регистрацию» ниже). Если лимит превышен — обработка прекращается на этом шаге, см. раздел «Обработка ошибок» (429). Если лимит не превышен — выполнить авто-регистрацию: захешировать пароль через bcrypt (`bcrypt.DefaultCost`) и создать новую запись пользователя; полученный `id` используется дальше как `userId`. Если создание строки падает с нарушением уникального индекса по login (гонка параллельной регистрации того же login) — это НЕ ошибка 500. Сервер ОБЯЗАН распознавать именно этот случай, а не любую ошибку INSERT, по коду ошибки PostgreSQL `23505` (`unique_violation`): для драйвера `pgx` — `var pgErr *pgconn.PgError; errors.As(err, &pgErr) && pgErr.Code == "23505"`; для `database/sql` поверх `lib/pq` — приведение `err.(*pq.Error)` и проверка `.Code == "23505"`. Только при совпадении этого конкретного кода сервер ОБЯЗАН трактовать ошибку как переход к сценарию "пользователь уже есть" и повторно выполнить поиск/сравнение пароля; любая другая ошибка INSERT (код БД отличен от 23505, либо ошибка не распознана как *pgconn.PgError/*pq.Error) обрабатывается как обычная ошибка БД — 500 INTERNAL_ERROR, как указано в таблице «Обработка ошибок» (см. «Связанные задачи», PET-99).

6. Если пользователь найден — сравнить сохранённый bcrypt-хеш с переданным паролем через `bcrypt.CompareHashAndPassword`. При несовпадении — см. раздел «Обработка ошибок» (403). При совпадении — `userId` берётся из найденной строки.

7. Сгенерировать `access_token` (claim `type=access`, срок жизни 14 дней) и `refresh_token` (claim `type=refresh`, срок жизни 60 дней). Оба — JWT (HS256), payload содержит `login`, `id` (uuid пользователя строкой), `type`, `exp`, `iat`.

8. Сохранить выданный `refresh_token` в БД для пользователя. Эта операция ОБЯЗАНА завершиться успешно, иначе клиенту должна быть возвращена ошибка, а не токены, которые сервер не смог сохранить (см. «Связанные задачи», PET-17) — сервер не может вернуть 200 OK, если не гарантирует, что выданный refresh_token в дальнейшем можно предъявить для обновления сессии.

9. Вернуть `200 OK` с телом:

| Поле          | Тип    | Обязательность | Описание                                |
| ------------- | ------ | -------------- | --------------------------------------- |
| access_token  | string | обязательно    | JWT для доступа к защищённым эндпоинтам |
| refresh_token | string | обязательно    | JWT для получения новой пары токенов    |

## 3a. Гостевой доступ

Отдельный эндпоинт `POST /auth/guest` — не использует общий обработчик `/auth/login`/`/auth/register` и не проверяет пароль "quest" — обрабатывается отдельным обработчиком. Вместо login/password клиент передаёт идентификатор устройства/гостевой сессии.

Тело запроса:

| Поле      | Тип    | Обязательность       | Описание                                                                                                                                                                                                      |
| --------- | ------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| device_id | string | обязательно, непусто | стабильный идентификатор гостевой сессии/устройства, сгенерированный и сохранённый на клиенте; повторные вызовы с тем же значением ОБЯЗАНЫ возвращать токены того же гостевого аккаунта, а не создавать новый |

Ответ — `200 OK`, то же тело, что и у `/auth/login` (`access_token`, `refresh_token`).

Сервер ОБЯЗАН выполнить:

1. Проверить метод — POST; декодировать JSON-тело в структуру с полем `device_id`.

2. Проверить, что `device_id` непустой. Иначе см. раздел «Обработка ошибок» (400).

3. Выполнить поиск пользователя по колонке `guest_device_id = device_id` (схема колонки/индекса — см. ниже). **Если найден** — это отдельный явный случай алгоритма: сервер ОБЯЗАН использовать найденную запись (её `id` как `userId`) и сразу перейти к выдаче токенов (шаг 5 ниже), НЕ создавая новую запись — повторный вызов с тем же `device_id` (например, при перезапуске приложения) ОБЯЗАН возвращать токены того же гостя, а не плодить дубликаты.

**Схема.** В таблицу пользователей добавляется колонка `guest_device_id text NULL` и уникальный частичный индекс:

```
CREATE UNIQUE INDEX users_guest_device_id_idx
  ON users (guest_device_id)
  WHERE guest_device_id IS NOT NULL;
```

Индекс частичный (условие `WHERE guest_device_id IS NOT NULL`), чтобы обычные (не гостевые) пользователи, у которых эта колонка всегда `NULL`, не конфликтовали друг с другом на уникальности.

Миграция гостя в постоянный аккаунт — отдельная будущая фича, в этой версии не реализуется (см. «Связанные задачи», PET-97).

## 3b. Rate limiting на регистрацию

Срабатывает только на ветке «пользователь не найден, сейчас будет создан новый» (шаг 5 основного сценария) — обычный вход существующего пользователя (неважно, успешный или с неверным паролем) под лимит не подпадает и счётчик не трогает.

**Хранилище лимита.** Отдельная таблица в той же PostgreSQL-БД (не переиспользуем таблицу пользователей — там нет ни IP, ни времени создания):

```
CREATE TABLE registration_rate_limit (
  ip    inet NOT NULL,
  day   date NOT NULL,   -- календарный день в UTC
  count integer NOT NULL DEFAULT 0,
  PRIMARY KEY (ip, day)
);
```

**Определение IP клиента.** Backend развёрнут на Render за прокси/балансировщиком, поэтому `RemoteAddr` обычно равен адресу прокси, а не клиента. IP берётся из первого адреса в заголовке `X-Forwarded-For`, если заголовок присутствует; если заголовка нет — используется `RemoteAddr` запроса как fallback. Известное ограничение: если заголовок неверно проксируется/не настроен на границе, значение можно подделать — для MVP это принятый риск, отдельная защита (проверка доверенных прокси) не реализуется.

**Алгоритм (шаг 5, до создания пользователя):**

1. Вычислить `day` — текущая календарная дата в UTC (`time.Now().UTC().Format("2006-01-02")`), не локальное время сервера.

2. Атомарно увеличить счётчик одним запросом (без отдельных SELECT+UPDATE, чтобы не ловить гонку при параллельных запросах с одного IP):\
   `INSERT INTO registration_rate_limit (ip, day, count) VALUES ($1, $2, 1) ON CONFLICT (ip, day) DO UPDATE SET count = registration_rate_limit.count + 1 RETURNING count;`

3. Если вернувшийся `count > 3` — лимит превышен: авто-регистрация НЕ выполняется, сервер сразу возвращает `429` (см. «Обработка ошибок»). Инкремент при этом уже произведён — это осознанно: строка на (ip, day) не растёт бесконтрольно, а дальнейшие попытки в этот день будут отклоняться тем же способом.

4. Если `count ≤ 3` — продолжить сценарий обычным образом (создание пользователя, шаг 5 и далее).

5. Ошибка БД на этом шаге (не удалось выполнить upsert) обрабатывается как обычная ошибка БД — `500 INTERNAL_ERROR` (не пропускаем регистрацию в обход лимита, если счётчик недоступен — fail closed, а не fail open).

**Хранение и очистка.** Старые строки (day в прошлом) не нужны после истечения дня — периодическая очистка (например, раз в сутки удалять строки старше 7 дней) полезна, но не блокирует MVP: при ожидаемых объёмах регистраций рост таблицы незначителен. Отдельная задача на cron-очистку не заводится в этой итерации.

## 4. Бизнес-правила и валидация

* `login` уникален на уровне схемы БД; повторный `login` не создаёт вторую запись, а трактуется как попытка входа. Уникальность проверяется по нормализованному значению `lower(trim(login))` — уникальный индекс строится по этому выражению, а не по сырому значению (см. «Связанные задачи», PET-100).

* Пароль ОБЯЗАН храниться исключительно как bcrypt-хеш, никогда в открытом виде.

* Сервер ОБЯЗАН отклонять пароли короче 8 символов с ошибкой 400 VALIDATION_ERROR; дополнительных требований к сложности пароля не предъявляется. Сервер ОБЯЗАН также отклонять `login` короче 2 символов (после trim) с той же ошибкой 400 VALIDATION_ERROR (см. «Связанные задачи», PET-101).

* Секретный ключ подписи JWT ОБЯЗАН читаться из переменной окружения (например, `JWT_SECRET`) при старте сервиса и НЕ ДОЛЖЕН быть захардкожен в исходном коде (см. «Связанные задачи», PET-16).

* Access token: claim `type=access`, срок жизни 14 дней. Refresh token: claim `type=refresh`, срок жизни 60 дней. Оба подписываются HS256 общим секретом.

* В БД хранится только один активный `refresh_token` на пользователя. Это принятое ограничение single-session: вход с другого устройства тихо инвалидирует предыдущую сессию (см. «Общие требования: Сессия, 401 и авто-refresh токена»).

* Регистрация новых аккаунтов (ветка «login не найден» в основном сценарии) ОБЯЗАНА быть ограничена rate limiting по IP — не более 3 регистраций в день с одного адреса. Точный механизм (таблица, алгоритм, определение IP) — см. §3b «Rate limiting на регистрацию» (см. «Связанные задачи», PET-98).

* Сообщения об ошибках в этой версии возвращаются на русском языке — это принято как временная норма; клиент обязан показывать собственный локализованный текст по коду ошибки, а не по полю message с сервера (см. «Общие требования: Формат ошибок API»). Полноценная серверная локализация — низкоприоритетная задача на будущее (см. «Связанные задачи», PET-102).

## 5. Обработка ошибок

| Условие                                                                                              | Статус | Код ошибки       | Сообщение                                                                                                              |
| ---------------------------------------------------------------------------------------------------- | ------ | ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Метод запроса не POST                                                                                | 405    | BAD_REQUEST      | «Method not allowed»                                                                                                   |
| Тело запроса не парсится как JSON                                                                    | 400    | BAD_REQUEST      | «Некорректное тело запроса»                                                                                            |
| login или password пустые/отсутствуют                                                                | 400    | VALIDATION_ERROR | «Поля login и password обязательны»                                                                                    |
| password короче 8 символов                                                                           | 400    | VALIDATION_ERROR | «Пароль должен быть не короче 8 символов»                                                                              |
| Ошибка БД при поиске пользователя                                                                    | 500    | INTERNAL_ERROR   | «Ошибка базы данных»                                                                                                   |
| Ошибка БД при создании пользователя                                                                  | 500    | INTERNAL_ERROR   | «Ошибка при создании пользователя»                                                                                     |
| Login не найден (авто-регистрация) и IP уже исчерпал лимит регистраций за текущий день UTC (см. §3b) | 429    | RATE_LIMITED     | «Слишком много попыток регистрации, попробуйте позже»                                                                  |
| Пользователь существует, но пароль не совпал                                                         | 403    | FORBIDDEN        | «Неверный пароль»                                                                                                      |
| Ошибка генерации access/refresh JWT                                                                  | 500    | INTERNAL_ERROR   | «Не удалось сгенерировать access/refresh token»                                                                        |
| Ошибка сохранения refresh_token после аутентификации                                                 | 500    | INTERNAL_ERROR   | «Не удалось сохранить сессию» — клиенту НЕ ДОЛЖНЫ возвращаться токены при этой ошибке (см. «Связанные задачи», PET-17) |
| device_id пустой/отсутствует (POST /auth/guest, см. §3a)                                             | 400    | VALIDATION_ERROR | «Поле device_id обязательно»                                                                                           |

404 и 409 в этом флоу принципиально не используются — сервер не различает "вход" и "регистрацию" как отдельные операции с разными кодами ошибок. Ответ 405 ОБЯЗАН быть документирован в OpenAPI для всех auth-эндпоинтов; код ошибки в теле для 405 переиспользует `BAD_REQUEST` — это осознанное решение, отдельный код `METHOD_NOT_ALLOWED` не заводится (см. «Связанные задачи», PET-18).

## 6. Хранение состояния и побочные эффекты

* Новая строка в таблице пользователей создаётся только если `login` не существовал.

* Колонка `refresh_token` пользователя обновляется при каждом успешном запросе и ОБЯЗАНА быть согласована с ответом клиенту (см. раздел 5).

* Серверные сессии не создаются — состояние авторизации полностью описывается парой JWT и колонкой `refresh_token` в БД.

* Отдельная таблица `registration_rate_limit(ip, day, count)` хранит счётчики регистраций по IP за календарный день UTC — см. §3b. Строка обновляется атомарным upsert при каждой попытке авто-регистрации (успешной или отклонённой по лимиту).
