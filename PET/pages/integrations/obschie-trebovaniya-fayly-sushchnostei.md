## Назначение

В проекте несколько сущностей с файлами (фотография питомца, файлы события — фото и документы — и, вероятно, другие в будущем). Вместо отдельного набора endpoint'ов загрузки/подтверждения/удаления на каждую сущность — единый generic-механизм: один API загрузки файлов, параметризованный типом владельца (`owner_type`) и его id (`owner_id`). Конкретная сущность подключается к нему регистрацией в «Реестре типов владельцев» (см. ниже) — не написанием нового endpoint'а.

Чтение файлов НЕ входит в этот generic-механизм — оно остаётся на стороне каждой сущности (см. «Область действия» в конце страницы): форма ответа отличается (одна фотография у питомца vs потенциальный список у будущей галереи), и обобщать её было бы преждевременно.

## Модель данных

Единая таблица `file`, общая для всех типов владельцев:

```
CREATE TABLE file (
  id            uuid PRIMARY KEY,
  owner_type    text NOT NULL,        -- см. «Реестр типов владельцев»
  owner_id      uuid NOT NULL,        -- id владеющей сущности (pet.id и т.п.)
  user_id       uuid NOT NULL,        -- владелец файла, из токена на момент выдачи upload-url
  object_key    text NOT NULL,        -- ключ объекта в S3, вида "{owner_type}/{owner_id}/{file.id}"
  content_type  text NOT NULL,
  filename      text NULL,           -- исходное имя файла, как выбрано пользователем; см. ниже
  position      integer NULL,         -- порядок в галерее; NULL для типов с кардинальностью "ровно 1", неотрицательное целое (0, 1, 2, ...) для типов с кардинальностью "до N"
  confirmed_at  timestamptz NULL,     -- NULL = загрузка ожидает подтверждения, см. «Подтверждение загрузки»
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

Строка с `confirmed_at IS NULL` — не готовый к использованию файл (presigned PUT URL выдан, но не подтверждено, что байты реально загружены в S3). Такие строки НЕ ДОЛЖНЫ учитываться ни при чтении файлов сущности, ни при подсчёте кардинальности (см. ниже) — они существуют только для того, чтобы шаг «Подтверждение загрузки» мог найти запись по `file_id` и повторно проверить владение.

`filename` — необязательное поле общего механизма: клиент может передать его в `POST /files/upload-url` (см. «Основной сценарий» ниже), и тогда оно сохраняется и возвращается читающей стороной конкретного `owner_type`, которому оно нужно (см. «Файлы события — Backend» — единственный на данный момент `owner_type`, использующий это поле, для документов). Владельцы, которым исходное имя файла не нужно (например, `pet_photo` — там единственная фотография не подписывается именем в UI), просто не передают и не читают это поле; сам generic-механизм не требует и не проверяет его заполненность — эта проверка, если нужна, специфична для `owner_type` и описывается на его собственной странице.

## Реестр типов владельцев

Каждый `owner_type`, которым может пользоваться этот механизм, регистрируется на бэкенде тремя параметрами — не веткой `if/switch` внутри общего хендлера, а записью в статической таблице соответствий (map «owner_type → { проверка владения, кардинальность, допустимые content-type }»), к которой хендлеры `upload-url`/`complete`/`delete` обращаются одинаково, независимо от количества зарегистрированных типов:

| `owner_type` | Сущность | Кардинальность | Проверка владения | Допустимые `content_type` |
| --- | --- | --- | --- | --- |
| `pet_photo` | Питомец (`pet`) | ровно 1 | `pet.id = owner_id AND pet.user_id = userID AND pet.deleted_at IS NULL` | `image/jpeg`, `image/png`, `image/webp` |
| `event_file` | Событие (`event`) | до 10 | `event.id = owner_id AND event.deleted_at IS NULL AND EXISTS (SELECT 1 FROM pet WHERE pet.id = event.pet_id AND pet.user_id = userID AND pet.deleted_at IS NULL)` | `image/jpeg`, `image/png`, `image/webp`, `application/pdf` |

Будущие типы владельцев добавляются в этот реестр отдельной работой при реализации соответствующей сущности — сама эта страница не меняется, расширяется только таблица.

`owner_type`, отсутствующий в реестре, — `400` на любом из трёх endpoint'ов ниже (а не `404`: это ошибка клиента, использующего несуществующий тип, а не вопрос владения ресурсом).

## Основной сценарий: загрузка/замена файла

1. `POST /files/upload-url`. Тело: `{owner_type, owner_id, content_type, filename?}` (`filename` — опциональная строка, не более 255 символов; см. «Модель данных» о том, для чего и кем она используется).

   a. Система проверяет `Authorization`, извлекает `userID`.

   b. Система проверяет, что `owner_type` есть в реестре — иначе `400`.

   c. Система выполняет проверку владения для пары (`owner_type`, `owner_id`) по правилу из реестра — иначе `404` (единая политика, см. «Общие требования: IDOR и владение ресурсами»; конкретная SQL-проверка зависит от `owner_type`, но её результат всегда бинарный «доступ есть/доступа нет», без утечки деталей).

   d. Система проверяет `content_type` по перечню допустимых для этого `owner_type` — иначе `400`.

   e. Система генерирует `file.id` (UUID), вычисляет `object_key = "{owner_type}/{owner_id}/{file.id}"`, вставляет строку в `file` с `confirmed_at = NULL` и `filename` = переданное значение (либо `NULL`, если не передано).

   f. Система подписывает presigned PUT URL на `object_key` своими S3-ключами, с TTL и привязкой к `content_type` (см. «Общие требования: S3-хранилище файлов»).

   g. Система возвращает `200 OK` с телом `{file_id, upload_url, content_type, expires_in}`.

2. Клиент выполняет `PUT upload_url` напрямую в S3 с байтами файла и тем же `Content-Type`.

3. `POST /files/{file_id}/complete` — «Подтверждение загрузки»:

   a. Система проверяет `Authorization`, извлекает `userID`, ищет строку `file` по `id` — иначе `404`.

   b. Система повторно выполняет проверку владения для (`owner_type`, `owner_id`) найденной строки по правилу из реестра — иначе `404`. Повторная проверка обязательна: между шагами 1 и 3 могло пройти время, а `file_id` в пути — единственный параметр запроса, поэтому нельзя полагаться на то, что владение не изменилось (питомец мог быть удалён) или довериться самому факту существования строки как доказательству прав текущего пользователя.

   c. Система устанавливает `confirmed_at = now()`.

   d. Кардинальность применяется по правилу из реестра для этого `owner_type`:
      * **Ровно 1** (например, `pet_photo`): любая другая ранее подтверждённая строка (`confirmed_at IS NOT NULL`) с той же парой (`owner_type`, `owner_id`) удаляется — и запись из `file`, и (best-effort) объект в S3. Замена единственной фотографии — ожидаемое поведение, не ошибка.
      * **До N** (например, `event_file`, N = 10, см. «Файлы события — Backend»): если число уже подтверждённых строк для этой пары равно лимиту — `409 Conflict`, шаг подтверждения не выполняется; клиент обязан сначала удалить один из существующих файлов (см. «Удаление файла»). Тихого вытеснения старого файла новым для этого случая нет — в отличие от кардинальности «ровно 1», где именно такая замена и есть весь смысл операции. Если лимит не достигнут, система присваивает подтверждаемой строке `position = (максимальный существующий `position` среди уже подтверждённых строк этой пары) + 1`, либо `0`, если подтверждённых строк ещё нет — таким образом `position` отражает порядок подтверждения загрузок и используется читающей стороной конкретной сущности для сортировки списка (см. страницу конкретного `owner_type`). Удаление одной из строк не переприсваивает `position` оставшимся — значения не переиспользуются и не компактируются.

   e. Система возвращает `204 No Content`.

## Удаление файла

1. `DELETE /files/{file_id}`.

2. Система проверяет `Authorization`, извлекает `userID`, ищет строку `file` по `id` — не найдена (либо уже удалена) — `404`; клиент трактует такой `404` как «уже удалено», не как ошибку (та же идиома, что при повторном `DELETE /pet/{id}`, см. «Удаление питомца — Backend»).

3. Система повторно проверяет владение для (`owner_type`, `owner_id`) найденной строки по правилу из реестра — иначе `404`.

4. Система удаляет строку `file` и предпринимает best-effort попытку удалить объект в S3 (ошибка удаления в S3 не проваливает запрос — та же логика, что описана в «Фотография питомца — Backend» для одиночной фотографии).

5. Система возвращает `204 No Content`.

## Бизнес-правила и валидация

* Ни один из трёх endpoint'ов этой страницы не принимает и не возвращает `object_key` — клиент оперирует только `file_id`, presigned URL и параметрами `owner_type`/`owner_id`, которые сам же указал (см. «Общие требования: S3-хранилище файлов» — клиент никогда не работает с S3-ключами напрямую).

* `POST /files/upload-url` не идемпотентен по Idempotency-Key: повторный вызов с теми же `owner_type`/`owner_id`/`content_type` создаёт новую строку `file` с новым `file_id` и новым presigned URL — это осознанно, «отменить» незавершённую загрузку можно, просто не вызвав `complete`; неподтверждённые строки не мешают следующей попытке и не видны при чтении (см. «Модель данных»).

* Неподтверждённые (`confirmed_at IS NULL`) строки старше некоторого срока — технический долг на очистку (аналогично `pet_idempotency_key`, см. «Добавление питомца — Backend»); периодическая очистка не реализуется в этой итерации, отдельная задача не заводится.

## Обработка ошибок

| Статус | Условие                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------ |
| 400    | `owner_type` отсутствует в реестре; `content_type` недопустим для данного `owner_type`. Формат тела ошибки — см. «Общие требования: Формат ошибок API». |
| 401    | Токен отсутствует, некорректен или истёк.                                                        |
| 404    | Владение (`owner_type` + `owner_id`) не подтверждено (не существует/чужое/мягко удалено); `file_id` не найден (в т.ч. уже удалён). |
| 409    | Достигнут лимит кардинальности «до N» для данного `owner_type` (см. «Подтверждение загрузки», шаг d) — не возникает для `owner_type` с кардинальностью «ровно 1» (например, `pet_photo`); для `event_file` возникает при попытке подтвердить 11-й файл события (см. «Файлы события — Backend»). |
| 500    | Ошибка БД или ошибка подписи presigned URL/обращения к S3-хранилищу.                              |

## Область действия

Эта страница описывает только запись (загрузка/замена/удаление). Чтение файлов сущности — presigned GET URL в ответе самой сущности (например, поле `photo_url` в `GET /pet/{id}` или поле `files`/`files_count` в ответах событий) — специфично для каждого `owner_type` и описывается на его собственной странице, а не здесь: сервер уже выполняет проверку владения при выборке самой сущности, отдельная генерализация чтения через `owner_type`/`owner_id` не даёт дополнительной пользы и усложнила бы форму ответа (одна фотография у питомца vs список у события, причём для события форма ответа ещё и различается между списочными и одиночными эндпоинтами — см. «Файлы события — Backend»).
