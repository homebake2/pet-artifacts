## Назначение

Флоу ведёт список вакцинаций питомца: название, дата введения, дата следующей вакцинации, опционально — связанные записи в календаре: факт на дату введения (событие `event`, которое уже произошло), напоминание на дату и время следующей вакцинации (настройки напоминания с одним напоминанием) и до пяти дополнительных напоминаний на произвольные моменты (каждое — отдельные настройки напоминания с одним напоминанием) — и до 10 прикреплённых файлов.

## Модель данных

```
CREATE TABLE vaccination (
  id                 uuid PRIMARY KEY,
  pet_id             uuid NOT NULL REFERENCES pet(id),
  name               text NOT NULL,       -- ≤ 100 символов
  administered_date  date NOT NULL,
  administered_time  time NOT NULL DEFAULT '00:00', -- время суток введения (местное время пояса запроса); хранится в вакцинации и не зависит от дальнейших правок факта в календаре
  next_date          date NULL,
  next_time          time NULL,           -- время суток следующей вакцинации; задано, только когда задан next_date
  completed_at       timestamptz NULL,    -- момент завершения (отметка «выполнено» напоминания на следующую вакцинацию); при заданном completed_at next_date IS NULL
  administered_event_id  uuid NULL,       -- event.id факта на administered_date, если создан
  next_plan_id           uuid NULL,       -- reminder_plan.id напоминания на next_date + next_time, если создано
  idempotency_key    text NULL,           -- Idempotency-Key запроса создания; уникален на пару (pet_id, idempotency_key) среди строк с ключом
  deleted_at         timestamptz NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

**Дополнительные напоминания** хранятся как обычные настройки напоминания (`reminder_plan`, `source = vaccination_extra`, `source_id` = `vaccination.id`, разовое расписание, одно напоминание) — отдельной таблицы нет. Настройки с `source = vaccination_extra` и `source_id` вакцинации и есть её дополнительные напоминания; их не более пяти. Напоминание на следующую дату — настройки с `source = vaccination` (`id` = `next_plan_id`). Дополнительные напоминания существуют только при заданном `next_date`.

## Действующие лица и предусловия

* Инициатор — авторизованный владелец питомца.

* Питомец должен существовать, принадлежать инициатору и не быть мягко удалённым.

## Основной сценарий

**Список.** `GET /pet/{id}/vaccinations` — возвращает неудалённые вакцинации питомца, отсортированные по `next_date` (сначала записи с ближайшей `next_date`, затем записи без `next_date` — по `administered_date` убыв.). Опциональные query-параметры `limit`/`offset` — постраничная выдача. Каждый элемент — `GetVaccinationResponse`: `id`, `pet_id`, `name`, `administered_date`, `administered_time` (`HH:MM`, всегда задано), `next_date` (опционально), `next_time` (опционально, `HH:MM`; задано, только когда задана `next_date`), `completed_at` (опционально; задан у завершённой вакцинации), `administered_event_id` (опциональный id связанного факта; отсутствует, если факт мягко удалён, например, из календаря) и `next_plan_id` (опциональный id настроек связанного напоминания; отсутствует, если напоминание не создавалось либо его настроек уже нет — например, напоминание удалено или отмечено в календаре), `extra_reminders` (массив дополнительных напоминаний, до 5 элементов, по возрастанию момента; каждый — `{plan_id, date, time}`: id настроек и момент напоминания в часовом поясе настроек; пустой массив, если дополнительных напоминаний нет), `files_count` (см. «Общие требования: Файлы сущностей», по аналогии с `event.files_count`). Проверка владения — по `pet_id`, см. «Бизнес-правила».

**Создание.** `POST /pet/{id}/vaccinations`. Тело: `name` (обязательно, ≤100), `administered_date` (обязательно, `YYYY-MM-DD`), `next_date` (опционально, `YYYY-MM-DD`), `administered_time` (`HH:MM` или `HH:MM:SS`, OpenAPI `format: time`, опционально — время суток введения: сохраняется в вакцинации и задаёт время факта на дату введения; если не передано — полночь), `add_reminder_on_next` (boolean, по умолчанию `false`; без `next_date` напоминание не создаётся), `next_time` (`HH:MM` или `HH:MM:SS`, опционально — время суток следующей вакцинации и напоминания на `next_date`; если не передано — полночь; сохраняется в вакцинации), `extra_reminders` (опционально, массив до 5 элементов `{date, time}`: `YYYY-MM-DD` и `HH:MM[:SS]` — моменты дополнительных напоминаний; допускается только при заданной `next_date`), `skip_administered_event` (boolean, по умолчанию `false`; при `true` факт на дату введения не создаётся и `administered_event_id` остаётся пустым — используется, когда вакцинация вносится после отметки «выполнено» напоминания на предыдущую вакцинацию, чей факт уже есть в календаре, см. «Бизнес-правила»). Обязательный query-параметр `tz` — имя часового пояса IANA (например, `Europe/Moscow`): даты и `administered_time`/`next_time` трактуются как местное время этого пояса. Опциональный заголовок `Idempotency-Key` (тот же механизм, что у `POST /events`, привязка по `(pet_id, idempotency_key)`, см. «Бизнес-правила»).

1. Система проверяет владение питомцем (см. «Бизнес-правила»).
2. Система валидирует поля тела (см. «Бизнес-правила»).
3. Система вставляет строку `vaccination` (с `next_time`, если задана `next_date`).
4. Если `skip_administered_event = true` — факт не создаётся, `administered_event_id` остаётся `NULL` (см. «Бизнес-правила»). Иначе — всегда создаёт факт `event` с `type=vaccination`, `value = {name}` (название вакцины; подписей текстом сервер не формирует — локализованное «Вакцинация» клиент подставляет по типу, см. «Модель значения события и реестр метрик»), `date = administered_date` + `administered_time` как местное время пояса `tz`, `notes = null`, привязанный к тому же питомцу; сохраняет его `id` в `administered_event_id`. Момент факта не может быть позднее текущего (правило факта, см. «Добавление события — Backend»), иначе `400`.
5. Если `add_reminder_on_next` и задан `next_date` — создаёт настройки напоминания (`reminder_plan`, серверный `id`) для того же питомца: `type=vaccination`, `value = {name}`, `notes = null`, `source = vaccination`, `source_id` = `id` вакцинации, расписание разовое — `frequency_type = once`, `start_date = next_date`, `times = [next_time]`, `tz` — из запроса; одновременно создаётся ровно одно напоминание (см. [Напоминания — Backend](../calendar/napominaniya-backend.md), «Источник настроек»). Момент `next_date` + `next_time` обязан быть строго в будущем, иначе `400`. `id` настроек сохраняется в `next_plan_id`.
6. Для каждого элемента `extra_reminders` создаёт настройки напоминания (`reminder_plan`, серверный `id`) для того же питомца: `type=vaccination`, `value = {name, vaccination_at}` (`vaccination_at` — момент `next_date` + `next_time` как RFC3339 со смещением пояса `tz`), `notes = null`, `source = vaccination_extra`, `source_id` = `id` вакцинации, `frequency_type = once`, `start_date` = `date`, `times = [time]`, `tz` — из запроса; одновременно создаётся ровно одно напоминание. Не зависит от `add_reminder_on_next`. Момент каждого обязан быть строго в будущем, иначе `400`.
7. Возвращает `201 Created` с телом `{id, administered_event_id, next_plan_id}` — идентификатор созданной вакцинации, id факта на дату введения и id настроек напоминания на следующую дату (`null`, если соответствующей записи нет). При повторе с тем же `Idempotency-Key` в теле только `id`. Идентификаторы настроек дополнительных напоминаний в ответе не возвращаются — клиент получает их из списка (`extra_reminders`).

**Редактирование.** `PATCH /vaccinations/{id}`. Тело — частичное, любое из: `name`, `administered_date`, `next_date`, `add_reminder_on_next`, `administered_time`, `next_time`, `extra_reminders`; query-параметр `tz` — как при создании. `200 OK` с телом `{administered_event_id, next_plan_id}` — актуальные id связанного факта и настроек напоминания на следующую дату после синхронизации (`null` — записи нет). Связанные записи обновляются на месте, а не пересоздаются (число связанных записей ограничено — один факт и не более шести напоминаний — и не подвержено риску массового размножения строк, в отличие от лекарств, см. «Лекарства — Backend»).

* Связанный факт существует и не удалён — если в запросе изменена `administered_date`, передано `administered_time` либо изменено имя, обновляются его дата (`administered_date` с учётом этого запроса), время суток и `value.name`; если `administered_time` в запросе не передано, время суток факта сохраняется прежним (равно сохранённому в вакцинации `administered_time`; переданное значение обновляет и `administered_time` вакцинации — независимо от того, есть ли связанный факт). Итоговый момент не может быть позднее текущего (правило факта) — иначе `400`.
* Связанного факта нет либо он уже мягко удалён (например, из календаря), а в запросе передана `administered_date` или `administered_time` — создаётся новый факт, как в шаге 4 создания, его `id` записывается в `administered_event_id`. Факт не удаляется через редактирование вакцинации: он удаляется только вместе с вакцинацией либо самостоятельно из календаря.
* `add_reminder_on_next = true`, настройки напоминания существуют (`next_plan_id` задан и настройки не удалены) — обновляется `value.name` (по тому же правилу, что для факта) и, если в запросе передана `next_date` или `next_time`, расписание настроек (разовое на новый момент — как изменение расписания в «Напоминания — Backend», эндпоинт C); новый момент обязан быть строго в будущем, иначе `400`. Если `next_date` и `next_time` не менялись, расписание не трогается — в том числе когда момент уже прошёл.
* `add_reminder_on_next = true`, а настроек нет (не создавались либо уже удалены — например, напоминание удалено или отмечено в календаре) — создаются новые настройки, как в шаге 5 создания (момент обязан быть в будущем, иначе `400`), `id` записывается в `next_plan_id`.
* `add_reminder_on_next = false` — настройки напоминания, если они есть, жёстко удаляются вместе с напоминанием (см. «Напоминания — Backend», эндпоинт D), `next_plan_id` очищается.
* Флаг не передан — напоминание не создаётся и не удаляется; если в запросе передана `next_date` или `next_time`, существующие настройки переносятся на новый момент (подпись не меняется) по тому же правилу.
* `next_date: null` (или пустая строка) очищает дату следующей вакцинации и `next_time`; настройки напоминания на следующую вакцинацию и все дополнительные напоминания, если они есть, при этом жёстко удаляются, `next_plan_id` очищается — независимо от значения `add_reminder_on_next` и переданного `extra_reminders` (непустой `extra_reminders` вместе с `next_date: null` — `400`).
* `next_time` — если передано, обновляет сохранённое время следующей вакцинации и, при наличии напоминания на следующую дату, переносит его (по правилу выше). Если передана только `next_date` без `next_time`, сохранённое время остаётся прежним.
* `extra_reminders` — если передан, задаёт полный итоговый набор дополнительных напоминаний: элемент с `plan_id` существующих дополнительных настроек этой вакцинации обновляется на месте (если изменились `date`/`time` — разовое расписание переносится на новый момент, строго в будущем, иначе `400`; неизменённый элемент не трогается, в том числе когда его момент уже прошёл); элемент без `plan_id` — создаёт новые настройки, как в шаге 6 создания; существующее дополнительное напоминание, которого нет в списке, жёстко удаляется. `plan_id`, не принадлежащий дополнительным напоминаниям этой вакцинации (в том числе равный `next_plan_id`), — `400`. Пустой массив удаляет все дополнительные напоминания. Если не передан — дополнительные напоминания не меняются (кроме удаления при очистке `next_date`).
* `name` обновляется как передан; `value.name` факта обновляется при изменении имени, `value.name` напоминания на следующую дату — только вместе с `add_reminder_on_next = true` (см. выше); `value.name` дополнительных напоминаний обновляется при изменении имени всегда — они не зависят от флага.

* **`value.vaccination_at` дополнительных напоминаний поддерживается сервером.** При любом изменении итоговых `next_date`/`next_time` вакцинации — запросом `PATCH /vaccinations/{id}` либо переносом напоминания на следующую вакцинацию в календаре («Напоминания — Backend», эндпоинт C) — в той же транзакции `value.vaccination_at` всех дополнительных напоминаний пересчитывается по новому моменту. Расписание самих дополнительных напоминаний при этом не меняется (оно задаётся пользователем).

**Удаление.** `DELETE /vaccinations/{id}` — мягко удаляет запись (`deleted_at`), мягко удаляет `administered_event_id` (если он есть) и жёстко удаляет настройки напоминания `next_plan_id` и все настройки дополнительных напоминаний вместе с их напоминаниями (если они есть; жёсткое удаление — по правилам «Напоминания — Backend»). `204 No Content`. Повторный вызов — `404`, трактуется клиентом как «уже удалено» (см. «Общие требования: Soft-delete»).

## Бизнес-правила и валидация

* Обязательные поля создания: `name`, `administered_date`. `next_date` — опционально.

* `next_date` не проверяется на «позже `administered_date`» — сервер допускает любые сочетания дат. Сами даты на сервере тоже не ограничиваются (ограничения вводит форма, см. «Вакцинации — Frontend»); ограничения сервера касаются только создаваемых записей: факт на дату введения не может быть в будущем, напоминание на следующую дату — в прошлом (см. «Основной сценарий»); если напоминание не создаётся (`add_reminder_on_next` не включён), `next_date` не проверяется.

* `administered_time`, `next_time` и `time` элементов `extra_reminders` опциональны: запись, создаваемая без соответствующего времени, получает время суток «полночь»; если запись не создаётся и не обновляется, время игнорируется. У каждой даты своё время — общего времени на все записи нет.

* `add_reminder_on_next = true` без `next_date` — не ошибка: напоминание не создаётся (при редактировании существующие настройки напоминания жёстко удаляются).

* **Дополнительные напоминания.** Не более пяти (`400` при превышении); непустой `extra_reminders` без итоговой `next_date` — `400`. Моменты (`date` + `time` в поясе `tz`) всех напоминаний вакцинации — дополнительных и, если оно есть или создаётся, напоминания на следующую дату — различны (`400` при совпадении). Момент каждого дополнительного напоминания не может быть позже итогового момента следующей вакцинации (`next_date` + `next_time` в поясе `tz`), иначе `400`; проверка выполняется для создаваемых и изменяемых напоминаний, а также при изменении `next_date`/`next_time` — для всех существующих дополнительных (если хотя бы одно оказалось позже нового момента, `400` и ничего не меняется). Относительно даты введения моменты не ограничиваются. Дополнительные напоминания не зависят от `add_reminder_on_next`.

* Дата и время суток записей (`administered_date` + `administered_time`, `next_date` + `next_time`) трактуются как местное время часового пояса `tz` (обязателен у создания и редактирования); отсутствующий `tz` и неизвестное имя пояса — `400`.

* **Напоминание изменяется и из календаря.** Настройки напоминания остаются связанными с вакцинацией (`source = vaccination` / `vaccination_extra`): тип, подпись и заметка в календаре не меняются (меняются только здесь), а перенос напоминания на следующую вакцинацию в календаре («Изменить все») записывает новую дату в `next_date` и время суток в `next_time` вакцинации (время факта не затрагивает). Перенос дополнительного напоминания в календаре меняет только его настройки: `next_date` и `next_time` вакцинации не меняются. Замена одного напоминания вакцинации (основного или дополнительного) в календаре недоступна. Правила — «Напоминания — Backend», раздел «Источник настроек».

* **Отметка «выполнено» в календаре.** Когда напоминание на следующую вакцинацию отмечено «выполнено» (создан факт), `next_date` и `next_time` вакцинации очищаются (`next_plan_id` становится `null` вместе с удалением настроек), все дополнительные напоминания жёстко удаляются, и вакцинация перестаёт быть «просроченной». Такая вакцинация считается **завершённой**: в той же транзакции в `completed_at` записывается момент отметки; у неё нет ни даты следующей вакцинации, ни напоминаний, клиент показывает статус «Завершена», а запись остаётся в списке как история. Если на завершённой вакцинации через `PATCH` снова задана `next_date`, `completed_at` очищается — вакцинация снова активна. Очистка `next_date` самим пользователем (`next_date: null`) завершённой её не делает. Следующий цикл вакцинации ведётся новой записью: клиент создаёт её `POST /pet/{id}/vaccinations` с `skip_administered_event = true`: единственным фактом выполнения остаётся созданный отметкой, второй факт на ту же дату не создаётся. У такой вакцинации `administered_event_id` пуст; она ведёт себя как вакцинация с удалённым из календаря фактом (см. «Редактирование»: факт создаётся, только если в `PATCH` передана `administered_date` или `administered_time`). Отметка «не выполнено» и удаление напоминания `next_date` не меняют. Отметка дополнительного напоминания «выполнено» создаёт факт, закрывает напоминание и `next_date` не меняет; удаление дополнительного напоминания в календаре убирает его из `extra_reminders`.

* **Идемпотентность создания.** `Idempotency-Key` (UUID v4, иначе `400`) хранится в строке вакцинации и уникален на пару `(pet_id, idempotency_key)`. Повторный `POST` с тем же ключом для того же питомца не создаёт новую запись и новые напоминания, а возвращает `201 Created` с `id` вакцинации, созданной первым запросом, — в том числе когда два запроса с одним ключом пришли одновременно (запрос, проигравший гонку, не оставляет после себя фактов и напоминаний) и когда созданная вакцинация уже мягко удалена (удаление не освобождает ключ).

* Питомец должен принадлежать инициатору и не быть мягко удалён — иначе `404`/`400` соответственно, по общей политике (см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md)).

* **Статус («Просрочена» / «Скоро» / «Актуальна») не хранится и не возвращается backend'ом** — вычисляется на клиенте из `next_date` (см. «Вакцинации — Frontend»). Backend возвращает только сырые даты и `completed_at`, по которому клиент показывает «Завершена».

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Не заполнено обязательное поле / дата не `YYYY-MM-DD` / `administered_time`/`next_time` не `HH:MM[:SS]` / `name` длиннее 100 символов / момент факта на дату введения позднее текущего / момент напоминания на следующую дату или дополнительного напоминания не в будущем / более 5 дополнительных напоминаний / дополнительные напоминания без `next_date` / момент дополнительного напоминания позже момента следующей вакцинации / совпадение моментов напоминаний вакцинации / `plan_id` не относится к дополнительным напоминаниям этой вакцинации / отсутствует или неизвестный часовой пояс `tz` / `Idempotency-Key` не UUID v4 |
| 401 | Токен отсутствует или недействителен |
| 404 | Питомец/вакцинация не найдены, мягко удалены или принадлежат другому пользователю |
| 500 | Внутренняя ошибка БД |

## Хранение состояния и побочные эффекты

Создание/редактирование/удаление вакцинации создаёт/обновляет/мягко удаляет одну строку `event` (факт на дату введения) и создавать/обновлять/жёстко удалять настройки напоминания (`reminder_plan`) с одним напоминанием (`reminder`) каждые — одни на следующую дату и до пяти дополнительных (см. «Основной сценарий»). Данные питомца не затрагиваются.
