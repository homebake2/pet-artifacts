## Назначение

Флоу ведёт список вакцинаций питомца: название, дата введения, дата следующей вакцинации, опционально — два связанных напоминания в календаре (на дату введения и/или на дату следующей вакцинации) и до 10 прикреплённых файлов.

## Модель данных

```
CREATE TABLE vaccination (
  id                 uuid PRIMARY KEY,
  pet_id             uuid NOT NULL REFERENCES pet(id),
  name               text NOT NULL,       -- ≤ 100 символов
  administered_date  date NOT NULL,
  next_date          date NULL,
  administered_event_id  uuid NULL,       -- event.id напоминания на administered_date, если создано
  next_event_id          uuid NULL,       -- event.id напоминания на next_date, если создано
  idempotency_key    text NULL,           -- Idempotency-Key запроса создания; уникален на пару (pet_id, idempotency_key) среди строк с ключом
  deleted_at         timestamptz NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

## Действующие лица и предусловия

* Инициатор — авторизованный владелец питомца.

* Питомец должен существовать, принадлежать инициатору и не быть мягко удалённым.

## Основной сценарий

**Список.** `GET /pet/{id}/vaccinations` — возвращает неудалённые вакцинации питомца, отсортированные по `next_date` (сначала записи с ближайшей `next_date`, затем записи без `next_date` — по `administered_date` убыв.). Опциональные query-параметры `limit`/`offset` — постраничная выдача. Каждый элемент — `GetVaccinationResponse`: `id`, `pet_id`, `name`, `administered_date`, `next_date` (опционально), `administered_event_id` и `next_event_id` (опциональные id связанных событий-напоминаний; отсутствуют, если соответствующее событие не создавалось), `files_count` (см. «Общие требования: Файлы сущностей», по аналогии с `event.files_count`). Проверка владения — по `pet_id`, см. «Бизнес-правила».

**Создание.** `POST /pet/{id}/vaccinations`. Тело: `name` (обязательно, ≤100), `administered_date` (обязательно, `YYYY-MM-DD`), `next_date` (опционально, `YYYY-MM-DD`), `add_event_on_administered` (boolean, по умолчанию `false`), `add_event_on_next` (boolean, по умолчанию `false`; без `next_date` напоминание не создаётся), `event_time` (`HH:MM` или `HH:MM:SS`, OpenAPI `format: time`, опционально — время суток создаваемых напоминаний; если не передано — полночь), `event_label` (опционально, ≤150 символов — уже локализованная клиентом подпись напоминаний: у сервера нет локали пользователя). Опциональный query-параметр `tz` — имя часового пояса IANA (например, `Europe/Moscow`), по умолчанию UTC: дата и `event_time` напоминаний трактуются как местное время этого пояса. Опциональный заголовок `Idempotency-Key` (тот же механизм, что у `POST /events`, привязка по `(pet_id, idempotency_key)`, см. «Бизнес-правила»).

1. Система проверяет владение питомцем (см. «Бизнес-правила»).
2. Система валидирует поля тела (см. «Бизнес-правила»).
3. Система вставляет строку `vaccination`.
4. Если `add_event_on_administered` — создаёт событие `type=other`, `value.label` = `event_label`, а если он не передан или пуст — `"Вакцинация: " + name` (обрезка до 50 символов лимита `other.label`, см. «Модель значения события и реестр метрик»), `date = administered_date` + `event_time` как местное время пояса `tz`, `notes = null`, привязанное к тому же питомцу; сохраняет его `id` в `administered_event_id`.
5. Аналогично для `add_event_on_next` и `next_event_id`, с `date = next_date` + `event_time`.
6. Возвращает `201 Created` с телом `{id}` — идентификатором созданной вакцинации.

**Редактирование.** `PATCH /vaccinations/{id}`. Тело — частичное, любое из: `name`, `administered_date`, `next_date`, `add_event_on_administered`, `add_event_on_next`, `event_time`, `event_label`; query-параметр `tz` — как при создании. `204 No Content`. Связанное событие обновляется на месте, а не пересоздаётся (связь «один флаг — одно событие» не подвержена риску массового размножения строк, в отличие от лекарств, см. «Лекарства — Backend»).

* `add_event_on_administered = true`, связанное событие существует и не удалено — обновляются его дата (`administered_date` с учётом этого запроса), время суток и подпись (`event_label`, а если он не передан или пуст — `"Вакцинация: " + name`); если `event_time` в запросе не передан, время суток события сохраняется прежним.
* `add_event_on_administered = true`, а связанного события нет либо оно уже мягко удалено (например, из календаря) — создаётся новое событие-напоминание, как в шаге 4 создания, его `id` записывается в `administered_event_id`.
* `add_event_on_administered = false` — связанное событие, если оно есть, мягко удаляется (обычным механизмом soft-delete события, см. «Удаление события — Backend»), `administered_event_id` очищается.
* Флаг не передан — событие не создаётся и не удаляется; если в запросе передана `administered_date` или `event_time`, существующее связанное событие переносится на новую дату/время (подпись при этом не меняется).
* Симметрично — для `add_event_on_next`/`next_event_id`/`next_date`. Дополнительно: `next_date: null` (или пустая строка) очищает дату следующей вакцинации; напоминание на `next_date`, если оно есть, при этом мягко удаляется, `next_event_id` очищается — независимо от значения `add_event_on_next`.
* `name` обновляется как передан; подпись уже существующего напоминания обновляется только вместе с флагом `true` (см. выше).

**Удаление.** `DELETE /vaccinations/{id}` — мягко удаляет запись (`deleted_at`) и, если есть, мягко удаляет `administered_event_id`/`next_event_id`. `204 No Content`. Повторный вызов — `404`, трактуется клиентом как «уже удалено» (см. «Общие требования: Soft-delete»).

## Бизнес-правила и валидация

* Обязательные поля создания: `name`, `administered_date`. `next_date` — опционально.

* `next_date` не проверяется на «позже `administered_date`» — сервер допускает любые сочетания дат (переиспользование одной и той же формы для внесения задним числом уже выполненных курсов).

* `event_time` опционален: напоминание, создаваемое без `event_time`, получает время суток «полночь»; если ни одно напоминание не создаётся и не обновляется, `event_time` игнорируется.

* `add_event_on_next = true` без `next_date` — не ошибка: напоминание не создаётся (при редактировании существующее напоминание мягко удаляется).

* Дата и время суток напоминаний (`administered_date`/`next_date` + `event_time`) трактуются как местное время часового пояса `tz` (по умолчанию UTC); неизвестное имя пояса — `400`.

* **Идемпотентность создания.** `Idempotency-Key` (UUID v4, иначе `400`) хранится в строке вакцинации и уникален на пару `(pet_id, idempotency_key)`. Повторный `POST` с тем же ключом для того же питомца не создаёт новую запись и новые напоминания, а возвращает `201 Created` с `id` вакцинации, созданной первым запросом, — в том числе когда два запроса с одним ключом пришли одновременно (запрос, проигравший гонку, не оставляет после себя событий-напоминаний) и когда созданная вакцинация уже мягко удалена (удаление не освобождает ключ).

* Питомец должен принадлежать инициатору и не быть мягко удалён — иначе `404`/`400` соответственно, по общей политике (см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md)).

* **Статус («Просрочена» / «Скоро» / «Актуальна») не хранится и не возвращается backend'ом** — вычисляется на клиенте из `next_date` (см. «Вакцинации — Frontend»). Backend возвращает только сырые даты.

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Не заполнено обязательное поле / дата не `YYYY-MM-DD` / `event_time` не `HH:MM[:SS]` / `name` длиннее 100 символов / `event_label` длиннее 150 символов / неизвестный часовой пояс `tz` / `Idempotency-Key` не UUID v4 |
| 401 | Токен отсутствует или недействителен |
| 404 | Питомец/вакцинация не найдены, мягко удалены или принадлежат другому пользователю |
| 500 | Внутренняя ошибка БД |

## Хранение состояния и побочные эффекты

Создание/редактирование/удаление вакцинации может дополнительно создавать/обновлять/мягко удалять до двух строк `event` (см. «Основной сценарий»). Данные питомца не затрагиваются.
