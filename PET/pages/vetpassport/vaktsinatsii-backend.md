## Назначение

Флоу ведёт список вакцинаций питомца: название, дата введения, дата следующей вакцинации, опционально — две связанные записи в календаре: факт на дату введения (событие `event`, которое уже произошло) и/или напоминание на дату следующей вакцинации (настройки напоминания с одним напоминанием) — и до 10 прикреплённых файлов.

## Модель данных

```
CREATE TABLE vaccination (
  id                 uuid PRIMARY KEY,
  pet_id             uuid NOT NULL REFERENCES pet(id),
  name               text NOT NULL,       -- ≤ 100 символов
  administered_date  date NOT NULL,
  next_date          date NULL,
  administered_event_id  uuid NULL,       -- event.id факта на administered_date, если создан
  next_plan_id           uuid NULL,       -- reminder_plan.id напоминания на next_date, если создано
  idempotency_key    text NULL,           -- Idempotency-Key запроса создания; уникален на пару (pet_id, idempotency_key) среди строк с ключом
  deleted_at         timestamptz NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

## Действующие лица и предусловия

* Инициатор — авторизованный владелец питомца.

* Питомец должен существовать, принадлежать инициатору и не быть мягко удалённым.

## Основной сценарий

**Список.** `GET /pet/{id}/vaccinations` — возвращает неудалённые вакцинации питомца, отсортированные по `next_date` (сначала записи с ближайшей `next_date`, затем записи без `next_date` — по `administered_date` убыв.). Опциональные query-параметры `limit`/`offset` — постраничная выдача. Каждый элемент — `GetVaccinationResponse`: `id`, `pet_id`, `name`, `administered_date`, `next_date` (опционально), `administered_event_id` (опциональный id связанного факта; отсутствует, если факт мягко удалён, например, из календаря) и `next_plan_id` (опциональный id настроек связанного напоминания; отсутствует, если напоминание не создавалось либо его настроек уже нет — например, напоминание удалено или отмечено в календаре), `files_count` (см. «Общие требования: Файлы сущностей», по аналогии с `event.files_count`). Проверка владения — по `pet_id`, см. «Бизнес-правила».

**Создание.** `POST /pet/{id}/vaccinations`. Тело: `name` (обязательно, ≤100), `administered_date` (обязательно, `YYYY-MM-DD`), `next_date` (опционально, `YYYY-MM-DD`), `administered_time` (`HH:MM` или `HH:MM:SS`, OpenAPI `format: time`, опционально — время суток факта на дату введения; если не передано — полночь), `add_reminder_on_next` (boolean, по умолчанию `false`; без `next_date` напоминание не создаётся), `next_time` (`HH:MM` или `HH:MM:SS`, опционально — время суток напоминания на `next_date`; если не передано — полночь), `event_label` (опционально, ≤150 символов — уже локализованная клиентом подпись записей: у сервера нет локали пользователя). Обязательный query-параметр `tz` — имя часового пояса IANA (например, `Europe/Moscow`): даты и `administered_time`/`next_time` трактуются как местное время этого пояса. Опциональный заголовок `Idempotency-Key` (тот же механизм, что у `POST /events`, привязка по `(pet_id, idempotency_key)`, см. «Бизнес-правила»).

1. Система проверяет владение питомцем (см. «Бизнес-правила»).
2. Система валидирует поля тела (см. «Бизнес-правила»).
3. Система вставляет строку `vaccination`.
4. Всегда создаёт факт `event` с `type=other`, `value.label` = `event_label`, а если он не передан или пуст — `"Вакцинация: " + name` (обрезка до 50 символов лимита `other.label`, см. «Модель значения события и реестр метрик»), `date = administered_date` + `administered_time` как местное время пояса `tz`, `notes = null`, привязанный к тому же питомцу; сохраняет его `id` в `administered_event_id`. Момент факта не может быть позднее текущего (правило факта, см. «Добавление события — Backend»), иначе `400`.
5. Если `add_reminder_on_next` и задан `next_date` — создаёт настройки напоминания (`reminder_plan`, серверный `id`) для того же питомца: `type=other`, `value.label` — как в шаге 4, `notes = null`, `source = vaccination`, `source_id` = `id` вакцинации, расписание разовое — `frequency_type = once`, `start_date = next_date`, `times = [next_time]`, `tz` — из запроса; одновременно создаётся ровно одно напоминание (см. [Напоминания — Backend](../calendar/napominaniya-backend.md), «Источник настроек»). Момент `next_date` + `next_time` обязан быть строго в будущем, иначе `400`. `id` настроек сохраняется в `next_plan_id`.
6. Возвращает `201 Created` с телом `{id}` — идентификатором созданной вакцинации.

**Редактирование.** `PATCH /vaccinations/{id}`. Тело — частичное, любое из: `name`, `administered_date`, `next_date`, `add_reminder_on_next`, `administered_time`, `next_time`, `event_label`; query-параметр `tz` — как при создании. `204 No Content`. Связанные записи обновляются на месте, а не пересоздаются (связь «одна вакцинация — один факт и одно напоминание» не подвержена риску массового размножения строк, в отличие от лекарств, см. «Лекарства — Backend»).

* Связанный факт существует и не удалён — если в запросе изменена `administered_date`, передано `administered_time` либо изменено имя/`event_label`, обновляются его дата (`administered_date` с учётом этого запроса), время суток и подпись (`event_label`, а если он не передан или пуст — `"Вакцинация: " + name`); если `administered_time` в запросе не передано, время суток факта сохраняется прежним. Итоговый момент не может быть позднее текущего (правило факта) — иначе `400`.
* Связанного факта нет либо он уже мягко удалён (например, из календаря), а в запросе передана `administered_date` или `administered_time` — создаётся новый факт, как в шаге 4 создания, его `id` записывается в `administered_event_id`. Факт не удаляется через редактирование вакцинации: он удаляется только вместе с вакцинацией либо самостоятельно из календаря.
* `add_reminder_on_next = true`, настройки напоминания существуют (`next_plan_id` задан и настройки не удалены) — обновляются подпись (`value.label`, по тому же правилу, что для факта) и, если в запросе передана `next_date` или `next_time`, расписание настроек (разовое на новый момент — как изменение расписания в «Напоминания — Backend», эндпоинт C); новый момент обязан быть строго в будущем, иначе `400`. Если `next_date` и `next_time` не менялись, расписание не трогается — в том числе когда момент уже прошёл.
* `add_reminder_on_next = true`, а настроек нет (не создавались либо уже удалены — например, напоминание удалено или отмечено в календаре) — создаются новые настройки, как в шаге 5 создания (момент обязан быть в будущем, иначе `400`), `id` записывается в `next_plan_id`.
* `add_reminder_on_next = false` — настройки напоминания, если они есть, жёстко удаляются вместе с напоминанием (см. «Напоминания — Backend», эндпоинт D), `next_plan_id` очищается.
* Флаг не передан — напоминание не создаётся и не удаляется; если в запросе передана `next_date` или `next_time`, существующие настройки переносятся на новый момент (подпись не меняется) по тому же правилу.
* `next_date: null` (или пустая строка) очищает дату следующей вакцинации; настройки напоминания, если они есть, при этом жёстко удаляются, `next_plan_id` очищается — независимо от значения `add_reminder_on_next`.
* `name` обновляется как передан; подпись факта обновляется при изменении имени/`event_label`, подпись напоминания — только вместе с `add_reminder_on_next = true` (см. выше).

**Удаление.** `DELETE /vaccinations/{id}` — мягко удаляет запись (`deleted_at`), мягко удаляет `administered_event_id` (если он есть) и жёстко удаляет настройки напоминания `next_plan_id` вместе с их напоминанием (если они есть; жёсткое удаление — по правилам «Напоминания — Backend»). `204 No Content`. Повторный вызов — `404`, трактуется клиентом как «уже удалено» (см. «Общие требования: Soft-delete»).

## Бизнес-правила и валидация

* Обязательные поля создания: `name`, `administered_date`. `next_date` — опционально.

* `next_date` не проверяется на «позже `administered_date`» — сервер допускает любые сочетания дат. Сами даты на сервере тоже не ограничиваются (ограничения вводит форма, см. «Вакцинации — Frontend»); ограничения сервера касаются только создаваемых записей: факт на дату введения не может быть в будущем, напоминание на следующую дату — в прошлом (см. «Основной сценарий»); если напоминание не создаётся (`add_reminder_on_next` не включён), `next_date` не проверяется.

* `administered_time` и `next_time` опциональны: запись, создаваемая без соответствующего времени, получает время суток «полночь»; если запись не создаётся и не обновляется, время игнорируется. У каждой даты своё время — общего времени на обе записи нет.

* `add_reminder_on_next = true` без `next_date` — не ошибка: напоминание не создаётся (при редактировании существующие настройки напоминания жёстко удаляются).

* Дата и время суток записей (`administered_date` + `administered_time`, `next_date` + `next_time`) трактуются как местное время часового пояса `tz` (обязателен у создания и редактирования); отсутствующий `tz` и неизвестное имя пояса — `400`.

* **Напоминание изменяется и из календаря.** Настройки напоминания остаются связанными с вакцинацией (`source = vaccination`): тип, подпись и заметка в календаре не меняются (меняются только здесь), а перенос напоминания в календаре («Изменить все») записывает новую дату в `next_date` вакцинации (время суток хранится только в напоминании и время факта не затрагивает). Замена одного напоминания вакцинации в календаре недоступна. Правила — «Напоминания — Backend», раздел «Источник настроек».

* **Отметка «выполнено» в календаре.** Когда напоминание на следующую вакцинацию отмечено «выполнено» (создан факт), `next_date` вакцинации очищается (`next_plan_id` становится `null` вместе с удалением настроек), и вакцинация перестаёт быть «просроченной». Отметка «не выполнено» и удаление напоминания `next_date` не меняют.

* **Идемпотентность создания.** `Idempotency-Key` (UUID v4, иначе `400`) хранится в строке вакцинации и уникален на пару `(pet_id, idempotency_key)`. Повторный `POST` с тем же ключом для того же питомца не создаёт новую запись и новые напоминания, а возвращает `201 Created` с `id` вакцинации, созданной первым запросом, — в том числе когда два запроса с одним ключом пришли одновременно (запрос, проигравший гонку, не оставляет после себя фактов и напоминаний) и когда созданная вакцинация уже мягко удалена (удаление не освобождает ключ).

* Питомец должен принадлежать инициатору и не быть мягко удалён — иначе `404`/`400` соответственно, по общей политике (см. [Общие требования: IDOR и владение ресурсами](../common/obschie-trebovaniya-idor-i-vladenie-resursami.md)).

* **Статус («Просрочена» / «Скоро» / «Актуальна») не хранится и не возвращается backend'ом** — вычисляется на клиенте из `next_date` (см. «Вакцинации — Frontend»). Backend возвращает только сырые даты.

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Не заполнено обязательное поле / дата не `YYYY-MM-DD` / `administered_time`/`next_time` не `HH:MM[:SS]` / `name` длиннее 100 символов / `event_label` длиннее 150 символов / момент факта на дату введения позднее текущего / момент напоминания на следующую дату не в будущем / отсутствует или неизвестный часовой пояс `tz` / `Idempotency-Key` не UUID v4 |
| 401 | Токен отсутствует или недействителен |
| 404 | Питомец/вакцинация не найдены, мягко удалены или принадлежат другому пользователю |
| 500 | Внутренняя ошибка БД |

## Хранение состояния и побочные эффекты

Создание/редактирование/удаление вакцинации создаёт/обновляет/мягко удаляет одну строку `event` (факт на дату введения) и создавать/обновлять/жёстко удалять одни настройки напоминания (`reminder_plan`) с одним напоминанием (`reminder`) (см. «Основной сценарий»). Данные питомца не затрагиваются.
