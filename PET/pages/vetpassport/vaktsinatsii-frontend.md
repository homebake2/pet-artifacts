## Назначение

Таб «Вакцинации» экрана «Ветпаспорт»: блок «Ближайшая вакцинация» + список всех вакцинаций питомца, экраны добавления/редактирования вакцинации.

## Основной сценарий

1. Таб открывается запросом списка вакцинаций питомца. Пока запрос не завершён — скелетон списка (см. «Общие требования: UI-паттерны запросов»); если список пуст — пустое состояние с призывом добавить первую вакцинацию.

2. Система определяет **статус** каждой вакцинации: «Завершена» — по признаку `completed_at` из ответа, остальные статусы вычисляются полностью на клиенте по `next_date` (backend их не хранит и не возвращает, см. «Вакцинации — Backend»):
   * `completed_at` задан — **«Завершена»** (статус по `next_date` не вычисляется; у завершённой вакцинации `next_date` отсутствует).
   * `next_date` отсутствует — статус не вычисляется и не показывается.
   * `next_date` раньше текущей календарной даты — **«Просрочена»**.
   * `next_date` наступает в течение 30 дней от текущей даты включительно — **«Скоро»**.
   * `next_date` позже, чем через 30 дней — **«Актуальна»**.

3. Блок «Ближайшая вакцинация» вверху таба показывает вакцинацию с ближайшей будущей/сегодняшней `next_date` среди всех вакцинаций питомца (минимальная `next_date >= сегодня`). Если ни у одной вакцинации нет `next_date >= сегодня` (включая случай, когда ни у одной вакцинации `next_date` вообще не задан), блок не отображается вовсе — карточки нет.

4. Список показывает все вакцинации карточками: название, дата и время введения (`administered_date` + `administered_time` записи — без обращения к связанному факту), дата и время следующей (если есть), признак статуса (если вычислен, см. шаг 2). Для каждой вакцинации имеется возможность открыть форму редактирования и удалить её. Наличие связанных записей клиент определяет по элементу списка (`GetVaccinationResponse`): факт на дату введения есть, если задан `administered_event_id`, напоминание на следующую дату — если задан `next_plan_id`, дополнительные напоминания — по массиву `extra_reminders` (отдельного поля `has_events` в ответе нет).

5. Имеется возможность добавить вакцинацию и открыть форму редактирования существующей; форма общая для обоих режимов (тот же паттерн одной формы для create/edit с разным режимом, что в «Добавление питомца — Frontend»). Поля формы:

   * Название вакцины (обязательное, ≤100 символов).
   * **Дата и время введения** — одно поле выбора даты и времени (обязательное). Момент не может быть позже текущего. При выборе даты время по умолчанию `09:00`.
   * **Дата и время следующей вакцинации** — одно поле выбора даты и времени (опциональное). Дата не раньше текущей даты. При выборе даты время по умолчанию `09:00`. Это же время используется как время напоминания на следующую вакцинацию — отдельного поля «Время напоминания» нет.
   * Признак «Добавить напоминание на дату следующей вакцинации» (создаёт напоминание на момент из поля «Дата и время следующей вакцинации»; по умолчанию включён; недоступен, пока это поле не заполнено; момент должен быть в будущем).
   * Блок «Дополнительные напоминания» — от нуля до пяти полей выбора даты и времени (см. раздел «Дополнительные напоминания» ниже).
   * Блок прикрепления файлов (до 10, изображения и документы — см. «Общие требования: Файлы сущностей»).

   Клиент отправляет время как `HH:mm` (сервер принимает `HH:MM` и `HH:MM:SS`). Запись-факт «Уже произошло» на дату введения создаётся всегда — отдельного признака для неё нет.

6. При редактировании форма предзаполняется текущими значениями; признак напоминания изначально включён, если у записи есть `next_plan_id`. Время в поле «Дата и время введения» предзаполняется значением `administered_time` записи (отдельный запрос факта для этого не нужен), время в поле «Дата и время следующей вакцинации» — значением `next_time` записи (по умолчанию `09:00`, если `next_time` не задано), дополнительные напоминания — элементами `extra_reminders`; так сохранение без изменения этих полей не сдвигает записи. Ограничения дат (см. «Бизнес-правила и валидация») проверяются только для изменённых полей: уже сохранённая «Дата следующей вакцинации» в прошлом (статус «Просрочена») и уже сохранённые дополнительные напоминания, момент которых прошёл, не мешают отредактировать остальные поля. Блок файлов показывает уже прикреплённые файлы записи. Отключение признака напоминания приведёт при сохранении к удалению созданного напоминания на следующую вакцинацию (см. «Вакцинации — Backend»); дополнительные напоминания от признака не зависят и остаются. Форма не показывает отдельного предупреждения об удалении (в отличие от лекарств, где риск многократного пересоздания событий по расписанию оправдывает подтверждение, см. «Лекарства — Frontend»).

7. «Сохранить» применяет результат оптимистично и сразу возвращает на таб «Вакцинации», не дожидаясь ответа сервера (см. «Общие требования: Оптимистичные обновления (dataSource=network)»).

8. Удаление — оптимистичное, с окном отмены (см. там же, раздел «Оптимистичное удаление с окном отмены (Undo)»). Пока созданная запись не подтверждена сервером (временная карточка с индикацией «синхронизируется»), она доступна только для просмотра: открыть, отредактировать и удалить её нельзя (см. там же, раздел «Визуальная индикация фоновой синхронизации»).

## Дополнительные напоминания

Дополнительные напоминания — отдельные напоминания вакцинации на произвольные даты и время (например, за неделю и за день до следующей вакцинации). Каждое дополнительное напоминание — разовое напоминание в календаре (см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md)), связанное с вакцинацией.

* Имеется возможность добавить дополнительное напоминание — новое поле выбора даты и времени. Всего можно добавить не более пяти; при достижении предела действие добавления недоступно.

* Добавление недоступно, пока в форме не заполнено поле «Дата и время следующей вакцинации». Дополнительные напоминания нельзя создать для вакцинации без следующей даты.

* Новое поле предзаполняется значением поля «Дата и время следующей вакцинации» на момент добавления. Последующее изменение поля «Дата и время следующей вакцинации» уже добавленные поля не меняет, но если «следующая» оказалась раньше какого-либо из них, это поле считается некорректным (см. «Бизнес-правила и валидация»).

* Имеется возможность удалить любое из добавленных полей (в том числе все). Минимального числа дополнительных напоминаний нет.

* Если пользователь очищает поле «Дата и время следующей вакцинации», блок «Дополнительные напоминания» становится недоступным, добавленные поля из формы убираются; при сохранении ранее созданные дополнительные напоминания удаляются (по тому же правилу, что и напоминание на следующую вакцинацию, см. «Вакцинации — Backend»).

* Признак «Добавить напоминание на дату следующей вакцинации» дополнительные напоминания не включает и не отключает: они создаются независимо от него, при условии заполненного поля «Дата и время следующей вакцинации».

## Следующая вакцинация после отметки «Выполнено»

Когда в календаре отмечено «Выполнено» напоминание на следующую вакцинацию, система предлагает внести следующую вакцинацию (см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md), раздел «Отметка прошедшего напоминания»). При ответе «Да» открывается форма создания вакцинации — та же форма, что при добавлении, со следующими отличиями:

* Питомец и «Название вакцины» предзаполнены из завершённой вакцинации (название — `source_title` напоминания).

* «Дата и время введения» предзаполнены моментом напоминания, отмеченного выполненным (то есть датой и временем факта, созданного отметкой). Пользователь может изменить их как обычно, действуют те же ограничения (момент не позже текущего). Факт, созданный отметкой, при этом не переносится: он остаётся на своём моменте в календаре, а в вакцинации сохраняется введённая дата.

* Факт на дату введения новой вакцинацией не создаётся: единственным фактом выполнения остаётся созданный отметкой напоминания (в запросе создания передаётся `skip_administered_event = true`; см. «Вакцинации — Backend»). Если отметка завершилась ошибкой (напоминание осталось неотмеченным), передаётся `skip_administered_event = false`.

* «Дата и время следующей вакцинации», дополнительные напоминания и файлы пусты, признак напоминания включён по умолчанию, как при обычном добавлении.

Закрытие формы без сохранения ничего не откатывает: завершённая вакцинация остаётся завершённой, факт — в календаре; следующую вакцинацию можно добавить позже обычным путём.

## Бизнес-правила и валидация

* Доступность возможностей зависит от роли пользователя у питомца (поле `access`, см. [Общие требования: Доступ к питомцу](../common/obschie-trebovaniya-dostup-k-pitomtsu.md)): возможности создания, изменения и удаления доступны ролям `owner` и `full`; для роли `view` они не показываются, экран только отображает данные. Запись, связанная с несколькими питомцами, изменяема только если роль `owner`/`full` у каждого её питомца, иначе она показывается без возможностей изменения. `403 FORBIDDEN` (роль изменилась на другом устройстве) обрабатывается обновлением данных и сообщением, что действие недоступно.

* Обязательные поля: «Название вакцины», «Дата и время введения». «Дата и время следующей вакцинации» и дополнительные напоминания — опциональны.

* «Дата и время введения» — одно поле; время суток в нём обязательно всегда (факт на дату введения создаётся всегда). Дата не может быть позднее текущей (валидация формы, зеркально серверу нет — сервер такой проверки для даты не делает, см. «Вакцинации — Backend»; расхождение осознанное: клиент направляет пользователя к разумному вводу, но не блокирует внесение данных нестандартным путём на уровне API).

* «Дата и время следующей вакцинации» — одно поле; дата не может быть раньше текущей: в выборе даты нет дат в прошлом. Время суток в нём хранится в записи вакцинации и определяет время напоминания на следующую вакцинацию и значение по умолчанию для дополнительных напоминаний. Сервер самих дат не ограничивает (см. «Вакцинации — Backend»).

* Дополнительные напоминания: не более пяти; доступны только при заполненном поле «Дата и время следующей вакцинации»; момент каждого должен быть строго позже текущего и не позже момента следующей вакцинации (поле «Дата и время следующей вакцинации»; проверяется при изменении любого из полей, в том числе при переносе «следующей» на более раннее время); моменты всех напоминаний вакцинации (дополнительных и, если включено, напоминания на следующую вакцинацию) не совпадают между собой — по аналогии с запретом одинаковых времён в расписании лекарства.

* Напоминание на следующую вакцинацию можно перенести из календаря («Изменить все», см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md), раздел «Связанные напоминания»): новые дата и время записываются в поле «Дата и время следующей вакцинации», а название и тип в календаре меняются только здесь. Перенос дополнительного напоминания из календаря меняет только его момент и поле «Дата и время следующей вакцинации» не затрагивает. Отметка напоминания на следующую вакцинацию «Выполнено» очищает «Дату и время следующей вакцинации» и удаляет дополнительные напоминания — вакцинация перестаёт быть «просроченной»; список вакцинаций после этого обновляется. Отметка «Выполнено» дополнительного напоминания следующую дату не очищает. После отметки основного напоминания система предлагает внести следующую вакцинацию (см. раздел «Следующая вакцинация после отметки «Выполнено»»); завершённая вакцинация остаётся в списке как история.

* Факт на дату введения не может быть в будущем (при сегодняшней дате время не позже текущего), напоминания (на следующую дату и дополнительные) — не в прошлом (момент строго позже текущего): при нарушении отправка блокируется с сообщением, что дату или время нужно изменить, — форма не отправляет заведомо отклоняемый запрос (сервер вернёт `400`, см. «Вакцинации — Backend»).

* Запросы создания и редактирования передают обязательный query-параметр `tz` — часовой пояс устройства, в котором сервер трактует даты и время (см. «Вакцинации — Backend»). Так запись получает тот же момент времени, что и в режиме `dataSource=local`. Подписей текстом клиент серверу не передаёт: факт и напоминания вакцинации имеют тип `vaccination` и `value` с названием вакцины, а локализованное «Вакцинация» подставляет клиент по типу. Запросы передают `administered_time`, `next_time`, флаг `add_reminder_on_next` и список `extra_reminders` (каждый элемент — `date`, `time`, а для уже сохранённого напоминания — ещё `plan_id`). Запрос создания из формы «Следующая вакцинация после отметки «Выполнено»» дополнительно передаёт `skip_administered_event = true`.

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле | Форма не отправляется, сообщение под полем |
| Момент дополнительного напоминания не в будущем, позже момента следующей вакцинации либо совпадает с моментом другого напоминания вакцинации | Форма не отправляется, сообщение под соответствующим полем |
| Транзиентная ошибка сервера при сохранении (нет сети/таймаут/5xx) | Оптимистичное изменение остаётся применённым, запрос уходит в очередь фоновых повторов, карточка показывает индикацию «синхронизируется» (см. «Общие требования: Оптимистичные обновления», разделы «Классификация ошибок мутации», «Очередь фоновых мутаций и повторные попытки») |
| Постоянная ошибка сервера при сохранении (400/403/409) | Оптимистичное изменение откатывается, пользователю показывается сообщение об ошибке; введённые данные для повторной отправки не сохраняются (см. там же, «Обработка ошибок и откат») |
| Отложенный `DELETE` не доставлен — транзиентная ошибка | Запрос уходит в очередь фоновых повторов, вакцинация остаётся удалённой из списка без отката (см. там же, «Оптимистичное удаление с окном отмены (Undo)») |
| Отложенный `DELETE` завершился постоянной ошибкой / повторы исчерпаны | Вакцинация восстанавливается в списке, пользователю показывается сообщение об ошибке с возможностью повторить удаление (см. там же) |
| Вакцинация уже удалена на другом устройстве (404 при открытии формы редактирования/при сохранении) | Тихо убрать из списка / показать «уже удалено», без сообщения об ошибке (см. «Общие требования: Soft-delete», раздел «UX при гонках удаления») |

## Хранение состояния и побочные эффекты

После создания/редактирования/удаления вакцинации — инвалидация кэша списка вакцинаций питомца. Если операция создала/изменила/удалила связанный факт или напоминание — также инвалидация кэшей календаря, блока ближайшего события и списка событий питомца (для факта), чтобы запись сразу появилась/исчезла там; при изменении напоминания клиент также синхронизирует локальные уведомления (см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md)). Кэш списка вакцинаций патчится синхронно и оптимистично; кэш календаря/списка событий обновляется фоновым refetch (см. «Общие требования: Оптимистичные обновления (dataSource=network)»).
