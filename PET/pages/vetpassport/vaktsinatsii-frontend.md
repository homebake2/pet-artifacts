## Назначение

Таб «Вакцинации» экрана «Ветпаспорт»: блок «Ближайшая вакцинация» + список всех вакцинаций питомца, экраны добавления/редактирования вакцинации.

## Основной сценарий

1. Таб открывается запросом списка вакцинаций питомца. Пока запрос не завершён — скелетон списка (см. «Общие требования: UI-паттерны запросов»); если список пуст — пустое состояние с призывом добавить первую вакцинацию.

2. Система вычисляет **статус** каждой вакцинации по `next_date`, полностью на клиенте (backend статус не хранит и не возвращает, см. «Вакцинации — Backend»):
   * `next_date` отсутствует — статус не вычисляется и не показывается.
   * `next_date` раньше текущей календарной даты — **«Просрочена»**.
   * `next_date` наступает в течение 30 дней от текущей даты включительно — **«Скоро»**.
   * `next_date` позже, чем через 30 дней — **«Актуальна»**.

3. Блок «Ближайшая вакцинация» вверху таба показывает вакцинацию с ближайшей будущей/сегодняшней `next_date` среди всех вакцинаций питомца (минимальная `next_date >= сегодня`). Если ни у одной вакцинации нет `next_date >= сегодня` (включая случай, когда ни у одной вакцинации `next_date` вообще не задан), блок не отображается вовсе — карточки нет.

4. Список показывает все вакцинации карточками: название, дата введения, дата следующей (если есть), признак статуса (если вычислен, см. шаг 2). Для каждой вакцинации имеется возможность открыть форму редактирования и удалить её. Наличие связанных записей клиент определяет по элементу списка (`GetVaccinationResponse`): факт на дату введения есть, если задан `administered_event_id`, напоминание на следующую дату — если задан `next_plan_id` (отдельного поля `has_events` в ответе нет).

5. Имеется возможность добавить вакцинацию и открыть форму редактирования существующей; форма общая для обоих режимов, см. «Добавление питомца — Frontend» — тот же паттерн одной формы для create/edit с разным режимом): Название вакцины (обязательное, ≤100 символов), Дата введения (обязательная, не позднее текущей даты — по аналогии с датой рождения питомца), Время введения (обязательное, по умолчанию `09:00`; момент «Дата введения» + «Время введения» не может быть позже текущего), Дата следующей вакцинации (опциональная, не раньше текущей даты), Время напоминания (по умолчанию `09:00`; обязательное, если включено напоминание), признак «Добавить напоминание на дату следующей вакцинации» (создаёт напоминание; по умолчанию включён; недоступен, пока не заполнена «Дата следующей вакцинации»; момент «Дата следующей вакцинации» + «Время напоминания» должен быть в будущем). Каждая дата отображается в одной строке со своим временем; клиент отправляет время как `HH:mm` (сервер принимает `HH:MM` и `HH:MM:SS`). Запись-факт «Уже произошло» на дату введения создаётся всегда — отдельного признака для неё нет. Блок прикрепления файлов (до 10, изображения и документы — см. «Общие требования: Файлы сущностей»).

6. При редактировании форма предзаполняется текущими значениями; признак напоминания изначально включён, если у записи есть `next_plan_id`, а «Время введения» и «Время напоминания» предзаполняются временем уже существующих связанных записей — факта (`administered_event_id`) и напоминания (`next_plan_id`) соответственно (значение по умолчанию `09:00` — только если запись недоступна, например удалена из календаря либо напоминание уже отмечено), так что сохранение без изменения этих полей не сдвигает записи. Ограничения дат (см. «Бизнес-правила и валидация») проверяются только для изменённых полей: уже сохранённая «Дата следующей вакцинации» в прошлом (статус «Просрочена») не мешает отредактировать остальные поля. Блок файлов показывает уже прикреплённые файлы записи. Отключение признака напоминания приведёт при сохранении к удалению созданного напоминания (см. «Вакцинации — Backend») — форма не показывает отдельного предупреждения об этом (в отличие от лекарств, где риск многократного пересоздания событий по расписанию оправдывает подтверждение, см. «Лекарства — Frontend») — здесь на кону не больше одной записи за раз.

7. «Сохранить» применяет результат оптимистично и сразу возвращает на таб «Вакцинации», не дожидаясь ответа сервера (см. «Общие требования: Оптимистичные обновления (dataSource=network)»).

8. Удаление — оптимистичное, с окном отмены (см. там же, раздел «Оптимистичное удаление с окном отмены (Undo)»). Пока созданная запись не подтверждена сервером (временная карточка с индикацией «синхронизируется»), она доступна только для просмотра: открыть, отредактировать и удалить её нельзя (см. там же, раздел «Визуальная индикация фоновой синхронизации»).

## Бизнес-правила и валидация

* Обязательные поля: «Название вакцины», «Дата введения». «Дата следующей вакцинации» — опциональна.

* «Дата введения» не может быть позднее текущей даты (валидация формы, зеркально серверу нет — сервер такой проверки не делает, см. «Вакцинации — Backend»; расхождение осознанное: клиент направляет пользователя к разумному вводу, но не блокирует внесение данных нестандартным путём на уровне API).

* «Дата следующей вакцинации» не может быть раньше текущей даты: в выборе даты нет дат в прошлом. Сервер самих дат не ограничивает (см. «Вакцинации — Backend»).

* «Время введения» обязательно всегда (факт на дату введения создаётся всегда); «Время напоминания» обязательно, если включено напоминание.

* Напоминание на следующую вакцинацию можно перенести из календаря («Изменить все», см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md), раздел «Связанные напоминания»): новая дата записывается в «Дату следующей вакцинации», а название и тип в календаре меняются только здесь. Отметка такого напоминания «Выполнено» очищает «Дату следующей вакцинации» — вакцинация перестаёт быть «просроченной»; список вакцинаций после этого обновляется.

* Факт на дату введения не может быть в будущем (при сегодняшней дате время не позже текущего), напоминание на следующую дату — не в прошлом (при сегодняшней дате время позже текущего): при нарушении отправка блокируется с сообщением, что дату или время нужно изменить, — форма не отправляет заведомо отклоняемый запрос (сервер вернёт `400`, см. «Вакцинации — Backend»).

* Запросы создания и редактирования передают `event_label` — подпись записей на языке интерфейса («Вакцинация: {название}» для русского, «Vaccination: {название}» для английского) и обязательный query-параметр `tz` — часовой пояс устройства, в котором сервер трактует даты и время (см. «Вакцинации — Backend»). Так запись получает ту же подпись и тот же момент времени, что и в режиме `dataSource=local`. Запросы передают `administered_time`, `next_time` и флаг `add_reminder_on_next`.

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле | Форма не отправляется, сообщение под полем |
| Транзиентная ошибка сервера при сохранении (нет сети/таймаут/5xx) | Оптимистичное изменение остаётся применённым, запрос уходит в очередь фоновых повторов, карточка показывает индикацию «синхронизируется» (см. «Общие требования: Оптимистичные обновления», разделы «Классификация ошибок мутации», «Очередь фоновых мутаций и повторные попытки») |
| Постоянная ошибка сервера при сохранении (400/403/409) | Оптимистичное изменение откатывается, пользователю показывается сообщение об ошибке; введённые данные для повторной отправки не сохраняются (см. там же, «Обработка ошибок и откат») |
| Отложенный `DELETE` не доставлен — транзиентная ошибка | Запрос уходит в очередь фоновых повторов, вакцинация остаётся удалённой из списка без отката (см. там же, «Оптимистичное удаление с окном отмены (Undo)») |
| Отложенный `DELETE` завершился постоянной ошибкой / повторы исчерпаны | Вакцинация восстанавливается в списке, пользователю показывается сообщение об ошибке с возможностью повторить удаление (см. там же) |
| Вакцинация уже удалена на другом устройстве (404 при открытии формы редактирования/при сохранении) | Тихо убрать из списка / показать «уже удалено», без сообщения об ошибке (см. «Общие требования: Soft-delete», раздел «UX при гонках удаления») |

## Хранение состояния и побочные эффекты

После создания/редактирования/удаления вакцинации — инвалидация кэша списка вакцинаций питомца. Если операция создала/изменила/удалила связанный факт или напоминание — также инвалидация кэшей календаря, блока ближайшего события и списка событий питомца (для факта), чтобы запись сразу появилась/исчезла там; при изменении напоминания клиент также синхронизирует локальные уведомления (см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md)). Кэш списка вакцинаций патчится синхронно и оптимистично; кэш календаря/списка событий обновляется фоновым refetch (см. «Общие требования: Оптимистичные обновления (dataSource=network)»).
