## Назначение

Флоу ведёт список лекарств питомца: название, дозировка (базовая, свободный текст), схема приёма (частота + одно или несколько времён приёма в день), дата начала и опциональная дата окончания курса, заметка, до 10 прикреплённых файлов. Опционально по расписанию создаётся набор напоминаний в календаре — в виде обычных настроек напоминания (`reminder_plan`) с напоминаниями (см. [Напоминания — Backend](../calendar/napominaniya-backend.md)); не более одного набора на лекарство одновременно. Логика частоты и времени приёма ориентирована на паттерн приложения «Здоровье» (Apple Health, раздел «Лекарства»): частота выбирается из нескольких видов (каждый день / определённые дни недели / через N дней / по необходимости), и на каждый день приёма может приходиться несколько времён приёма с собственной дозой.

## Модель данных

```
CREATE TABLE medication (
  id                uuid PRIMARY KEY,
  pet_id            uuid NOT NULL REFERENCES pet(id),
  name              text NOT NULL,        -- ≤ 100 символов
  dosage            text NOT NULL,        -- ≤ 100 символов, свободный текст ("1 пипетка", "1 таблетка"); базовая доза по умолчанию для всех времён приёма
  frequency_type    text NOT NULL,        -- 'daily' | 'specific_days' | 'every_n_days' | 'as_needed'
  weekdays          jsonb NULL,            -- массив int 1..7 (пн=1 .. вс=7), только при frequency_type = 'specific_days', иначе NULL
  interval_days     integer NULL,          -- 2..365, только при frequency_type = 'every_n_days', иначе NULL
  times             jsonb NULL,            -- [{time: 'HH:MM[:SS]', dose_note: text|null}], 1..4 элемента; NULL при frequency_type = 'as_needed'
  start_date        date NULL,             -- обязателен при любом frequency_type, кроме 'as_needed'; NULL при 'as_needed'
  end_date          date NULL,             -- NULL = курс без определённой даты окончания ("бессрочно"); NULL всегда при 'as_needed'
  reminder_plan_id  uuid NULL,             -- reminder_plan.id набора напоминаний; NULL, если набора нет
  note              text NULL,             -- ≤ 1000 символов
  idempotency_key   text NULL,             -- Idempotency-Key запроса создания; уникален на пару (pet_id, idempotency_key) среди строк с ключом
  deleted_at        timestamptz NULL,
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now()
);
```

Набор напоминаний лекарства — это настройки напоминания `reminder_plan`, созданные по расписанию лекарства: их данные — `type = medication`, `value = {name}`, `notes` = дозировка лекарства (см. «Расчёт расписания», шаг 3). `reminder_plan_id` — ссылка лекарства на эти настройки; набор есть, пока такие настройки существуют, а настройки существуют, пока есть хотя бы одно незавершённое напоминание (см. [Напоминания — Backend](../calendar/napominaniya-backend.md): настройки без незавершённых напоминаний удаляются). Если настройки удалены (все напоминания отмечены или удалены в календаре, либо удалён весь набор), ссылка на чтении возвращается как `null` — отдельного boolean-флага и хранимого списка id нет, поэтому рассинхронизация с реальным набором невозможна. Настройки набора имеют источник `source = medication`, `source_id` = `medication.id` (см. [Напоминания — Backend](../calendar/napominaniya-backend.md), раздел «Источник настроек»), поэтому запись лекарства и набор остаются согласованными в обе стороны:

* название и дозировка лекарства применяются к настройкам набора при каждом изменении (`PATCH /medications/{id}`);
* из календаря можно изменить расписание набора («Изменить все»): оно применяется и к самому лекарству, а тип, значение и заметка настроек из календаря не меняются;
* из календаря можно удалить напоминание, отметить его, удалить весь набор или заменить один приём (новая запись независима от лекарства); лекарство при этом не удаляется.

`frequency_type = 'as_needed'` («по необходимости») описывает лекарство без фиксированного расписания приёма (например, обезболивающее «по мере необходимости»): у него нет `weekdays`/`interval_days`/`times`/`start_date`/`end_date`, оно никогда не участвует в расчёте расписания и никогда не имеет напоминаний — см. «Бизнес-правила».

## Расчёт расписания

Общая для создания, регенерации и ручного «Добавить напоминания» операция: даты и моменты расписания вычисляются единым расчётом настроек напоминаний — виды частоты, перебор дат, `end_date`, местное время `tz`, переход на летнее время, только будущие моменты, пропуск закрытых моментов, потолок 60 (см. [Напоминания — Backend](../calendar/napominaniya-backend.md), раздел «Расчёт расписания»). Дано `frequency_type` (`daily` / `specific_days` / `every_n_days`), `weekdays`, `interval_days`, `times`, `start_date`, `end_date`. Для `frequency_type = 'as_needed'` расчёт не вызывается (у него нет расписания); вида `once` у лекарства нет.

Расписание материализуется настройками напоминания и напоминаниями. Данные настроек: `source = medication`, `source_id` = `medication.id`, `type = medication`, `value = {name: <medication.name>}` (`dose_amount`/`dose_unit` не передаются — дозировка лекарства в Ветпаспорте свободный текст, а не структурированные число+единица, которых требует форма `value.dose_amount`/`value.dose_unit`, см. «Модель значения события и реестр метрик»), `notes = medication.dosage`, расписание — `frequency_type`/`weekdays`/`interval_days`/`start_date`/`end_date` лекарства и времена из `times[i].time`, `tz` из запроса, питомец — питомец лекарства. Для каждой входящей в расписание даты `d`, для каждого элемента `times` (в порядке возрастания времени суток независимо от порядка в массиве) создаётся одно напоминание: `remind_at = d + times[i].time` как местное время часового пояса клиента (query-параметр `tz` запроса, см. «Бизнес-правила»); если у элемента задан `dose_note`, он записывается в заметку напоминания (`reminder.notes`, см. «Напоминания — Backend», раздел «Заметка напоминания») и показывается вместо дозировки лекарства, иначе в календаре показывается дозировка из заметки настроек (доза попадает в заметку, чтобы карточка в календаре была самодостаточной).

Создаются только будущие моменты расписания: прошедшие (в том числе при курсе, начатом задним числом) не материализуются — иначе каждый прошедший приём стал бы напоминанием, требующим отметки. Моменты, для которых у настроек уже есть закрытое напоминание (`closed_at IS NOT NULL`) с тем же `remind_at`, пропускаются — чтобы пересоздание не вернуло приём, который пользователь уже отметил, удалил или заменил.

### Потолок числа генерируемых напоминаний

Одна операция расчёта расписания (создание, регенерация, ручное «Добавить напоминания») не создаёт больше 60 напоминаний одновременно — это ограничивает разброс количества строк, который вносят несколько времён приёма в день (например, 4 приёма в день × 15 дней = 60). Если пересечение `end_date`/паттерна даёт больше будущих дат-времён, чем 60, перебор останавливается на 60-м напоминании, а остаток курса не материализуется — пользователь может создать следующий набор позже: когда набора напоминаний не останется (все напоминания закрыты или набор удалён), действие «Добавить напоминания» снова доступно. Это же ограничение действует и для лекарств без `end_date` («бессрочных») — на них тоже единовременно материализуется не более 60 ближайших напоминаний по паттерну.

## Основной сценарий

**Список.** `GET /pet/{id}/medications` — неудалённые лекарства питомца, отсортированные по ближайшему будущему `next_dose` (см. «Вычисление next_dose» ниже; лекарства с `next_dose = null`, включая все `as_needed`, — в конце), затем — по `created_at` убыв. Элемент — `GetMedicationResponse`: `id`, `pet_id`, `name`, `dosage`, `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date`, `note`, `reminder_plan_id` (id настроек напоминания расписания; `null`, если набора напоминаний нет или его настроек уже нет), `next_dose` (вычисляемые дата+время ближайшего будущего/текущего приёма, `null` — см. ниже), `files_count`. Признак «есть набор напоминаний» — `reminder_plan_id` не `null`. Обязательный query-параметр `tz` — часовой пояс, в котором вычисляется `next_dose`.

**Создание.** `POST /pet/{id}/medications`. Тело: `name` (обязательно, ≤100), `dosage` (обязательно, ≤100), `frequency_type` (обязательно, одно из `daily`/`specific_days`/`every_n_days`/`as_needed`), `weekdays` (массив int 1..7, без повторов, минимум 1 элемент — обязателен, если и только если `frequency_type = specific_days`), `interval_days` (целое 2..365 — обязателен, если и только если `frequency_type = every_n_days`), `times` (массив 1..4 элементов `{time: HH:MM или HH:MM:SS (OpenAPI format: time), dose_note?: ≤100}`, времена без повторов — обязателен, если и только если `frequency_type != as_needed`), `start_date` (`YYYY-MM-DD` — обязателен, если и только если `frequency_type != as_needed`), `end_date` (`YYYY-MM-DD`, опционально, только если `frequency_type != as_needed`; если задан — должен быть `>= start_date`), `note` (опционально, ≤1000), `add_reminders` (boolean, по умолчанию `false`; недопустим/игнорируется при `frequency_type = as_needed`). Обязательный query-параметр `tz` — часовой пояс расписания. Опциональный заголовок `Idempotency-Key` (UUID v4, иначе `400`): ключ хранится в строке записи и уникален на пару `(pet_id, idempotency_key)`; повторный запрос с тем же ключом для того же питомца не создаёт новую запись, а возвращает `201 Created` с `id` ранее созданной — в том числе при одновременных запросах с одним ключом и когда созданная запись уже мягко удалена (удаление не освобождает ключ).

1. Проверка владения питомцем (см. «Бизнес-правила»).
2. Валидация полей, включая согласованность набора полей с `frequency_type` (см. «Бизнес-правила»).
3. Вставка строки `medication`.
4. Если `add_reminders = true` — расчёт расписания (см. выше), вставка строки `reminder_plan` и до 60 строк `reminder`, запись `id` настроек в `reminder_plan_id`. Если расчёт не даёт ни одного будущего момента (например, `end_date` в прошлом) — набор не создаётся, лекарство сохраняется без напоминаний; это не ошибка.
5. `201 Created` с телом `{id}` — идентификатором созданного лекарства.

**Ручное создание набора напоминаний** (кнопка «Добавить напоминания» на карточке). `POST /medications/{id}/reminders`, без тела; обязательный query-параметр `tz` — часовой пояс расписания. Доступно только если `reminder_plan_id` пуст и `frequency_type != as_needed` — иначе `409 Conflict` (набор уже существует) либо `400` (у `as_needed`-лекарства нет расписания). Выполняет расчёт расписания по текущим `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date` лекарства и создаёт настройки и напоминания тем же способом, что шаг 4 создания; если будущих моментов нет — `400` (в отличие от создания лекарства, где это не ошибка: здесь пользователь явно просит создать набор). `200 OK` с обновлённым `GetMedicationResponse` — теми же полями, что у элемента списка (включая `reminder_plan_id` и `files_count`; списка `files` в ответе нет).

**Ручное удаление набора напоминаний** (кнопка «Удалить напоминания» на карточке). `DELETE /medications/{id}/reminders`. Требует, чтобы набор напоминаний был (`reminder_plan_id` не `null`) — иначе `404`. Жёстко удаляет (физическое `DELETE`, не soft-delete) настройки `reminder_plan` вместе со всеми их напоминаниями — незавершёнными и закрытыми — и файлами (см. «Исключение из правила soft-delete» ниже), очищает `reminder_plan_id`. `204 No Content`. Факты приёма, созданные ранее отметкой «выполнено», не затрагиваются.

**Редактирование.** `PATCH /medications/{id}`. Тело — частичное: любое из `name`, `dosage`, `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date`, `note`, плюс `regenerate_reminders` (boolean, по умолчанию `false`, см. ниже); обязательный query-параметр `tz` — часовой пояс расписания для пересоздаваемых напоминаний. `note` очищается пустой строкой `""`; отсутствие поля или `null` — значение не меняется.

1. Если запрос меняет хотя бы одно из «полей расписания» — `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date` (поле присутствует в теле и отличается от текущего значения) **и** набор напоминаний лекарства на момент запроса есть (`reminder_plan_id` не `null`):
   * если `regenerate_reminders = true` (клиент уже показал пользователю диалог подтверждения и получил согласие, см. «Лекарства — Frontend») — сервер применяет к настройкам набора новое расписание так же, как «Изменить все» в «Напоминания — Backend» (эндпоинт C): жёстко удаляет будущие незавершённые напоминания (см. «Исключение из правила soft-delete»), пересчитывает расписание уже по новым значениям полей (с учётом изменений из этого же запроса), создаёт новые напоминания (с дозами по времени, см. «Расчёт расписания», шаг 3) и обновляет расписание настроек; прошедшие незавершённые и закрытые напоминания не затрагиваются, а моменты с закрытыми напоминаниями заново не создаются. Если новое расписание не даёт ни одного будущего момента — `400`;
   * если `regenerate_reminders` отсутствует или `false` — сервер обновляет только переданные поля лекарства и НЕ трогает существующий набор: настройки и напоминания остаются как были, даже если формально перестали соответствовать новому расписанию (осознанно принятое поведение, см. «Бизнес-правила»).
2. Если ни одно из полей расписания не меняется — `regenerate_reminders`, если передан, игнорируется (пересоздавать нечего).
3. Если запрос меняет `frequency_type` на `as_needed` — все прочие поля расписания (`weekdays`, `interval_days`, `times`, `start_date`, `end_date`) должны в этом же запросе обнулиться (переданы как `null`/отсутствовать в теле при уже пустых текущих значениях недопустимо в обратную сторону, см. «Бизнес-правила»); если у лекарства при этом набор напоминаний есть — переход в `as_needed` обязан сопровождаться `regenerate_reminders = true` (иначе `400`: `as_needed` не может сосуществовать с набором напоминаний); в этом случае сервер жёстко удаляет настройки набора вместе со всеми напоминаниями и новых не создаёт.
4. `note` обновляется как передан, без побочных эффектов на набор напоминаний. `name` и `dosage` обновляются как переданы, и, если набор напоминаний есть, в той же транзакции применяются к его настройкам (`value.name`, `notes`); напоминания не пересоздаются, а доза по времени приёма (`dose_note`) остаётся у своих напоминаний.
5. `204 No Content`.

**Удаление лекарства.** `DELETE /medications/{id}` — мягко удаляет запись лекарства (`deleted_at`) и, если набор напоминаний есть, жёстко удаляет его настройки вместе со всеми напоминаниями (та же логика, что «Ручное удаление набора напоминаний» — см. «Исключение из правила soft-delete»: удаление лекарства — тоже путь, которым пользователь может многократно создавать/удалять лекарство с напоминаниями). Факты приёма, созданные ранее отметкой «выполнено», не затрагиваются. `204 No Content`; повторный вызов — `404` («уже удалено»).

## Бизнес-правила и валидация

* Обязательные поля создания: `name`, `dosage`, `frequency_type`; остальные — по правилам согласованности с `frequency_type` ниже.

* **Согласованность полей расписания с `frequency_type`:**
  * `weekdays` обязателен (массив, 1..7 уникальных значений 1..7) тогда и только тогда, когда `frequency_type = specific_days`; в любом другом случае должен отсутствовать/быть `null`.
  * `interval_days` (целое 2..365) обязателен тогда и только тогда, когда `frequency_type = every_n_days`; иначе должен отсутствовать/быть `null`.
  * `times` (массив 1..4 элементов, времена без повторов, каждый `dose_note` ≤100) и `start_date` обязательны тогда и только тогда, когда `frequency_type != as_needed`; при `as_needed` оба должны отсутствовать/быть `null`.
  * `end_date`, если передан, допустим только при `frequency_type != as_needed` и должен быть `>= start_date`.
  * `add_reminders = true` (при создании) и вызов `POST /medications/{id}/reminders` недопустимы при `frequency_type = as_needed`.
  * Нарушение любого из перечисленных правил — `400`.

* **Потолок числа генерируемых напоминаний = 60.** Ограничение защищает от создания чрезмерного количества строк одной операцией — несколько времён приёма в день умножают число дат расписания (см. «Потолок числа генерируемых напоминаний» выше). Курсы длиннее потолка или лекарства без `end_date` материализуют только ближайшие 60 напоминаний одной операцией; продолжение — повторным вызовом после исчерпания набора.

* **Исключение из правила soft-delete.** Общее правило проекта — мягкое удаление (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)). Настройки напоминания и напоминания, созданные по расписанию лекарства, удаляются физически (см. [Напоминания — Backend](../calendar/napominaniya-backend.md), «Бизнес-правила и валидация»), а не мягко — этим флоу в трёх местах: «Ручное удаление набора напоминаний», ветка `regenerate_reminders = true` редактирования (только будущие незавершённые напоминания) и удаление самого лекарства. Причина — многократное включение/выключение признака «добавить напоминания» или повторная регенерация расписания способны быстро накопить в БД большое количество бесполезных строк (это не пользовательские данные о самочувствии питомца, а служебные записи, полностью описываемые самим лекарством); мягкое удаление здесь не даёт никакой пользы, которую даёт для обычных событий. Факты (`event`), созданные отметкой напоминания «выполнено», — обычные события и удаляются мягко без исключений.

* Расписание пересчитывается только явными действиями (создание с `add_reminders=true`, `POST .../reminders`, регенерация с `regenerate_reminders=true`) — простое изменение `name`/`dosage`/`note` никогда не создаёт, не удаляет и не пересчитывает напоминания; `name` и `dosage` при этом обновляют данные настроек существующего набора (название и дозировку в календаре).

* **Часовой пояс расписания.** `GET /pet/{id}/medications`, `POST /pet/{id}/medications`, `PATCH /medications/{id}` и `POST /medications/{id}/reminders` принимают обязательный query-параметр `tz` — имя часового пояса IANA (например, `Europe/Moscow`), значения по умолчанию нет. Даты расписания и `times` трактуются как местное время этого пояса: напоминания создаются на соответствующий момент времени, `next_dose` вычисляется так же. Отсутствующий `tz` и неизвестное имя пояса — `400`.

* Питомец должен принадлежать инициатору и не быть мягко удалён — иначе `404`/`400`.

## Вычисление `next_dose`

`next_dose` в `GetMedicationResponse` — минимальный момент (дата + время) из расписания (см. «Расчёт расписания»), который `>= текущий момент`, вычисленный по текущим `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date` лекарства — независимо от того, создан ли фактический набор напоминаний (`reminder_plan_id`). Даты расписания и `times` — местное время пояса `tz` запроса: «сегодня» определяется по текущему моменту в этом поясе. Время, а не только дата, участвует в сравнении: если сегодняшняя дата входит в расписание, но все времена приёма на сегодня уже прошли, `next_dose` — первый приём ближайшей следующей подходящей даты. `next_dose = null`, если: `frequency_type = as_needed`, либо все моменты расписания раньше текущего (актуально для лекарств с `end_date` в прошлом). Соответствующий блок на карточке не показывается, если `next_dose = null` (см. «Лекарства — Frontend»).

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Не заполнено обязательное поле / дата не `YYYY-MM-DD` / элемент `times[].time` не `HH:MM[:SS]` / нарушено правило согласованности полей расписания с `frequency_type` (см. «Бизнес-правила») / `weekdays` вне 1..7 или с повторами / `interval_days` вне 2..365 / `times` не 1..4 элемента или с повторяющимся временем / `end_date` раньше `start_date` / `add_reminders=true` или `POST .../reminders` при `frequency_type=as_needed` / `POST .../reminders` или `regenerate_reminders=true`, когда расписание не даёт ни одного будущего момента / отсутствует или неизвестный часовой пояс `tz` / `Idempotency-Key` не UUID v4 |
| 401 | Токен отсутствует или недействителен |
| 404 | Питомец/лекарство не найдены, мягко удалены или принадлежат другому пользователю / `DELETE .../reminders`, когда набора напоминаний уже нет |
| 409 | `POST /medications/{id}/reminders`, когда набор напоминаний уже есть (сначала нужно удалить существующий набор) |
| 500 | Внутренняя ошибка БД |

## Хранение состояния и побочные эффекты

Создание/редактирование/удаление лекарства и оба действия с напоминаниями могут дополнительно создавать/жёстко удалять строку `reminder_plan` и до 60 строк `reminder` (см. «Основной сценарий» и «Исключение из правила soft-delete»). Данные питомца не затрагиваются.
