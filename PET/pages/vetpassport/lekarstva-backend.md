## Назначение

Флоу ведёт список лекарств питомца: название, дозировка (базовая, свободный текст), схема приёма (частота + одно или несколько времён приёма в день), дата начала и опциональная дата окончания курса, заметка, до 10 прикреплённых файлов. Опционально по расписанию создаётся набор событий-напоминаний в календаре — не более одного набора на лекарство одновременно. Логика частоты и времени приёма ориентирована на паттерн приложения «Здоровье» (Apple Health, раздел «Лекарства»): частота выбирается из нескольких видов (каждый день / определённые дни недели / через N дней / по необходимости), и на каждый день приёма может приходиться несколько времён приёма с собственной дозой.

## Модель данных

```
CREATE TABLE medication (
  id                uuid PRIMARY KEY,
  pet_id            uuid NOT NULL REFERENCES pet(id),
  name              text NOT NULL,        -- ≤ 100 символов
  dosage            text NOT NULL,        -- ≤ 100 символов, свободный текст ("1 пипетка", "1 таблетка"); базовая доза по умолчанию для всех времён приёма
  frequency_type    text NOT NULL,        -- 'daily' | 'specific_days' | 'every_n_days' | 'as_needed'
  weekdays          jsonb NULL,            -- массив int 1..7 (пн=1 .. вс=7), только при frequency_type = 'specific_days', иначе NULL
  interval_days     integer NULL,          -- 2..365, только при frequency_type = 'every_n_days', иначе NULL
  times             jsonb NULL,            -- [{time: 'HH:mm', dose_note: text|null}], 1..4 элемента; NULL при frequency_type = 'as_needed'
  start_date        date NULL,             -- обязателен при любом frequency_type, кроме 'as_needed'; NULL при 'as_needed'
  end_date          date NULL,             -- NULL = курс без определённой даты окончания ("бессрочно"); NULL всегда при 'as_needed'
  event_ids         jsonb NOT NULL DEFAULT '[]',  -- массив event.id, не более 60 элементов
  note              text NULL,             -- ≤ 1000 символов
  deleted_at        timestamptz NULL,
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now()
);
```

`event_ids` — источник истины по тому, есть ли у лекарства созданные события (`event_ids != '[]'`), а не отдельный boolean-флаг: ровно одно поле, которое нельзя рассинхронизировать с реальным набором событий.

`frequency_type = 'as_needed'` («по необходимости») описывает лекарство без фиксированного расписания приёма (например, обезболивающее «по мере необходимости»): у него нет `weekdays`/`interval_days`/`times`/`start_date`/`end_date`, оно никогда не участвует в расчёте расписания и никогда не имеет событий-напоминаний — см. «Бизнес-правила».

## Расчёт расписания

Общая для создания, регенерации и ручного «Добавить событие» функция: дано `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date`. Функция не вызывается для `frequency_type = 'as_needed'` (у него нет расписания).

1. Перебор календарных дат начиная со `start_date` по возрастанию. Дата `d` входит в расписание, если:
   * `frequency_type = 'daily'` — входит любая дата;
   * `frequency_type = 'specific_days'` — ISO-номер дня недели `d` (пн=1..вс=7) присутствует в `weekdays`;
   * `frequency_type = 'every_n_days'` — `(d - start_date) в днях` кратно `interval_days` (то есть `d = start_date`, `start_date + interval_days`, `start_date + 2 * interval_days`, …).

2. Перебор останавливается, как только выполнено любое из:
   * достигнута `end_date` (дата `d > end_date` в переборе не включается);
   * достигнут потолок в 60 сгенерированных событий (см. «Потолок числа генерируемых событий» ниже) — считая по всем времени-слотам сразу, а не по количеству дат;
   * без `end_date` и без совпадающих дат в пределах 730 дней от `start_date` (только теоретический случай защиты от бесконечного перебора при некорректных входных данных — на валидных `weekdays`/`interval_days` такое недостижимо).

3. Для каждой входящей в расписание даты `d`, для каждого элемента `times` (в порядке следования массива) создаётся одно событие: `type = medication`, `value = {name: <medication.name>}` (`dose_amount`/`dose_unit` не передаются — дозировка лекарства в Ветпаспорте свободный текст, а не структурированные число+единица, которых требует форма `value.dose_amount`/`value.dose_unit`, см. «Модель значения события и реестр метрик»), `notes = <times[i].dose_note либо, если он не задан, medication.dosage>` (доза попадает в заметку события, чтобы карточка события в календаре была самодостаточной), `date = d` + `times[i].time`, привязанное к тому же питомцу.

Даты и времена расписания создаются целиком (включая события в прошлом относительно текущей даты), независимо от того, лежат ли они в прошлом или в будущем, — как и раньше, расписание не фильтруется по «только будущее».

### Потолок числа генерируемых событий

Одна операция расчёта расписания (создание, регенерация, ручное «Добавить событие») не создаёт больше 60 событий одновременно — это ограничивает разброс количества событий, который вносят несколько времён приёма в день (например, 4 приёма в день × 15 дней = 60). Если пересечение `end_date`/паттерна даёт больше дат-времён, чем 60, перебор из шага 2 останавливается на 60-м событии, а остаток курса не материализуется — пользователь может создать следующий набор позже тем же путём, что и раньше при исчерпании старого потолка (`repeat_count = 14`): удалить набор («Удалить события») и заново запросить создание, когда время подойдёт. Это же ограничение действует и для лекарств без `end_date` («бессрочных») — на них тоже единовременно материализуется не более 60 ближайших событий по паттерну.

## Основной сценарий

**Список.** `GET /pet/{id}/medications` — неудалённые лекарства питомца, отсортированные по ближайшему будущему `next_dose` (см. «Вычисление next_dose» ниже; лекарства с `next_dose = null`, включая все `as_needed`, — в конце), затем — по `created_at` убыв. Элемент — `MedicationResponse`: `id`, `name`, `dosage`, `frequency_type`, `weekdays`, `interval_days`, `times`, `next_dose` (вычисляемые дата+время ближайшего будущего/текущего приёма, `null` — см. ниже), `has_events` (`event_ids` не пуст), `files_count`.

**Создание.** `POST /pet/{id}/medications`. Тело: `name` (обязательно, ≤100), `dosage` (обязательно, ≤100), `frequency_type` (обязательно, одно из `daily`/`specific_days`/`every_n_days`/`as_needed`), `weekdays` (массив int 1..7, без повторов, минимум 1 элемент — обязателен, если и только если `frequency_type = specific_days`), `interval_days` (целое 2..365 — обязателен, если и только если `frequency_type = every_n_days`), `times` (массив 1..4 элементов `{time: HH:mm, dose_note?: ≤100}`, времена без повторов — обязателен, если и только если `frequency_type != as_needed`), `start_date` (`YYYY-MM-DD` — обязателен, если и только если `frequency_type != as_needed`), `end_date` (`YYYY-MM-DD`, опционально, только если `frequency_type != as_needed`; если задан — должен быть `>= start_date`), `note` (опционально, ≤1000), `add_event` (boolean, по умолчанию `false`; недопустим/игнорируется при `frequency_type = as_needed`). Опциональный `Idempotency-Key`.

1. Проверка владения питомцем (см. «Бизнес-правила»).
2. Валидация полей, включая согласованность набора полей с `frequency_type` (см. «Бизнес-правила»).
3. Вставка строки `medication`.
4. Если `add_event = true` — расчёт расписания (см. выше), вставка до 60 строк `event`, запись их `id` в `event_ids`.
5. `201 Created` с `MedicationDetailResponse` (все поля строки + `files`).

**Ручное создание набора событий** (кнопка «Добавить событие» на карточке). `POST /medications/{id}/events`, без тела. Доступно только если `event_ids` пуст и `frequency_type != as_needed` — иначе `409 Conflict` (набор уже существует) либо `400` (у `as_needed`-лекарства нет расписания). Выполняет расчёт расписания по текущим `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date` лекарства и создаёт события тем же способом, что шаг 4 создания. `200 OK` с обновлённым `MedicationDetailResponse`.

**Ручное удаление набора событий** (кнопка «Удалить события» на карточке). `DELETE /medications/{id}/events`. Требует, чтобы `event_ids` не был пуст — иначе `404`. Жёстко удаляет (физическое `DELETE`, не soft-delete) все строки `event`, чьи `id` перечислены в `event_ids` (см. «Исключение из правила soft-delete» ниже), очищает `event_ids` до `[]`. `204 No Content`.

**Редактирование.** `PATCH /medications/{id}`. Тело — частичное: любое из `name`, `dosage`, `frequency_type`, `weekdays`, `interval_days`, `times`, `start_date`, `end_date`, `note`, плюс `regenerate_events` (boolean, по умолчанию `false`, см. ниже).

1. Если запрос меняет хотя бы одно из «полей расписания» — `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date` (поле присутствует в теле и отличается от текущего значения) **и** `event_ids` лекарства на момент запроса не пуст:
   * если `regenerate_events = true` (клиент уже показал пользователю диалог подтверждения и получил согласие, см. «Лекарства — Frontend») — сервер жёстко удаляет старые события по прежним `event_ids` (см. «Исключение из правила soft-delete»), затем пересчитывает расписание уже по новым значениям полей (с учётом изменений из этого же запроса) и создаёт новый набор событий, записывая новые `id` в `event_ids`;
   * если `regenerate_events` отсутствует или `false` — сервер обновляет только переданные поля лекарства и НЕ трогает существующие события: `event_ids` и сами события остаются как были, даже если формально перестали соответствовать новому расписанию (осознанно принятое поведение, см. «Бизнес-правила»).
2. Если ни одно из полей расписания не меняется — `regenerate_events`, если передан, игнорируется (пересоздавать нечего).
3. Если запрос меняет `frequency_type` на `as_needed` — все прочие поля расписания (`weekdays`, `interval_days`, `times`, `start_date`, `end_date`) должны в этом же запросе обнулиться (переданы как `null`/отсутствовать в теле при уже пустых текущих значениях недопустимо в обратную сторону, см. «Бизнес-правила»); если у лекарства при этом `event_ids` не пуст — переход в `as_needed` обязан сопровождаться `regenerate_events = true` (иначе `400`: `as_needed` не может сосуществовать с непустым `event_ids`).
4. Остальные поля (`name`, `dosage`, `note`) обновляются как переданы, без побочных эффектов на события.
5. `204 No Content`.

**Удаление лекарства.** `DELETE /medications/{id}` — мягко удаляет запись лекарства (`deleted_at`) и, если `event_ids` не пуст, жёстко удаляет все события по этому списку (та же логика, что «Ручное удаление набора событий» — см. «Исключение из правила soft-delete»: удаление лекарства — тоже путь, которым пользователь может многократно создавать/удалять лекарство с событиями). `204 No Content`; повторный вызов — `404` («уже удалено»).

## Бизнес-правила и валидация

* Обязательные поля создания: `name`, `dosage`, `frequency_type`; остальные — по правилам согласованности с `frequency_type` ниже.

* **Согласованность полей расписания с `frequency_type`:**
  * `weekdays` обязателен (массив, 1..7 уникальных значений 1..7) тогда и только тогда, когда `frequency_type = specific_days`; в любом другом случае должен отсутствовать/быть `null`.
  * `interval_days` (целое 2..365) обязателен тогда и только тогда, когда `frequency_type = every_n_days`; иначе должен отсутствовать/быть `null`.
  * `times` (массив 1..4 элементов, времена без повторов, каждый `dose_note` ≤100) и `start_date` обязательны тогда и только тогда, когда `frequency_type != as_needed`; при `as_needed` оба должны отсутствовать/быть `null`.
  * `end_date`, если передан, допустим только при `frequency_type != as_needed` и должен быть `>= start_date`.
  * `add_event = true` (при создании) и вызов `POST /medications/{id}/events` недопустимы при `frequency_type = as_needed`.
  * Нарушение любого из перечисленных правил — `400`.

* **Потолок числа генерируемых событий = 60.** Ограничение защищает от создания чрезмерного количества событий одной операцией — несколько времён приёма в день умножают число дат расписания (см. «Потолок числа генерируемых событий» выше). Курсы длиннее потолка или лекарства без `end_date` материализуют только ближайшие 60 событий одной операцией; продолжение — повторным вызовом после исчерпания набора.

* **Исключение из правила soft-delete.** Общее правило проекта — мягкое удаление события (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)). Для событий, созданных этим флоу по расписанию лекарства, действует единственное во всём проекте исключение: они удаляются физически (`DELETE FROM event WHERE id = ANY(...)`), а не мягко — в трёх местах: «Ручное удаление набора событий», ветка `regenerate_events = true` редактирования, и удаление самого лекарства. Причина — многократное включение/выключение чекбокса «добавить событие» или повторная регенерация расписания способны быстро накопить в БД большое количество мягко удалённых строк `event`, бесполезных даже для истории (это не пользовательские данные о самочувствии питомца, а служебные напоминания, полностью описываемые самим лекарством); мягкое удаление здесь не даёт никакой пользы, которую даёт для обычных событий (история, отображение в «мягко удалённых» отчётах не предусмотрено нигде в проекте). Любое другое удаление события в проекте (включая события-напоминания вакцинации, см. «Вакцинации — Backend») остаётся мягким без исключений.

* Расписание пересчитывается только явными действиями (создание с `add_event=true`, `POST .../events`, регенерация с `regenerate_events=true`) — простое изменение `name`/`dosage`/`note` никогда не создаёт, не удаляет и не пересчитывает события.

* Питомец должен принадлежать инициатору и не быть мягко удалён — иначе `404`/`400`.

## Вычисление `next_dose`

`next_dose` в `MedicationResponse`/`MedicationDetailResponse` — минимальный момент (дата + время) из расписания (см. «Расчёт расписания»), который `>= текущий момент`, вычисленный по текущим `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date` лекарства — независимо от того, создан ли фактический набор событий (`event_ids`). Время, а не только дата, участвует в сравнении: если сегодняшняя дата входит в расписание, но все времена приёма на сегодня уже прошли, `next_dose` — первый приём ближайшей следующей подходящей даты. `next_dose = null`, если: `frequency_type = as_needed`, либо все моменты расписания раньше текущего (актуально для лекарств с `end_date` в прошлом). Соответствующий блок на карточке не показывается, если `next_dose = null` (см. «Лекарства — Frontend»).

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Не заполнено обязательное поле / дата не `YYYY-MM-DD` / элемент `times` не `HH:mm` / нарушено правило согласованности полей расписания с `frequency_type` (см. «Бизнес-правила») / `weekdays` вне 1..7 или с повторами / `interval_days` вне 2..365 / `times` не 1..4 элемента или с повторяющимся временем / `end_date` раньше `start_date` / `add_event=true` или `POST .../events` при `frequency_type=as_needed` |
| 401 | Токен отсутствует или недействителен |
| 404 | Питомец/лекарство не найдены, мягко удалены или принадлежат другому пользователю / `DELETE .../events`, когда `event_ids` уже пуст |
| 409 | `POST /medications/{id}/events`, когда `event_ids` уже не пуст (сначала нужно удалить существующий набор) |
| 500 | Внутренняя ошибка БД |

## Хранение состояния и побочные эффекты

Создание/редактирование/удаление лекарства и оба действия с событиями могут дополнительно жёстко создавать/жёстко удалять до 60 строк `event` (см. «Основной сценарий» и «Исключение из правила soft-delete»). Данные питомца не затрагиваются.
