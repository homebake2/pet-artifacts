## Назначение

Флоу ведёт список лекарств питомца: название, дозировка, периодичность приёма (в днях), дата начала курса, количество приёмов, заметка, до 10 прикреплённых файлов. Опционально по расписанию (периодичность × количество приёмов, начиная с даты начала) создаётся набор событий-напоминаний в календаре — не более одного набора на лекарство одновременно.

## Модель данных

```
CREATE TABLE medication (
  id                uuid PRIMARY KEY,
  pet_id            uuid NOT NULL REFERENCES pet(id),
  name              text NOT NULL,        -- ≤ 100 символов
  dosage            text NOT NULL,        -- ≤ 100 символов, свободный текст ("1 пипетка", "1 таблетка")
  periodicity_days  integer NOT NULL,     -- 1..365
  start_date        date NOT NULL,
  repeat_count      integer NOT NULL,     -- 1..14, количество приёмов в расписании
  event_time        time NULL,            -- время создаваемых событий; NULL, если события не создавались
  event_ids         jsonb NOT NULL DEFAULT '[]',  -- массив event.id, не более 14 элементов
  note              text NULL,            -- ≤ 1000 символов
  deleted_at        timestamptz NULL,
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now()
);
```

`event_ids` — источник истины по тому, есть ли у лекарства созданные события (`event_ids != '[]'`), а не отдельный boolean-флаг: ровно одно поле, которое нельзя рассинхронизировать с реальным набором событий.

## Расчёт расписания

Общая для создания, регенерации и ручного «Добавить событие» функция: дано `start_date`, `periodicity_days`, `repeat_count`, `event_time`. Даты расписания:

```
date[i] = start_date + i * periodicity_days,  i = 0 .. repeat_count - 1
```

Всего `repeat_count` дат (включая саму `start_date` как дату первого приёма), независимо от того, лежат ли они в прошлом или в будущем относительно текущей даты, — расписание создаётся целиком, а не только на будущее. Каждой дате соответствует одно событие: `type = medication`, `value = {name: <medication.name>}` (`dose_amount`/`dose_unit` не передаются — дозировка лекарства в Ведпаспорте свободный текст, а не структурированные число+единица, которых требует форма `value.dose_amount`/`value.dose_unit`, см. «Модель значения события и реестр метрик»), `notes = <medication.dosage>` (дозировка попадает в заметку события, чтобы карточка события в календаре была самодостаточной), `date = date[i]` + `event_time`, привязанное к тому же питомцу.

`repeat_count` ограничен 14 — это жёсткий потолок на количество событий, создаваемых одной операцией (см. «Бизнес-правила»).

## Основной сценарий

**Список.** `GET /pet/{id}/medications` — неудалённые лекарства питомца, отсортированные по ближайшей будущей дате расписания (см. «Вычисление next_dose» ниже), затем — без будущей даты — по `created_at` убыв. Элемент — `MedicationResponse`: `id`, `name`, `dosage`, `periodicity_days`, `next_dose` (вычисляемая дата ближайшего будущего/сегодняшнего приёма из расписания, `null`, если все даты расписания в прошлом), `has_events` (`event_ids` не пуст), `files_count`.

**Создание.** `POST /pet/{id}/medications`. Тело: `name` (обязательно, ≤100), `dosage` (обязательно, ≤100), `periodicity_days` (обязательно, целое 1..365), `start_date` (обязательно, `YYYY-MM-DD`), `repeat_count` (обязательно, целое 1..14), `note` (опционально, ≤1000), `add_event` (boolean, по умолчанию `false`), `event_time` (`HH:mm`, обязательно, если `add_event = true`). Опциональный `Idempotency-Key`.

1. Проверка владения питомцем (см. «Бизнес-правила»).
2. Валидация полей (см. «Бизнес-правила»).
3. Вставка строки `medication`.
4. Если `add_event = true` — расчёт расписания (см. выше), вставка до 14 строк `event`, запись их `id` в `event_ids`, запись `event_time`.
5. `201 Created` с `MedicationDetailResponse` (все поля строки + `files`).

**Ручное создание набора событий** (кнопка «Добавить событие» на карточке). `POST /medications/{id}/events`. Тело: `event_time` (`HH:mm`, обязательно). Доступно только если `event_ids` пуст — иначе `409 Conflict` (сначала нужно удалить существующий набор, см. ниже). Выполняет расчёт расписания по текущим `start_date`/`periodicity_days`/`repeat_count` лекарства и создаёт события тем же способом, что шаг 4 создания; сохраняет `event_time`. `200 OK` с обновлённым `MedicationDetailResponse`.

**Ручное удаление набора событий** (кнопка «Удалить события» на карточке). `DELETE /medications/{id}/events`. Требует, чтобы `event_ids` не был пуст — иначе `404`. Жёстко удаляет (физическое `DELETE`, не soft-delete) все строки `event`, чьи `id` перечислены в `event_ids` (см. «Исключение из правила soft-delete» ниже), очищает `event_ids` до `[]` и `event_time` до `NULL`. `204 No Content`.

**Редактирование.** `PATCH /medications/{id}`. Тело — частичное: любое из `name`, `dosage`, `periodicity_days`, `start_date`, `repeat_count`, `note`, `event_time`, плюс `regenerate_events` (boolean, по умолчанию `false`, см. ниже).

1. Если запрос меняет хотя бы одно из `periodicity_days`/`start_date`/`repeat_count` (поле присутствует в теле и отличается от текущего значения) **и** `event_ids` лекарства на момент запроса не пуст:
   * если `regenerate_events = true` (клиент уже показал пользователю диалог подтверждения и получил согласие, см. «Лекарства — Frontend») — сервер жёстко удаляет старые события по прежним `event_ids` (см. «Исключение из правила soft-delete»), затем пересчитывает расписание уже по новым значениям полей (с учётом изменений из этого же запроса) и `event_time` (из запроса либо из уже сохранённого значения) и создаёт новый набор событий, записывая новые `id` в `event_ids`;
   * если `regenerate_events` отсутствует или `false` — сервер обновляет только переданные поля лекарства и НЕ трогает существующие события: `event_ids` и сами события остаются как были, даже если формально перестали соответствовать новому расписанию (осознанно принятое поведение, см. «Бизнес-правила»).
2. Если ни одно из `periodicity_days`/`start_date`/`repeat_count` не меняется — `regenerate_events`, если передан, игнорируется (пересоздавать нечего).
3. Остальные поля (`name`, `dosage`, `note`, `event_time` вне контекста регенерации) обновляются как переданы, без побочных эффектов на события.
4. `204 No Content`.

**Удаление лекарства.** `DELETE /medications/{id}` — мягко удаляет запись лекарства (`deleted_at`) и, если `event_ids` не пуст, жёстко удаляет все события по этому списку (та же логика, что «Ручное удаление набора событий» — см. «Исключение из правила soft-delete»: удаление лекарства — тоже путь, которым пользователь может многократно создавать/удалять лекарство с событиями). `204 No Content`; повторный вызов — `404` («уже удалено»).

## Бизнес-правила и валидация

* Обязательные поля создания: `name`, `dosage`, `periodicity_days`, `start_date`, `repeat_count`.

* `periodicity_days` — целое от 1 до 365. `repeat_count` — целое от 1 до 14 (жёсткий потолок, см. ниже).

* **Потолок `repeat_count` = 14.** Ограничение защищает от создания чрезмерного количества событий одной операцией (при периодичности в 1 день это двухнедельный курс — типичная верхняя граница длительности курса лекарств для большинства случаев; более длинные курсы требуют повторного добавления набора событий после его завершения). Значение `repeat_count` вне диапазона 1..14 — `400`.

* **Исключение из правила soft-delete.** Общее правило проекта — мягкое удаление события (см. [Общие требования: Soft-delete](../common/obschie-trebovaniya-soft-delete.md)). Для событий, созданных этим флоу по расписанию лекарства, действует единственное во всём проекте исключение: они удаляются физически (`DELETE FROM event WHERE id = ANY(...)`), а не мягко — в трёх местах: «Ручное удаление набора событий», ветка `regenerate_events = true` редактирования, и удаление самого лекарства. Причина — многократное включение/выключение чекбокса «добавить событие» или повторная регенерация расписания способны быстро накопить в БД большое количество мягко удалённых строк `event`, бесполезных даже для истории (это не пользовательские данные о самочувствии питомца, а служебные напоминания, полностью описываемые самим лекарством); мягкое удаление здесь не даёт никакой пользы, которую даёт для обычных событий (история, отображение в «мягко удалённых» отчётах не предусмотрено нигде в проекте). Любое другое удаление события в проекте (включая события-напоминания вакцинации, см. «Вакцинации — Backend») остаётся мягким без исключений.

* `event_time` обязателен при `add_event = true` (создание), при `POST /medications/{id}/events`, и при регенерации, если ни в текущем запросе, ни ранее сохранённое значение не задано.

* Расписание пересчитывается только явными действиями (создание с `add_event=true`, `POST .../events`, регенерация с `regenerate_events=true`) — простое изменение `name`/`dosage`/`note` никогда не создаёт, не удаляет и не пересчитывает события.

* Питомец должен принадлежать инициатору и не быть мягко удалён — иначе `404`/`400`.

## Вычисление `next_dose`

`next_dose` в `MedicationResponse`/`MedicationDetailResponse` — минимальная дата из расписания (см. «Расчёт расписания»), которая `>= текущая календарная дата`, вычисленная по текущим `start_date`/`periodicity_days`/`repeat_count` лекарства — независимо от того, создан ли фактический набор событий (`event_ids`). Если все даты расписания раньше текущей даты — `next_dose = null`, и соответствующий блок на карточке не показывается (см. «Лекарства — Frontend»).

## Обработка ошибок

| Статус | Условие |
| --- | --- |
| 400 | Не заполнено обязательное поле / дата не `YYYY-MM-DD` / `event_time` не `HH:mm` / `periodicity_days` вне 1..365 / `repeat_count` вне 1..14 / `add_event=true` без `event_time` / регенерация нужна, но `event_time` не определён ни разу |
| 401 | Токен отсутствует или недействителен |
| 404 | Питомец/лекарство не найдены, мягко удалены или принадлежат другому пользователю / `DELETE .../events`, когда `event_ids` уже пуст |
| 409 | `POST /medications/{id}/events`, когда `event_ids` уже не пуст (сначала нужно удалить существующий набор) |
| 500 | Внутренняя ошибка БД |

## Хранение состояния и побочные эффекты

Создание/редактирование/удаление лекарства и оба действия с событиями могут дополнительно жёстко создавать/жёстко удалять до 14 строк `event` (см. «Основной сценарий» и «Исключение из правила soft-delete»). Данные питомца не затрагиваются.
