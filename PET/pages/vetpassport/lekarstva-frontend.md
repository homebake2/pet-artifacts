## Назначение

Таб «Лекарства»: список лекарств питомца, экраны добавления/редактирования, действия «Добавить событие»/«Удалить события» на карточке.

## Основной сценарий

1. Таб открывается запросом списка лекарств — скелетон/пустое состояние по общим правилам.

2. Список показывает лекарства карточками: название, «{dosage} · каждые {periodicity_days} дней», «Следующий приём: {next_dose}» (строка не показывается, если `next_dose = null` — см. «Лекарства — Backend», раздел «Вычисление `next_dose`»), иконки «редактировать»/«удалить», и одну из двух кнопок в зависимости от `has_events`: **«Добавить событие»** (если `has_events = false`) или **«Удалить события»** (если `has_events = true`).

3. Форма добавления/редактирования (одна форма на оба режима): Название лекарства (обязательное, ≤100), Дозировка (обязательное, ≤100, например «1 пипетка»), Периодичность (дней) (обязательное целое, 1–365), Дата начала (обязательная), **Сколько раз принять** (обязательное целое, 1–14 — новое поле; вместе с периодичностью и датой начала определяет, на какие даты и в каком количестве будут созданы события, см. «Лекарства — Backend», раздел «Расчёт расписания»), чекбокс «Добавить событие» (заменяет прежнюю ссылку «Добавить в календарь»), при отметке чекбокса — поле «Время события» (`HH:mm`, обязательное, по умолчанию `09:00`), Заметка (опционально, ≤1000, multiline), блок прикрепления файлов (до 10).

4. При редактировании форма предзаполняется текущими значениями; чекбокс «Добавить событие» изначально отмечен, если `has_events = true` (т.е. `event_ids` не пуст).

## Действия с событиями на карточке

* **«Добавить событие»** (видна только при `has_events = false`) — сразу, без открытия формы, вызывает `POST /medications/{id}/events` с текущим `event_time` лекарства, если он уже был задан ранее, иначе перед вызовом запрашивает у пользователя время события тем же полем «Время события», что и в форме (компактный диалог с одним полем). Кнопка блокируется и показывает индикатор загрузки на время запроса (см. «Общие требования: UI-паттерны запросов»); после успеха список обновляется, кнопка сменяется на «Удалить события».

* **«Удалить события»** (видна только при `has_events = true`) — показывает диалог подтверждения («события будут удалены безвозвратно — продолжить?», см. «Лекарства — Backend», раздел «Исключение из правила soft-delete» — удаление здесь необратимо, в отличие от остальных удалений в приложении); при подтверждении вызывает `DELETE /medications/{id}/events`. После успеха кнопка сменяется на «Добавить событие».

## Пересоздание событий при редактировании расписания

Если на форме редактирования лекарства, у которого `has_events = true` на момент открытия формы, изменено хотя бы одно из полей «Периодичность (дней)», «Дата начала», «Сколько раз принять» — при нажатии «Сохранить» система показывает диалог подтверждения ДО отправки запроса: «Изменения расписания требуют пересоздания событий. Пересоздать?» с вариантами «Пересоздать» / «Не пересоздавать» (без третьего варианта «Отмена» — сохранение формы происходит в любом случае, разница только в судьбе событий, см. ниже).

* **«Пересоздать»** — форма отправляет `PATCH /medications/{id}` с `regenerate_events: true` и изменёнными полями; сервер жёстко удаляет старые события и создаёт новые по обновлённому расписанию (см. «Лекарства — Backend»).

* **«Не пересоздавать»** — форма отправляет тот же `PATCH /medications/{id}` без `regenerate_events` (либо `false`); изменённые поля лекарства сохраняются, существующие события НЕ удаляются и НЕ пересоздаются — они остаются как есть, даже если больше не соответствуют новому расписанию. Это осознанно принятое расхождение, а не ошибка синхронизации: пользователь явно выбрал не трогать события.

Если у лекарства на момент открытия формы `has_events = false`, либо ни одно из трёх полей расписания не было изменено, диалог не показывается — сохранение выполняется обычным `PATCH /medications/{id}` без вопроса.

Включение чекбокса «Добавить событие» на форме, если он был выключен (независимо от того, менялись ли поля расписания), — это обычное создание набора событий, а не регенерация: диалог подтверждения не показывается, `PATCH` уходит с `add_event`-эквивалентными изменениями (либо, если проще для реализации, форма в этом случае вызывает тот же путь, что кнопка «Добавить событие» на карточке, после сохранения остальных полей).

## Бизнес-правила и валидация

* Обязательные поля: «Название лекарства», «Дозировка», «Периодичность (дней)», «Дата начала», «Сколько раз принять».

* «Периодичность (дней)» — целое от 1 до 365. «Сколько раз принять» — целое от 1 до 14 (форма не позволяет ввести больше — см. «Лекарства — Backend», потолок `repeat_count`).

* «Время события» обязательно, если отмечен чекбокс «Добавить событие».

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле / «Сколько раз принять» вне 1–14 | Форма не отправляется, сообщение под полем |
| Ошибка сервера при сохранении/действиях с событиями | Snackbar/alert, форма/карточка не меняют состояние, повторная попытка возможна |
| Лекарство уже удалено на другом устройстве | Тихо убрать из списка / «уже удалено» |
| `POST /medications/{id}/events`, когда события уже существуют (409, гонка между устройствами) | Snackbar с сообщением «события уже добавлены», кнопка на карточке приводится в соответствие с `has_events` при следующем обновлении списка |
| `DELETE /medications/{id}/events`, когда событий уже нет (404, гонка между устройствами) | Трактуется как «уже удалено» — тихо, без error-тоста, кнопка приводится в соответствие с `has_events` |

## Хранение состояния и побочные эффекты

После создания/редактирования/удаления лекарства или любого из действий с событиями — инвалидация кэша списка лекарств питомца И кэша календаря/списка событий питомца (созданные/удалённые события-напоминания должны сразу появиться/исчезнуть там же).
