## Назначение

Таб «Лекарства»: список лекарств питомца, экраны добавления/редактирования, действия «Добавить событие»/«Удалить события» на карточке. Выбор частоты и времени приёма построен по образцу раздела «Лекарства» приложения «Здоровье» (Apple Health): частота — один из нескольких видов (каждый день / определённые дни недели / через N дней / по необходимости), и на каждый день приёма может приходиться несколько времён со своей дозой.

## Основной сценарий

1. Таб открывается запросом списка лекарств — скелетон/пустое состояние по общим правилам.

2. Список показывает лекарства карточками: название, «{dosage} · {человекочитаемое описание частоты}» (см. «Человекочитаемое описание частоты» ниже), «Следующий приём: {next_dose}» (дата и время; строка не показывается, если `next_dose = null` — лекарства «по необходимости» или курс с датой окончания в прошлом, см. «Лекарства — Backend», раздел «Вычисление `next_dose`»), иконки «редактировать»/«удалить», и одну из двух кнопок в зависимости от `has_events`: **«Добавить событие»** (если `has_events = false` и `frequency_type != as_needed`) или **«Удалить события»** (если `has_events = true`). У лекарств «по необходимости» (`frequency_type = as_needed`) кнопка действий с событиями не показывается вовсе — у них нет расписания.

3. Форма добавления/редактирования (одна форма на оба режима):

   * Название лекарства (обязательное, ≤100).
   * Дозировка (обязательное, ≤100, например «1 пипетка») — базовая доза, используется по умолчанию для всех времён приёма, если для конкретного времени не задана своя.
   * **Частота приёма** (обязательный выбор одного из четырёх вариантов): «Каждый день», «Определённые дни недели», «Через каждые N дней», «По необходимости».
     * «Определённые дни недели» — показывает выбор дней недели (Пн–Вс, множественный выбор, минимум один день отмечен).
     * «Через каждые N дней» — показывает поле «Интервал (дней)» (целое, 2–365).
     * «По необходимости» — скрывает все дальнейшие поля расписания (дату начала/окончания, времена приёма, чекбокс «Добавить событие»): у такого лекарства нет расписания и не может быть событий-напоминаний.
   * Дата начала (обязательна, если частота ≠ «По необходимости»).
   * Дата окончания — переключатель «Без даты окончания» (по умолчанию включён) / «Дата окончания» с полем даты, которая должна быть не раньше даты начала. Показывается только при частоте ≠ «По необходимости».
   * **Времена приёма** (только при частоте ≠ «По необходимости») — список из 1–4 строк, каждая: время (`HH:mm`, обязательно, без повторов в списке), необязательное поле «Доза для этого времени» (≤100; если оставлено пустым — используется общая «Дозировка»). Кнопка «Добавить время» (до 4 строк), у каждой строки — удаление (не даёт остаться меньше одной строки).
   * Чекбокс «Добавить событие» (только при частоте ≠ «По необходимости») — при отметке создаётся набор событий-напоминаний в календаре по указанной схеме приёма; отдельного поля времени события не требуется — используются времена из «Времён приёма».
   * Заметка (опционально, ≤1000, multiline), блок прикрепления файлов (до 10).

4. При редактировании форма предзаполняется текущими значениями; чекбокс «Добавить событие» изначально отмечен, если `has_events = true` (т.е. `event_ids` не пуст).

## Человекочитаемое описание частоты

На карточке и в других местах, где нужно кратко показать схему приёма, частота переводится в текст по `frequency_type`:

| `frequency_type` | Текст |
| --- | --- |
| `daily` | «Каждый день, {times[0].time}» (и далее через запятую остальные времена, если их больше одного) |
| `specific_days` | Сокращённые названия дней через запятую («Пн, Ср, Пт»), затем времена приёма через запятую |
| `every_n_days` | «Каждые {interval_days} дн., {времена приёма через запятую}» |
| `as_needed` | «По необходимости» |

## Действия с событиями на карточке

* **«Добавить событие»** (видна только при `has_events = false` и `frequency_type != as_needed`) — сразу, без открытия формы, вызывает `POST /medications/{id}/events` (расписание пересчитывается сервером по уже сохранённым `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date`, отдельного запроса времени у пользователя не требуется). Кнопка блокируется и показывает индикатор загрузки на время запроса (см. «Общие требования: UI-паттерны запросов»); после успеха список обновляется, кнопка сменяется на «Удалить события».

* **«Удалить события»** (видна только при `has_events = true`) — показывает диалог подтверждения («события будут удалены безвозвратно — продолжить?», см. «Лекарства — Backend», раздел «Исключение из правила soft-delete» — удаление здесь необратимо, в отличие от остальных удалений в приложении); при подтверждении вызывает `DELETE /medications/{id}/events`. После успеха кнопка сменяется на «Добавить событие».

## Пересоздание событий при редактировании расписания

Если на форме редактирования лекарства, у которого `has_events = true` на момент открытия формы, изменено хотя бы одно из полей расписания — «Частота приёма» (включая набор дней недели или интервал), «Времена приёма», «Дата начала», «Дата окончания» — при нажатии «Сохранить» система показывает диалог подтверждения ДО отправки запроса: «Изменения расписания требуют пересоздания событий. Пересоздать?» с вариантами «Пересоздать» / «Не пересоздавать» (без третьего варианта «Отмена» — сохранение формы происходит в любом случае, разница только в судьбе событий, см. ниже). Переключение частоты на «По необходимости» у лекарства с `has_events = true` всегда трактуется как изменение расписания и всегда требует «Пересоздать» (события при этом просто удаляются, новых не создаётся, — вариант «Не пересоздавать» здесь не предлагается, так как у `as_needed` не может быть событий).

* **«Пересоздать»** — форма отправляет `PATCH /medications/{id}` с `regenerate_events: true` и изменёнными полями; сервер жёстко удаляет старые события и создаёт новые по обновлённому расписанию (см. «Лекарства — Backend»).

* **«Не пересоздавать»** — форма отправляет тот же `PATCH /medications/{id}` без `regenerate_events` (либо `false`); изменённые поля лекарства сохраняются, существующие события НЕ удаляются и НЕ пересоздаются — они остаются как есть, даже если больше не соответствуют новому расписанию. Это осознанно принятое расхождение, а не ошибка синхронизации: пользователь явно выбрал не трогать события.

Если у лекарства на момент открытия формы `has_events = false`, либо ни одно из полей расписания не было изменено, диалог не показывается — сохранение выполняется обычным `PATCH /medications/{id}` без вопроса.

Включение чекбокса «Добавить событие» на форме, если он был выключен (независимо от того, менялись ли поля расписания), — это обычное создание набора событий, а не регенерация: диалог подтверждения не показывается, `PATCH` уходит с `add_event`-эквивалентными изменениями (либо, если проще для реализации, форма в этом случае вызывает тот же путь, что кнопка «Добавить событие» на карточке, после сохранения остальных полей).

## Бизнес-правила и валидация

* Обязательные поля: «Название лекарства», «Дозировка», «Частота приёма»; «Дата начала» и «Времена приёма» — обязательны, если частота ≠ «По необходимости».

* «Дни недели» — минимум один выбранный день, только при частоте «Определённые дни недели». «Интервал (дней)» — целое от 2 до 365, только при частоте «Через каждые N дней».

* «Времена приёма» — от 1 до 4 строк, каждое время `HH:mm`, без повторов; форма не позволяет добавить 5-ю строку или удалить последнюю оставшуюся.

* «Дата окончания», если задана, не может быть раньше «Даты начала».

* «Время события» отдельным полем на форме больше нет — событие использует времена из «Времён приёма».

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле / нарушено согласование полей расписания с частотой / «Дата окончания» раньше «Даты начала» | Форма не отправляется, сообщение под полем |
| Ошибка сервера при сохранении/действиях с событиями | Snackbar/alert, форма/карточка не меняют состояние, повторная попытка возможна |
| Лекарство уже удалено на другом устройстве | Тихо убрать из списка / «уже удалено» |
| `POST /medications/{id}/events`, когда события уже существуют (409, гонка между устройствами) | Snackbar с сообщением «события уже добавлены», кнопка на карточке приводится в соответствие с `has_events` при следующем обновлении списка |
| `DELETE /medications/{id}/events`, когда событий уже нет (404, гонка между устройствами) | Трактуется как «уже удалено» — тихо, без error-тоста, кнопка приводится в соответствие с `has_events` |

## Хранение состояния и побочные эффекты

После создания/редактирования/удаления лекарства или любого из действий с событиями — инвалидация кэша списка лекарств питомца И кэша календаря/списка событий питомца (созданные/удалённые события-напоминания должны сразу появиться/исчезнуть там же).
