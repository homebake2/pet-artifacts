## Назначение

Таб «Лекарства»: список лекарств питомца, экраны добавления/редактирования, действия «Добавить событие»/«Удалить события» над лекарством. Выбор частоты и времени приёма построен по образцу раздела «Лекарства» приложения «Здоровье» (Apple Health): частота — один из нескольких видов (каждый день / определённые дни недели / через N дней / по необходимости), и на каждый день приёма может приходиться несколько времён со своей дозой.

## Основной сценарий

1. Таб открывается запросом списка лекарств — скелетон/пустое состояние по общим правилам.

2. Список показывает лекарства карточками: название, «{dosage} · {человекочитаемое описание частоты}» (см. «Человекочитаемое описание частоты» ниже), «Следующий приём: {next_dose}» (дата и время; строка не показывается, если `next_dose = null` — лекарства «по необходимости» или курс с датой окончания в прошлом, см. «Лекарства — Backend», раздел «Вычисление `next_dose`»). Для каждого лекарства имеется возможность открыть форму редактирования, удалить его и — в зависимости от наличия набора событий — одно из двух действий: **«Добавить событие»** (набора событий нет и `frequency_type != as_needed`) или **«Удалить события»** (набор событий есть). Набор событий есть, если массив `event_ids` в элементе списка (`GetMedicationResponse`) не пуст. У лекарств «по необходимости» (`frequency_type = as_needed`) действия с событиями недоступны — у них нет расписания.

3. Форма добавления/редактирования (одна форма на оба режима):

   * Название лекарства (обязательное, ≤100).
   * Дозировка (обязательное, ≤100, например «1 пипетка») — базовая доза, используется по умолчанию для всех времён приёма, если для конкретного времени не задана своя.
   * **Частота приёма** (обязательный выбор одного из четырёх вариантов): «Каждый день», «Определённые дни недели», «Через каждые N дней», «По необходимости».
     * «Определённые дни недели» — показывает выбор дней недели (Пн–Вс, множественный выбор, минимум один день отмечен).
     * «Через каждые N дней» — показывает поле «Интервал (дней)» (целое, 2–365).
     * «По необходимости» — скрывает все дальнейшие поля расписания (дату начала/окончания, времена приёма, признак «Добавить событие»): у такого лекарства нет расписания и не может быть событий-напоминаний.
   * Дата начала (обязательна, если частота ≠ «По необходимости»).
   * Дата окончания — вариант «Без даты окончания» (по умолчанию) либо заданная дата, которая должна быть не раньше даты начала. Показывается только при частоте ≠ «По необходимости».
   * **Времена приёма** (только при частоте ≠ «По необходимости») — список из 1–4 строк, каждая: время (клиент отправляет `HH:mm`; сервер принимает `HH:MM` и `HH:MM:SS`, обязательно, без повторов в списке), необязательное поле «Доза для этого времени» (≤100; если оставлено пустым — используется общая «Дозировка»). Имеется возможность добавить время приёма (до 4 строк) и удалить любую строку (нельзя оставить меньше одной строки).
   * Признак «Добавить событие» (только при частоте ≠ «По необходимости») — при включении создаётся набор событий-напоминаний в календаре по указанной схеме приёма; отдельного поля времени события не требуется — используются времена из «Времён приёма».
   * Заметка (опционально, ≤1000, multiline), блок прикрепления файлов (до 10).

4. При редактировании форма предзаполняется текущими значениями; признак «Добавить событие» изначально включён, если набор событий есть (`event_ids` не пуст). Блок файлов показывает уже прикреплённые файлы лекарства; файлы, добавленные при редактировании, сохраняются за этим лекарством.

5. Создание/редактирование/удаление лекарства выполняется оптимистично — форма закрывается сразу после клиентской валидации, не дожидаясь ответа сервера; удаление — с окном отмены (см. «Общие требования: Оптимистичные обновления (dataSource=network)»). Пока созданная запись не подтверждена сервером (временная карточка с индикацией «синхронизируется»), она доступна только для чтения: открыть, отредактировать, удалить её и выполнить действия «Добавить событие»/«Удалить события» нельзя (см. там же, раздел «Визуальная индикация фоновой синхронизации»).

## Человекочитаемое описание частоты

На карточке и в других местах, где нужно кратко показать схему приёма, частота переводится в текст по `frequency_type`:

| `frequency_type` | Текст |
| --- | --- |
| `daily` | «Каждый день, {times[0].time}» (и далее через запятую остальные времена, если их больше одного) |
| `specific_days` | Сокращённые названия дней через запятую («Пн, Ср, Пт»), затем времена приёма через запятую |
| `every_n_days` | «Каждые {interval_days} дн., {времена приёма через запятую}» |
| `as_needed` | «По необходимости» |

## Действия с событиями

* **«Добавить событие»** (доступно, только если набор событий отсутствует — `event_ids` пуст — и `frequency_type != as_needed`) — сразу, без открытия формы, вызывает `POST /medications/{id}/events` (расписание пересчитывается сервером по уже сохранённым `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date`, отдельного запроса времени у пользователя не требуется). Действие блокируется и индицирует загрузку на время запроса (см. «Общие требования: UI-паттерны запросов»). Ответ — `200 OK` с `GetMedicationResponse` (те же поля, что у элемента списка, включая `event_ids`, без списка `files`); после успеха список обновляется, и вместо этого действия становится доступно «Удалить события».

* **«Удалить события»** (доступно, только если набор событий есть — `event_ids` не пуст) — показывает диалог подтверждения («события будут удалены безвозвратно — продолжить?», см. «Лекарства — Backend», раздел «Исключение из правила soft-delete» — удаление здесь необратимо, в отличие от остальных удалений в приложении); при подтверждении вызывает `DELETE /medications/{id}/events`. После успеха вместо этого действия становится доступно «Добавить событие».

## Пересоздание событий при редактировании расписания

Если на форме редактирования лекарства, у которого на момент открытия формы набор событий есть (`event_ids` не пуст), признак «Добавить событие» остаётся включённым и изменено хотя бы одно из полей расписания — «Частота приёма» (включая набор дней недели или интервал), «Времена приёма», «Дата начала», «Дата окончания» — при сохранении система показывает диалог подтверждения ДО отправки запроса: «Изменения расписания требуют пересоздания событий. Пересоздать?» с вариантами «Пересоздать» / «Не пересоздавать» (без третьего варианта «Отмена» — сохранение формы происходит в любом случае, разница только в судьбе событий, см. ниже). Переключение частоты на «По необходимости» у лекарства с набором событий всегда трактуется как изменение расписания и всегда требует «Пересоздать» (события при этом просто удаляются, новых не создаётся, — вариант «Не пересоздавать» здесь не предлагается, так как у `as_needed` не может быть событий).

* **«Пересоздать»** — форма отправляет `PATCH /medications/{id}` с `regenerate_events: true` и изменёнными полями; сервер жёстко удаляет старые события и создаёт новые по обновлённому расписанию (см. «Лекарства — Backend»).

* **«Не пересоздавать»** — форма отправляет тот же `PATCH /medications/{id}` без `regenerate_events` (либо `false`); изменённые поля лекарства сохраняются, существующие события НЕ удаляются и НЕ пересоздаются — они остаются как есть, даже если больше не соответствуют новому расписанию. Это осознанно принятое расхождение, а не ошибка синхронизации: пользователь явно выбрал не трогать события.

Если у лекарства на момент открытия формы набора событий нет, либо ни одно из полей расписания не было изменено, диалог не показывается — сохранение выполняется обычным `PATCH /medications/{id}` без вопроса.

Включение признака «Добавить событие» на форме, если он был выключен (независимо от того, менялись ли поля расписания), — это обычное создание набора событий, а не регенерация: диалог подтверждения не показывается, `PATCH` уходит с `add_event`-эквивалентными изменениями (либо, если проще для реализации, форма в этом случае вызывает тот же путь, что действие «Добавить событие», после сохранения остальных полей).

Отключение признака «Добавить событие» на форме лекарства, у которого набор событий есть (при частоте ≠ «По необходимости»), — это удаление набора событий, а не регенерация. При сохранении показывается тот же диалог подтверждения, что у действия «Удалить события» («События будут удалены безвозвратно — продолжить?», варианты «Отмена» / «Удалить»); диалог «Пересоздать?» при этом не показывается, даже если поля расписания менялись. «Отмена» оставляет форму открытой и ничего не сохраняет. «Удалить» сохраняет поля лекарства запросом `PATCH /medications/{id}` без `regenerate_events` и затем вызывает `DELETE /medications/{id}/events`; оба запроса — одна мутация очереди фоновых повторов (`PATCH` всегда раньше `DELETE`), `404` от `DELETE` (событий уже нет) считается успехом. Оптимистично сразу становится доступно действие «Добавить событие».

## Бизнес-правила и валидация

* Обязательные поля: «Название лекарства», «Дозировка», «Частота приёма»; «Дата начала» и «Времена приёма» — обязательны, если частота ≠ «По необходимости».

* «Дни недели» — минимум один выбранный день, только при частоте «Определённые дни недели». «Интервал (дней)» — целое от 2 до 365, только при частоте «Через каждые N дней».

* «Времена приёма» — от 1 до 4 строк, каждое время в формате `HH:mm` (сервер принимает `HH:MM` и `HH:MM:SS`), без повторов; форма не позволяет добавить 5-ю строку или удалить последнюю оставшуюся.

* «Дата окончания», если задана, не может быть раньше «Даты начала».

* «Время события» отдельным полем на форме больше нет — событие использует времена из «Времён приёма».

* Запрос списка лекарств, создание, редактирование и «Добавить событие» передают query-параметр `tz` — часовой пояс устройства: сервер строит события приёма и вычисляет `next_dose`, трактуя даты расписания и времена приёма как местное время этого пояса (см. «Лекарства — Backend»), — так же, как это делает режим `dataSource=local`.

* При редактировании очищенная «Заметка» передаётся в `PATCH /medications/{id}` пустой строкой `""` — так сервер очищает значение (см. «Лекарства — Backend»).

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле / нарушено согласование полей расписания с частотой / «Дата окончания» раньше «Даты начала» | Форма не отправляется, сообщение под полем |
| Транзиентная ошибка сервера при создании/редактировании лекарства (нет сети/таймаут/5xx) | Оптимистичное изменение остаётся применённым, запрос уходит в очередь фоновых повторов, карточка показывает индикацию «синхронизируется» (см. «Общие требования: Оптимистичные обновления», разделы «Классификация ошибок мутации», «Очередь фоновых мутаций и повторные попытки») |
| Постоянная ошибка сервера при создании/редактировании лекарства (400/403/409) | Оптимистичное изменение откатывается, пользователю показывается сообщение об ошибке; введённые данные для повторной отправки не сохраняются (см. там же, «Обработка ошибок и откат») |
| Отложенный `DELETE` лекарства не доставлен — транзиентная ошибка | Запрос уходит в очередь фоновых повторов, лекарство остаётся удалённым из списка без отката (см. там же, «Оптимистичное удаление с окном отмены (Undo)») |
| Отложенный `DELETE` лекарства завершился постоянной ошибкой / повторы исчерпаны | Лекарство восстанавливается в списке, пользователю показывается сообщение об ошибке с возможностью повторить удаление (см. там же) |
| Ошибка сервера при действиях с событиями («Добавить событие»/«Удалить события») | Пользователю показывается сообщение об ошибке, состояние лекарства не меняется, повторная попытка возможна — эти действия вне охвата правила об оптимистичных обновлениях (см. «Общие требования: Оптимистичные обновления», раздел «Охват») |
| Лекарство уже удалено на другом устройстве | Тихо убрать из списка / «уже удалено» |
| `POST /medications/{id}/events`, когда события уже существуют (409, гонка между устройствами) | Сообщение «события уже добавлены»; доступные действия с событиями приводятся в соответствие с `event_ids` при следующем обновлении списка |
| `DELETE /medications/{id}/events`, когда событий уже нет (404, гонка между устройствами) | Трактуется как «уже удалено» — тихо, без сообщения об ошибке; доступные действия с событиями приводятся в соответствие с `event_ids` |

## Хранение состояния и побочные эффекты

После создания/редактирования/удаления лекарства или любого из действий с событиями — инвалидация кэша списка лекарств питомца И кэша календаря/списка событий питомца (созданные/удалённые события-напоминания должны сразу появиться/исчезнуть там же). Кэш списка лекарств патчится синхронно и оптимистично при создании/редактировании/удалении лекарства; кэш календаря/списка событий обновляется фоновым refetch (см. «Общие требования: Оптимистичные обновления (dataSource=network)»).
