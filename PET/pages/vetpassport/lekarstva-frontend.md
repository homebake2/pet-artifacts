## Назначение

Таб «Лекарства»: список лекарств питомца, экраны добавления/редактирования, действия «Добавить напоминания»/«Удалить напоминания» над лекарством. Выбор частоты и времени приёма построен по образцу раздела «Лекарства» приложения «Здоровье» (Apple Health): частота — один из нескольких видов (каждый день / определённые дни недели / через N дней / по необходимости), и на каждый день приёма может приходиться несколько времён со своей дозой.

## Основной сценарий

1. Таб открывается запросом списка лекарств — скелетон/пустое состояние по общим правилам.

2. Список показывает лекарства карточками: название, «{dosage} · {человекочитаемое описание частоты}» (см. «Человекочитаемое описание частоты» ниже), «Следующий приём: {next_dose}» (дата и время; строка не показывается, если `next_dose = null` — лекарства «по необходимости» или курс с датой окончания в прошлом, см. «Лекарства — Backend», раздел «Вычисление `next_dose`»). Для каждого лекарства имеется возможность открыть форму редактирования, удалить его и — в зависимости от наличия набора событий — одно из двух действий: **«Добавить напоминания»** (набора напоминаний нет и `frequency_type != as_needed`) или **«Удалить напоминания»** (набор напоминаний есть). Набор напоминаний есть, если `reminder_plan_id` в элементе списка (`GetMedicationResponse`) не `null`. У лекарств «по необходимости» (`frequency_type = as_needed`) действия с напоминаниями недоступны — у них нет расписания.

3. Форма добавления/редактирования (одна форма на оба режима):

   * Название лекарства (обязательное, ≤100).
   * Дозировка (обязательное, ≤100, например «1 пипетка») — базовая доза, используется по умолчанию для всех времён приёма, если для конкретного времени не задана своя.
   * **Частота приёма** (обязательный выбор одного из четырёх вариантов): «Каждый день», «Определённые дни недели», «Через каждые N дней», «По необходимости».
     * «Определённые дни недели» — показывает выбор дней недели (Пн–Вс, множественный выбор, минимум один день отмечен).
     * «Через каждые N дней» — показывает поле «Интервал (дней)» (целое, 2–365).
     * «По необходимости» — скрывает все дальнейшие поля расписания (дату начала/окончания, времена приёма, признак «Добавить напоминания»): у такого лекарства нет расписания и не может быть напоминаний.
   * Дата начала (обязательна, если частота ≠ «По необходимости»).
   * Дата окончания — вариант «Без даты окончания» (по умолчанию) либо заданная дата, которая должна быть не раньше даты начала. Показывается только при частоте ≠ «По необходимости».
   * **Времена приёма** (только при частоте ≠ «По необходимости») — список из 1–4 строк, каждая: время (клиент отправляет `HH:mm`; сервер принимает `HH:MM` и `HH:MM:SS`, обязательно, без повторов в списке), необязательное поле «Доза для этого времени» (≤100; если оставлено пустым — используется общая «Дозировка»). Имеется возможность добавить время приёма (до 4 строк) и удалить любую строку (нельзя оставить меньше одной строки).
   * Признак «Добавить напоминания» (только при частоте ≠ «По необходимости») — при включении создаётся набор напоминаний в календаре по указанной схеме приёма (только будущие приёмы, не более 60 за раз — см. «Лекарства — Backend»); отдельного поля времени не требуется — используются времена из «Времён приёма». Если в выбранном расписании нет будущих приёмов, признак при сохранении не создаёт набор (лекарство сохраняется без напоминаний).
   * Заметка (опционально, ≤1000, multiline), блок прикрепления файлов (до 10).

4. При редактировании форма предзаполняется текущими значениями; признак «Добавить напоминания» изначально включён, если набор напоминаний есть (`reminder_plan_id` не `null`). Блок файлов показывает уже прикреплённые файлы лекарства; файлы, добавленные при редактировании, сохраняются за этим лекарством.

5. Создание/редактирование/удаление лекарства выполняется оптимистично — форма закрывается сразу после клиентской валидации, не дожидаясь ответа сервера; удаление — с окном отмены (см. «Общие требования: Оптимистичные обновления (dataSource=network)»). Пока созданная запись не подтверждена сервером (временная карточка с индикацией «синхронизируется»), она доступна только для чтения: открыть, отредактировать, удалить её и выполнить действия «Добавить напоминания»/«Удалить напоминания» нельзя (см. там же, раздел «Визуальная индикация фоновой синхронизации»).

## Человекочитаемое описание частоты

На карточке и в других местах, где нужно кратко показать схему приёма, частота переводится в текст по `frequency_type`:

| `frequency_type` | Текст |
| --- | --- |
| `daily` | «Каждый день, {times[0].time}» (и далее через запятую остальные времена, если их больше одного) |
| `specific_days` | Сокращённые названия дней через запятую («Пн, Ср, Пт»), затем времена приёма через запятую |
| `every_n_days` | «Каждые {interval_days} дн., {времена приёма через запятую}» |
| `as_needed` | «По необходимости» |

## Действия с напоминаниями

* **«Добавить напоминания»** (доступно, только если набор напоминаний отсутствует — `reminder_plan_id` равен `null` — и `frequency_type != as_needed`) — сразу, без открытия формы, вызывает `POST /medications/{id}/reminders` (расписание пересчитывается сервером по уже сохранённым `frequency_type`/`weekdays`/`interval_days`/`times`/`start_date`/`end_date`, отдельного запроса времени у пользователя не требуется; создаются только будущие приёмы, не более 60). Действие блокируется и индицирует загрузку на время запроса (см. «Общие требования: UI-паттерны запросов»). Ответ — `200 OK` с `GetMedicationResponse` (те же поля, что у элемента списка, включая `reminder_plan_id`, без списка `files`); после успеха список обновляется, и вместо этого действия становится доступно «Удалить напоминания». Если в расписании нет будущих приёмов (`400`), показывается сообщение «В расписании нет будущих приёмов».

* **«Удалить напоминания»** (доступно, только если набор напоминаний есть — `reminder_plan_id` не `null`) — показывает диалог подтверждения («напоминания будут удалены безвозвратно — продолжить?», см. «Лекарства — Backend», раздел «Исключение из правила soft-delete» — удаление здесь необратимо, в отличие от остальных удалений в приложении); при подтверждении вызывает `DELETE /medications/{id}/reminders`. После успеха вместо этого действия становится доступно «Добавить напоминания».

* Отметки «Выполнено / Не выполнено», замена и удаление отдельного приёма выполняются из календаря как у любого напоминания (см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md)); отметка «Выполнено» создаёт факт приёма (тип «Лекарство»). Замена одного приёма не создаёт и не меняет запись в разделе «Лекарства»: новая запись — независимый факт либо независимое напоминание. Расписание набора можно изменить и из календаря («Изменить все», см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md), раздел «Связанные напоминания»): изменение применяется и к лекарству, а название, дозировка и тип приёма в календаре меняются только здесь. Название и дозировка, изменённые на форме лекарства, применяются к напоминаниям набора без их пересоздания. Когда все напоминания набора закрыты или удалены, настройки набора исчезают, `reminder_plan_id` становится `null`, и снова доступно «Добавить напоминания».

## Пересоздание напоминаний при редактировании расписания

Если на форме редактирования лекарства, у которого на момент открытия формы набор напоминаний есть (`reminder_plan_id` не `null`), признак «Добавить напоминания» остаётся включённым и изменено хотя бы одно из полей расписания — «Частота приёма» (включая набор дней недели или интервал), «Времена приёма», «Дата начала», «Дата окончания» — при сохранении система показывает диалог подтверждения ДО отправки запроса: «Изменения расписания требуют пересоздания напоминаний. Пересоздать?» с вариантами «Пересоздать» / «Не пересоздавать» (без третьего варианта «Отмена» — сохранение формы происходит в любом случае, разница только в судьбе напоминаний, см. ниже). Переключение частоты на «По необходимости» у лекарства с набором напоминаний всегда трактуется как изменение расписания и всегда требует «Пересоздать» (напоминания при этом просто удаляются, новых не создаётся, — вариант «Не пересоздавать» здесь не предлагается, так как у `as_needed` не может быть напоминаний).

Если у будущих напоминаний набора есть собственные файлы (клиент узнаёт число таких напоминаний из `future_reminders_with_files_count` ответа `GET /reminder-plans/{reminder_plan_id}`, см. «Напоминания — Backend»), диалог дополняется предупреждением «У {N} напоминаний есть собственные файлы — при пересоздании они будут удалены»; это относится и к удалению набора при переходе на «По необходимости».

* **«Пересоздать»** — форма отправляет `PATCH /medications/{id}` с `regenerate_reminders: true` и изменёнными полями; сервер жёстко удаляет будущие незавершённые напоминания и создаёт новые по обновлённому расписанию; прошедшие незавершённые остаются, а уже закрытые приёмы заново не создаются (см. «Лекарства — Backend»).

* **«Не пересоздавать»** — форма отправляет тот же `PATCH /medications/{id}` без `regenerate_reminders` (либо `false`); изменённые поля лекарства сохраняются, существующие напоминания НЕ удаляются и НЕ пересоздаются — они остаются как есть, даже если больше не соответствуют новому расписанию. Это осознанно принятое расхождение, а не ошибка синхронизации: пользователь явно выбрал не трогать напоминания.

Если у лекарства на момент открытия формы набора напоминаний нет, либо ни одно из полей расписания не было изменено, диалог не показывается — сохранение выполняется обычным `PATCH /medications/{id}` без вопроса.

Включение признака «Добавить напоминания» на форме, если он был выключен (независимо от того, менялись ли поля расписания), — это обычное создание набора напоминаний, а не регенерация: диалог подтверждения не показывается, `PATCH` уходит с `add_reminders`-эквивалентными изменениями (либо, если проще для реализации, форма в этом случае вызывает тот же путь, что действие «Добавить напоминания», после сохранения остальных полей).

Отключение признака «Добавить напоминания» на форме лекарства, у которого набор напоминаний есть (при частоте ≠ «По необходимости»), — это удаление набора, а не регенерация. При сохранении показывается тот же диалог подтверждения, что у действия «Удалить напоминания» («Напоминания будут удалены безвозвратно — продолжить?», варианты «Отмена» / «Удалить»); диалог «Пересоздать?» при этом не показывается, даже если поля расписания менялись. «Отмена» оставляет форму открытой и ничего не сохраняет. «Удалить» сохраняет поля лекарства запросом `PATCH /medications/{id}` без `regenerate_reminders` и затем вызывает `DELETE /medications/{id}/reminders`; оба запроса — одна мутация очереди фоновых повторов (`PATCH` всегда раньше `DELETE`), `404` от `DELETE` (набора уже нет) считается успехом. Оптимистично сразу становится доступно действие «Добавить напоминания».

## Бизнес-правила и валидация

* Обязательные поля: «Название лекарства», «Дозировка», «Частота приёма»; «Дата начала» и «Времена приёма» — обязательны, если частота ≠ «По необходимости».

* «Дни недели» — минимум один выбранный день, только при частоте «Определённые дни недели». «Интервал (дней)» — целое от 2 до 365, только при частоте «Через каждые N дней».

* «Времена приёма» — от 1 до 4 строк, каждое время в формате `HH:mm` (сервер принимает `HH:MM` и `HH:MM:SS`), без повторов; форма не позволяет добавить 5-ю строку или удалить последнюю оставшуюся.

* «Дата окончания», если задана, не может быть раньше «Даты начала».

* Отдельного поля «Время напоминания» на форме нет — напоминания используют времена из «Времён приёма».

* Запрос списка лекарств, создание, редактирование и «Добавить напоминания» передают обязательный query-параметр `tz` — часовой пояс устройства: сервер строит напоминания приёма и вычисляет `next_dose`, трактуя даты расписания и времена приёма как местное время этого пояса (см. «Лекарства — Backend»), — так же, как это делает режим `dataSource=local`.

* При редактировании очищенная «Заметка» передаётся в `PATCH /medications/{id}` пустой строкой `""` — так сервер очищает значение (см. «Лекарства — Backend»).

## Обработка ошибок

| Ситуация | Что делает система |
| --- | --- |
| Не заполнено обязательное поле / нарушено согласование полей расписания с частотой / «Дата окончания» раньше «Даты начала» | Форма не отправляется, сообщение под полем |
| Транзиентная ошибка сервера при создании/редактировании лекарства (нет сети/таймаут/5xx) | Оптимистичное изменение остаётся применённым, запрос уходит в очередь фоновых повторов, карточка показывает индикацию «синхронизируется» (см. «Общие требования: Оптимистичные обновления», разделы «Классификация ошибок мутации», «Очередь фоновых мутаций и повторные попытки») |
| Постоянная ошибка сервера при создании/редактировании лекарства (400/403/409) | Оптимистичное изменение откатывается, пользователю показывается сообщение об ошибке; введённые данные для повторной отправки не сохраняются (см. там же, «Обработка ошибок и откат») |
| Отложенный `DELETE` лекарства не доставлен — транзиентная ошибка | Запрос уходит в очередь фоновых повторов, лекарство остаётся удалённым из списка без отката (см. там же, «Оптимистичное удаление с окном отмены (Undo)») |
| Отложенный `DELETE` лекарства завершился постоянной ошибкой / повторы исчерпаны | Лекарство восстанавливается в списке, пользователю показывается сообщение об ошибке с возможностью повторить удаление (см. там же) |
| Ошибка сервера при действиях с напоминаниями («Добавить напоминания»/«Удалить напоминания») | Пользователю показывается сообщение об ошибке, состояние лекарства не меняется, повторная попытка возможна — эти действия вне охвата правила об оптимистичных обновлениях (см. «Общие требования: Оптимистичные обновления», раздел «Охват») |
| Лекарство уже удалено на другом устройстве | Тихо убрать из списка / «уже удалено» |
| `POST /medications/{id}/reminders`, когда набор напоминаний уже существует (409, гонка между устройствами) | Сообщение «напоминания уже добавлены»; доступные действия с напоминаниями приводятся в соответствие с `reminder_plan_id` при следующем обновлении списка |
| `DELETE /medications/{id}/reminders`, когда набора напоминаний уже нет (404, гонка между устройствами) | Трактуется как «уже удалено» — тихо, без сообщения об ошибке; доступные действия с напоминаниями приводятся в соответствие с `reminder_plan_id` |

## Хранение состояния и побочные эффекты

После создания/редактирования/удаления лекарства или любого из действий с напоминаниями — инвалидация кэша списка лекарств питомца И кэшей календаря и блока ближайшего события (созданные/удалённые напоминания должны сразу появиться/исчезнуть там же); после любой из этих операций клиент также синхронизирует локальные уведомления (см. [Напоминания — Frontend](../calendar/napominaniya-frontend.md), раздел «Локальные уведомления»). Кэш списка лекарств патчится синхронно и оптимистично при создании/редактировании/удалении лекарства; кэш календаря/списка событий обновляется фоновым refetch (см. «Общие требования: Оптимистичные обновления (dataSource=network)»).
